# Расширяемые `Pull` и `Stream`

Наши `Pull` и `Stream` типы предоставляют альтернативный способ описания ленивых вычислений,
но они не более выразительны, чем `LazyList`.
Фактически, мы могли бы написать нашу программу преобразования файлов аналогичным образом,
если бы определили `Pipe[I, O]` как псевдоним для `LazyList[I] => LazyList[O]`.
Вместо того, чтобы полагаться на монолитную `IO` оболочку, которая скрывает эффективный источник потока,
мы можем расширить определение `Pull` и `Stream` для поддержки оценки произвольных эффектов.
Давайте параметризуем `Pull` и `Stream` с возможностью оценки эффекта
для генерации либо результирующего значения, либо выходного значения.
Для этого мы добавим дополнительный конструктор данных в `Pull`:

```dotty
enum Pull[+F[_], +O, +R]:
  case Result[+R](result: R) extends Pull[Nothing, Nothing, R]
  case Output[+O](value: O) extends Pull[Nothing, O, Unit]
  case Eval[+F[_], R](action: F[R]) extends Pull[F, Nothing, R]
  case FlatMap[+F[_], X, +O, +R](
    source: Pull[F, O, X], f: X => Pull[F, O, R]) extends Pull[F, O, R]
```

Мы добавили новый `Eval` конструктор данных, который оборачивает
действие типа `F[R]`. `Eval[F, R]` extends `Pull[F, Nothing, R]`,
указывая, что он не выводит никаких значений (и, следовательно, может использоваться везде, где нам нужен `Pull[F, O, R]`).
Мы также добавили параметр типа `+F[_]` в `Pull`. Параметр является ковариантным,
что позволяет `Result` и `Output` фиксировать тип эффекта на `Nothing`,
указывая, что они не оценивают никаких эффектов.

### Аннотации дисперсии на `Pull`

Мы решили определить все параметры типа `Pull` как ковариантные,
что обеспечивает нам лучший вывод типа и более точные типы.
Вместо этого мы могли бы определить каждый параметр как инвариантный следующим образом:

```dotty
enum Pull[F[_], O, R]:
  case Result(result: R)
  case Output(value: O)
  case Eval(action: F[R])
  case FlatMap[F[_], X, O, R](
    source: Pull[F, O, X], f: X => Pull[F, O, R]) extends Pull[F, O, R]
```

Эта версия, конечно, выглядит намного проще! К сожалению, она не так приятна в использовании.
Рассмотрим следующие примеры:

```dotty
scala> Pull.Output(1)
val res0: Pull[Nothing, Int, Unit] = Output(1)

scala> Pull.Result(true)
val res1: Pull[Nothing, Nothing, Boolean] = Result(true)
```

Пока что эти типы выглядят так же, как в определении коварианта.
Проблема возникает, когда мы пытаемся объединить эти значения.
Например, мы должны иметь возможность написать `res0 >> res1`, но это приводит к следующей ошибке:

```dotty
scala> res0 >> res1
-- [E007] Ошибка несоответствия типа: ------------------------------------------
1 |res0 >> res1
  | ^^^^
  | Найдено: (res1 : Pull[Nothing, Nothing, Boolean])
  | Требуется: Pull[Nothing, Int, Unit]
```

В этом примере `res0` has fixed `F = Nothing`, `O = Int`, `R = Unit` и не может быть объединен с pull,
который has fixed `F = Nothing`, `O = Nothing`, `R = Boolean`.
Однако мы можем избежать этого, отложив применение конкретных типов:

```dotty
scala> Pull.Output(1) >> Pull.Result(true)
val res2: Pull[Nothing, Int, Boolean] = Result(true)
```

В этом случае Scala может вывести `O = Int` и `R = Boolean` при вводе комбинированного выражения.

Версия `Pull` с аннотациями дисперсии не страдает от этой проблемы.
В целом, аннотации дисперсии добавляют много шума в определение `Pull` и, как мы скоро увидим, методы на `Pull`.
Но полученный API гораздо приятнее в использовании.

Давайте посмотрим, как добавление параметра эффекта влияет на определения различных операций в `Pull`.
Сначала давайте посмотрим на `step`: Предыдущее определение возвращало `Either[R, (O, Pull[O, R])]`.
Нам нужно изменить тип возвращаемого значения, чтобы учесть случай, когда `step` встречается с `Eval` узлом.
Мы можем отобразить обернутый `F[R]` чтобы преобразовать его в `Either`, поместив результат типа `R` слева.
Это говорит о том, что `step` теперь необходимо возвращать `F[Either[R, (O, Pull[O, R])]`.
В результате этого изменения, когда мы рекурсивно вызываем `step`, нам нужно упорядочить наши вычисления с `flatMap`.
Но как мы можем `map` и `flatMap` в конструкторе абстрактного типа `F`? Мы можем запросить `Monad[F]`:

```dotty
def step[F2[x] >: F[x], O2 >: O, R2 >: R](
  using F: Monad[F2] #1
): F2[Either[R2, (O2, Pull[F2, O2, R2])]] =
  this match
    case Result(r) => F.unit(Left(r)) #2
    case Output(o) => F.unit(Right(o, Pull.done))
    case Eval(action) => action.map(Left(_)) #3
    case FlatMap(source, f) =>
      source match
        case FlatMap(s2, g) =>
          s2.flatMap(x => g(x).flatMap(y => f(y))).step
        case other => other.step.flatMap: #4
          case Left(r) => f(r).step
          case Right((hd, tl)) => F.unit(Right((hd, tl.flatMap(f))))
```

Простое изменение добавления `Eval` конструктора имело глубокие последствия для `step`!
Мы подобрали `Monad` ограничение для нашего типа эффекта
и использовали монадическую рекурсию вместо обычной рекурсии для вычисления последовательности.
В результате, `step` стек безопасен только тогда, когда тип эффекта имеет
стек-безопасность `flatMap` (из-за `other.step.flatMap(...)` вызова).

Сигнатура `step` также стала намного сложнее. Мы выбрали три параметра типа с границами, которые указывают,
что они являются супертипами `F`, `O` и `R`.
Без этих параметров типа Scala жалуется, что мы пытаемся использовать ковариантные параметры в инвариантных позициях.
Как мы делали в предыдущих главах, мы можем механически преобразовать такие ошибки
в рабочие определения посредством введения параметров типа с ограничениями супертипа, хотя это становится очень сложным.
В качестве альтернативы мы могли бы определить `step` как метод расширения,
избежав необходимости в новых параметрах типа:

```dotty
def step(using F: Monad[F]): F[Either[R, (O, Pull[F, O, R])]] =
  self match
    case Result(r) => F.unit(Left(r))
    case Output(o) => F.unit(Right(o, Pull.done))
    case Eval(action) => action.map(Left(_))
    case FlatMap(source, f) =>
      source match
        case FlatMap(s2, g) =>
          s2.flatMap(x => g(x).flatMap(y => f(y))).step
        case other => other.step.flatMap:
          case Left(r) => f(r).step
          case Right((hd, tl)) => F.unit(Right((hd, tl.flatMap(f))))
```

Мы будем использовать методы на протяжении всей этой главы, но если ограничения типов станут непреодолимыми,
смело определяйте операции с помощью методов расширения.
Это часто проще в обмен на потерю некоторого вывода типа.

Методы `fold` и `toList` нужны аналогичные обработки,
поскольку `fold` вызовы `step` рекурсивны и `toList` вызовы `fold`:

```dotty
def fold[F2[x] >: F[x], R2 >: R, A](init: A)(f: (A, O) => A)(
  using F: Monad[F2]
): F2[(R2, A)] =
  step.flatMap:
    case Left(r) => F.unit((r, init))
    case Right((hd, tl)) => tl.fold(f(init, hd))(f)

def toList[F2[x] >: F[x]: Monad, O2 >: O]: F2[List[O2]] =
  fold(List.newBuilder[O])((bldr, o) => bldr += o).map(_(1).result)
```

`fold` больше не может быть аннотирован с помощью аннотация `tailrec`,
поскольку теперь она использует монадическую рекурсию вместо обычной рекурсии.
Опять же, мы полагаемся на `flatMap` эффект монады, чтобы быть безопасным в стеке.

Операция `uncons` более интересна. Вспомним предыдущее определение:

```dotty
def uncons: Pull[Nothing, Either[R, (O, Pull[O, R])]] =
  Pull.done >> Result(step)
```

Мы можем адаптировать это к эффективной версии pull, создав `Eval` узел, который оборачивает вызов `step`:

```dotty
def uncons[F2[x] >: F[x], O2 >: O, R2 >: R](
  using Monad[F2]
): Pull[F2, Nothing, Either[R2, (O2, Pull[F2, O2, R2])]] =
  Eval(step)
```

Поскольку мы вызываем `step`, мы вынуждены добавить ограничение монады на тип эффекта,
и это означает, что мы больше не можем вызывать `uncons`
неэффективный pull — то есть pull с `F = Nothing` — потому что нет `Monad[Nothing]` экземпляра.
Аналогично, каждая операция, которая использует `uncons`, например `take`,
также должна будет нести ограничение `Monad[F]`.

Чтобы исправить это, мы можем отложить вызов `step` до тех пор, пока не будет оценен результирующий pull.
Давайте создадим новый `Uncons` конструктор данных, который хранит ссылку на исходный pull.
Затем давайте расширим определение `step` для обработки этого конструктора:

```dotty
case Uncons(source: Pull[F, O, R])
  extends Pull[F, Nothing, Either[R, (O, Pull[F, O, R])]]

def step[F2[x] >: F[x], O2 >: O, R2 >: R](
  using F: Monad[F2]
): F2[Either[R2, (O2, Pull[F2, O2, R2])]] =
  this match
    case Result(r) => F.unit(Left(r))
    case Output(o) => F.unit(Right(o, Pull.done))
    case Eval(action) => action.map(Left(_))
    case Uncons(source) =>
      source.step.map(s => Left(s.asInstanceOf[R2]))
    case FlatMap(source, f) =>
      source match
        case FlatMap(s2, g) =>
          s2.flatMap(x => g(x).flatMap(y => f(y))).step
        case other => other.step.flatMap:
          case Left(r) => f(r).step
          case Right((hd, tl)) => F.unit(Right((hd, tl.flatMap(f))))
```

Определение `Uncons` интересно — оно расширяет `Pull[F, Nothing, Either[R, (O, Pull[F, O, R])]]`
и ссылается на базовый `Pull[F, O, R]`.
Тип говорит, что расконсервирование a `Pull[F, O, R]` приводит к pull,
который может оценивать эффекты в `F`, не выводит никаких элементов
и приводит либо к конечному значению `R` исходного pull, либо к выходному значению `O` и остатку `Pull[F, O, R]`.

Когда мы сталкиваемся с `Uncons` узлом в реализации `step`, мы шагаем по источнику pull
и оборачиваем его результат в `Left`.
Для этого нам нужен экземпляр `Monad[F2]`, и этот экземпляр уже есть в области видимости.

Оставшиеся операции `Pull` переносятся в эффективную версию с небольшими изменениями —
часто требуется только корректировка для передачи параметра типа для эффекта.
См. код главы для дополнительных примеров. Как насчет `Stream` и `Pipe`?

```dotty
opaque type Stream[+F[_], +O] = Pull[F, O, Unit]
```

Как и `Pull`, `Stream` выбирает новый ковариантный параметр типа для типа эффекта.
Различные конструкторы и методы, определенные для `Stream` всех,
должны быть изменены для учета этого дополнительного параметра типа,
но поскольку вся тяжелая работа выполняется `Pull`, это полностью механическое преобразование:

```dotty
object Stream:
  def empty: Stream[Nothing, Nothing] = Pull.done #1

  def apply[O](os: O*): Stream[Nothing, O] = #2
    fromList(os.toList)

  def fromList[O](os: List[O]): Stream[Nothing, O] =
    os match
      case Nil => Pull.done
      case hd :: tl => Pull.Output(hd) >> fromList(tl)

  extension [F[_], O](self: Stream[F, O])
    def toPull: Pull[F, O, Unit] = self

    def fold[A](
      init: A)(f: (A, O) => A)(using Monad[F]): F[A] = #3
      self.fold(init)(f).map(_(1))

    def toList(using Monad[F]): F[List[O]] = #4
      self.toList
```

Как `fold` и `toList` на `Pull`, эквивалентные операции на `Stream` теперь возвращают эффективное действие.
Мы говорим, что `fold` и `toList` являются элиминаторами типа —
интерпретируя `Stream` или компиляция алгебры потоков в целевую монаду.

Можем ли мы по-прежнему использовать эти элиминаторы с неэффективными потоками? Да, но это немного неудобно.
Нам нужно явно передать соответствующий экземпляр монады:

```dotty
scala> val x = Stream(1, 2, 3).
         repeat. #1
         take(5).
         toList(using Monad.tailrecMonad).
         result
val x: List[Int] = List(1, 2, 3, 1, 2)
```

В этом примере мы использовали `TailRec` монаду, поэтому общее вычисление потока безопасно для стека.
Нам нужно явно передать экземпляр монады (или иным образом приписать тип нашего потока как `Stream[TailRec, Int]`),
и нам нужно запустить трамплин, вызвав `result` результат `toList`.
Мы можем предоставить неэффективные версии каждого элиминатора, чтобы избежать этого шаблона:

```dotty
extension [O](self: Stream[Nothing, O])
  def fold[A](init: A)(f: (A, O) => A): A =
    self.fold(init)(f)(using Monad.tailrecMonad).result(1)

  def toList: List[O] =
    self.toList(using Monad.tailrecMonad).result

scala> val s = Stream(1, 2, 3).repeat.take(5)
val s: Stream[Nothing, Int] = ...

scala> val x = s.toList #1
val x: List[Int] = List(1, 2, 3, 1, 2)

scala> val y = (s: Stream[IO, Int]).toList #2
val y: IO[List[Int]] = ...
```

Давайте добавим несколько новых конструкторов и комбинаторов для `Stream` работы с эффектами.

Реализовать `mapEval` метод расширения на тип `Stream`:

### Упражнение 15.11

Реализуйте `unfoldEval` на обоих объектах `Stream` и `Pull` сопутствующих объектах:

```dotty
object Stream:
  def unfoldEval[F[_], O, R](
    init: R)(f: R => F[Option[(O, R)]]): Stream[F, O]

object Pull:
  def unfoldEval[F[_], O, R](
    init: R)(f: R => F[Either[R, (O, R)]]): Pull[F, O, R]
```

Наконец, давайте обновим `Pipe`, чтобы учесть эффекты:

```dotty
type Pipe[F[_], -I, +O] = Stream[F, I] => Stream[F, O]
```

Теперь у нас есть выбор дизайна для тип `Pipe`.
Мы решили добавить один параметр типа `F[_]` к определению `Pipe`, который указывает тип эффекта как входного потока,
так и выходного потока.
Используя этот параметр типа как во входном, так и в выходном потоке, мы вынуждены определять параметр инвариантно
(попробуйте определить его ковариантно и посмотрите, на что жалуется компилятор).
Однако, делая это, мы отказываемся от некоторой общности. Вместо этого мы могли бы определить `Pipe` так:

```dotty
type Pipe[-F[_], -I, +G[_], +O] = Stream[F, I] => Stream[G, O]
```

Хотя это определение более выразительно, оно также и более сложное.
И поскольку `Pipe` это всего лишь псевдоним типа, мы всегда можем использовать явный тип функции в случаях,
когда нам нужна дополнительная выразительность.
Поэтому мы будем придерживаться более простого определения.

### Эффективные потоковые вычисления

Теперь `Pull`, когда `Stream`, и `Pipe` поддерживают оценку произвольных эффектов,
мы можем строить вычисления, которые постепенно получают данные из источника, преобразуют их и отправляют результаты в приемник.
Если источники представлены потоками, а преобразования представлены трубами, как мы представляем приемники?

Оказывается, нам не нужна никакая особая поддержка для приемников!
Фактически, `mapEval` метод из упражнения 15.10 обеспечивает основу для эффективных приемников.
Мы принимаем соглашение, что приемник — это канал, который изменяет выход на либо `Unit` — по `Nothing` сути,
потребляя каждое выходное значение из исходного потока. Рассмотрим эти примеры приемников:

```dotty
def log[O]: Pipe[IO, O, Unit] = _.mapEval(o => IO(println(o)))

def drain[F[_], O]: Pipe[F, O, Nothing] = _.flatMap(_ => Stream.empty)
```

Приемник `log` использует `mapEval` для печати каждого выходного значения источника на консоль.
`drain` Приемник отбрасывает все выходные элементы источника.
Собирая все части вместе, мы можем описать эффективное потоковое вычисление:

```dotty
case class Message(id: UUID, timestamp: Instant, ...)

def format(m: Message): String = s"id: $id, timestamp: $timestamp, ..."

val dequeue: IO[Message] = ...

val logAll: Stream[IO, Unit] =
  Stream.eval(dequeue).repeat.map(format).pipe(log)
```

В этом примере `dequeue` операция блокируется до тех пор, пока не появится сообщение
(возможно, из распределенной очереди сообщений).
Операция `logAll` многократно оценивает `dequeue`
и для каждого полученного сообщения форматирует сообщения в строку и выводит результат на консоль.
Общее вычисление потока имеет `Stream[IO, Unit]` тип. Как нам запустить этот поток?
Нашими единственными элиминаторами являются `fold` и `toList`.
Вызов `toList` был бы проблемой, так как каждое действие журнала вывело бы единичное значение,
которое накапливалось бы в построителе списков, в конечном итоге используя всю нашу кучу.
Вместо этого давайте `fold` и отбросим каждое выходное значение.
Это часто возникает при работе с эффективными потоками, поэтому мы можем создать новый элиминатор:

```dotty
extension [F[_], O](self: Stream[F, O])
  def run(using Monad[F]): F[Unit] =
    fold(())((_, _) => ()).map(_(1))

val program: IO[Unit] = logAll.run
```

### 15.3.2 Обработка ошибок

Некоторые типы эффектов предоставляют возможность обработки ошибок, возникающих во время оценки.
Код главы 13 определяет `Task[A]` тип как непрозрачный тип вокруг `IO[Try[A]]`.
`Task` позволяет нам игнорировать наличие потенциальных ошибок, пока мы не захотим их обработать:

```dotty
val a: Task[Int] = Task("asdf".toInt)
val b: Task[Int] = a.map(_ + 1)
val c: Task[Try[Int]] = b.attempt
val d: Try[Int] = c.unsafeRunSync(pool)
```

Когда задача, назначенная для `a` оценивается, преобразование из строки в целое число завершается ошибкой с `NumberFormatException`.
`Task` обрабатывает это исключение и сохраняет его внутри, обернутым в `Failure`
(напомним, что `Failure` это конструктор данных `Try`).
В определении `b` вызов `map` оказывается пустой операцией.
В определении `c` вызов `attempt` раскрывает базовый `Try[Int]`.

`Task` добавляет канал ошибок в `IO` — канал для передачи ошибок, которые произошли в ходе вычислений,
во многом таким же образом, как `Try` и `Either` обеспечивает неэффективные вычисления.
Мы можем определить `Monad[Task]` экземпляр, который работает так же, как экземпляры монад для `Try` и `Either`,
замыкаясь при столкновении с `Failure`.
`Task` также предоставляет `handleErrorWith` комбинатор, полученный из `attempt` и `flatMap`:

```dotty
def handleErrorWith(h: Throwable => Task[A]): Task[A] =
  attempt.flatMap:
    case Failure(t) => h(t)
    case Success(a) => Task(a)

val a: Task[Int] = Task("asdf".toInt)
val b: Task[Int] = a.map(_ + 1)
val c: Task[Int] = b.handleErrorWith(_ => Task(0))
```

`handleErrorWith` чем-то похож на `flatMap` в том, что он обеспечивает последовательность,
но канала ошибок вместо канала результатов.
Что происходит, когда мы используем `Task` with `Stream`?
Мы можем использовать `eval` так же, как мы делали с `IO`:

```dotty
val s: Stream[Task, Int] = Stream.eval(Task("asdf".toInt))
```

Когда мы преобразуем этот поток в задачу через один из элиминаторов потока (например, `toList` или `run`),
мы получим ошибку, которая оборачивает `NumberFormatException`.
Полезно иметь возможность обрабатывать такие ошибки как часть API `Stream` и `Pull`,
поэтому давайте добавим `handleErrorWith` к каждому:

```dotty
enum Pull[+F[_], +O, +R]:
  case Handle(
    source: Pull[F, O, R],
    handler: Throwable => Pull[F, O, R]
  ) extends Pull[F, O, R]

  def handleErrorWith[F2[x] >: F[x], O2 >: O, R2 >: R](
    handler: Throwable => Pull[F2, O2, R2]): Pull[F2, O2, R2] =
    Pull.Handle(this, handler)

extension [F[_], O](self: Stream[F, O])
  def handleErrorWith(handler: Throwable => Stream[F, O]): Stream[F, O] =
    Pull.Handle(self, handler)
```

Мы добавили новый конструктор в `Pull`, который захватывает исходный pull и обработчик ошибок.
Затем нам нужно расширить определение `step` для интерпретации этого `Handle` конструктора.
При выполнении шага и обнаружении `Handle`, нам нужно выполнить шаг внутреннего pull и обработать любые ошибки,
которые возникли при этом.
Но `step` определено для работы с произвольным эффектом `F[_]`, имеющим экземпляр монады,
а монада не предоставляет возможности обработки ошибок. Чтобы решить эту проблему,
давайте введем новый класс типов, который добавляет возможности обработки ошибок к `Monad`:

```dotty
trait MonadThrow[F[_]] extends Monad[F]:
  extension [A](fa: F[A])
    def attempt: F[Try[A]]
    def handleErrorWith(h: Throwable => F[A]): F[A] =
      attempt.flatMap:
        case Failure(t) => h(t)
        case Success(a) => unit(a)

  def raiseError[A](t: Throwable): F[A]
```

`MonadThrow` расширяет `Monad` и добавляет возможность выявлять ошибки и впоследствии обрабатывать их.

### Упражнение 15.12

Определите законы для `MonadThrow`. Рассмотрите, как `attempt` следует взаимодействовать с `raiseError` и `unit`.

Теперь мы можем обновить определение слова `step` «взять» пример `MonadThrow`:

```dotty
def step[F2[x] >: F[x], O2 >: O, R2 >: R](
  using F: MonadThrow[F2]
): F2[Either[R2, (O2, Pull[F2, O2, R2])]] =
  this match
    ...
    case Handle(source, f) =>
      source match
        case Handle(s2, g) =>
          s2.handleErrorWith(x =>
            g(x).handleErrorWith(y => f(y))).step #1
        case other =>
          other.step
            .map:
              case Right((hd, tl)) => Right((hd, Handle(tl, f)))
              case Left(r) => Left(r)
            .handleErrorWith(t => f(t).step) #2
```

Эта реализация сначала проверяет наличие левовложенных обработчиков ошибок
и переписывает такое вложение в правовложенное, как мы делаем для левовложенных вызовов `flatMap`.
В противном случае она выполняет исходное извлечение и обрабатывает любые возникшие ошибки
путем делегирования методу `handleErrorWith` для целевой эффект `F`.
Если ошибок не происходит, то мы передаем обработчик ошибок на оставшийся pull.

В результате `step` принятия `MonadThrow`,
все различные элиминаторы `MonadThrow` также должны принимать: `fold`, `toList`, и `run`.
Мы можем аналогичным образом добавить поддержку явного вызова ошибок в pull и stream, введя `raiseError` конструктор для каждого.
Смотрите код главы для получения полной информации.

Теперь, когда у нас есть `handleErrorWith` и `raiseError` для потока, мы можем определить `onComplete`:

```dotty
extension [F[_], O](self: Stream[F, O])
  def onComplete(that: => Stream[F, O]): Stream[F, O] =
    self.handleErrorWith(t => that ++ raiseError(t)) ++ that
```

Метод `onComplete` позволяет нам оценивать поток после завершения исходного потока, независимо от того,
завершился ли исходный поток успешно или завершился с ошибкой. Это особенно эффективно,
когда переданный поток `onComplete` оценивает эффект.

Позволяет ли `onComplete` нам безопасно получать и освобождать ресурсы, такие как дескрипторы файлов?
Давайте посмотрим:

```dotty
def acquire(path: String): Task[Source] =
  Task(Source.fromFile(path))

def use(source: Source): Stream[Task, Unit] =
  Stream.eval(Task(source.getLines))
    .flatMap(itr => Stream.fromIterator(itr))
    .mapEval(line => Task(println(line)))

def release(source: Source): Task[Unit] =
  Task(source.close()))

val printLines: Stream[Task, Unit] =
  Stream.eval(acquire("path/to/file")).flatMap(resource =>
    use(resource).onComplete(Stream.eval(release(resource))))
```

Сначала мы оцениваем `acquire` задачу открытия файла, а затем получаем `flatMap` результат,
создавая поток, который использует открытый файл и освобождает его через `onComplete`.
Затем мы выводим каждую строку файла на консоль.
Если мы запустим это, возможно, с некоторым дополнительным протоколированием получения
и завершения ресурсов, мы увидим, что это делает именно то, что нам нужно.

К сожалению, этот подход имеет серьезное ограничение: он некомпозируемый.
Давайте рассмотрим, что произойдет, если мы немного рефакторим все, извлекая вывод каждой строки до вызова `onComplete`:

```dotty
val printLines: Stream[Task, Unit] =
  Stream.eval(acquire("path/to/file"))
    .flatMap: resource =>
      Stream.eval(source => Task(source.getLines))
        .flatMap(itr => Stream.fromIterator(itr))
        .onComplete(Stream.eval(release(resource)))
    .mapEval(line => Task(println(line)))
```

Эта программа должна вести себя так же, как и оригинал, и на самом деле так и происходит, когда нет ошибок.
Однако, если финал `mapEval` завершается с исключением, то обработчик ошибок, зарегистрированный с помощью `onComplete`,
не вызывается, общее вычисление завершается неудачей, и ресурс никогда не финализируется.

Другим проблемным случаем является раннее завершение в результате взятия только некоторых элементов исходного потока.
Представьте, что мы изменили `use` так, чтобы взять первые 10 строк файла.
Если мы поместим `take(10)` в тело `use`, то весь поток будет вести себя правильно.
Однако если мы перейдем `take(10)` к вызову `onComplete`, то первые 10 строк будут возвращены,
и ресурс никогда не будет завершен.

В обоих этих случаях мы ожидаем, что ресурс будет завершен независимо от того, что еще происходит в потоке.
Опираться только на `flatMap` и `onComplete` не дает нам достаточно власти,
чтобы предоставить эту гарантию — мы вернемся к этой гарантии в ближайшее время.

Добавление поддержки обработки ошибок `Stream` приводит к более сильному ограничению на формы его устранения.
Следовательно, больше невозможно преобразовать a `Stream[IO, X]` в an `IO[List[X]]`
или любое другое `IO` значение, поскольку `IO` не имеет экземпляр `MonadThrow`.
Правильный ли это компромисс? На практике большинство типов монадических эффектов поддерживают обработку ошибок,
поэтому это ограничение не такое уж ограничивающее, как кажется на первый взгляд,
но стоит поэкспериментировать с другими вариантами API.

А как насчет неэффективных потоков?
Ранее мы оценивали их в `TailRec` монаде, которая также не имеет `MonadThrow` экземпляра.
Это решается проще — мы можем добавить обработку ошибок в `TailRec` во многом таким же образом,
как мы добавили ее в `IO`, встроив `Try` внутрь него:

```dotty
opaque type SyncTask[A] = TailRec[Try[A]]
```

Мы можем определить `MoandThrow[SyncTask]` экземпляр и изменить неэффективные элиминаторы для оценки потоков,
используя `SyncTask` вместо `TailRec`. В общем, каждый раз,
когда мы добавляем дополнительную функциональность к потокам и извлечениям,
мы должны быть осторожны с тем, как эта функциональность изменяет требования к элиминаторам.

### 15.3.3 Обеспечение безопасности ресурсов

`Stream` может использоваться для общения с произвольными ресурсами — не только файлами,
но и соединениями с базами данных, сетевыми сокетами и т.д.
В последнем разделе мы попытались открыть файл и убедиться, что он закрыт,
независимо от того, как завершается наше потоковое вычисление, и обнаружили,
что сделать это сложнее, чем добавить поддержку обработки ошибок.
Давайте еще раз рассмотрим различные типы завершения, которые нам нужно поддерживать.

Предположим, что у нас есть `lines: Stream[Task, String]` представление строк большого файла.
Это источник или производитель, и он ссылается на ресурс (дескриптор файла),
который мы хотим закрыть, независимо от того, как этот производитель потребляется.

Когда нам следует закрыть этот дескриптор файла — в самом конце нашей программы? Нет.
В идеале мы бы закрыли файл, как только узнаем, что закончили чтение из `lines`.
Мы определенно закончили, если достигли последней строки файла; в этот момент больше нет значений для создания,
и файл можно безопасно закрыть.
Итак, это дает нам первое правило, которому нужно следовать:
производитель должен освободить все базовые ресурсы, как только он узнает,
что у него больше нет значений для создания, будь то из-за обычного истощения или исключения.

Однако этого недостаточно, поскольку потребитель потока может сам решить прекратить потребление раньше.
Рассмотрим `lines.take(5).toList`. Вызов `take(5)` остановится после получения только пяти строк,
возможно, до того, как файл будет исчерпан.
В этом случае мы хотим убедиться, что любая необходимая очистка ресурсов будет выполнена до завершения всего потока.
Обратите внимание, что `toList` не может нести за это ответственность, поскольку `toList` не имеет представления о том,
что `Stream` его интерпретация внутренне состоит из других потоков, один из которых требует завершения.
Таким образом, у нас есть второе правило, которому нужно следовать: любой поток `s`,
который потребляет значения из другого потока, `t` должен гарантировать,
что действия по очистке `t` выполняются до `s` остановок.

Подводя итог, можно сказать, что поток `s` может прекратиться из-за:

1. Истощение производителя, когда у источника больше нет значений для вывода
2. Досрочное прекращение, когда остаток источника выбрасывается
3. Ненормальное завершение работы при возникновении исключения

Независимо от причины, в каждом случае мы хотим закрыть базовый ресурс(ы).

Теперь, когда у нас есть наши руководящие принципы, как мы на самом деле реализуем это?
Чтобы справиться с ранним завершением, нам нужен способ выполнения действий по очистке исходного потока, даже если он отброшен.
Это предполагает дизайн, в котором действия по очистке полученных ресурсов отслеживаются интерпретатором,
а не являются примитивными действиями в потоке, составленном с помощью `flatMap` и `handleErrorWith`.
Давайте представим новый конструктор потока, который фиксирует этот шаблон:

```dotty
def resource[F[_], R](acquire: F[R])(release: R => F[Unit]): Stream[F, R]
```

Операция `resource` создает единый поток элементов из `acquire` и гарантирует,
что `release` действие оценивается в соответствии с установленными нами руководящими принципами.
Как мы можем реализовать `resource`? В оставшейся части этого раздела мы рассмотрим один подход,
но не беспокойтесь обо всех деталях реализации.
Важная концепция здесь — как `resource` ведет себя, а не как реализуется.

Для начала мы введем понятие области, в которой происходит интерпретация потока.
Область может быть открытой или закрытой.
Открытая область имеет связанное с ней действие очистки, которое мы будем называть финализатор.
Открытая область действия может также иметь любое количество подобластей.
Мы можем зарегистрировать новый финализатор в области действия, открыв подобласть, которая ссылается на этот финализатор.
Открытая область действия может быть закрыта, что имеет эффект сначала закрытия всех подобластей действия,
а затем запуска финализатора.

Поскольку мы представляем финализаторы как значения type `F[Unit]`,
`Scope` тип должен быть параметризован нашим типом эффекта.
Для реализации различных переходов состояний, таких как открытие подобласти и закрытие дерева областей,
нам нужна возможность манипулировать состоянием в эффекте `F`.
Мы можем сделать это с помощью новый тип — `Ref`:

```dotty
final class Ref[F[_], A] private (
  underlying: AtomicReference[A],
  delay: [A] => (() => A) => F[A] #1
):

  def get: F[A] = delay(() => underlying.get)

  def set(a: A): F[Unit] = delay(() => underlying.set(a))

  def modify[B](f: A => (A, B)): F[B] = delay: () =>
    @annotation.tailrec
    def loop(): B =
      val oldA = underlying.get
      val (newA, result) = f(oldA)
      if underlying.compareAndSet(oldA, newA) then result else loop()
    loop()

object Ref:
  def apply[F[_], A](initial: A)(using F: Monad[F]): Ref[F, A] =
    new Ref(new AtomicReference[A](initial),
      [A] => (th: () => A) => F.unit(()).map(_ => th()))
```

A `Ref[F, A]` — это чисто функциональный эквивалент переменной типа `A`,
где весь доступ и мутация выполняются в эффекте `F`.
Эта реализация использует a `java.util.concurrent.AtomicReference` в качестве базового хранилища,
одновременно предоставляя эффективные аксессоры и мутаторы.

Операция `modify` особенно полезна.
Она атомарно вычисляет новое значение из текущего значения
и позволяет возвращать произвольное дополнительное значение.
Используя `Ref` and `modify`, мы можем реализовать `Scope` как конечный автомат с состояниями `Open` and `Closed`:

```dotty
class Scope[F[_]](
  parent: Option[Scope[F]],
  val id: Id,
  state: Ref[F, Scope.State[F]]
)(using F: MonadThrow[F]):
  import Scope.State

  def open(finalizer: F[Unit]): F[Scope[F]] = ???
  def close: F[Unit] = ???

object Scope:
  enum State[F[_]]:
    case Open(
      finalizer: F[Unit], subscopes: Vector[Scope[F]]) extends State[F]
    case Closed() extends State[F]

  def root[F[_]](using F: MonadThrow[F]): Scope[F[_]] =
    new Scope(None, new Id, Ref(State.Open(F.unit(()), Vector.empty))
```

A `Scope` сохраняет свое изменяемое состояние в `Ref[F, State[F]]`. `State[F]`
Тип представляет собой перечисление, состоящее из `Open` и `Closed` случаев.
`Open` сохраняет ссылку на финализатор для этой области и подобластей.

Подобласть можно открыть, вычислив новое `Open` состояние с зарегистрированной новой подобластью:

```dotty
def open(finalizer: F[Unit]): F[Scope[F]] =
  state
    .modify:
      case State.Open(myFinalizer, subscopes) =>
        val sub = new Scope(Some(this), new Id,
                            Ref(State.Open(finalizer, Vector.empty)))
        State.Open(myFinalizer, subscopes :+ sub) -> F.unit(sub)
      case State.Closed() =>
        val next = parent match
          case None =>
            F.raiseError(new RuntimeException("корневая область уже закрыта"))
          case Some(p) => p.open(finalizer)
        State.Closed() -> next
    .flatten
```

Нам нужно обработать два случая: когда `open` вызывается в `Open` области действия
и когда он вызывается в `Closed` области действия.
Если область действия открыта, то сначала мы создаем новую область действия для нового финализатора,
а затем вычисляем новое `Open` состояние, которое ссылается на новую область действия в ее подобластях.
Напомним, что сигнатура `modify` позволяет нам возвращать произвольное значение вместе с обновленным состоянием;
здесь мы возвращаем `F[Scope[F]]` как это произвольное значение. Игнорируя `Closed` случай на мгновение,
у нас есть `state.modify(...)`, который возвращает `F[F[Scope[F]]`, который мы `flatten` преобразуем в `F[Scope[F]]`.

Этот шаблон расширяем до любого конечного автомата, который мы можем себе представить.
Мы сохраняем текущее состояние в `Ref` и выполняем переходы в терминах `ref.modify(f).flatten`,
где `f` вычисляет следующее состояние из текущего состояния и возвращает действие для оценки после успешной модификации состояния `Ref`.

Возвращаясь к `Closed` случаю, мы могли бы сделать открытие подобласти в закрытой области ошибкой.
Вместо этого мы передаем открытый запрос в родительскую область.
Эта область также может быть закрыта, что приведет к рекурсивному распространению вверх по дереву до тех пор,
пока мы не встретим открытую область или не достигнем корня.
Мы сообщаем об ошибке только в том случае, если достигнем корня, не встретив открытой области.
Операция `close` реализуется аналогичным образом:

```dotty
def close: F[Unit] =
  state
    .modify:
      case State.Open(finalizer, subscopes) =>
        val finalizers = (subscopes.reverseIterator.map(_.close) ++
          Iterator(finalizer)).toList
        def go(rem: List[F[Unit]], error: Option[Throwable]): F[Unit] =
          rem match
            case Nil => error match
              case None => F.unit(())
              case Some(t) => F.raiseError(t)
            case hd :: tl =>
              hd.attempt.flatMap(res =>
                go(tl, error orElse res.toEither.swap.toOption))
        State.Closed() -> go(finalizers, None)
      case State.Closed() => State.Closed() -> F.unit(())
    .flatten
```

Вызов `close` для открытой области действия переводит состояние области действия в `Closed`.
Мы вычисляем действие, которое закрывает все подобласти действия, а затем запускает финализатор исходной области действия.
Мы должны быть осторожны, чтобы поменять порядок подобластей действия на обратный, чтобы гарантировать,
что финализаторы запускаются в стекоподобном режиме (т. е. финализаторы должны запускаться в порядке «последним пришел, первым вышел»).
Мы также должны быть осторожны, чтобы запускать все финализаторы, даже если происходят ошибки.
Мы не можем просто пройти по списку действий; в противном случае мы бы закоротили при первой ошибке.

Теперь давайте интегрируем `Scope` в `Stream` и `Pull`.
Начнем с создания двух новых случаев в `Pull` перечислении:

```dotty
case OpenScope[+F[_], +O, +R](
  source: Pull[F, O, R], finalizer: Option[F[Unit]]
) extends Pull[F, O, R]

case WithScope[+F[_], +O, +R](
  source: Pull[F, O, R], scopeId: Id, returnScope: Id
) extends Pull[F, O, R]
```

`OpenScope` ссылается на исходный pull и финализатор.
При обнаружении `OpenScope` интерпретатор вызывает `open` активную область, передавая финализатор.
Затем он интерпретирует исходный pull, используя вновь открытую область как новую активную область.
`WithScope` ссылается на исходный pull, идентификатор области, используемой во время интерпретации этого исходного pull,
и идентификатор области, к которой следует вернуться после завершения исходного pull.

Подразумевается, что эти новые случаи подразумевают, что интерпретатор (т.е. `fold` и `step`)
должен отслеживать активную область и разрешать шагу изменять текущую область.
Чтобы разрешить изменения активной области, нам нужно изменить результат, `step` включив новую активную область.
Мы могли бы изменить тип результата с `Either[R, (O, Pull[F, O, R])]` на `(Scope[F], Either[R, (O, Pull[F, O, R])])`, но это немного утомительно.
Вместо этого давайте введем новый тип, представляющий результат шага:

```dotty
enum StepResult[F[_], +O, +R]:
  case Done(scope: Scope[F], result: R)
  case Out(scope: Scope[F], head: O, tail: Pull[F, O, R])
```

Давайте изменим `fold` управление активной областью.
Нам нужно создать корневую область и закрыть ее после завершения сворачивания,
и нам нужно изменить активную область для каждого `StepResult.Out`:

```dotty
def fold[F2[x] >: F[x], R2 >: R, A](init: A)(f: (A, O) => A)(
  using F: MonadThrow[F2]
): F2[(R2, A)] =
  scope = Scope.root[F2]
  def go(scope: Scope[F2], p: Pull[F2, O, R2], acc: A): F2[(R2, A)] =
    p.step(scope).flatMap:
      case StepResult.Done(_, r) => F.unit((r, init))
      case StepResult.Out(newScope, hd, tl) =>
        go(newScope, tl, f(init, hd))
  go(scope, this, init).attempt.flatMap(res =>
    scope.close.flatMap(_ => res.fold(F.raiseError, F.unit))
```

Операция `step` теперь принимает активную область в качестве аргумента,
а результат `step` указывает следующую область для использования.
Изменение `step` на handle `OpenScope` довольно просто:
мы делегируем в `open` активной области, а затем используем `WithScope` для оценки исходного потока источника
с использованием недавно открытой подобласти.
После завершения мы восстанавливаем исходную область:

```dotty
case OpenScope(source, finalizer) =>
  scope.open(finalizer.getOrElse(F.unit(()))).flatMap(subscope =>
    WithScope(source, subscope.id, scope.id).step(subscope))
```

Изменение `step` for `WithScope` немного сложнее.
Сначала мы ищем в дереве областей целевую область,
а затем используем эту область для пошагового выполнения исходного потока.
Если в результате получается `Done`, то мы закрываем целевую область и ищем область, в которую нужно вернуться.
В противном случае мы распространяемся `WithScope` по оставшемуся потоку, возвращенному в `Out`:

```dotty
case WithScope(source, scopeId, returnScopeId) =>
  scope.findScope(scopeId)
    .map(_.map(_ -> true).getOrElse(scope -> false))
    .flatMap:
      case (newScope, closeAfterUse) =>
        source.step(newScope).attempt.flatMap:
          case Success(Out(scope, hd, tl)) => #1
            F.unit(Out(scope, hd,
                      WithScope(tl, scopeId, returnScopeId)))
          case Success(Done(outScope, r)) => #2
            scope.findScope(returnScopeId)
              .map(_.getOrElse(outScope))
              .flatMap: nextScope =>
                scope.close.as(Done(nextScope, r))
          case Failure(t) => #3
            scope.close.flatMap(_ => F.raiseError(t))
```

Благодаря этим изменениям мы можем реализовать `resource` в терминах `Eval` и `OpenScope`:

```dotty
def resource[F[_], R](acquire: F[R])(release: R => F[Unit]): Stream[F, R] =
  Pull.Eval(acquire).flatMap(r =>
    Pull.OpenScope(Pull.Output(r), Some(release(r))))
```

Эта реализация обрабатывает как истощение производителя, так и аварийное завершение.
Однако нам все еще нужно сделать еще одну вещь для обработки раннего завершения:
всякий раз, когда мы потенциально можем отбросить остаток потока, мы должны сделать это в новой области.
Это гарантирует, что все ресурсы будут выделены подобластям,
и все поддерево области будет закрыто в самое ближайшее подходящее время.

Давайте добавим `scope` метод, `Stream` который открывает новую область действия,
а затем введем такие области действия для любых операций,
которые могут частично оценивать потоки — таких операций, как `take`, `takeWhile` и так далее:

```dotty
def scope: Stream[F, O] =
  Pull.OpenScope(self, None)

def take(n: Int): Stream[F, O] =
  self.take(n).void.scope
```

С этим изменением `take` вводит новую область действия. Если `take` частично оценивает свой источник,
то `Done` случай источника никогда не достигается.
Но область действия, введенная `take` достигает своего конца, и все поддерево закрывается,
включая любые ресурсы, выделенные во время частично оцененного исходного потока.

Собрав все эти части вместе, мы можем вернуться к упражнению 15.8,
на этот раз используя нашу эффективную версию `Stream`:

```dotty
def file(path: String): Stream[Task, Source] =
  Stream.resource(Task(Source.fromFile(path)))(s => Task(s.close()))

def lines(path: String): Stream[Task, String] =
  file(path).flatMap(source =>
    Stream.eval(Task(source.getLines)).flatMap(Stream.fromIterator)
  )

def fileWriter(path: String): Stream[Task, BufferedWriter] =
  Stream.resource(
    Task(Files.newBufferedWriter(Paths.get(path))))(w => Task(w.close()))

def writeLines(path: String): Pipe[Task, String, Unit] =
  lines => fileWriter(path).flatMap(writer =>
    lines.mapEval(line => Task:
      writer.write(line)
      writer.newLine
    ))

val conversion: Pipe[Task, String, String] =
  trimmed andThen
  nonEmpty andThen
  nonComment andThen
  asDouble andThen
  toCelsius andThen
  toString

def convert(inputFile: String, outputFile: String): Task[Unit] =
  lines(inputFile).pipe(conversion).pipe(writeLines(outputFile)).run
```

### 15.3.4 Динамическое распределение ресурсов

Реалистичным программам может потребоваться динамически распределять ресурсы,
преобразуя при этом некоторый входной поток.
Например, мы можем столкнуться со следующими сценариями:

1. **Динамическое распределение ресурсов** — Читать файл `fahrenheits.txt`, содержащий список имен файлов.
   Объедините эти файлы в один логический поток, преобразуйте этот поток в градусы Цельсия и выведите объединенный поток в `celsius.txt`.
2. **Multi-sink output** — Это похоже на динамическое распределение ресурсов, но вместо создания одного выходного файла,
   создайте выходной файл для каждого входного файла в `fahrenheits.txt`.
   Назовите выходной файл, добавив `.celsius` к имени входного файла.

Можно ли включить эти возможности в наше определение `Stream` таким образом, чтобы сохранить безопасность ресурсов?
Да, можно! На самом деле у нас уже есть возможность делать эти вещи, используя `flatMap` комбинатор,
который мы уже определили для произвольный `Stream` тип.

Например, `flatMap` с учетом наших существующих комбинаторов давайте запишем этот первый сценарий следующим образом:

```dotty
def convertAll(inputFile: String, outputFile: String): Task[Unit] =
  lines(inputFile)
    .flatMap(lines).pipe(conversion).pipe(writeLines(outputFile)).run
```

Этот код полностью безопасен с точки зрения ресурсов,
то есть все файловые дескрипторы будут автоматически закрыты исполнителем сразу после завершения работы,
даже при наличии исключений.

Мы можем записывать данные в несколько файлов, просто изменив порядок вызовов `flatMap`:

```dotty
def convertMultisink(inputFile: String): Task[Unit] =
  lines(inputFile).flatMap(file =>
    lines(file).pipe(conversion).pipe(writeLines(file + ".celsius"))).run
```

## Приложения

Идеи, представленные в этой главе, широко применимы.
Удивительное количество программ можно отлить в терминах потоковой обработки —
как только вы осознаете эту абстракцию, вы начнете видеть ее повсюду.
Давайте рассмотрим некоторые области, где она применима:

- **Файловый ввод/вывод** — Мы уже продемонстрировано, как использовать потоковую обработку для файлового ввода-вывода.
  Хотя мы сосредоточились на построчном чтении и записи для примеров здесь,
  мы также можем использовать библиотеку для обработки двоичных файлов.
- **Обработка сообщений, конечные автоматы и актеры** —
  Большие системы часто организованы как система слабосвязанных компонентов, которые общаются посредством передачи сообщений.
  Эти системы часто выражаются в терминах акторов, которые общаются посредством явных отправок и получения сообщений.
  Мы можем выразить компоненты в этих архитектурах как потоковые вычисления,
  что позволяет нам описывать чрезвычайно сложные конечные машины и поведения с использованием высокоуровневого, композиционного API.
- **Серверы и веб-приложения**. Веб-приложение можно рассматривать как преобразование потока HTTP-запросов в поток HTTP-ответов.
- **Программирование пользовательского интерфейса**.
  Мы можем рассматривать отдельные события пользовательского интерфейса,
  такие как щелчки мыши, как потоки, а сам пользовательский интерфейс —
  как одну большую сеть потоковых вычислений, определяющих, как пользовательский интерфейс реагирует на взаимодействие с пользователем.
- **Большие данные и распределенные системы** — Библиотеки потоковой обработки могут быть распределены
  и распараллелены для обработки больших объемов данных. Ключевым моментом здесь является то,
  что узлы сети потоковой обработки не обязательно должны находиться на одной машине.

Библиотека FS2 ([https://fs2.io/](https://fs2.io/)) основана на идеях, изложенных в этой главе,
и представляет собой потоковую библиотеку промышленного уровня.
FS2 предоставляет `Stream`, `Pull`, и `Pipe` и поддерживает широкий спектр функций,
не обсуждаемых здесь, включая параллелизм, разветвление по входу и выходу, прерывание-возобновление
и поддержку современных типов эффектов, которые сами по себе намного мощнее типов `IO` и `Task` разработанных в этой книге.
Он также имеет богатый набор API для взаимодействия с файлами, сетевыми сокетами и различными другими источниками и приемниками.
Различные библиотеки более высокого уровня построены на FS2, включая популярный веб-фреймворк http4s ([https://http4s.org](https://http4s.org))
и библиотеки баз данных, такие как Skunk ([https://typelevel.org/skunk](https://typelevel.org/skunk))
и doobie ([https://tpolecat.github.io/doobie/](https://tpolecat.github.io/doobie/)).

### Краткое содержание

- Императивный ввод-вывод является монолитным, сочетающим высокоуровневые алгоритмы с низкоуровневыми деталями,
  связанными с итерациями и безопасностью ресурсов.
- Потоковые вычисления имеют ряд важных свойств: они инкрементальны, ресурсобезопасны и композиционны.
  Они также могут поддерживать раннее завершение (т. е. частичную оценку), обработку ошибок и оценку эффектов.
- `Stream` и `Pull` позволяют выполнять компонуемые, ресурсосберегающие, потоковые вычисления,
  которые строятся на основе типов эффектов, созданных в предыдущих главах.
- `take(5)` и `takeWhile(_ > 10)` являются примерами операций, которые могут преждевременно завершить потоковое вычисление.
- Тип `Pull` предоставляет выразительные конструкторы и комбинаторы для построения потоковых вычислений,
  активно используя монадическую рекурсию.
- `Pull[F, O, R]` описывает потоковое вычисление, которое может оценивать эффекты типа `F[_]`,
  выводить ноль или более значений типа `O` и завершаться конечным результатом типа `R`.
- Тип `Stream` предоставляет другой API, `Pull` который смещает фокус с составляющих подвычислений
  на выходные элементы вычисления. `Stream` дополняет `Pull`, а не заменяет его.
- `Stream[F, O]` описывает потоковое вычисление, которое может оценивать эффекты типа `F[_]`
  и выводить ноль или более значений типа `O`.
- A `Stream[F, O]` можно преобразовать в a `Pull[F, O, Unit]`, и наоборот.
- Оба `Stream` и `Pull` имеют экземпляры монад, которые отличаются поведением.
  `Stream` Экземпляр обеспечивает поведение map-then-concat, похожее на список,
- в то время как `Pull` экземпляр обеспечивает последовательность потоковых вычислений.
- `Pipe[F, I, O]` является псевдонимом для `Stream[F, I] => Stream[F, O]`.
- Композиция труб — это просто композиция функций (например, `p1 andThen p2`).
- Приёмники — это каналы, которые выводят поток `Unit` значений `Nothing`.
- Для обеспечения безопасности ресурсов ресурсы должны быть завершены, когда производитель исчерпан,
  оценка потока завершается преждевременно или оценка потока завершается из-за необработанной ошибки.
- Операция `resource` создает `Stream` a `Stream[F, R]` из эффекта приобретения `F[R]` и финализатора `R => F[Unit]`.
- Тип `Ref[F, A]` моделирует изменяемую ячейку, которая хранит значение `A`
  и предоставляет методы доступа или мутаторы через эффект `F`.
- Потоковые вычисления широко применяются в различных областях, включая файловый и сетевой ввод-вывод,
  системы передачи сообщений, HTTP-серверы, пользовательские интерфейсы и распределенную обработку данных.
