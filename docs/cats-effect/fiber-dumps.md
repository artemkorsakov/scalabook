# Дампы волокон (Fiber Dumps)

## Проблема: асинхронные взаимоблокировки (Async Deadlocks)

Асинхронные взаимоблокировки — одна из самых сложных для диагностики проблем в асинхронных приложениях. 
Классический сценарий: волокно A ожидает волокно B, которое, в свою очередь, ожидает волокно A (простейший случай циклического ожидания).

В синхронном мире JVM у нас есть **дампы потоков (thread dumps)** — мощный инструмент, 
показывающий состояние каждого потока и его стек вызовов. 
При взаимоблокировке вы видите точные строки кода, где каждый поток заблокирован.

В асинхронном мире Cats Effect всё сложнее. Когда волокно блокируется (например, на `Deferred.get`), 
среда выполнения удаляет все ссылки на него из активного планирования. 
Волокно «засыпает» до тех пор, пока его не разбудят. В результате классические дампы потоков JVM **бесполезны**:

- Вы увидите потоки `io-compute-*`, которые просто крутятся в цикле ожидания, но не увидете, _какое именно_ волокно заснуло и на чём.
- Единственный способ отладки — добавлять `IO.println` в код в надежде воспроизвести проблему. Это мучительно и часто бесполезно в production-среде.

Начиная с Cats Effect 3.3.0, появилась возможность получать **дампы волокон (fiber dumps)**.

## Что такое дамп волокон?

Дамп волокон — это **снимок (snapshot) состояния всех волокон**, известных среде выполнения Cats Effect в данный момент. Он показывает:

- **Статус** каждого волокна (`WAITING`, `YIELDING`, `RUNNING`, `QUEUED`).
- **Трассировку стека** с информацией о комбинаторах (`flatMap`, `map`, `deferred` и т.д.) и точных местах в пользовательском коде.
- Сводную статистику по пулам и глобальным волокнам.

Вот как выглядит дамп для простой взаимоблокировки (см. пример ниже):

```
cats.effect.IOFiber@56824a14 WAITING
  ├ flatMap @ Deadlock$.$anonfun$run$2(Deadlock.scala:26)
  ├ flatMap @ Deadlock$.$anonfun$run$1(Deadlock.scala:25)
  ├ deferred @ Deadlock$.<clinit>(Deadlock.scala:22)
  ╰ flatMap @ Deadlock$.<clinit>(Deadlock.scala:22)

cats.effect.IOFiber@6194c61c WAITING
  ├ get @ Deadlock$.$anonfun$run$1(Deadlock.scala:24)
  ╰ get @ Deadlock$.$anonfun$run$1(Deadlock.scala:24)

Global: enqueued 0, waiting 2
```

### Детальный разбор примера взаимоблокировки

Рассмотрим код, который приводит к этой взаимоблокировке:

```dotty
import cats.effect.{IO, IOApp}

object Deadlock extends IOApp.Simple:
  val run: IO[Unit] =
    for
      latch <- IO.deferred[Unit]  // Создаём Deferred (как семафор)
      body = latch.get            // Волокно, которое будет ожидать сигнал
      fiber <- body.start         // Запускаем это волокно в фоне
      _     <- fiber.join         // Основное волокно ждёт завершения фонового
      _     <- latch.complete(()) // Никогда не выполнится!
    yield ()
```

**Что здесь происходит (классический deadlock):**

1. Создаётся `Deferred[Unit]` (пустой).
2. Фоновое волокно (`body`) запускается и блокируется на `latch.get` — оно ждёт сигнала от основного волокна.
3. Основное волокно вызывает `fiber.join` — оно ждёт завершения фонового волокна.
4. Взаимоблокировка: основное волокно ждёт фоновое, а фоновое ждёт сигнала от основного. Никто не может продвинуться.

**Как дамп волокон помогает:**

- **Первое волокно (`@56824a14`):** Находится в состоянии `WAITING`. Трассировка показывает, что оно ожидает на `fiber.join` (строка 26).
- **Второе волокно (`@6194c61c`):** В состоянии `WAITING`. Трассировка показывает, что оно ожидает на `latch.get` (строка 24).

Теперь у нас есть **чёткая, прямая улика**, указывающая на причину deadlock'а. 
Мы видим оба волокна и точные строки кода, где они заблокированы.

## Как запустить дамп волокон?

### Сигналы POSIX (Linux, macOS, BSD)

Способ запуска дампа зависит от платформы и доступных сигналов. 
Cats Effect пытается зарегистрировать обработчики для **двух сигналов**: `INFO` (macOS/BSD) и `USR1` (Linux). На практике:

- **macOS / BSD:** Нажмите **`Ctrl + T`** в терминале, где запущено приложение. Вы увидите дамп волокон прямо в stdout/stderr. 
  Это работает благодаря тому, что терминал отправляет сигнал `SIGINFO`.
- **Linux:** Используйте команду `kill -USR1 <pid>`, где `<pid>` — идентификатор процесса вашего приложения.
- **Node.js:** Используйте **`kill -USR2 <pid>`**.

> **Важно:** Дампы волокон **не работают** в обычной Windows (без WSL), так как в ней нет сигналов POSIX. 
> Также они отключены в **JDK 8** из-за отсутствия свободных сигналов.

### JMX (Java Management Extensions)

Если сигналы POSIX недоступны или вы предпочитаете программный подход, 
Cats Effect регистрирует **MBean** с именем `cats.effect.unsafe.metrics.LiveFiberSnapshotTriggerMBean`. 
Вызвав его единственный метод `liveFiberSnapshot`, вы получите массив строк — дамп волокон.

**Пример программного получения дампа через JMX:**

```dotty
import java.lang.management.ManagementFactory
import javax.management.ObjectName

// Получаем MBeanServer
val server    = ManagementFactory.getPlatformMBeanServer
val mbeanName =
  new ObjectName("cats.effect.unsafe.metrics:type=LiveFiberSnapshotTrigger-0")

// Вызываем метод liveFiberSnapshot
val fibers = server
  .invoke(mbeanName, "liveFiberSnapshot", Array.empty, Array.empty)
  .asInstanceOf[Array[String]]
  .filter(_.trim.nonEmpty)

fibers.foreach(println)
```

### Программное получение дампа

> **⚠️ ПРЕДУПРЕЖДЕНИЕ:** Программное получение дампа создаёт **сильную ссылку** на каждое волокно. 
> Это предотвращает сборку мусора этих волокон до тех пор, пока объект снимка (snapshot) находится в области видимости. 
> **Это может привести к утечкам памяти**, если использовать эту функцию в production-цикле. 
> Используйте только для отладки!

Самый прямой способ получить дамп — использовать метод `runtime.liveFiberSnapshot()`:

```dotty
import cats.effect.{IO, IOApp}
import cats.syntax.all.*

object Main extends IOApp.Simple:
  val run: IO[Unit] =
    for
      snapshot <- IO.delay(runtime.liveFiberSnapshot())
      // Вывод волокон, привязанных к конкретным рабочим потокам (только JVM/Native)
      _ <- snapshot.workers.toList.traverse_ { case (worker, fibers) =>
        IO.println(s"Worker ${worker.thread} #${worker.index}") *>
          fibers.traverse_(fiber => IO.println(fiber.pretty))
      }
      // Вывод глобальных волокон (не привязанных к потокам, 
      // например, заблокированных на Deferred)
      _ <- snapshot.external.traverse_(fiber => IO.println(fiber.pretty))
    yield ()
```

## Состояния волокон (Fiber Statuses)

Во время дампа каждое волокно имеет один из следующих статусов:

| Статус          | Описание                                                                                                                                               | Типичные причины                                            |
|:----------------|:-------------------------------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------|
| **`WAITING`**   | Волокно заблокировано семантически (semantic blocking). Оно ждёт внешнего события: `Deferred.get`, `Semaphore.acquire`, `IO.sleep`, `IO.async` и т.д.  | Взаимоблокировки, долгие таймауты, ожидание ресурсов.       |
| **`YIELDING`**  | Волокно приостановлено кооперативно (yield). Оно готово к выполнению, но планировщик ещё не дал ему CPU.                                               | Высокая загрузка CPU, большое количество активных волокон.  |
| **`RUNNING`**   | Волокно в настоящий момент выполняется на каком-то рабочем потоке.                                                                                     | Нормальное рабочее состояние.                               |
| **`QUEUED`**    | Волокно находится в очереди (например, заблокировано на `Mutex` или `Semaphore`). Оно ждёт своей очереди.                                              | Высокий параллелизм, ограниченные ресурсы.                  |

## Трассировка стека волокна (`pretty` print)

Для каждого волокна выводится цепочка комбинаторов (stack trace):

```
cats.effect.IOFiber@6194c61c WAITING
  ├ get @ Deadlock$.$anonfun$run$1(Deadlock.scala:24)
  ╰ get @ Deadlock$.$anonfun$run$1(Deadlock.scala:24)
```

- **`get @ Deadlock$.$anonfun$run$1`:** Показывает комбинатор (`get`) и приблизительное место в коде (анонимная функция).
- Число в скобках (`(Deadlock.scala:24)`) — строка в исходном файле, где находится вызов (если доступно).
- Символы `├`, `╰` — просто визуализация дерева вызовов (не имеют синтаксического значения).

## Особенности на разных платформах

### JVM

- Полноценная поддержка: все статусы, трассировка с номерами строк (при включённых debug-символах), интеграция с сигналами.
- Поддержка MBean для программного доступа.
- Имена потоков (`io-compute-*`) выводятся в статистике.

### Node.js (JavaScript)

- Механизм работает! Используйте `kill -USR2 <pid>`.
- Трассировка может быть менее детальной из-за агрессивного inlining оптимизатором.
- Нет привязки к именам потоков (один поток).
- **Браузер:** Пока не поддерживается.

### Scala Native

- Ограниченная поддержка. Некоторые функции (например, привязка к рабочим потокам) могут быть недоступны.
- Требуется нативная поддержка сигналов.

## Дополнительная статистика

После списка волокон выводится сводная статистика:

```
Global: enqueued 0, waiting 2
```

- **`enqueued`:** Количество волокон в очереди на выполнение (ожидают CPU).
- **`waiting`:** Количество волокон в состоянии `WAITING` (семантически заблокированы).

## Конфигурация

Дампы волокон включены **по умолчанию**. 
Однако сбор информации о трассировке для дампов может создавать дополнительную нагрузку. 
Исследования показали, что эта нагрузка составляет менее 1% в реалистичных приложениях, 
но для сверхчувствительных к производительности систем вы можете отключить эту функцию через [конфигурацию `IORuntime`](io-runtime-config.md).

## Итог

Дампы волокон — это мощный и незаменимый инструмент для отладки сложных конкурентных программ на Cats Effect. 
Они превращают решение проблемы «асинхронный deadlock» из мучительного гадания в структурированный процесс: 
запустил дамп → увидел заблокированные волокна → исправил ошибку.

Запомните главные способы:

1. **macOS:** Нажмите `Ctrl+T`.
2. **Linux:** `kill -USR1 <pid>`.
3. **Node.js:** `kill -USR2 <pid>`.
4. **JMX:** Вызовите метод `liveFiberSnapshot` у MBean.
5. **Программно:** Используйте `runtime.liveFiberSnapshot()` (только для отладки из-за риска утечек).
