# Внешние эффекты и ввод/вывод

## Введение

В функциональном программировании есть важное правило: функции должны быть чистыми. 
Это значит, что они всегда возвращают один и тот же результат для одних и тех же входных данных 
и не производят скрытых изменений (побочных эффектов) — например, не читают файлы, 
не отправляют запросы в сеть и не меняют глобальное состояние.

Но если программа вообще не взаимодействует с внешним миром, она бесполезна. Нам нужно:

- читать данные из файлов и баз данных,
- выводить результаты в консоль или интерфейс,
- отправлять HTTP-запросы.

Как совместить чистоту функций с необходимостью работать с внешним миром?

### Описание действий вместо их выполнения

Вместо того чтобы выполнять операции ввода-вывода напрямую, 
функциональные языки предлагают **описывать** их в виде значений. 
Эти значения можно комбинировать, передавать в функции и даже строить из них сложные сценарии — 
но сами действия не выполняются до самого последнего момента.

Например:

- `readFile("data.txt")` — не читает файл сразу, а возвращает **описание** операции чтения.
- `print("Hello")` — не выводит текст на экран, а создает **объект**, описывающий это действие.

Только когда вся программа собрана из таких описаний, специальный механизм 
(например, рантайм языка) выполняет их в правильном порядке.

### Почему это удобно?

1. **Чистые функции остаются чистыми**  
   Логика программы работает с описаниями действий, а не с реальными эффектами, поэтому сохраняется предсказуемость.

2. **Контроль над выполнением**  
   Можно комбинировать простые операции в сложные сценарии, не теряя контроля над тем, когда и как они выполнятся.

3. **Безопасность**  
   Операции ввода-вывода не разбросаны по коду, а явно выделены в отдельные структуры данных.

### Как это работает технически?

Функциональные языки используют специальный тип (часто называемый `IO`), который:

- **Представляет действие**, а не результат.
- **Позволяет связывать операции** (например, "прочитать файл → обработать данные → записать результат").
- **Откладывает выполнение** до момента, когда программа явно его запустит.

Таким образом, вместо смешивания логики и побочных эффектов мы сначала строим **план вычислений**, а затем выполняем его.

Этот подход позволяет писать код, который сохраняет преимущества функционального программирования, 
но при этом остается практичным для реальных задач.

## Факторизация эффектов: от императивного к функциональному стилю

### Этап 1: Исходный императивный код

Рассмотрим следующий пример:

```dotty
case class Player(name: String, score: Int)

def contest(p1: Player, p2: Player): Unit =
  if p1.score > p2.score then
    println(s"${p1.name} is the winner!")
  else if p2.score > p1.score then
    println(s"${p2.name} is the winner!")
  else
    println("It's a draw.")
```

**Проблемы:**

- Бизнес-логика определения победителя и вывод результата смешаны
- Невозможно протестировать логику без реального вывода в консоль
- Код нельзя переиспользовать для других целей (например, вывода в GUI)

### Этап 2: Отделение чистой логики

```dotty
// Чистая функция без побочных эффектов
def winner(p1: Player, p2: Player): Option[Player] =
  if p1.score > p2.score then Some(p1)
  else if p1.score < p2.score then Some(p2)
  else None

// Эффекты вынесены на границу программы
def contest(p1: Player, p2: Player): Unit =
  winner(p1, p2) match
    case Some(Player(name, _)) => println(s"$name is the winner!")
    case None                  => println("It's a draw.")
```

**Улучшения:**

1. `winner` стала чистой функцией:
   - Всегда возвращает одинаковый результат для одинаковых входных данных
   - Легко тестируется
   - Может использоваться в других контекстах

2. `contest` теперь:
   - Только обрабатывает эффект вывода
   - Содержит минимум логики

> Всегда возможно разложить нечистую процедуру на чистую функцию ядра и две процедуры с побочными эффектами:
> 
> - одна, поставляющая входные данные чистой функции, 
> - и другая, которая что-то делает с выходными данными чистой функции.

### Этап 3: Дальнейшее разделение ответственностей

Мы можем рефакторить это еще дальше.
У функции `contest` все еще есть две обязанности:

- вычисление того, какое сообщение отображать, 
- и затем вывод этого сообщения на консоль.

```dotty
// Чистое преобразование результата в сообщение
def winnerMsg(p: Option[Player]): String =
  p match
    case Some(p) => s"${p.name} is the winner!"
    case None    => "It's a draw."

// Функция эффектов стала тривиальной
def contest(p1: Player, p2: Player): Unit =
  println(winnerMsg(winner(p1, p2)))
```

**Получилась следующая архитектура программы:**

1. `winner` (чистая функция) - определяет победителя
2. `winnerMsg` (чистая функция) - форматирует результат
3. `contest` (эффекты) - вывод на консоль

### Общий принцип рефакторинга

1. **Выявление ядра**:
   - Находим части кода, которые можно выразить без эффектов
   - Выделяем их в чистые функции

2. **Изоляция эффектов**:
   - Оставляем минимальное количество операций с побочными эффектами
   - Выносим их на границы программы

3. **Композиция**:
   - Строим программу как композицию чистых преобразований
   - Эффекты выполняются только в конце

Тот же принцип применяется в более крупных и сложных программах.
Мы не меняем то, **что** делает программа, 
а только внутренние детали того, **как** она разбивается на более мелкие функции.
Суть здесь в том, что внутри каждой функции с побочными эффектами находится чистая функция, ожидающая выхода.

Можно немного формализовать это понимание.
Учитывая нечистую функцию `f` типа `A => B`, можно разбить `f` на две функции:

- Чистая функция типа `A => D`, где `D` есть некоторое описание результата `f`.
- Нечистая функция типа `D => B`, которую можно рассматривать как интерпретатора этих описаний.

Давайте рассмотрим многократное применение этой стратегии к программе.
Каждый раз, когда мы ее применяем, мы делаем больше функций чистыми и выдвигаем побочные эффекты на внешние слои.
Мы могли бы назвать эти нечистые функции "императивной оболочкой" вокруг чистого ядра программы.
В конце концов, мы достигаем функций, которые, как кажется, требуют побочных эффектов,
таких как встроенная `println`, которая имеет тип `String => Unit`.

### Пример тестирования

```dotty
// Тестируем чистые части
val alice = Player("Alice", 10)
val bob   = Player("Bob", 5)

assert(winner(alice, bob).contains(alice))
assert(winnerMsg(Some(alice)) == "Alice is the winner!")
```

### Расширение архитектуры

Если потребуется изменить способ вывода (например, в файл вместо консоли), нужно будет изменить только `contest`:

```dotty
def fileContest(p1: Player, p2: Player): Unit =
  Files.write(
    Paths.get("result.txt"),
    winnerMsg(winner(p1, p2)).getBytes
  )
```

При этом чистая логика останется неизменной.

**Вывод**: 

Постепенное выделение чистых функций делает код:

- Более понятным
- Легко тестируемым
- Гибким к изменениям
- Пригодным для повторного использования

Это решение разделяет валидацию пользователя (чистые функции `validateUsername`, `validatePassword` и `validateUser`)

```dotty
def validateUsername(username: String): Either[String, String] =
  if username.length < 3 then
    Left("Username too short")
  else
    Right(username)

def validatePassword(password: String): Either[String, String] =
  if password.length < 8 then
    Left("Password too weak")
  else
    Right(password)

def validateUser(username: String, password: String): Either[String, User] =
  (validateUsername(username), validatePassword(password)) match
    case (Right(validUser), Right(validPass)) =>
      Right(User(validUser, passwordHash(validPass)))
    case (Left(error1), Left(error2)) =>
      Left(s"$error1, $error2")
    case (Left(error), _) =>
      Left(error)
    case (_, Left(error)) =>
      Left(error)
```

## Концепция IO: формализация подхода к управлению побочными эффектами

### Базовая реализация IO-абстракции

Традиционные процедуры ввода-вывода, такие, как `println`, 
совмещают две различные ответственности:

1. Описание того, что нужно сделать (интенция)
2. Непосредственное выполнение действия (эффект)

Мы можем разделить эти аспекты, введя специальный тип данных `IO`:

```dotty
trait IO:
  /** Выполняет описанное действие. Метод помечен как "unsafe", чтобы
    * подчеркнуть, что это точка входа для реальных побочных эффектов.
    */
  def unsafeRun(): Unit

object IO:
  /** Создает IO-действие для вывода строки в консоль.
    * @param msg
    *   Строка для вывода
    * @return
    *   IO-действие, описывающее вывод
    */
  def PrintLine(msg: String): IO = new IO:
    def unsafeRun(): Unit = println(msg)
```

### Пример использования

```dotty
// Создание описания действия
val hello: IO = PrintLine("Hello, World!")

// Фактическое выполнение (в реальном приложении это делается один раз в "корне" программы)
hello.unsafeRun() // Печатает "Hello, World!"
```

### Ключевые характеристики подхода

1. **Описание вместо выполнения**:
    - `IO` представляет собой неизменяемое описание действия
    - Само действие не выполняется до явного вызова `unsafeRun()`

2. **Чистота функций**:
    - Функции, возвращающие `IO`, остаются чистыми, так как просто создают описания
    - Все побочные эффекты изолированы в `unsafeRun()`

3. **Композируемость**:
    - Описания действий можно комбинировать в более сложные программы

### Применение к примеру выше

```dotty
def contest(p1: Player, p2: Player): IO =
  PrintLine(winnerMsg(winner(p1, p2)))
```

Функция `contest` теперь чистая; она возвращает значение `IO`, просто описывающее действие,
которое должно произойти, но на самом деле не выполняющее его.
Мы говорим, что `contest` имеет (или производит) _эффект_ или является _эффективным_,
но на самом деле в интерпретаторе `IO` только метод `unsafeRun` имеет побочный эффект.

Преимущества новой версии:

1. **Единая ответственность**:
    - `contest` теперь только собирает программу из компонентов
    - `winner` определяет победителя (чистая логика)
    - `winnerMsg` форматирует сообщение (чистое преобразование)
    - `PrintLine` описывает вывод (эффект)

2. **Контроль выполнения**:
    - Программа описывается декларативно
    - Точка выполнения (`unsafeRun`) контролируется явно

3. **Тестируемость**:
    - Можно тестировать `contest` без реального вывода в консоль
    - Проверять только структуру возвращаемого `IO`-значения

### Архитектурные последствия

Такой подход приводит к следующей архитектуре приложения:

1. **Ядро**:
   - Чистые функции бизнес-логики
   - Преобразования данных
   - Генерация описаний эффектов

2. **Периферия**:
   - Интерпретатор `unsafeRun()`
   - Реализация конкретных эффектов
   - Адаптеры к внешним системам

Разделение позволяет:

- Легко тестировать ядро программы
- Заменять реализацию эффектов (например, для тестов)
- Контролировать выполнение побочных эффектов
- Создавать предсказуемые программы

## Обработка входящих эффектов

### Проблема входных эффектов

В предыдущих примерах тип `IO` позволял описывать только выходные операции (например, вывод в консоль). 
Однако многие программы требуют взаимодействия с внешними источниками данных.
Предположим, мы хотим написать программу, которая запрашивает у пользователя температуру в градусах Фаренгейта,
а затем преобразует это значение в градусы Цельсия и выводит его пользователю.
Типичная императивная программа может выглядеть примерно так, как в следующем листинге.

```dotty
def fahrenheitToCelsius(f: Double): Double =
  (f - 32) * 5.0 / 9.0

def converter(): Unit =
  println("Enter a temperature in degrees Fahrenheit: ")
  val d = readLine.toDouble
  println(fahrenheitToCelsius(d))
```

### Ограничения простого IO

Попытка переписать это в функциональном стиле сталкивается с проблемой:

```dotty
def converter(): IO =
  val prompt: IO =
    PrintLine("Enter a temperature in degrees Fahrenheit: ")
  // Невозможно получить введенное значение в чистом виде
```

### Расширенная версия IO

Решение заключается в параметризации типа `IO`, чтобы он мог представлять вычисления, возвращающие значения.
Здесь добавлены функции `map` и `flatMap`, поэтому `IO` могут использоваться в for-comprehensions.

```dotty
trait IO[A]:
  self =>

  /**
   * Выполняет описанное действие и возвращает результат типа A
   * @return Результат выполнения эффекта
   */
  def unsafeRun(): A

  /**
   * Преобразует результат IO-действия
   * @param f Функция преобразования
   * @return Новое IO-действие
   */
  def map[B](f: A => B): IO[B] = new:
    def unsafeRun(): B = f(self.unsafeRun())

  /**
   * Последовательно комбинирует IO-действия
   * @param f Функция, возвращающая новое IO-действие
   * @return Комбинированное действие
   */
  def flatMap[B](f: A => IO[B]): IO[B] = new:
    def unsafeRun(): B = f(self.unsafeRun()).unsafeRun()

object IO:
  /**
   * Создает IO-действие из выражения
   * @param a Выражение, которое может содержать эффекты
   * @return IO-действие
   */
  def apply[A](a: => A): IO[A] = new:
    def unsafeRun(): A = a
```

### Реализация конвертера температур

Теперь мы можем полностью описать программу преобразования температур:

```dotty
def ReadLine: IO[String]             = IO(readLine())
def PrintLine(msg: String): IO[Unit] = IO(println(msg))

def converter: IO[Unit] =
  for
    _     <- PrintLine("Enter a temperature in degrees Fahrenheit: ")
    input <- ReadLine
    temp = input.toDouble
    _ <- PrintLine(s"${fahrenheitToCelsius(temp)} Celsius")
  yield ()
```

Наше определение `converter` больше не имеет побочных эффектов;
это ссылочно прозрачное описание вычисления с эффектами,
а `converter.unsafeRun` - это интерпретатор, который фактически выполнит эти эффекты.

### Ключевые особенности решения

1. **Полноценное взаимодействие**:
    - Теперь можно описывать как ввод, так и вывод
    - `ReadLine` возвращает `IO[String]` с ожидаемым вводом

2. **Композиция операций**:
    - `map` позволяет преобразовывать результаты
    - `flatMap` позволяет последовательно соединять операции
    - for-comprehension обеспечивает удобный синтаксис

3. **Ссылочная прозрачность**:
    - `converter` остается чистой функцией
    - Все эффекты отложены до вызова `unsafeRun()`

4. **Безопасность типов**:
    - Тип `IO[A]` явно указывает на возвращаемое значение
    - Ошибки обработки данных обнаруживаются на этапе компиляции

### Дополнительные примеры

1. **Эхо-программа**:
    ```dotty
    val echo: IO[Unit] = ReadLine.flatMap(PrintLine)
    ```

2. **Чтение числа**:
    ```dotty
    val readInt: IO[Int] = ReadLine.map(_.toInt)
    ```

3. **Интерактивный диалог**:
    ```dotty
    val questionnaire: IO[Unit] =
      for
        _    <- PrintLine("What's your name?")
        name <- ReadLine
        _    <- PrintLine(s"Hello, $name! How old are you?")
        age  <- ReadLine.map(_.toInt)
        _    <- PrintLine(s"$age is a great age!")
      yield ()
    ```

### Архитектурные преимущества

1. **Четкое разделение**:
    - Описание программы (чистый код)
    - Выполнение эффектов (один вызов `unsafeRun()`)

2. **Тестируемость**:
    - Можно подменять реальные эффекты тестовыми
    - Проверять логику без реального ввода/вывода

3. **Модифицируемость**:
    - Легко изменять источники ввода (файл, сеть, консоль)
    - Просто добавлять новые преобразования данных

Такой подход позволяет создавать сложные интерактивные программы, 
сохраняя при этом все преимущества функционального программирования.

### Упражнение 9.1.3: Сумма и произведение

**Задание:** 

Реализуйте программу, которая:

1. Запрашивает у пользователя два числа
2. Повторяет запрос при некорректном вводе, используя рекурсию в `IO`-контексте
3. Выводит их сумму и произведение

```dotty
def readInput(): IO[String] = ???

def readNumber(): IO[Int] = ???

val sumAndProduct: IO[Unit] = ???
```

@:note(🔍 Показать решение)

Следующее решение реализует интерактивную программу для чтения чисел 
с валидацией ввода и вычисления их суммы и произведения, используя функциональный подход с `IO`:

- **`readInput`** запрашивает ввод и возвращает строку в `IO`-контексте;
- **`readNumber`** рекурсивно обрабатывает некорректный ввод, преобразуя строку в число с проверкой через `toIntOption`;
- **`sumAndProduct`** композирует два безопасных чтения числа через for-comprehension и выводит результаты вычислений, 
  сохраняя ссылочную прозрачность и откладывая выполнение эффектов до вызова `unsafeRun()`.

Код демонстрирует **чистую композицию эффектов**, **обработку ошибок без исключений** 
и **интерактивность** при сохранении неизменяемости.

```dotty
def readInput(): IO[String] =
  for
    _     <- PrintLine("Введите число: ")
    input <- ReadLine
  yield input

def readNumber(): IO[Int] =
  readInput().flatMap: input =>
    input.toIntOption match
      case Some(num) => IO(num)
      case None =>
        PrintLine("Введено некорректное число! Повторите ввод!").flatMap: _ =>
          readNumber()

val sumAndProduct: IO[Unit] =
  for
    a <- readNumber()
    b <- readNumber()
    _ <- PrintLine(s"Сумма: ${a + b}")
    _ <- PrintLine(s"Произведение: ${a * b}")
  yield ()
```

## Преимущества и ограничения подхода `IO`

Концепция `IO` (ввод-вывод) представляет собой фундаментальный механизм для работы с эффектами в функциональном программировании. 
Ее текущая реализация служит базовым уровнем абстракции, обеспечивающим взаимодействие с внешним миром 
при сохранении чистоты основной части программы.

### Основные характеристики подхода

1. **Разделение чистого кода и кода с побочными эффектами**
    - Явное выделение всех операций с побочными эффектами в специальный контекст `IO`
    - Гарантия, что функции без `IO` остаются чистыми (детерминированными и без побочных эффектов)
    - Принудительное указание мест взаимодействия с внешней средой в типе функции

2. **Реификация (овеществление) вычислений**
    - `IO`-выражения являются полноценными значениями языка
    - Возможности работы:
        - Хранение в коллекциях
        - Передача в качестве аргументов
        - Динамическое конструирование
        - Композиция в более сложные операции

3. **Интерпретируемая модель**
    - Отделение описания вычислений от их выполнения
    - Возможность замены интерпретатора без изменения клиентского кода 
      (`converter` остается идентичным все зависимости от реализации `IO`)
    - Сокрытие внутреннего представления `IO` от пользователя

### Подробные преимущества

1. **Четкое разделение кода**
    - *Пример*: Чистая функция `validateInput` возвращает `Either`, тогда как `readInput` возвращает `IO[String]`
    - *Преимущество*: Упрощение анализа и рефакторинга кода

2. **Тестируемость**
    - Возможности:
        - Подмена реальных эффектов тестовыми интерпретаторами
        - Проверка логики без запуска фактических операций ввода-вывода
    - *Пример теста*:
      ```dotty
      val testIO = IO.pure("test") // Эмуляция ввода без реального чтения
      assert(runTest(testIO) == expected)
      ```

3. **Композируемость**
    - Базовые операции:
        - `map` - преобразование результата
        - `flatMap` - последовательная композиция
    - *Пример*:
      ```dotty
      val combined = readFile("data.txt").flatMap(parseContent)
      ```

4. **Гибкость выполнения**
    - Варианты интерпретаторов:
        - Синхронный (блокирующий)
        - Асинхронный (на основе коллбэков)
        - Ленивый (отложенное выполнение)
        - Тестовый (с моками эффектов)

### Ограничения текущей реализации

1. **Проблемы со стеком**
    - *Причина*: Рекурсивная природа цепочек `flatMap`
    - *Проявление*: Глубокие последовательности операций вызывают переполнение стека
    - *Пример опасного кода*:
      ```dotty
      def recursiveIO(n: Int): IO[Unit] = 
          IO.unit.flatMap(_ => if n > 0 then recursiveIO(n - 1) else IO.unit)
      ```
    - *Решение*: Требуется механизм "ленивого" выполнения или трамплины

2. **Непрозрачность эффектов**
    - *Проблемы*:
        - Невозможность статического анализа возможных эффектов
        - Отсутствие информации о природе операции (чтение, запись, сетевой вызов)
        - Риск бесконечного выполнения или "зависания"
    - *Пример*:
      ```dotty
      val riskyIO: IO[String] = ??? // Неясно, что именно делает этот эффект
      ```

3. **Синхронная модель выполнения**
    - *Ограничения*:
        - Блокировка потока при выполнении операций ввода-вывода
        - Неэффективное использование ресурсов в высоконагруженных системах
        - Сложность реализации конкурентных сценариев
    - *Пример*:
      ```dotty
      // Последовательное блокирующее выполнение
      val syncOps = writeFile("a.txt").flatMap(readFile("b.txt"))
      ```

### Примеры и последствия ограничений

**Кейс 1: Проблемы стека**

```dotty
def deepChain(depth: Int): IO[Int] =
  (0 until depth).foldLeft(IO(0)): (acc, _) =>
    acc.flatMap(n => IO(n + 1))

deepChain(100000).unsafeRun()
// При depth > 100000 приведет к java.lang.StackOverflowError
```

**Кейс 2: Неочевидные эффекты**

```dotty
val ambiguousProgram: IO[Unit] =
  for
    _ <- fetchURL("http://example.com")
    _ <- logToFile("debug.log")
    _ <- launchMissiles() // Эффект скрыт в цепочке операций
  yield ()
```

### Способы устранения ограничений `IO`

Для решения проблемы переполнения стека применяют *трамплины* (trampolining) 
или переходят на *ленивое выполнение* через контейнеры типа `TailRec`. 
Непрозрачность эффектов устраняют через *типизированные эффекты* (например, `IO[FileOperation, A]`) 
или *систему возможностей* (capabilities). 
Асинхронность достигается интеграцией с `Future`/`Promise` 
или использованием *green threads* (как в ZIO/Cats-Effect). 
Для контроля ресурсов применяют *bracket-паттерн*, 
а для анализа эффектов — *HKD (Higher-Kinded Data)* или *эффект-трекинги* на уровне типов. 
Эти подходы сохраняют преимущества `IO`, устраняя её слабые места.

## Заключение

Текущая реализация `IO` обеспечивает надежную основу для работы с эффектами, предлагая:

- Ясное разделение чистого и кода с побочными эффектами
- Богатые возможности композиции программ
- Гибкость в выборе стратегии выполнения

При этом остаются возможности для совершенствования в области:

- Производительности (асинхронность, управление стеком)
- Экспрессивности (описание природы эффектов)
- Безопасности (контроль за ресурсами и ошибками)
