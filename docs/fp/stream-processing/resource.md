# Обеспечение безопасности ресурсов

`Stream` может использоваться для общения с произвольными ресурсами — не только файлами,
но и соединениями с базами данных, сетевыми сокетами и т.д.
В последнем разделе мы попытались открыть файл и убедиться, что он закрыт,
независимо от того, как завершается наше потоковое вычисление, и обнаружили,
что сделать это сложнее, чем добавить поддержку обработки ошибок.
Давайте еще раз рассмотрим различные типы завершения, которые нам нужно поддерживать.

Предположим, что у нас есть `lines: Stream[Task, String]` представление строк большого файла.
Это источник или производитель, и он ссылается на ресурс (дескриптор файла),
который мы хотим закрыть, независимо от того, как этот производитель потребляется.

Когда нам следует закрыть этот дескриптор файла — в самом конце нашей программы? Нет.
В идеале мы бы закрыли файл, как только узнаем, что закончили чтение из `lines`.
Мы определенно закончили, если достигли последней строки файла; в этот момент больше нет значений для создания,
и файл можно безопасно закрыть.
Итак, это дает нам первое правило, которому нужно следовать:
производитель должен освободить все базовые ресурсы, как только он узнает,
что у него больше нет значений для создания, будь то из-за обычного истощения или исключения.

Однако этого недостаточно, поскольку потребитель потока может сам решить прекратить потребление раньше.
Рассмотрим `lines.take(5).toList`. Вызов `take(5)` остановится после получения только пяти строк,
возможно, до того, как файл будет исчерпан.
В этом случае мы хотим убедиться, что любая необходимая очистка ресурсов будет выполнена до завершения всего потока.
Обратите внимание, что `toList` не может нести за это ответственность, поскольку `toList` не имеет представления о том,
что `Stream` его интерпретация внутренне состоит из других потоков, один из которых требует завершения.
Таким образом, у нас есть второе правило, которому нужно следовать: любой поток `s`,
который потребляет значения из другого потока, `t` должен гарантировать,
что действия по очистке `t` выполняются до `s` остановок.

Подводя итог, можно сказать, что поток `s` может прекратиться из-за:

1. Истощение производителя, когда у источника больше нет значений для вывода
2. Досрочное прекращение, когда остаток источника выбрасывается
3. Ненормальное завершение работы при возникновении исключения

Независимо от причины, в каждом случае мы хотим закрыть базовый ресурс(ы).

Теперь, когда у нас есть наши руководящие принципы, как мы на самом деле реализуем это?
Чтобы справиться с ранним завершением, нам нужен способ выполнения действий по очистке исходного потока, даже если он отброшен.
Это предполагает дизайн, в котором действия по очистке полученных ресурсов отслеживаются интерпретатором,
а не являются примитивными действиями в потоке, составленном с помощью `flatMap` и `handleErrorWith`.
Давайте представим новый конструктор потока, который фиксирует этот шаблон:

```dotty
def resource[F[_], R](acquire: F[R])(release: R => F[Unit]): Stream[F, R]
```

Операция `resource` создает единый поток элементов из `acquire` и гарантирует,
что `release` действие оценивается в соответствии с установленными нами руководящими принципами.
Как мы можем реализовать `resource`? В оставшейся части этого раздела мы рассмотрим один подход,
но не беспокойтесь обо всех деталях реализации.
Важная концепция здесь — как `resource` ведет себя, а не как реализуется.

Для начала мы введем понятие области, в которой происходит интерпретация потока.
Область может быть открытой или закрытой.
Открытая область имеет связанное с ней действие очистки, которое мы будем называть финализатор.
Открытая область действия может также иметь любое количество подобластей.
Мы можем зарегистрировать новый финализатор в области действия, открыв подобласть, которая ссылается на этот финализатор.
Открытая область действия может быть закрыта, что имеет эффект сначала закрытия всех подобластей действия,
а затем запуска финализатора.

Поскольку мы представляем финализаторы как значения type `F[Unit]`,
`Scope` тип должен быть параметризован нашим типом эффекта.
Для реализации различных переходов состояний, таких как открытие подобласти и закрытие дерева областей,
нам нужна возможность манипулировать состоянием в эффекте `F`.
Мы можем сделать это с помощью новый тип — `Ref`:

```dotty
final class Ref[F[_], A] private (
  underlying: AtomicReference[A],
  delay: [A] => (() => A) => F[A] #1
):

  def get: F[A] = delay(() => underlying.get)

  def set(a: A): F[Unit] = delay(() => underlying.set(a))

  def modify[B](f: A => (A, B)): F[B] = delay: () =>
    @annotation.tailrec
    def loop(): B =
      val oldA = underlying.get
      val (newA, result) = f(oldA)
      if underlying.compareAndSet(oldA, newA) then result else loop()
    loop()

object Ref:
  def apply[F[_], A](initial: A)(using F: Monad[F]): Ref[F, A] =
    new Ref(new AtomicReference[A](initial),
      [A] => (th: () => A) => F.unit(()).map(_ => th()))
```

A `Ref[F, A]` — это чисто функциональный эквивалент переменной типа `A`,
где весь доступ и мутация выполняются в эффекте `F`.
Эта реализация использует a `java.util.concurrent.AtomicReference` в качестве базового хранилища,
одновременно предоставляя эффективные аксессоры и мутаторы.

Операция `modify` особенно полезна.
Она атомарно вычисляет новое значение из текущего значения
и позволяет возвращать произвольное дополнительное значение.
Используя `Ref` and `modify`, мы можем реализовать `Scope` как конечный автомат с состояниями `Open` and `Closed`:

```dotty
class Scope[F[_]](
  parent: Option[Scope[F]],
  val id: Id,
  state: Ref[F, Scope.State[F]]
)(using F: MonadThrow[F]):
  import Scope.State

  def open(finalizer: F[Unit]): F[Scope[F]] = ???
  def close: F[Unit] = ???

object Scope:
  enum State[F[_]]:
    case Open(
      finalizer: F[Unit], subscopes: Vector[Scope[F]]) extends State[F]
    case Closed() extends State[F]

  def root[F[_]](using F: MonadThrow[F]): Scope[F[_]] =
    new Scope(None, new Id, Ref(State.Open(F.unit(()), Vector.empty))
```

A `Scope` сохраняет свое изменяемое состояние в `Ref[F, State[F]]`. `State[F]`
Тип представляет собой перечисление, состоящее из `Open` и `Closed` случаев.
`Open` сохраняет ссылку на финализатор для этой области и подобластей.

Подобласть можно открыть, вычислив новое `Open` состояние с зарегистрированной новой подобластью:

```dotty
def open(finalizer: F[Unit]): F[Scope[F]] =
  state
    .modify:
      case State.Open(myFinalizer, subscopes) =>
        val sub = new Scope(Some(this), new Id,
                            Ref(State.Open(finalizer, Vector.empty)))
        State.Open(myFinalizer, subscopes :+ sub) -> F.unit(sub)
      case State.Closed() =>
        val next = parent match
          case None =>
            F.raiseError(new RuntimeException("корневая область уже закрыта"))
          case Some(p) => p.open(finalizer)
        State.Closed() -> next
    .flatten
```

Нам нужно обработать два случая: когда `open` вызывается в `Open` области действия
и когда он вызывается в `Closed` области действия.
Если область действия открыта, то сначала мы создаем новую область действия для нового финализатора,
а затем вычисляем новое `Open` состояние, которое ссылается на новую область действия в ее подобластях.
Напомним, что сигнатура `modify` позволяет нам возвращать произвольное значение вместе с обновленным состоянием;
здесь мы возвращаем `F[Scope[F]]` как это произвольное значение. Игнорируя `Closed` случай на мгновение,
у нас есть `state.modify(...)`, который возвращает `F[F[Scope[F]]`, который мы `flatten` преобразуем в `F[Scope[F]]`.

Этот шаблон расширяем до любого конечного автомата, который мы можем себе представить.
Мы сохраняем текущее состояние в `Ref` и выполняем переходы в терминах `ref.modify(f).flatten`,
где `f` вычисляет следующее состояние из текущего состояния и возвращает действие для оценки после успешной модификации состояния `Ref`.

Возвращаясь к `Closed` случаю, мы могли бы сделать открытие подобласти в закрытой области ошибкой.
Вместо этого мы передаем открытый запрос в родительскую область.
Эта область также может быть закрыта, что приведет к рекурсивному распространению вверх по дереву до тех пор,
пока мы не встретим открытую область или не достигнем корня.
Мы сообщаем об ошибке только в том случае, если достигнем корня, не встретив открытой области.
Операция `close` реализуется аналогичным образом:

```dotty
def close: F[Unit] =
  state
    .modify:
      case State.Open(finalizer, subscopes) =>
        val finalizers = (subscopes.reverseIterator.map(_.close) ++
          Iterator(finalizer)).toList
        def go(rem: List[F[Unit]], error: Option[Throwable]): F[Unit] =
          rem match
            case Nil => error match
              case None => F.unit(())
              case Some(t) => F.raiseError(t)
            case hd :: tl =>
              hd.attempt.flatMap(res =>
                go(tl, error orElse res.toEither.swap.toOption))
        State.Closed() -> go(finalizers, None)
      case State.Closed() => State.Closed() -> F.unit(())
    .flatten
```

Вызов `close` для открытой области действия переводит состояние области действия в `Closed`.
Мы вычисляем действие, которое закрывает все подобласти действия, а затем запускает финализатор исходной области действия.
Мы должны быть осторожны, чтобы поменять порядок подобластей действия на обратный, чтобы гарантировать,
что финализаторы запускаются в стекоподобном режиме (т. е. финализаторы должны запускаться в порядке «последним пришел, первым вышел»).
Мы также должны быть осторожны, чтобы запускать все финализаторы, даже если происходят ошибки.
Мы не можем просто пройти по списку действий; в противном случае мы бы закоротили при первой ошибке.

Теперь давайте интегрируем `Scope` в `Stream` и `Pull`.
Начнем с создания двух новых случаев в `Pull` перечислении:

```dotty
case OpenScope[+F[_], +O, +R](
  source: Pull[F, O, R], finalizer: Option[F[Unit]]
) extends Pull[F, O, R]

case WithScope[+F[_], +O, +R](
  source: Pull[F, O, R], scopeId: Id, returnScope: Id
) extends Pull[F, O, R]
```

`OpenScope` ссылается на исходный pull и финализатор.
При обнаружении `OpenScope` интерпретатор вызывает `open` активную область, передавая финализатор.
Затем он интерпретирует исходный pull, используя вновь открытую область как новую активную область.
`WithScope` ссылается на исходный pull, идентификатор области, используемой во время интерпретации этого исходного pull,
и идентификатор области, к которой следует вернуться после завершения исходного pull.

Подразумевается, что эти новые случаи подразумевают, что интерпретатор (т.е. `fold` и `step`)
должен отслеживать активную область и разрешать шагу изменять текущую область.
Чтобы разрешить изменения активной области, нам нужно изменить результат, `step` включив новую активную область.
Мы могли бы изменить тип результата с `Either[R, (O, Pull[F, O, R])]` на `(Scope[F], Either[R, (O, Pull[F, O, R])])`, но это немного утомительно.
Вместо этого давайте введем новый тип, представляющий результат шага:

```dotty
enum StepResult[F[_], +O, +R]:
  case Done(scope: Scope[F], result: R)
  case Out(scope: Scope[F], head: O, tail: Pull[F, O, R])
```

Давайте изменим `fold` управление активной областью.
Нам нужно создать корневую область и закрыть ее после завершения сворачивания,
и нам нужно изменить активную область для каждого `StepResult.Out`:

```dotty
def fold[F2[x] >: F[x], R2 >: R, A](init: A)(f: (A, O) => A)(
  using F: MonadThrow[F2]
): F2[(R2, A)] =
  scope = Scope.root[F2]
  def go(scope: Scope[F2], p: Pull[F2, O, R2], acc: A): F2[(R2, A)] =
    p.step(scope).flatMap:
      case StepResult.Done(_, r) => F.unit((r, init))
      case StepResult.Out(newScope, hd, tl) =>
        go(newScope, tl, f(init, hd))
  go(scope, this, init).attempt.flatMap(res =>
    scope.close.flatMap(_ => res.fold(F.raiseError, F.unit))
```

Операция `step` теперь принимает активную область в качестве аргумента,
а результат `step` указывает следующую область для использования.
Изменение `step` на handle `OpenScope` довольно просто:
мы делегируем в `open` активной области, а затем используем `WithScope` для оценки исходного потока источника
с использованием недавно открытой подобласти.
После завершения мы восстанавливаем исходную область:

```dotty
case OpenScope(source, finalizer) =>
  scope.open(finalizer.getOrElse(F.unit(()))).flatMap(subscope =>
    WithScope(source, subscope.id, scope.id).step(subscope))
```

Изменение `step` for `WithScope` немного сложнее.
Сначала мы ищем в дереве областей целевую область,
а затем используем эту область для пошагового выполнения исходного потока.
Если в результате получается `Done`, то мы закрываем целевую область и ищем область, в которую нужно вернуться.
В противном случае мы распространяемся `WithScope` по оставшемуся потоку, возвращенному в `Out`:

```dotty
case WithScope(source, scopeId, returnScopeId) =>
  scope.findScope(scopeId)
    .map(_.map(_ -> true).getOrElse(scope -> false))
    .flatMap:
      case (newScope, closeAfterUse) =>
        source.step(newScope).attempt.flatMap:
          case Success(Out(scope, hd, tl)) => #1
            F.unit(Out(scope, hd,
                      WithScope(tl, scopeId, returnScopeId)))
          case Success(Done(outScope, r)) => #2
            scope.findScope(returnScopeId)
              .map(_.getOrElse(outScope))
              .flatMap: nextScope =>
                scope.close.as(Done(nextScope, r))
          case Failure(t) => #3
            scope.close.flatMap(_ => F.raiseError(t))
```

Благодаря этим изменениям мы можем реализовать `resource` в терминах `Eval` и `OpenScope`:

```dotty
def resource[F[_], R](acquire: F[R])(release: R => F[Unit]): Stream[F, R] =
  Pull.Eval(acquire).flatMap(r =>
    Pull.OpenScope(Pull.Output(r), Some(release(r))))
```

Эта реализация обрабатывает как истощение производителя, так и аварийное завершение.
Однако нам все еще нужно сделать еще одну вещь для обработки раннего завершения:
всякий раз, когда мы потенциально можем отбросить остаток потока, мы должны сделать это в новой области.
Это гарантирует, что все ресурсы будут выделены подобластям,
и все поддерево области будет закрыто в самое ближайшее подходящее время.

Давайте добавим `scope` метод, `Stream` который открывает новую область действия,
а затем введем такие области действия для любых операций,
которые могут частично оценивать потоки — таких операций, как `take`, `takeWhile` и так далее:

```dotty
def scope: Stream[F, O] =
  Pull.OpenScope(self, None)

def take(n: Int): Stream[F, O] =
  self.take(n).void.scope
```

С этим изменением `take` вводит новую область действия. Если `take` частично оценивает свой источник,
то `Done` случай источника никогда не достигается.
Но область действия, введенная `take` достигает своего конца, и все поддерево закрывается,
включая любые ресурсы, выделенные во время частично оцененного исходного потока.

Собрав все эти части вместе, мы можем вернуться к упражнению 15.8,
на этот раз используя нашу эффективную версию `Stream`:

```dotty
def file(path: String): Stream[Task, Source] =
  Stream.resource(Task(Source.fromFile(path)))(s => Task(s.close()))

def lines(path: String): Stream[Task, String] =
  file(path).flatMap(source =>
    Stream.eval(Task(source.getLines)).flatMap(Stream.fromIterator)
  )

def fileWriter(path: String): Stream[Task, BufferedWriter] =
  Stream.resource(
    Task(Files.newBufferedWriter(Paths.get(path))))(w => Task(w.close()))

def writeLines(path: String): Pipe[Task, String, Unit] =
  lines => fileWriter(path).flatMap(writer =>
    lines.mapEval(line => Task:
      writer.write(line)
      writer.newLine
    ))

val conversion: Pipe[Task, String, String] =
  trimmed andThen
  nonEmpty andThen
  nonComment andThen
  asDouble andThen
  toCelsius andThen
  toString

def convert(inputFile: String, outputFile: String): Task[Unit] =
  lines(inputFile).pipe(conversion).pipe(writeLines(outputFile)).run
```

### 15.3.4 Динамическое распределение ресурсов

Реалистичным программам может потребоваться динамически распределять ресурсы,
преобразуя при этом некоторый входной поток.
Например, мы можем столкнуться со следующими сценариями:

1. **Динамическое распределение ресурсов** — Читать файл `fahrenheits.txt`, содержащий список имен файлов.
   Объедините эти файлы в один логический поток, преобразуйте этот поток в градусы Цельсия и выведите объединенный поток в `celsius.txt`.
2. **Multi-sink output** — Это похоже на динамическое распределение ресурсов, но вместо создания одного выходного файла,
   создайте выходной файл для каждого входного файла в `fahrenheits.txt`.
   Назовите выходной файл, добавив `.celsius` к имени входного файла.

Можно ли включить эти возможности в наше определение `Stream` таким образом, чтобы сохранить безопасность ресурсов?
Да, можно! На самом деле у нас уже есть возможность делать эти вещи, используя `flatMap` комбинатор,
который мы уже определили для произвольный `Stream` тип.

Например, `flatMap` с учетом наших существующих комбинаторов давайте запишем этот первый сценарий следующим образом:

```dotty
def convertAll(inputFile: String, outputFile: String): Task[Unit] =
  lines(inputFile)
    .flatMap(lines).pipe(conversion).pipe(writeLines(outputFile)).run
```

Этот код полностью безопасен с точки зрения ресурсов,
то есть все файловые дескрипторы будут автоматически закрыты исполнителем сразу после завершения работы,
даже при наличии исключений.

Мы можем записывать данные в несколько файлов, просто изменив порядок вызовов `flatMap`:

```dotty
def convertMultisink(inputFile: String): Task[Unit] =
  lines(inputFile).flatMap(file =>
    lines(file).pipe(conversion).pipe(writeLines(file + ".celsius"))).run
```
