# Недостаток процессоров (CPU Starvation)

Одна из самых коварных тенденций в современном программном обеспечении, развертываемом на серверах, — это 
стратегия сокращения ресурсов приложения до минимума, упаковки этих приложений в контейнеры 
и попытки восстановить потерянную мощность путем репликации большого количества экземпляров. 
Хотя есть веские причины для контейнеризации приложений и их проектирования для развертывания в реплицированной топологии, 
абстрагированной от базовых хост-систем, вполне возможно переборщить с хорошим. 
Эта практика, известная как **«широкое» (wide) развёртывание**, 
вступает в фундаментальное противоречие с принципами работы Cats Effect.

## Почему мало CPU — это плохо для Cats Effect?

Представьте себе типичное приложение, развернутое в контейнере, 
которому администратор выделил **всего 2 виртуальных процессора (vCPU)**. 
Какие потоки будут бороться за эти два ядра?

Даже для простого приложения Cats Effect количество потоков может быть внушительным:

1. **`compute-worker`** (вычислительный пул): Обычно количество потоков равно числу vCPU. В нашем случае — **2 потока**. 
   Это единственные потоки, которые выполняют полезную, интенсивную вычислительную работу вашего приложения.
2. **`timer`** (поток диспетчеризации таймеров): **1 поток**. Обрабатывает таймеры (`IO.sleep` и т.д.).
3. **`async-io`** (поток диспетчеризации асинхронного ввода-вывода): **1 поток**.
4. **`blocking`** (блокирующий пул): По умолчанию создаёт потоки по мере необходимости, но как минимум **2 потока** могут быть активны.
5. **`JIT compiler`** (поток JIT-компилятора): **1 поток**. Незаменим для производительности JVM.
6. **`GC`** (поток сборщика мусора): **1 поток** (или несколько, в зависимости от выбранного сборщика).
7. **`main`** (основной поток): **1 поток**, который запускает `IOApp`.
8. **Потоки сторонних библиотек:** Например, AWS SDK v2 создаёт свои собственные пулы потоков.

**Итого:** В худшем случае около **9 активных потоков** борются за внимание всего **2 виртуальных ядер CPU**!

Коэффициент конкуренции (overcommit) за вычислительные ресурсы составляет `1 - 2/9 = 78%`. 
Это означает, что почти 80% времени ядро ОС тратит на _переключение контекста_ между этими потоками, 
а не на выполнение полезной работы вашего приложения. 
Результат — хроническое **голодание CPU** и предупреждения от Cats Effect.

## Сравнение: 2 CPU против 8 CPU

Давайте посмотрим, как изменится ситуация, если мы выделим контейнеру **8 виртуальных процессоров** 
(при этом общую мощность кластера оставим той же, пропорционально уменьшив количество экземпляров).

| Тип потока                    | При 2 vCPU (9 потоков)  | При 8 vCPU (9 потоков)  |
|:------------------------------|:------------------------|:------------------------|
| **Вычислительные (compute)**  | 2                       | 8                       |
| **Все остальные (прочие)**    | 7                       | 7                       |
| **Коэффициент конкуренции**   | `1 - 2/9 ≈ 78%`         | `1 - 8/15 ≈ 47%`        |

Даже при переходе с 2 на 8 ядер коэффициент конкуренции падает с 78% до 47%. 
Это уже рабочая, хотя и не идеальная конфигурация. 
При **16 vCPU** он упадет до `1 - 16/23 ≈ 30%`, а при **32 vCPU** — до `1 - 32/39 ≈ 18%`, 
где конкуренцию можно считать практически не влияющей на производительность.

## Аксиома для развертывания Cats Effect

Исходя из этого, можно сформулировать золотое правило:

> **«Приложениям с эффектом Cats Effect в реплицированных развертываниях, как правило, 
> выгоднее использовать немного более «высокие» и не такие «широкие» ресурсы.»**

Иными словами: **лучше иметь несколько мощных экземпляров (с 8, 16, 32 vCPU), чем много слабых (с 2, 1, 0.5 vCPU).**

Это прямо противоположно стандартным рекомендациям для многих HTTP-серверов на Java, 
основанных на блокирующем вводе-выводе (например, старые конфигурации Tomcat), где «узкие» поды (1-2 vCPU) — это норма. 
Cats Effect с его планировщиком в пользовательском пространстве work-stealing требует простора для маневра.

### Почему это работает?

Смысл Cats Effect — перенести большую часть логики планирования на уровень _приложения_ (в пользовательское пространство), 
где она может быть более агрессивно оптимизирована под асинхронные рабочие нагрузки. 
Планировщик в ядре ОС — это «тяжелая артиллерия», он хорош для общего случая, но создает существенные накладные расходы. 
Когда у вас крайне мало vCPU, у планировщика пользовательского пространства буквально нет ресурсов для маневра. 
Вы начинаете бороться не за производительность, а за то, чтобы просто переключить контекст.

> **"Широкий охват ограничивает ресурсы, доступные в пользовательском пространстве 
> (препятствуя существенному влиянию планировщика пользовательского пространства), 
> одновременно перекладывая общую проблему планирования на ядро (что гораздо менее эффективно)."**

Эта стратегия имеет смысл, когда планировщик пользовательского пространства очень ограничен по своим возможностям. 
Но она просто контрпродуктивна, когда планировщик пользовательского пространства _более_ оптимизирован, 
чем тот, что находится в ядре. 
Именно так обстоит дело с Cats Effect.

## Практические последствия и настройка

Конечно, всё не так просто, как удвоить количество vCPU и уменьшить вдвое количество экземпляров. 
Масштабирование — сложный процесс, и вам, вероятно, потребуется настроить другие ресурсы, 
такие как память, ограничения на соединения, количество файловых дескрипторов и сигналы автомасштабирования. 
Однако, 8 vCPU — это **хорошее эмпирическое правило для минимального количества процессоров**, 
которое должно быть доступно приложению на Cats Effect. 
16 или даже 32 vCPU, вероятно, еще больше повысят производительность, и стоит поэкспериментировать с такими параметрами настройки.

### Специальный случай: Kubernetes и `cpu_quota`

Одна из самых критических и частых причин «недостатка процессоров» в современных развертываниях — 
это **работа внутри Kubernetes без настроенной квоты на использование ЦП (`cpu_quota`)**.

Когда вы создаете pod в Kubernetes, вы можете указать `limits.cpu`. 
На основе этого значения kubelet настраивает контрольную группу (cgroup) для контейнера. 
Однако **JVM не умеет автоматически читать настройки cgroups старых версий (cgroup v1)**. 
В старых версиях Java (до Java 10) и в некоторых конфигурациях по умолчанию, 
JVM определяет количество доступных процессоров как `1`. 
Это **фатально** для Cats Effect, которое по умолчанию создаст только 1 вычислительный поток!

**Диагностика проблемы:**

- Вы развернули приложение в Kubernetes.
- Приложение работает, но имеет очень низкую производительность и стабильно выдает предупреждения о голодании.
- Вы проверили дампы потоков (`jstack`) и увидели, что в пуле `io-compute-*` всего 1 поток.

**Решение:**

У вас есть два пути:

1. **Настройте `cpu_quota` (обычно задается через `limits.cpu` в поде).** 
   После этого JVM сможет корректно определить количество доступных ядер, 
   начиная с Java 10 (по умолчанию) и в Java 8 с обновления 191 (если включена опция `-XX:+UseContainerSupport`).

2. **Явно укажите JVM количество процессоров** с помощью аргумента `-XX:ActiveProcessorCount=<n>`. Это самый надежный и контролируемый способ.
    ```dockerfile
    ENTRYPOINT ["java", "-XX:ActiveProcessorCount=8", "-jar", "app.jar"]
    ```
    Вы должны установить это значение равным значению `limits.cpu` в вашем поде Kubernetes 
    (или немного меньше, оставив запас для других процессов в контейнере). 
    Это критически важная настройка для любого Cats Effect приложения, работающего под управлением Kubernetes.

В более подробном руководстве по [контейнеризации Java-приложений для Kubernetes](https://learn.microsoft.com/en-us/azure/developer/java/containers/kubernetes#understand-jvm-available-processors) подробно описан задействованный механизм.

> **Ключевой вывод:** Все приложения Cats Effect, работающие в Kubernetes, 
> либо должны иметь настроенную `cpu_quota` (позволяя JVM автоматически определить количество ядер), 
> **либо** использовать аргумент `-XX:ActiveProcessorCount`, чтобы явно указать JVM, сколько ядер использовать. 
> Без этого ваше приложение будет работать на одном потоке и, скорее всего, будет страдать от голодания.
