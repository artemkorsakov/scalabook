# Free Monad

A free monad is a way to structure computations
that allows separating the description of a program from its interpretation.
It is an abstraction that encapsulates a sequence of operations as data,
which can be interpreted in various ways.

A free monad provides:

- An abstract syntax tree (AST) for expressing monadic operations
- An API for writing interpreters that give meaning to this AST

**Main ideas:**

- **Describing computations**: A free monad allows describing a sequence of operations as data without executing them immediately.
- **Interpretation**: This data can be interpreted later, depending on the context or requirements.
- **Flexibility**: A free monad is useful when you need to support multiple interpretations for the same set of operations.

**Where is it used:**

- **DSL (Domain-Specific Languages)**: A free monad is often used to create embedded DSLs,
  where the description of operations must be separated from their execution.
- **Testing**: In tests, one interpretation can be used for real execution of operations,
  while another can be used for simulation or mocking.
- **Asynchronous computations**: A free monad can be used to describe asynchronous operations
  that are then interpreted depending on the context (e.g., in different runtime environments).
- **Logging and debugging**: An interpretation can be added that logs each operation
  without changing the main program logic.

## Formal Definition

A free monad is a construction in category theory and functional programming
that allows representing a sequence of operations (computations) as a data structure
that can be interpreted in various ways.
Formally, a free monad is built on a functor and represents a monad that is "freely" generated by this functor.

Let \\(F\\) be a functor (in the sense of category theory).
Then the **free monad** \\(\text{Free}\[F\]\\), generated by functor \\(F\\),
is defined as a structure that satisfies the following properties:

- **Constructor**:
    - \\(\text{Free}\[F\]\\) can be represented as a sum type:
      \\(\text{Free}\[F, A\] = A + F(\text{Free}\[F, A\])\\).
      This means that a free monad either returns a value of type \\(A\\) (a completed computation),
      or continues the computation by applying functor \\(F\\) to the next step.
- **Unit**:
    - There is a natural transformation \\(\eta: A \to \text{Free}\[F, A\]\\),
      which embeds a value of type \\(A\\) into the free monad. This corresponds to a completed computation.
- **Coproduct (join)**:
    - There is a natural transformation \\(\mu: \text{Free}\[F, \text{Free}\[F, A\]\] \to \text{Free}\[F, A\]\\),
      which "flattens" nested free monads. This allows combining sequential computations.
- **Universal property**:
    - For any monad \\(M\\) and natural transformation \\(\alpha: F \to M\\), there exists
      a unique monad homomorphism \\(\text{Free}\[F\] \to M\\) that makes the diagram commute.
      This means that a free monad is the "most general" monad generated by functor \\(F\\).

A free monad allows representing computations as a tree, where each node is an operation
defined by functor \\(F\\), and leaves are values of type \\(A\\).
This tree can be interpreted in various ways, depending on the context.

If \\(F\\) is a functor representing a "database query" operation,
then \\(\text{Free}\[F, A\]\\) is a sequence of such queries
that can be interpreted as real database queries, test simulations, or even logging.

## Code

```dotty
trait Natural[F[_], G[_]]:
  def transform[A](a: F[A]): G[A]
  
sealed trait Free[F[_], A]

final case class UnitF[F[_], A](a: A) extends Free[F, A]

final case class LiftF[F[_], A](fn: F[A]) extends Free[F, A]

final case class FlatMap[F[_], A, B](a: Free[F, A], fx: A => Free[F, B])
    extends Free[F, B]

object Free:
  given freeFunctor[F[_]]: Functor[[X] =>> Free[F, X]] with
    extension [A](as: Free[F, A])
      override def map[B](f: A => B): Free[F, B] =
        FlatMap(as, a => UnitF(f(a)))

  given freeMonad[F[_]]: Monad[[X] =>> Free[F, X]] with
    override def unit[A](a: => A): Free[F, A] =
      UnitF(a)

    extension [A](fa: Free[F, A])
      override def flatMap[B](f: A => Free[F, B]): Free[F, B] =
        FlatMap(fa, f)

  def liftF[F[_], A](a: F[A]): Free[F, A] = LiftF[F, A](a)

  def foldF[F[_], M[_]: Monad as monad, A](
      fa: Free[F, A]
   )(
       trans: Natural[F, M]
   ): M[A] =
     fa match
       case UnitF(a)             => monad.unit(a)
       case LiftF(fn)            => trans.transform(fn)
       case FlatMap(UnitF(a), f) => foldF(f(a))(trans)
       case FlatMap(LiftF(a), f) =>
         monad.flatMap(trans.transform(a)) { aa => foldF(f(aa))(trans) }
       case FlatMap(FlatMap(a, f), g) =>
         foldF(FlatMap(a, aa => FlatMap(f(aa), g)))(trans)
 end Free  
```

### Algebraic Type of Free

```dotty
sealed trait Free[F[_], A]
```

`Free[F, A]` can be in one of three states:

#### `UnitF` — Pure Value

```dotty
final case class UnitF[F[_], A](a: A) extends Free[F, A]
```

- Represents a completed computation returning value `a`
- Analogous to `pure` / `unit` in monads
- Does not contain `F` effects

#### `LiftF` — Lifted Effect

```dotty
final case class LiftF[F[_], A](fn: F[A]) extends Free[F, A]
```

- Lifts effect `F[A]` into the free monad
- Represents a "raw" operation from functor `F`
- For example, if `F` is `Option`, then `LiftF(Some(42))` or `LiftF(None)`

#### `FlatMap` — Sequential Composition

```dotty
final case class FlatMap[F[_], A, B](
    a: Free[F, A],
    fx: A => Free[F, B]
) extends Free[F, B]
```

- Represents sequential execution of two computations
- First `a` is executed (getting `A`), then `fx` is applied to the result
- This is the building block for `flatMap` / `bind`

This representation encodes **monad laws as data**:

- `UnitF` is `pure`
- `FlatMap` is `flatMap`
- `LiftF` is lifting an effect from the base functor

### Functor Implementation

```dotty
given freeFunctor[F[_]]: Functor[[X] =>> Free[F, X]] with
  extension [A](as: Free[F, A])
    override def map[B](f: A => B): Free[F, B] =
      FlatMap(as, a => UnitF(f(a)))
```

**How it works:**

1. `map` transforms the value inside `Free[F, A]`
2. Uses `FlatMap` for sequential execution:
    - First we execute `as`
    - Then we apply a function that wraps `f(a)` in `UnitF`
3. This is the standard implementation of `map` via `flatMap` and `unit`

### Monad Implementation

```dotty
given freeMonad[F[_]]: Monad[[X] =>> Free[F, X]] with
  override def unit[A](a: => A): Free[F, A] = UnitF(a)

  extension [A](fa: Free[F, A])
    override def flatMap[B](f: A => Free[F, B]): Free[F, B] =
      FlatMap(fa, f)
```

**Note:**

- `unit` simply creates `UnitF(a)`
- `flatMap` literally creates `FlatMap(fa, f)` **without executing**!

This is a key difference: here `flatMap` **does not compute** the result, it only **builds a data structure**.

### Lifting an Effect into Free

```dotty
def liftF[F[_], A](a: F[A]): Free[F, A] = LiftF[F, A](a)
```

- Converts any effect `F[A]` into `Free[F, A]`
- Allows using operations from `F` inside the free monad

## Folding the Free Monad (Interpreter)

The most important part — `foldF` — is the interpreter that converts the data structure `Free[F, M]` into real computations in monad `M`.

```dotty
def foldF[F[_], M[_]: Monad as monad, A](
    fa: Free[F, A]
)(
    trans: Natural[F, M]
): M[A] = fa match { ... }
```

**`Natural[F, M]`** is a natural transformation:

```dotty
trait Natural[F[_], G[_]]:
  def transform[A](a: F[A]): G[A]
```

It can convert `F[A]` into `M[A]` for any type `A`.

### Case Breakdown

#### Case 1: UnitF (pure value)

```dotty
case UnitF(a) => monad.unit(a)
```

Simply returns `a` wrapped in monad `M`.

#### Case 2: LiftF (lifted effect)

```dotty
case LiftF(fn) => trans.transform(fn)
```

Applies the natural transformation to `fn: F[A]`, yielding `M[A]`.

#### Case 3: FlatMap with UnitF on the left

```dotty
case FlatMap(UnitF(a), f) => foldF(f(a))(trans)
```

If the first computation is a pure value `a`, simply continue with `f(a)`.

#### Case 4: FlatMap with LiftF on the left — effect execution

```dotty
case FlatMap(LiftF(a), f) =>
  monad.flatMap(trans.transform(a)) { aa => foldF(f(aa))(trans) }
```

This case is the **effect execution point** in the free monad.
When we encounter a `LiftF(a) >>= f` construct (effect `a` followed by continuation `f`),
we must actually execute this effect in the target monad `M`.
Without this rule, `foldF` would never execute any effect —
it would just recursively traverse the data structure without producing any computation.

**One execution step:**

1. **Transform the effect**:

    ```dotty
    trans.transform(a)   // F[A] => M[A]
    ```

    We use the natural transformation to convert the effect from the base functor `F` into the target monad `M`.

2. **Execute one monadic bind step**:
    ```dotty
    monad.flatMap(...) { aa => foldF(f(aa))(trans) }
    ```

     - `monad.flatMap` executes effect `M[A]` (first step)
     - The obtained value `aa` is substituted into continuation `f(aa)`
     - Then the result `f(aa)` is recursively folded

**Why this is stack-safe:**

```dotty
// Execution visualization:

Original:     FlatMap(LiftF(a), f)
                 ↓
Step 1:        monad.flatMap(trans.transform(a)) { aa => foldF(f(aa)) }
                 ↓
Step 2:        One effect is executed in M
                 ↓
Step 3:        foldF recursively processes continuation f(aa)
```

**Key feature** — there is **no recursive call to `foldF` within `foldF` before effect execution**:

- First, `trans.transform(a)` is executed (one step)
- Then `monad.flatMap` calls the passed function **after** obtaining the result
- Inside this function, `foldF` is called again, but on a reduced structure

**Call stack in the correct implementation:**

```
foldF(FlatMap(LiftF(a1), f1))
  → trans.transform(a1)        // execute effect 1
  → foldF(f1(aa1))             // recursion on next step
    → ...                      // stack does not grow!
```

If we tried to execute all effects at once (e.g., via `traverse` or a loop), then:

- Either we would lose laziness (computations would happen before we were ready)
- Or we would get deep recursion (each `flatMap` would add a frame to the stack)

#### Case 5: FlatMap with FlatMap on the left (associativity) — critical for stack safety!

```dotty
case FlatMap(FlatMap(a, f), g) =>
  foldF(FlatMap(a, aa => FlatMap(f(aa), g)))(trans)
```

**The problem this case solves:**

Without this rule, recursive `foldF` could create a deeply nested call structure like:

```
FlatMap(FlatMap(FlatMap(..., f1), f2), f3)
```

Naive recursive processing would lead to stack overflow for long chains of computations.

**Solution — one-step rewriting (like in [trampolining](../../fp/external-effects/stack_overflow_error.md)):**

1. **Original expression**: `((a >>= f) >>= g)`
    - First `a` is executed, then `f`, then `g`

2. **One transformation step**:

    ```dotty
    FlatMap(a, aa => FlatMap(f(aa), g))
    //    ↑                      ↑
    //    |                      └── applying g after f(aa)
    //    └── original computation
    ```

    Now: `(a >>= (aa => f(aa) >>= g))`

3. **Why this is safe**:
     - We perform **exactly one rewriting step**
     - The left `FlatMap` "bubbles" up, nesting is reduced
     - Then `foldF` recursively continues processing the simplified structure
     - Recursion depth is bounded, no stack overflow

**Visualization of the transformation:**

```
Before:                   After:
                            FlatMap
     FlatMap                 /   \
      /   \                 a    λ(aa)
   FlatMap  g                   |
    /   \                    FlatMap
   a     f                     /   \
                         f(aa)  g

Old structure:           New structure:
((a >>= f) >>= g)  →   (a >>= (aa => f(aa) >>= g))
```

**Key idea:**

We do not fold the entire expression at once; we take **one step** — pulling the left `FlatMap` outward.
This allows `foldF` to work as a **trampoline**: each iteration slightly simplifies the structure without deepening the call stack.

## Usage Example

[Source code](https://gitverse.ru/scalabook/typeclasses/content/master/src/main/scala/ru/scalabook/typeclasses/monad/FreeExample.scala)

```dotty
import cats.effect.{IO, IOApp, Ref}
import ru.scalabook.typeclasses.monad.Free
import ru.scalabook.typeclasses.monad.Free.*
import ru.scalabook.typeclasses.monad.Monad

object FreeExample extends IOApp.Simple:
  enum CounterOp[A]:
    case Increment extends CounterOp[Unit]
    case Get       extends CounterOp[Int]

  import CounterOp.*

  given Monad[IO] with
    override def unit[A](a: => A): IO[A] =
      IO.delay(a)

    extension [A](fa: IO[A])
      override def flatMap[B](f: A => IO[B]): IO[B] =
        fa.flatMap(f)

  def run: IO[Unit] =
    Ref.of[IO, Int](0).flatMap: ref =>
      // Natural transformation into IO
      given counterToIO: Natural[CounterOp, IO] with
        def transform[A](op: CounterOp[A]): IO[A] =
          op match
            case Increment =>
              ref.update(i => i + 1)
            case Get =>
              ref.get

      // Build the program
      val program: Free[CounterOp, Int] =
        for
          _ <- liftF[CounterOp, Unit](Increment)
          _ <- liftF[CounterOp, Unit](Increment)
          x <- liftF[CounterOp, Int](Get)
        yield x

      // Execute the program
      val result: IO[Int] = Free.foldF(program)(counterToIO)

      result.flatMap(i => IO.println(s"i = $i")).void
end FreeExample
// i = 2
```

### Why is this useful?

1. **Separation of description and execution**: The program is described as data, and the interpreter defines how to execute it
2. **Testing**: Multiple interpreters can be written (e.g., test, production, logging)
3. **Composition**: Different effects can be combined via free monads
4. **Refactoring**: Easy to change execution logic without changing the program description

### Structure Visualization

```
Free[F, A] =
    | UnitF(a)          // Pure value
    | LiftF(fa)         // Effect from F
    | FlatMap(fa, f)    // Sequence: first fa, then f

Example: liftF(Inc) >>= (_ => liftF(Get))
Becomes: FlatMap(LiftF(Inc), _ => LiftF(Get))
```

This is a powerful abstraction at the core of many effect systems (Cats Effect, ZIO, Monix).
