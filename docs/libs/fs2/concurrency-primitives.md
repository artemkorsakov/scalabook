# Примитивы параллелизма

В пакете [`fs2.concurrent`](https://github.com/typelevel/fs2/tree/main/core/shared/src/main/scala/fs2/concurrent) 
вы найдёте несколько полезных примитивов параллелизма, построенных на основе примитивов, определённых в библиотеке `cats-effect`. 
Среди них:

- `Topic[F, A]` — реализует паттерн издатель-подписчик (publish-subscribe) с возможностью многократной подписки на один и тот же поток сообщений.
- `Channel[F, A]` — реализует паттерн издатель-подписчик, но с единственным подписчиком и множеством издателей, 
  что делает его идеальным для сценариев с одним потребителем.
- `Signal[F, A]` — представляет собой изменяемое значение, которое можно читать и обновлять, 
  а также подписываться на его изменения, что позволяет использовать его как механизм сигнализации между потоками.

Кроме того, `Stream` предоставляет функции для взаимодействия с очередями (`Queue`) из библиотеки `cats-effect`, 
что позволяет легко интегрировать их в потоковые вычисления.

## Простые примеры (Simple Examples)

### Channel

`Channel` реализует паттерн издатель-подписчик (publish-subscribe) и особенно полезен в ситуациях, 
когда у нас есть **несколько издателей (publishers)** и **один подписчик (subscriber)**. 
В отличие от `Topic`, который позволяет множественным подписчикам получать одни и те же сообщения, 
`Channel` предназначен для маршрутизации сообщений от многих производителей к одному потребителю.

В следующем примере у нас есть два потока-издателя: `pub1` публикует строку `"Hello"` каждую 1 секунду, 
а `pub2` публикует строку `"World"` каждые 2 секунды. 
Кроме того, у нас есть подписчик `sub`, который потребляет и выводит каждый элемент на консоль. 
Все три потока запускаются параллельно и прерываются через 6 секунд.

```dotty
import cats.effect.*
import fs2.Stream
import scala.concurrent.duration.*
import cats.effect.unsafe.implicits.global
import fs2.concurrent.Channel

Channel.unbounded[IO, String].flatMap { channel =>
  // Издатель 1: отправляет "Hello" каждую секунду
  val pub1 =
    Stream.repeatEval(IO("Hello")).evalMap(channel.send).metered(1.second)

  // Издатель 2: отправляет "World" каждые 2 секунды
  val pub2 =
    Stream.repeatEval(IO("World")).evalMap(channel.send).metered(2.seconds)

  // Подписчик: читает из канала и выводит каждое полученное сообщение
  val sub = channel.stream.evalMap(IO.println)

  // Запускаем всех параллельно и прерываем через 6 секунд
  Stream(
    pub1,
    pub2,
    sub
  ).parJoinUnbounded.interruptAfter(6.seconds).compile.drain
}.unsafeRunSync()
// Hello
// World
// Hello
// Hello
// Hello
// World
// Hello
```

**Объяснение работы:**

- `Channel.unbounded[IO, String]` создаёт неограниченный канал для передачи строк.
- `pub1` и `pub2` используют `evalMap(channel.send)` для отправки каждого сгенерированного значения в канал.
- `channel.stream` создаёт поток, который читает все поступающие в канал сообщения в порядке их получения.
- `parJoinUnbounded` запускает все три потока параллельно без ограничений на количество одновременно выполняемых потоков.
- `interruptAfter(6.seconds)` гарантирует, что программа завершится через 6 секунд, независимо от того, закончили ли потоки свою работу.

### Topic

(Основано на примере [Pera Villega](https://perevillega.com/), доступном [здесь](https://underscore.io/blog/posts/2018/03/20/fs2.html))

`Topic` реализует классический паттерн издатель-подписчик (publish-subscribe) с поддержкой **множества подписчиков**. 
Каждое сообщение, опубликованное в топик, доставляется **всем активным подписчикам**. 
Это особенно полезно для сценариев широковещательной рассылки, 
когда одно и то же событие должно быть обработано несколькими независимыми потребителями.

В следующем примере издатель и подписчик запускаются одновременно. 
Издатель непрерывно публикует строку `"1"` в топик, а подписчик потребляет сообщения до тех пор, 
пока не получит четыре элемента, после чего завершается.

```dotty
import cats.effect.*
import cats.effect.unsafe.implicits.global
import fs2.Stream
import fs2.concurrent.Topic

Topic[IO, String].flatMap { topic =>
  // Издатель: бесконечно генерирует строку "1" и публикует её в топик
  val publisher = Stream.constant("1").covary[IO].through(topic.publish)

  // Подписчик: подписывается на топик с буфером 10 сообщений и берёт первые 4
  val subscriber = topic.subscribe(10).take(4)

  // Запускаем подписчика параллельно с издателем и собираем результаты
  subscriber.concurrently(publisher).compile.toVector
}.unsafeRunSync()
```

**Ключевые моменты:**

- `Topic[IO, String]` создаёт топик для сообщений типа `String`.
- `topic.publish` — это `Pipe`, который принимает поток элементов и публикует их в топик.
- `topic.subscribe(10)` создаёт поток, читающий сообщения из топика с размером буфера 10. 
  Буфер позволяет сглаживать пиковые нагрузки и предотвращает потерю сообщений, если подписчик временно не успевает их обрабатывать.
- `concurrently(publisher)` запускает издателя в фоновом режиме параллельно с подписчиком, игнорируя его выходные данные. 
  Это обеспечивает одновременную работу обоих потоков.

### Signal

`Signal` можно использовать как средство связи между двумя различными потоками. 
Он представляет собой потокобезопасное изменяемое значение, на изменение которого можно подписываться. 
`Signal` особенно полезен для реализации флагов остановки, сигналов завершения или передачи состояния между компонентами системы.

В следующем примере `s1` — это поток, который выводит текущее время каждую секунду и прерывается, когда сигнал принимает значение `true`. 
`s2` — это поток, который засыпает на четыре секунды, а затем устанавливает сигнал в `true`, что приводит к прерыванию `s1`.

(Обратите внимание, что `SignallingRef` расширяет `Signal`, предоставляя дополнительные возможности для атомарного обновления значения.)

```dotty
import cats.effect.*
import cats.effect.unsafe.implicits.global
import fs2.Stream
import fs2.concurrent.SignallingRef

import scala.concurrent.duration.*

SignallingRef[IO, Boolean](false).flatMap { signal =>
  // Поток s1: выводит время каждую секунду и прерывается по сигналу
  val s1 = Stream.awakeEvery[IO](1.second).interruptWhen(signal)

  // Поток s2: ждёт 4 секунды, затем устанавливает сигнал в true
  val s2 = Stream.sleep[IO](4.seconds) >> Stream.eval(signal.set(true))

  // Запускаем s1 и s2 параллельно
  s1.concurrently(s2).compile.toVector
}.unsafeRunSync()
```

**Детали реализации:**

- `SignallingRef[IO, Boolean](false)` создаёт сигнальную ссылку с начальным значением `false`.
- `interruptWhen(signal)` — это метод, который останавливает поток, как только `signal` становится `true`. 
  Он автоматически подписывается на изменения сигнала.
- `Stream.sleep[IO](4.seconds)` создаёт поток, который просто ждёт указанное время, не производя никаких выходных данных.
- `>>` — это оператор последовательной композиции: сначала выполняется левый поток (задержка), затем правый (установка сигнала).
- `concurrently` запускает `s2` в фоновом режиме параллельно с `s1`, что позволяет `s2` прервать `s1` по истечении четырёх секунд.

### Queue

[Очереди (`Queue`) из библиотеки `cats-effect`](../../cats-effect/std/queue.md) 
являются фундаментальным строительным блоком для организации асинхронного обмена данными между различными частями программы. 
FS2 предоставляет удобные методы для интеграции очередей в потоковую обработку.

В следующем примере `Stream.fromQueueNoneTerminated` используется для создания потока из `cats.effect.std.Queue`. 
Этот фрагмент возвращает `List(1, 2, 3)`: поток выдаст первые три значения, к
оторые возвращает очередь (`Some(1)`, `Some(2)`, `Some(3)`), и будет прерван после того, как очередь вернёт `None` — 
этот сигнал интерпретируется как маркер завершения потока.

```dotty
import cats.effect.IO
import cats.effect.std.Queue
import cats.effect.unsafe.implicits.global
import cats.syntax.all.*
import fs2.Stream

val program =
  for
    // Создаём неограниченную очередь для значений Option[Int]
    queue <- Queue.unbounded[IO, Option[Int]]

    // Создаём поток из очереди — он завершится, когда получит None
    streamFromQueue = Stream.fromQueueNoneTerminated(queue)

    // Наполняем очередь значениями: три числа и маркер завершения None
    _ <- Seq(Some(1), Some(2), Some(3), None).map(queue.offer).sequence

    // Запускаем поток и собираем все элементы в список
    result <- streamFromQueue.compile.toList
  yield result

program.unsafeRunSync()
```

**Важные детали:**

- `Stream.fromQueueNoneTerminated(queue)` создаёт поток, который читает из очереди до тех пор, пока не встретит значение `None`. 
  Как только `None` получен, поток завершается.
- `queue.offer` добавляет элемент в очередь. В данном случае мы последовательно добавляем несколько значений и маркер завершения.
- `.sequence` преобразует `List[IO[Unit]]` в `IO[List[Unit]]`, выполняя все операции по порядку. 
  Это гарантирует, что все элементы будут помещены в очередь до того, как мы начнём читать из неё.

## Продвинутые примеры

Эти структуры данных могут быть очень полезны в более сложных сценариях. 
Ниже приведены примеры использования каждой из них, изначально взятые из [репозитория gvolpe examples](https://github.com/gvolpe/advanced-http4s/tree/master/src/main/scala/com/github/gvolpe/fs2).

### FIFO (First IN / First OUT — первым пришёл — первым вышел)

Типичный случай использования `cats.effect.std.Queue[F, A]`, который также весьма полезен для взаимодействия с внешним миром, 
как показано в [основном руководстве](guide.md).

В этом примере `q1` имеет размер буфера 1, а `q2` — размер буфера 100. 
Вы сможете заметить эффект буферизации при извлечении элементов из `q2`: поскольку буфер `q2` больше, 
он может накапливать больше элементов, прежде чем потребитель начнёт их обрабатывать.

**Описание работы примера:**

- **Первый поток** генерирует числа от 0 до 999 и помещает их в `q1` (буфер 1). 
  Если `q1` заполнена, операция `offer` будет блокироваться (или асинхронно ожидать) до тех пор, пока не освободится место.
- **Второй поток** постоянно извлекает элементы из `q1` и помещает их в `q2` (буфер 100). 
  Это создаёт промежуточный буфер, который сглаживает пиковые нагрузки.
- **Третий поток** постоянно извлекает элементы из `q2` и выводит их на консоль. 
  Благодаря буферу размером 100, этот потребитель может работать с некоторой задержкой относительно производителя, не теряя данные.

```dotty
import cats.effect.{Concurrent, IO, IOApp}
import cats.effect.std.{Console, Queue}
import fs2.Stream

import scala.concurrent.duration.*

class Buffering[F[_]: {Concurrent, Console}](
    q1: Queue[F, Int],
    q2: Queue[F, Int]
):

  def start: Stream[F, Unit] =
    Stream(
      // Поток-производитель: генерирует числа от 0 до 999 и кладёт их в q1
      Stream.range(0, 1000).covary[F].foreach(q1.offer),

      // Поток-посредник: перекладывает элементы из q1 в q2
      Stream.repeatEval(q1.take).foreach(q2.offer),

      // Поток-потребитель: забирает элементы из q2 и выводит их
      // Примечание: .map не подойдёт здесь, так как мы пытаемся применить побочный эффект к чистому значению.
      // Используйте .foreach вместо .map для выполнения эффектов.
      Stream.repeatEval(q2.take).foreach(n =>
        Console[F].println(s"Извлекаем $n из очереди #2")
      )
    ).parJoin(3) // Запускаем все три потока параллельно
end Buffering

object Fifo extends IOApp.Simple:

  def run: IO[Unit] =
    val stream =
      for
        // Создаём две очереди с разными размерами буфера
        q1 <- Stream.eval(Queue.bounded[IO, Int](1))   // маленький буфер
        q2 <- Stream.eval(Queue.bounded[IO, Int](100)) // большой буфер
        bp = new Buffering[IO](q1, q2)
        // Запускаем буферизацию и даём ей поработать 5 секунд
        _ <- Stream.sleep[IO](5.seconds) concurrently bp.start.drain
      yield ()
    stream.compile.drain
```

**Наблюдения:**

- При буфере размером 1 производитель будет часто блокироваться, ожидая, пока посредник заберёт элемент.
- При буфере размером 100 посредник может накопить значительное количество элементов, 
  прежде чем потребитель начнёт их обрабатывать, что позволяет сгладить пиковые нагрузки и повысить общую пропускную способность системы.

### Один издатель / Множество подписчиков (Single Publisher / Multiple Subscriber)

Построение системы, подобной Kafka, на основе примитивов параллелизма, возможно с использованием `fs2.concurrent.Topic[F, A]`. 
В этом более сложном примере мы также покажем, как использовать `fs2.concurrent.Signal[F, A]` для прерывания запланированного потока.

**Сценарий:**

- **Издатель** публикует текстовые события каждую секунду в течение 15 секунд, затем отправляет одно событие `Quit` и продолжает публиковать текстовые события.
- **Три подписчика** подписываются на топик в разное время:
    - Подписчик #1 подписывается сразу и должен получить 15 событий.
    - Подписчик #2 подписывается с задержкой 5 секунд и должен получить 10 событий.
    - Подписчик #3 подписывается с задержкой 10 секунд и должен получить 5 событий.
- Когда подписчик получает событие `Quit`, он устанавливает сигнал прерывания, что останавливает издателя и завершает программу.

Программа завершается после 15 секунд, когда сигнал прерывает публикацию новых событий, 
поскольку финальное слияние потоков (`parJoin`) останавливается по завершении левого потока (издателя).

**Ожидаемый результат:**

- Подписчик #1 получает 15 событий.
- Подписчик #2 получает 10 событий.
- Подписчик #3 получает 5 событий.
- Издатель отправляет событие `Quit`.
- Подписчики поднимают сигнал прерывания при получении `Quit`.

```dotty
import scala.concurrent.duration.*
import cats.effect.std.Console
import cats.effect.{Clock, IO, IOApp, Temporal}
import cats.syntax.all.*
import fs2.{Pipe, Stream}
import fs2.concurrent.{SignallingRef, Topic}

// Определяем типы событий
sealed trait Event
case class Text(value: String)
    extends Event // текстовое событие с временной меткой
case object Quit extends Event // сигнал завершения

class EventService[F[_]](
    eventsTopic: Topic[F, Event],
    interrupter: SignallingRef[F, Boolean]
)(
    implicit
    F: Temporal[F],
    console: Console[F]
):

  // Издатель: публикует 15 текстовых событий, затем одно Quit, затем продолжает публиковать
  def startPublisher: Stream[F, Unit] =
    // Генерируем текстовые события каждую секунду с текущим временем
    val textEvents =
      Stream.awakeEvery[F](1.second)
        .zipRight(Stream.repeatEval(Clock[F].realTime.map(t =>
          Text(t.toString)
        )))

    // Создаём событие Quit и публикуем его
    val quitEvent = Stream.eval(eventsTopic.publish1(Quit).as(Quit))

    // Берём первые 15 текстовых событий, затем Quit, затем продолжаем публиковать
    // Прерываем, если сигнал стал true
    (textEvents.take(15) ++ quitEvent ++ textEvents)
      .through(eventsTopic.publish)
      .interruptWhen(interrupter)

  // Создаём 3 подписчиков, запускающихся в разное время, и объединяем их для параллельного выполнения
  def startSubscribers: Stream[F, Unit] =
    // Функция обработки событий для конкретного подписчика
    def processEvent(subscriberNumber: Int): Pipe[F, Event, Nothing] =
      _.foreach {
        case e @ Text(_) =>
          console.println(
            s"Подписчик #$subscriberNumber обрабатывает событие: $e"
          )
        case Quit =>
          // При получении Quit устанавливаем сигнал прерывания
          interrupter.set(true)
      }

    // Получаем поток событий из топика с буфером 10
    val events: Stream[F, Event] =
      eventsTopic.subscribe(10)

    // Три подписчика запускаются с разными задержками
    Stream(
      events.through(processEvent(1)), // подписчик #1 — сразу
      events.delayBy(
        5.second
      ).through(processEvent(2)), // подписчик #2 — через 5 секунд
      events.delayBy(
        10.second
      ).through(processEvent(3)) // подписчик #3 — через 10 секунд
    ).parJoin(3)                 // запускаем всех параллельно
  end startSubscribers
end EventService

object PubSub extends IOApp.Simple:

  val program =
    for
      topic  <- Stream.eval(Topic[IO, Event]) // создаём топик
      signal <- Stream.eval(SignallingRef[
        IO,
        Boolean
      ](false)) // создаём сигнал прерывания
      service = new EventService[IO](topic, signal) // создаём сервис
      _ <- service.startPublisher.concurrently(
        service.startSubscribers
      ) // запускаем издателя и подписчиков параллельно
    yield ()

  def run: IO[Unit] = program.compile.drain
```

**Ключевые концепции:**

- `Topic` обеспечивает доставку каждого сообщения всем активным подписчикам.
- `SignallingRef` используется как механизм «стоп-сигнала»: любой подписчик может остановить всю систему, получив событие `Quit`.
- `delayBy` добавляет задержку перед началом обработки потока, что позволяет подписчикам подключаться в разное время.
- `parJoin(3)` объединяет три потока подписчиков в один, выполняющийся параллельно.

### Разделяемый ресурс

Когда несколько процессов пытаются получить доступ к ценному ресурсу (например, к базе данных, файловой системе или сетевому соединению), 
вы можете ограничить количество одновременных доступов. 
Здесь на помощь приходит `cats.effect.std.Semaphore[F]` — семафор, который ограничивает параллельный доступ к общему ресурсу.

В этом примере три процесса пытаются одновременно получить доступ к общему ресурсу, 
но только один из них в каждый момент времени получает доступ. 
Остальные вынуждены ждать, пока ресурс снова не станет доступным (доступность равна 1, как указано счётчиком семафора).

**Возможный ход выполнения:**

```
P1 >> Доступность: 1
P2 >> Доступность: 1
P2 >> Начало работы | Доступность: 0
P3 >> Доступность: 0
--------------------------------
P1 >> Начало работы | Доступность: 0
P2 >> Завершено | Доступность: 0
--------------------------------
P3 >> Начало работы | Доступность: 0
P1 >> Завершено | Доступность: 0
--------------------------------
P3 >> Завершено | Доступность: 1
```

**Анализ выполнения:**

- Когда P1 и P2 запросили доступность, она была равна 1. P2 оказался быстрее и получил доступ к ресурсу, начав обработку.
- P3 был самым медленным и с самого начала видел, что доступность отсутствует (0).
- После того как P2 завершил работу, P1 немедленно начал обработку, и доступность снова стала 0.
- После завершения P1, P3 начал обработку.
- Наконец, P3 завершился, и доступность снова стала равна 1.

```dotty
import cats.effect.{IO, IOApp, Temporal}
import cats.effect.std.Semaphore
import cats.syntax.all.*
import fs2.Stream

import scala.concurrent.duration.*

class SlowProcess[F[_]: Temporal](name: String, s: Semaphore[F]):

  def execute: Stream[F, Unit] =
    for
      // Проверяем текущую доступность
      _ <-
        Stream.eval(s.available.map(a => println(s"$name >> Доступность: $a")))

      // Запрашиваем доступ (блокируется, если доступность = 0)
      _ <- Stream.eval(s.acquire)

      // Подтверждаем начало работы (доступность должна быть 0 после acquire)
      _ <- Stream.eval(s.available.map(a =>
        println(s"$name >> Начало работы | Доступность: $a")
      ))

      // Имитируем длительную работу (3 секунды)
      _ <- Stream.sleep(3.seconds)

      // Освобождаем ресурс
      _ <- Stream.eval(s.release)

      // Подтверждаем завершение
      _ <- Stream.eval(s.available.map(a =>
        println(s"$name >> Завершено | Доступность: $a")
      ))
    yield ()
end SlowProcess

object Resources extends IOApp.Simple:

  def run: IO[Unit] =
    val stream =
      for
        // Создаём семафор с начальной доступностью 1 (только один процесс одновременно)
        s <- Stream.eval(Semaphore[IO](1))

        // Создаём три процесса, конкурирующих за ресурс
        p1 = new SlowProcess[IO]("P1", s)
        p2 = new SlowProcess[IO]("P2", s)
        p3 = new SlowProcess[IO]("P3", s)

        // Запускаем все три процесса параллельно
        _ <- Stream(p1.execute, p2.execute, p3.execute).parJoin(3)
      yield ()
    stream.compile.drain
```

**Детали работы с семафором:**

- `Semaphore[IO](1)` создаёт семафор с одним разрешением. Это гарантирует, что только один процесс может владеть ресурсом в любой момент времени.
- `s.available` возвращает текущее количество доступных разрешений (неблокирующая операция).
- `s.acquire` запрашивает разрешение. Если разрешений нет, операция блокируется (асинхронно) до тех пор, пока разрешение не станет доступным.
- `s.release` освобождает разрешение, увеличивая счётчик доступности.
- `parJoin(3)` запускает все три процесса параллельно, что демонстрирует честную конкуренцию за ресурс.

**Применение в реальных проектах:**
Семафоры широко используются для:

- Ограничения количества одновременных подключений к базе данных.
- Регулирования доступа к внешним API с ограничением по частоте запросов.
- Управления пулом потоков или соединений.
- Реализации паттерна «ограничитель» (rate limiter).

## Заключение

Примитивы параллелизма в FS2 и Cats Effect предоставляют мощный и безопасный набор инструментов для построения конкурентных приложений. 
Используя `Channel`, `Topic`, `Signal`, `Queue` и `Semaphore`, вы можете реализовать сложные паттерны взаимодействия между потоками, такие как:

- **Издатель-подписчик** с одним или множеством подписчиков.
- **Механизмы прерывания** и управления жизненным циклом потоков.
- **Буферизация и регулирование** потоков данных.
- **Ограничение доступа** к общим ресурсам.

Все эти примитивы являются потокобезопасными и гарантируют корректное поведение даже в условиях высокой нагрузки и конкурентного доступа.
