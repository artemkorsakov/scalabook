# Проблема «производитель-потребитель» — параллелизм и волокна

Паттерн «производитель-потребитель» — один из краеугольных камней параллельного программирования. 
Он возникает всякий раз, когда одна часть системы генерирует данные, а другая часть — обрабатывает их.

**Классические примеры:**

- Веб-сервер: производитель (пул потоков, принимающих соединения) кладёт HTTP-запросы в очередь. 
  Потребители (воркеры) забирают их и обрабатывают.
- Логгер: производитель (приложение) отправляет сообщения в очередь логов. 
  Потребитель (пишущий поток) периодически сбрасывает их на диск.
- Парсер файлов: производитель читает строки из файла, потребитель разбирает их в объекты.

**Важные аспекты проблемы:**

- **Асинхронность:** Производитель и потребитель работают в параллельных потоках выполнения.
- **Разные скорости:** Производитель может генерировать данные быстрее, чем потребитель успевает их обрабатывать (или наоборот).
- **Координация:** Если очередь пуста, потребители должны **блокироваться** и ждать данных. 
  Если очередь ограничена и переполнена, производители должны **блокироваться**, ожидая свободного места.
- **Безопасность:** Только один производитель должен добавлять элемент в очередь одновременно. 
  Только один потребитель должен извлекать элемент одновременно (чтобы два потребителя не прочитали один и тот же элемент).

Эти требования идеально соответствуют возможностям Cats Effect: легковесным волокнам и конкурентным структурам данных (особенно `Queue`).

## Введение в волокна

### Что такое волокно?

[Волокно (fiber)](foundation/fibers.md) — это фундаментальный строительный блок конкурентного выполнения в Cats Effect. 
Проще всего представить его как **«легковесный поток»**:

- Волокно инкапсулирует действие `F[A]` (обычно `IO[A]`), которое оно должно выполнить.
- Волокна создаются и управляются средствами Cats Effect без вмешательства операционной системы.

```dotty
import cats.effect.{IO, IOApp}

object FiberExample extends IOApp.Simple:
  def run: IO[Unit] =
    for
      fiber <- IO.println("Привет из фонового волокна!").start
      // Основное волокно продолжает работу, не дожидаясь фонового
      _ <- IO.println("Основное волокно работает...")
      _ <- fiber.join // Ждём завершения фонового волокна (опционально)
    yield ()
    
// Основное волокно работает...
// Привет из фонового волокна! 
```

Вернёмся к паттерну «производитель-потребитель».

### Простая модель с неограниченной очередью

Допустим, у нас есть один производитель, один потребитель и неограниченная очередь.

```dotty
import cats.effect.std.Queue
import cats.effect.{IO, IOApp}

object UnboundedProducerConsumer extends IOApp.Simple:
  def run: IO[Unit] =
    for
      queue <- Queue.unbounded[IO, String]

      producer =
        for
          _ <- IO.println("Producer: генерирую данные...")
          _ <- queue.offer("result")
        yield ()

      consumer =
        for
          elem <- queue.take
          _    <- IO.println(s"Consumer: получил '$elem'")
        yield ()

      // Запускаем производителя и потребителя в параллельных волокнах
      producerFiber <- producer.start
      consumerFiber <- consumer.start

      _ <- producerFiber.join
      _ <- consumerFiber.join
    yield ()
```

**Что здесь происходит:**

1. Создаётся [неограниченная очередь (`unbounded`)](std/queue.md).
2. `producer` и `consumer` — это описания эффектов.
3. `.start` превращает каждое описание в волокно, которое начинает выполняться параллельно.
4. `queue.offer` (производитель) никогда не блокируется (очередь неограниченная).
5. `queue.take` (потребитель) блокирует волокно, если очередь пуста — но поток ОС не блокируется! 
   Как только появится элемент, волокно будет автоматически разбужено.

### Усложнение: несколько производителей и потребителей

Легко расширить до множества производителей и потребителей, используя `.start` для каждого.

```dotty
val producers = List.fill(10)(producer.start)
val consumers = List.fill(5)(consumer.start)

(producers ++ consumers).parSequence.void
```

Cats Effect гарантирует, что операции на `Queue` потокобезопасны: 
параллельные вызовы `offer` от разных производителей не повредят внутреннее состояние очереди.

### Ограниченная очередь (bounded queue)

Если мы ограничим размер очереди (например, для предотвращения переполнения памяти), то производители тоже должны уметь блокироваться.

```dotty
import cats.effect.std.Queue

for
  queue <- Queue.bounded[IO, String](10)  // максимум 10 элементов
  // ... производители и потребители
yield ()
```

**Важное отличие:** Если очередь заполнена, вызов `queue.offer` блокирует **волокно** производителя до тех пор, 
пока потребитель не заберёт элемент и не освободит место.

## Координация волокон с помощью `Deferred` и `Ref`

В простом случае `Queue` уже обеспечивает безопасную координацию. Но в более сложных сценариях могут потребоваться другие примитивы:

- [Ref](typeclasses/concurrent/ref.md) — атомарная ссылка для общего состояния.
- [Deferred](typeclasses/concurrent/deferred.md) — ожидание однократного сигнала.
- [Semaphore](std/semaphore.md) — счётный семафор для контроля параллелизма.
- [Mutex](std/mutex.md) — взаимное исключение для волокон.
- [Backpressure](std/backpressure.md) — управление потоком данных при перегрузках.
- [CountDownLatch](std/countdown-latch.md) — ожидание заданного количества событий.
- [CyclicBarrier](std/cyclic-barrier.md) — многократный барьер синхронизации.

> Cats Effect позволяет моделировать сложные конкурентные сценарии (вроде «производитель-потребитель») 
> на высоком уровне абстракции, не заботясь о низкоуровневом управлении потоками и блокировками. 
> Волокна дают конкурентность без расхода ресурсов, 
> а синхронизация через `Queue`, `Ref`, `Deferred` остаётся чистой и композируемой.

## Первая (и неэффективная) реализация

Нам нужна промежуточная структура, в которую производитель(и) могут вставлять данные, а потребитель(и) — извлекать данные. 
Предположим, у нас простая очередь. Изначально будет только один производитель и один потребитель. 
Производитель будет генерировать последовательность целых чисел (`1`, `2`, `3`...), потребитель будет просто считывать эту последовательность. 
Наша общая очередь будет экземпляром неизменяемого объекта `Queue[Int]`. 
Это хороший выбор, потому что неизменяемые структуры данных безопасны для совместного использования — 
проблема только в атомарности обновления ссылки на текущую очередь.

Доступ к очереди может (и будет!) быть одновременным, поэтому нам нужен способ защитить очередь, 
чтобы только один поток обрабатывал её одновременно. 
Хороший способ обеспечить упорядоченный доступ к некоторым общим данным — это [`Ref`](typeclasses/concurrent/ref.md). 
Экземпляр `Ref` обёртывает некоторые заданные данные и реализует методы для манипулирования этими данными безопасным способом.

Объект `Ref`, обёртывающий нашу очередь, будет иметь вид `Ref[F, Queue[Int]]` (для некоторого `F[_]`).

### Реализация производителя (`producer`)

Производитель будет генерировать последовательность целых чисел и добавлять их в очередь. 
Каждые 10000 элементов он будет выводить сообщение в лог, чтобы мы знали, что он всё ещё жив.

```dotty
import cats.effect.*
import cats.effect.std.Console
import cats.syntax.all.*
import scala.collection.immutable.Queue

def producer[F[_]: {Sync, Console}](
    queueR: Ref[F, Queue[Int]],
    counter: Int
): F[Unit] =
  for
    // Логирование каждые 10000 элементов
    _ <- Sync[F].whenA(counter % 10000 == 0)(
      Console[F].println(s"Произведено $counter элементов")
    )
    // Атомарное обновление очереди: добавляем следующий элемент
    _ <- queueR.getAndUpdate(_.enqueue(counter + 1))
    // Рекурсивный вызов для следующего элемента
    _ <- producer(queueR, counter + 1)
  yield ()
```

**Разбор кода:**

1. **`whenA`** — это условное выполнение эффекта. Если условие истинно, эффект выполняется; если ложно — возвращается `unit`. 
   Это идиоматичная альтернатива `if (...) then ... else Sync[F].unit`.
2. **`Console[F]`** — класс типов, предоставляющий [методы для работы с консолью](std/console.md) (`println`, `readLine` и т.д.). 
  `IO.println` внутри просто вызывает `Console[IO].println`.
3. **`getAndUpdate`** — атомарная операция `Ref`, которая читает текущее значение, применяет к нему функцию, 
   и записывает результат обратно. Здесь мы берём текущую очередь (`queue`), 
   добавляем в конец новое значение (`counter + 1`) и сохраняем обновлённую очередь. 
   Если другой поток одновременно обратится к `queueR`, он будет **заблокирован** (семантически) до завершения этой операции. 
   Обратите внимание: блокируется **волокно**, а не поток ОС.

### Реализация потребителя (`consumer`)

Потребитель должен извлекать элементы из очереди. Но очередь может быть пустой! 
Ему нужно корректно обрабатывать эту ситуацию, возвращая `None`, 
и продолжать попытки позже (в отличие от блокировки, как в настоящей конкурентной очереди).

```dotty
def consumer[F[_]: {Sync, Console}](
    queueR: Ref[F, Queue[Int]]
): F[Unit] =
  for
    maybeI <- queueR.modify { queue =>
      queue.dequeueOption match
        case Some((i, newQueue)) => (newQueue, Some(i))
        case None                => (queue, None)
    }
    _ <- Sync[F].whenA(maybeI.exists(_ % 10000 == 0))(
      Console[F].println(s"Потреблено ${maybeI.get} элементов")
    )
    _ <- consumer(queueR)
  yield ()
```

**Разбор кода:**

1. **`modify`** — атомарная операция `Ref`, которая позволяет одновременно прочитать текущее значение, 
   вычислить новое состояние и вернуть произвольный результат. Это один шаг — без гонок между чтением и записью.
2. **`dequeueOption`** — метод неизменяемой очереди, который возвращает `Option[(Int, Queue[Int])]`. 
   Если очередь не пуста, возвращает `Some((голова, хвост))`, иначе `None`.
3. В случае успеха: новое состояние — это `newQueue` (хвост), а возвращаемое значение — `Some(i)` (голова). 
   Если очередь пуста: состояние не меняется, возвращаемое значение — `None`.
4. Затем мы выводим сообщение каждые 10000 потребленных элементов. Обратите внимание на проверку: `maybeI.exists(_ % 10000 == 0)`.
5. И, наконец, рекурсивно вызываем `consumer` снова, чтобы обработать следующий элемент.

Кажется, всё логично. Производитель добавляет элементы, потребитель их забирает. Давайте посмотрим, как это всё соединить.

### Запуск: производитель и потребитель параллельно

Мы хотим запустить производителя и потребителя одновременно и позволить им работать, 
пока пользователь не прервёт программу (например, Ctrl+C). 
У нас есть два основных способа сделать это: **высокоуровневый** (`parMapN`) и **низкоуровневый** (ручное управление волокнами). 
Cats Effect рекомендует высокоуровневый подход.

#### Решение 1: Использование `parMapN` (рекомендуется)

```dotty
import cats.effect.*
import cats.effect.std.Console
import cats.syntax.all.*
import scala.collection.immutable.Queue

object InefficientProducerConsumer extends IOApp:
  override def run(args: List[String]): IO[ExitCode] =
    for
      queueR <- Ref.of[IO, Queue[Int]](Queue.empty[Int])
      result <- (consumer(queueR), producer(queueR, 0))
        .parMapN((_, _) => ExitCode.Success)
        .handleErrorWith { t =>
          Console[IO].errorln(s"Ошибка: ${t.getMessage}").as(ExitCode.Error)
        }
    yield result

  private def producer[F[_]: {Sync, Console}](
      queueR: Ref[F, Queue[Int]],
      counter: Int
  ): F[Unit] = ??? // как выше

  private def consumer[F[_]: {Sync, Console}](
      queueR: Ref[F, Queue[Int]]
  ): F[Unit] = ??? // как выше
```

**Что делает `parMapN`:**

- Запускает оба эффекта (`consumer` и `producer`) в отдельных волокнах.
- Если оба успешно завершатся (что в нашей программе никогда не произойдёт — они бесконечны), применит функцию и передаст результат дальше.
- Если **любой** из эффектов завершится с ошибкой, ошибка будет передана в `handleErrorWith`, 
  а второй эффект (ещё работающий) будет **автоматически отменён**.
- Если пользователь нажмёт Ctrl+C, `IOApp` отправит сигнал отмены, который корректно остановит оба волокна.

#### Решение 2: Ручное управление волокнами (не рекомендуется, но полезно для понимания)

В качестве альтернативы мы могли бы использовать `start` для явного создания волокон:

```dotty
override def run(args: List[String]): IO[ExitCode] =
  for
    queueR <- Ref.of[IO, Queue[Int]](Queue.empty[Int])
    producerFiber <- producer(queueR, 0).start
    consumerFiber <- consumer(queueR).start
    _ <- producerFiber.join
    _ <- consumerFiber.join
  yield ExitCode.Success
```

**Почему это плохо на практике:**

1. **Ошибки игнорируются.** `join` возвращает `Outcome[F, E, A]`, а не просто `A`. 
   Если волокно завершилось с ошибкой, `join` **не выбросит** исключение. Нужно вручную анализировать `Outcome`.
2. **Ошибка в одном волокне не отменяет другое.** Если `consumer` упадёт с ошибкой, 
   `producer` продолжит работать бесконечно, потребляя ресурсы.
3. **Блокирующий `join`.** Вызов `producerFiber.join` заблокирует текущее волокно до завершения `producer`. 
   Но `producer` никогда не завершается (бесконечный цикл). В результате `consumerFiber.join` никогда не будет достигнут, 
   и программа не сможет корректно завершиться или обработать ошибку.
4. **Наблюдение за ошибками откладывается.** Если `consumerFiber` завершится с ошибкой, мы её не увидим, 
   пока не завершится `producerFiber`. А он никогда не завершится.

**Итог:** Ручное управление волокнами коварно и чревато ошибками. 
Cats Effect предоставляет высокоуровневые комбинаторы (`parMapN`, `parSequence`, `race`), 
которые правильно обрабатывают отмену и распространение ошибок. Используйте их всегда, когда это возможно.

## Почему эта реализация неэффективна?

Кажется, что код работает. Производитель генерирует числа, потребитель их читает. 
Но это **крайне неэффективное решение** для реальной задачи. Давайте разберёмся, почему.

### Проблема 1: Постоянные блокировки на `Ref`

Каждая операция производителя (`getAndUpdate`) и потребителя (`modify`) требует эксклюзивного доступа к `Ref`. 
Это означает, что **в любой момент времени только одно волокно** (производитель ИЛИ потребитель) может работать с очередью.

- Пока производитель добавляет элемент, потребитель вынужден ждать.
- Пока потребитель извлекает элемент, производитель вынужден ждать.

По сути, производитель и потребитель работают **не параллельно**, а **последовательно**! 
Это сводит на нет весь смысл многопоточности.

### Проблема 2: Активное ожидание (busy-waiting) при пустой очереди

Что происходит, когда очередь пуста?

```dotty
// consumer
val maybeI <- queueR.modify { queue =>
  queue.dequeueOption match
    case Some((i, newQueue)) => (newQueue, Some(i))
    case None                => (queue, None)   // ← Очередь пуста, но мы не блокируемся!
}
```

Если очередь пуста, `modify` всё равно выполняется, возвращая `None`. 
Затем `consumer` **немедленно** рекурсивно вызывает сам себя, и цикл повторяется. 
Происходит **бесконечный цикл с максимальной скоростью**, который:

- Потребляет 100% одного ядра CPU.
- Постоянно блокирует `Ref`, мешая производителю добавить хотя бы один элемент.
- На самом деле производитель, скорее всего, **никогда не получит доступа** к `Ref`, так как потребитель постоянно держит блокировку.

Это классический **busy-waiting** — активное ожидание, которое является антипаттерном в асинхронном программировании. 
Настоящая очередь должна блокировать потребителя **до появления данных**, не потребляя процессор.

### Проблема 3: Отсутствие границ (boundedness)

Наша очередь не имеет ограничения на размер. Если производитель будет работать быстрее потребителя, 
очередь будет расти бесконечно, что в конце концов приведёт к `OutOfMemoryError`.

### Проблема 4: Нет безопасной остановки

В текущей реализации нет способа "мягко" остановить производителя и потребителя. Они работают вечно. 
Полагаться только на Ctrl+C — не всегда приемлемо. 
В реальной системе нужен механизм сигнализации о завершении (например, через `Deferred`).

### Что дальше?

Мы получили первую, работающую, но крайне неэффективную реализацию. Это было необходимо, чтобы понять:

- Правильную структуру (производитель, потребитель, общая очередь).
- Механизмы синхронизации (`Ref`).
- Способы запуска параллельных волокон (`parMapN` vs ручные `start`/`join`).

Но этот код **не должен использоваться в реальных проектах**!

## Более надежная реализация проблемы производителя/потребителя

В предыдущей неэффективной реализации мы столкнулись с двумя фундаментальными проблемами:

1. **Активное ожидание (busy-waiting):** Потребитель постоянно опрашивал очередь в цикле, даже когда она была пуста, 
   напрасно потребляя CPU и создавая конкуренцию за `Ref`.
2. **Последовательная работа:** Из-за постоянной блокировки `Ref` производитель и потребитель практически не работали параллельно.

Настоящая конкурентная очередь должна **блокировать потребителя семантически**, когда очередь пуста, 
и **блокировать производителя**, когда очередь ограничена и переполнена. 
При этом блокировка не должна затрагивать системные потоки — это одна из супервозможностей волокон Cats Effect.

Чтобы реализовать такую блокировку, нам понадобится ещё один примитив — [Deferred](typeclasses/concurrent/deferred.md).

### Новая модель состояния

В нашей первой реализации состояние содержало только очередь произведённых, но ещё не потреблённых элементов. 
Теперь нам нужно также отслеживать **ожидающих потребителей** (`takers`) — волокна, которые пришли за элементом, 
но обнаружили, что очередь пуста, и теперь ждут на `Deferred`.

```dotty
import cats.effect.Deferred
import scala.collection.immutable.Queue

case class State[F[_], A](
  queue: Queue[A],              // элементы, ожидающие обработки
  takers: Queue[Deferred[F, A]] // потребители, ожидающие элементы
)
```

**Логика работы:**

- **Потребитель (`take`)**:
   1. Если в очереди `queue` есть элементы → извлекаем первый, возвращаем его.
   2. Если очередь пуста → создаём новый `Deferred`, добавляем его в очередь `takers`, и вызываем `taker.get` (блокируемся).
- **Производитель (`offer`)**:
   1. Если есть ждущие потребители в `takers` → берём первого из очереди и «пробуждаем» его через `taker.complete(i)`, передавая новый элемент.
   2. Если ждущих потребителей нет → добавляем новый элемент в очередь `queue`.

Такая схема гарантирует, что:

- Потребитель не тратит CPU впустую — он блокируется и ждёт.
- Производитель может напрямую передать элемент ожидающему потребителю, минуя очередь.
- Доступ к состоянию всегда атомарен через `Ref.modify`.

### Реализация потребителя (`consumer`)

Потребитель теперь работает через вспомогательную функцию `take`, 
которая инкапсулирует логику извлечения элемента из общего состояния.

```dotty
def consumer[F[_]: {Async, Console}](
    id: Int,
    stateR: Ref[F, State[F, Int]]
): F[Unit] =
  // Функция, которая атомарно извлекает элемент из состояния
  def take: F[Int] =
    Deferred[F, Int].flatMap: taker =>
      stateR.modify {
        // Случай 1: В очереди есть элементы
        case State(queue, takers) if queue.nonEmpty =>
          val (i, rest) = queue.dequeue
          State(rest, takers) -> Async[F].pure(i)

        // Случай 2: Очередь пуста — регистрируем ожидающего потребителя
        case State(queue, takers) =>
          State(queue, takers.enqueue(taker)) -> taker.get
      }.flatten

  for
    i <- take
    _ <- Async[F].whenA(i % 10000 == 0)(
      Console[F].println(s"Потребитель $id обработал $i элементов")
    )
    _ <- consumer(id, stateR) // рекурсивно продолжаем потреблять
  yield ()
end consumer
```

#### Детальный разбор `take`

1. **Создание `Deferred`:** `Deferred[F, Int].flatMap { taker => ... }` — каждый вызов `take` создаёт свой собственный `Deferred`, 
   который будет использован, если очередь пуста.
2. **`stateR.modify`** — атомарное чтение и обновление состояния.
3. **Первый case (`queue.nonEmpty`):** Если есть элементы — извлекаем голову (`i`) и хвост (`rest`). 
   Новое состояние: `State(rest, takers)`. Возвращаем `Async[F].pure(i)` — элемент уже есть, не нужно блокироваться.
4. **Второй case (`queue.isEmpty`):** Если очередь пуста, добавляем созданный `taker` в очередь `takers`. 
   Новое состояние: `State(queue, takers.enqueue(taker))`. Возвращаем `taker.get` — это и есть блокировка. 
   Волокно приостановится до тех пор, пока какой-нибудь производитель не выполнит `taker.complete(i)`.
5. **`.flatten`** — так как `modify` возвращает `F[F[Int]]` (внешний слой — сам эффект изменения состояния, 
   внутренний — результат из выбранной ветки), `flatten` объединяет их в один `F[Int]`.

### Реализация производителя (`producer`)

Производитель также получает вспомогательную функцию `offer`, которая атомарно решает, 
куда направить новый элемент: ожидающему потребителю или в очередь.

```dotty
def producer[F[_]: {Async, Console}](
    id: Int,
    counterR: Ref[F, Int],
    stateR: Ref[F, State[F, Int]]
): F[Unit] =

  // Функция, которая атомарно добавляет элемент в состояние
  def offer(i: Int): F[Unit] =
    stateR.modify {
      // Случай 1: Есть ожидающие потребители
      case State(queue, takers) if takers.nonEmpty =>
        val (taker, rest) = takers.dequeue
        State(queue, rest) -> taker.complete(i).void

      // Случай 2: Нет ожидающих потребителей
      case State(queue, takers) =>
        State(queue.enqueue(i), takers) -> Async[F].unit
    }.flatten

  for
    // получаем текущий счётчик и увеличиваем
    i <- counterR.getAndUpdate(_ + 1)
    _ <- offer(i)
    _ <- Async[F].whenA(i % 100000 == 0)(
      Console[F].println(s"Производитель $id произвёл $i элементов")
    )
    // небольшая задержка для балансировки
    _ <- Async[F].sleep(1.microsecond)
    // рекурсивно продолжаем производить
    _ <- producer(id, counterR, stateR)
  yield ()
```

#### Детальный разбор `offer`

1. **`stateR.modify`** — атомарно читаем и обновляем состояние.
2. **Первый case (`takers.nonEmpty`):** Если есть ждущие потребители, берём первого из очереди (`taker`), 
   удаляем его из очереди (`rest`). 
   Возвращаем `taker.complete(i).void` — это действие пробуждает потребителя, передавая ему элемент `i`. 
   Обратите внимание: сам элемент **не попадает в очередь** `queue`! 
   Происходит прямая передача от производителя к потребителю.
3. **Второй case (`takers.isEmpty`):** Если ждущих потребителей нет, добавляем элемент в конец очереди `queue`. 
   Возвращаем `unit` — никаких дополнительных действий не требуется.
4. **`.flatten`** — аналогично потребителю, объединяет слои эффектов.

#### Искусственная задержка

Обратите внимание на строку:

```dotty
_ <- Async[F].sleep(1.microsecond)
```

Это **не** часть решения, а искусственная задержка, чтобы в демонстрационных целях производитель не перегружал потребителей. 
В реальном приложении она не нужна — если потребители успевают, то и задержка не требуется; 
если не успевают, очередь будет заполняться, и производители должны блокироваться (это мы рассмотрим позже, с ограниченной очередью).

### Запуск: несколько производителей и потребителей

Теперь мы можем легко запустить несколько производителей и несколько потребителей параллельно. 
Каждый из них будет работать в своём волокне, и все они будут совместно использовать одно и то же состояние `stateR`.

```dotty
import cats.effect.*
import cats.effect.std.Console
import cats.instances.list.*
import cats.syntax.all.*

import scala.collection.immutable.Queue

object ProducerConsumer extends IOApp:

  // Состояние (как определено выше)
    case class State[F[_], A](
      queue: Queue[A],              // элементы, ожидающие обработки
      takers: Queue[Deferred[F, A]] // потребители, ожидающие элементы
  )
  object State:
    def empty[F[_], A]: State[F, A] = State(Queue.empty, Queue.empty)

  override def run(args: List[String]): IO[ExitCode] =
    for
      stateR   <- Ref.of[IO, State[IO, Int]](State.empty[IO, Int])
      counterR <- Ref.of[IO, Int](1) // общий счётчик для всех производителей

      // 10 производителей и 10 потребителей
      producers = List.range(1, 11).map(producer(_, counterR, stateR))
      consumers = List.range(1, 11).map(consumer(_, stateR))

      res <- (producers ++ consumers)
        .parSequence
        .as(ExitCode.Success)
        .handleErrorWith { t =>
          Console[IO].errorln(s"Ошибка: ${t.getMessage}").as(ExitCode.Error)
        }
    yield res
    
  // consumer и producer определены выше  
```

**Что здесь происходит:**

1. `List.range(1, 11).map(producer(_, counterR, stateR))` создаёт **список описаний** 10 производителей. 
   Сами производители ещё не запущены — это просто `IO[Unit]`.
2. Аналогично для потребителей.
3. `(producers ++ consumers).parSequence` — `parSequence` запускает **все** элементы списка (все 20 волокон) параллельно. 
   Он вернёт управление только тогда, когда **все** они завершатся. 
   Но наши производители и потребители работают бесконечно (рекурсивные вызовы). 
   Значит, программа будет работать, пока пользователь не прервёт её (Ctrl+C).
4. `as(ExitCode.Success)` — когда `parSequence` завершится (что не произойдёт при обычной работе), вернуть `ExitCode.Success`.
5. `handleErrorWith` — если в любом из 20 волокон произойдёт ошибка, она будет перехвачена здесь, 
   а **все остальные волокна будут автоматически отменены**.

### Анализ решения: почему оно эффективно?

| Характеристика                    | Первая реализация (неэффективная)                           | Вторая реализация (с `Deferred`)                                         |
|:----------------------------------|:------------------------------------------------------------|:-------------------------------------------------------------------------|
| **Поведение при пустой очереди**  | Активное ожидание (busy-waiting), 100% CPU                  | Семантическая блокировка, 0% CPU                                         |
| **Конкуренция за `Ref`**          | Высокая (каждая операция требует блокировки)                | Низкая (`modify` выполняется только при реальном изменении состояния)    |
| **Прямая передача**               | Нет (всегда через очередь)                                  | Да (производитель → потребителю, минуя очередь)                          |
| **Масштабируемость**              | Плохая (производитель и потребитель почти последовательны)  | Отличная (несколько производителей и потребителей работают параллельно)  |
| **Использование CPU**             | Высокое (постоянные циклы и блокировки)                     | Низкое (волокна спят, когда нечего делать)                               |

## Производитель-потребитель с ограниченной очередью

В реализации с неограниченной очередью у нас проблема: 
если производители будут стабильно работать быстрее потребителей, 
очередь `queue` будет бесконечно расти, что в конечном итоге приведёт к `OutOfMemoryError`. 
Это неприемлемо для любой серьёзной системы, работающей 24/7.

**Решение:** Введём **ограничение на размер очереди** (`capacity`). Теперь:

- Если очередь **не заполнена**, производитель может добавить элемент.
- Если очередь **заполнена**, производитель должен **заблокироваться** (семантически) и ждать, пока потребитель не освободит место.

Для этого нам понадобится отслеживать не только ожидающих потребителей (`takers`), но и ожидающих производителей (`offerers`). 
Добавим их в наше состояние.

### Расширенная модель состояния

```dotty
case class State[F[_], A](
    queue: Queue[A],                        // элементы, ожидающие обработки
    capacity: Int,                          // максимальный размер очереди
    takers: Queue[Deferred[F, A]],          // потребители, ожидающие элемент
    offerers: Queue[(A, Deferred[F, Unit])] // производители, ожидающие места
)
```

**Что хранится в `offerers`:**

- Каждый элемент очереди `offerers` — это пара `(элемент, deferred)`.
- `deferred` имеет тип `Deferred[F, Unit]` — это канал, на котором будет заблокирован производитель.
- Когда появится свободное место, мы извлечём этого производителя, 
  поместим его элемент в очередь (или напрямую передадим потребителю) и завершим `deferred`, разблокировав производителя.

**Симметрия:** Обратите внимание на симметрию между `takers` и `offerers`:

- `takers` (ожидающие потребители): ждут `Deferred[F, A]` — им нужен элемент типа `A`.
- `offerers` (ожидающие производители): ждут `Deferred[F, Unit]` — им нужен только сигнал «место освободилось», сам элемент у них уже есть.

### Реализация потребителя (`consumer`) с учётом ограниченной очереди

Теперь у потребителя **четыре возможных сценария** при извлечении элемента из состояния, 
в зависимости от комбинации «пуста ли очередь» и «есть ли ожидающие производители».

#### Разбор всех четырёх сценариев

| Сценарий  | `queue`   | `offerers`  | Действие                                                                                                                                                                 |
|:----------|:----------|:------------|:-------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **1**     | Не пуста  | Пуста       | Просто извлечь элемент из `queue` и вернуть его.                                                                                                                         |
| **2**     | Не пуста  | Не пуста    | Извлечь элемент из `queue` (для потребителя) **И** разбудить первого ожидающего производителя, добавив его элемент в конец `queue`.                                      |
| **3**     | Пуста     | Не пуста    | Нет элементов в `queue`, но есть производители, которые уже ждут. Взять первого производителя, вернуть его элемент потребителю (минуя очередь), разбудить производителя. |
| **4**     | Пуста     | Пуста       | Нет элементов и нет ждущих производителей. Создать нового `taker`, добавить в очередь ожидания и заблокировать потребителя.                                              |

```dotty
def consumer[F[_]: {Async, Console}](
    id: Int,
    stateR: Ref[F, State[F, Int]]
): F[Unit] =
  val take: F[Int] =
    Deferred[F, Int].flatMap { taker =>
      stateR.modify {
        // Сценарий 1: Очередь не пуста, нет ожидающих производителей
        case State(queue, capacity, takers, offerers)
            if queue.nonEmpty && offerers.isEmpty =>
          val (i, rest) = queue.dequeue
          State(rest, capacity, takers, offerers) -> Async[F].pure(i)

        // Сценарий 2: Очередь не пуста, есть ожидающие производители
        case State(queue, capacity, takers, offerers)
            if queue.nonEmpty =>
          val (i, rest)               = queue.dequeue
          val ((move, release), tail) = offerers.dequeue
          // Добавляем элемент от пробуждённого производителя в очередь
          State(rest.enqueue(move), capacity, takers, tail) ->
            release.complete(()).as(i)

        // Сценарий 3: Очередь пуста, но есть ожидающие производители
        case State(queue, capacity, takers, offerers)
            if offerers.nonEmpty =>
          val ((i, release), rest) = offerers.dequeue
          State(queue, capacity, takers, rest) ->
            release.complete(()).as(i)

        // Сценарий 4: Очередь пуста и нет ожидающих производителей
        case State(queue, capacity, takers, offerers) =>
          State(queue, capacity, takers.enqueue(taker), offerers) -> taker.get
      }.flatten
    }

  for
    i <- take
    _ <- Async[F].whenA(i % 100000 == 0)(
      Console[F].println(s"Потребитель $id обработал $i элементов")
    )
    _ <- consumer(id, stateR)
  yield ()
end consumer
```

#### Детальный разбор сложных сценариев

**Сценарий 2 (`queue.nonEmpty && offerers.nonEmpty`):**

```dotty
val (i, rest) = queue.dequeue           // i — для текущего потребителя
val ((move, release), tail) = offerers.dequeue  // move — элемент от ждущего производителя
State(rest.enqueue(move), capacity, takers, tail) -> release.complete(()).as(i)
```

- Потребитель получает элемент `i` из головы очереди.
- Мы пробуждаем первого ожидающего производителя (`release.complete(())`).
- Элемент `move` этого производителя **помещается в конец очереди**, а не передаётся напрямую потребителю. 
  Почему? Потому что у нас уже есть элемент для текущего потребителя; 
  перемещение должно сохранить порядок (FIFO) для элементов, которые проходят через очередь.
- Обратите внимание на `.as(i)` — после того как `release.complete(())` выполнится, мы возвращаем `i` потребителю.

**Сценарий 3 (offerers.nonEmpty):**

```dotty
val ((i, release), rest) = offerers.dequeue
State(queue, capacity, takers, rest) -> release.complete(()).as(i)
```

- Очередь пуста, но есть производители, которые уже ждут.
- Мы берём первого из них, возвращаем его элемент `i` **непосредственно** потребителю (минуя очередь).
- Одновременно пробуждаем производителя (`release.complete(())`).
- Это оптимально — нет смысла класть элемент в очередь, чтобы сразу его извлечь.

### Реализация производителя (`producer`) с учётом ограниченной очереди

У производителя теперь **три сценария**:

| Сценарий  | Условие                                                                            | Действие                                                                                    |
|:----------|:-----------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------|
| **1**     | Есть ожидающие потребители (`takers.nonEmpty`)                                     | Передать элемент напрямую первому потребителю, минуя очередь.                               |
| **2**     | Нет ожидающих потребителей, но очередь **не заполнена** (`queue.size < capacity`)  | Добавить элемент в конец очереди.                                                           |
| **3**     | Нет ожидающих потребителей, и очередь **заполнена**                                | Создать `offerer` (с `Deferred[F, Unit]`) и заблокироваться до появления свободного места.  |

```dotty
def producer[F[_]: {Async, Console}](
    id: Int,
    counterR: Ref[F, Int],
    stateR: Ref[F, State[F, Int]]
): F[Unit] =
  def offer(i: Int): F[Unit] =
    Deferred[F, Unit].flatMap { offerer =>
      stateR.modify {
        // Сценарий 1: Есть ожидающие потребители
        case State(queue, capacity, takers, offerers)
            if takers.nonEmpty =>
          val (taker, rest) = takers.dequeue
          State(queue, capacity, rest, offerers) ->
            taker.complete(i).void

        // Сценарий 2: Нет ждущих потребителей, очередь не заполнена
        case State(queue, capacity, takers, offerers)
            if queue.size < capacity =>
          State(queue.enqueue(i), capacity, takers, offerers) ->
            Async[F].unit

        // Сценарий 3: Нет ждущих потребителей, очередь заполнена
        case State(queue, capacity, takers, offerers) =>
          State(queue, capacity, takers, offerers.enqueue((i, offerer))) ->
            offerer.get
      }.flatten
    }

  for
    i <- counterR.getAndUpdate(_ + 1)
    _ <- offer(i)
    _ <- Async[F].whenA(i % 100000 == 0)(
      Console[F].println(s"Производитель $id произвёл $i элементов")
    )
    _ <- producer(id, counterR, stateR)
  yield ()
end producer
```

**Важные изменения по сравнению с неограниченной версией:**

1. **Мы удалили вызов `Async[F].sleep(1.microsecond)`.** Искусственная задержка больше не нужна, 
   потому что теперь, когда очередь заполнена, производители будут **блокироваться автоматически**, ожидая освобождения места. 
   Это естественный механизм обратного давления (backpressure).
2. В сценарии 3 производитель создаёт `offerer` — пару из своего элемента и `Deferred[F, Unit]`, 
   на котором он блокируется через `offerer.get`. Потребитель разбудит его, когда освободится место.

### Запуск программы с ограниченной очередью

Финальная программа практически не отличается от предыдущей, за исключением указания `capacity` при создании состояния.

```dotty
object ProducerConsumerBounded extends IOApp:
  case class State[F[_], A](
      queue: Queue[A],
      capacity: Int,
      takers: Queue[Deferred[F, A]],
      offerers: Queue[(A, Deferred[F, Unit])]
  )

  object State:
    def empty[F[_], A](capacity: Int): State[F, A] =
      State(Queue.empty, capacity, Queue.empty, Queue.empty)

  override def run(args: List[String]): IO[ExitCode] =
    for
      // Создаём состояние с максимальным размером очереди 100
      stateR <- Ref.of[IO, State[IO, Int]](State.empty[IO, Int](capacity = 100))
      counterR <- Ref.of[IO, Int](1)

      producers = List.range(1, 11).map(producer(_, counterR, stateR))
      consumers = List.range(1, 11).map(consumer(_, stateR))

      res <- (producers ++ consumers)
        .parSequence
        .as(ExitCode.Success)
        .handleErrorWith { t =>
          Console[IO].errorln(s"Ошибка: ${t.getMessage}").as(ExitCode.Error)
        }
    yield res
    
  // producer и consumer определены выше (с учетом capacity)
```

**Что произойдёт при выполнении:**

1. Все 10 производителей и 10 потребителей стартуют параллельно.
2. Поначалу, пока очередь пуста, производители будут быстро её заполнять до предела (100 элементов).
3. Как только очередь заполнена, производители, пытающиеся добавить 101-й элемент, **блокируются** (семантически) и встают в очередь `offerers`.
4. Потребители забирают элементы из очереди. Как только очередь становится не полностью заполненной, 
   первый ждущий производитель пробуждается и добавляет свой элемент (или передаёт его напрямую, если есть ждущий потребитель).
5. Система приходит к равновесию: производители и потребители работают с общей скоростью, 
   определяемой пропускной способностью потребителей. 
   Очередь остаётся заполненной примерно на 100 элементов, но не переполняется.

### Анализ текущего решения

| Характеристика                        | Неограниченная очередь                                 | Ограниченная очередь (финальное решение)                 |
|:--------------------------------------|:-------------------------------------------------------|:---------------------------------------------------------|
| **Контроль памяти**                   | Отсутствует (риск OOM)                                 | Полный (размер очереди фиксирован)                       |
| **Обратное давление (backpressure)**  | Нет (производители работают на максимальной скорости)  | Есть (производители блокируются при заполнении очереди)  |
| **Сложность кода**                    | Умеренная                                              | Выше (но вся сложность инкапсулирована в `modify`)       |
| **Блокировка производителей**         | Нет (только потребители)                               | Да (симметрично с потребителями)                         |
| **Прямая передача**                   | Только producer → consumer (минуя очередь)             | Также возможна, но с учётом ограничения размера          |
| **Использование CPU**                 | Эффективное (блокировки через `Deferred`)              | Эффективное (ещё и производители не тратят CPU впустую)  |

## Обработка отмены

Зададимся вопросом: **является ли наша реализация безопасной с точки зрения отмены?** 
То есть, что происходит, если волокно, в котором работает потребитель или производитель, 
отменяется (например, по таймауту, из-за ошибки в другом волокне или принудительно через `fiber.cancel`)? 
Не станет ли состояние противоречивым?

Это критически важный вопрос. В Cats Effect отмена — это **согласованный механизм**: 
волокно не может быть остановлено в произвольной точке выполнения. 
Отмена происходит только в **точках отмены** — обычно между шагами `flatMap` (внутри for-comprehension). 
Наша задача — убедиться, что при отмене:

1. Ресурсы не утекают.
2. Общее состояние (`stateR`) остаётся консистентным.
3. Блокирующие операции могут быть прерваны.

### Анализ производителя (`producer`)

Давайте сосредоточимся на внутренней функции `offer`. Перепишем её в виде for-comprehension для ясности:

```dotty
def offer[F[_]: Async](i: Int): F[Unit] =
  for
    offerer <- Deferred[F, Unit]    // Шаг 1: создаём Deferred
    op      <- stateR.modify{ ... } // Шаг 2: атомарно обновляем состояние, получаем эффект `op`
    _       <- op                   // Шаг 3: выполняем `op`
  yield ()
```

**Что может пойти не так при отмене?**

- **Отмена до шага 1 или после шага 1, но до шага 2:** Созданный `offerer` не имеет сильных ссылок (кроме локальной переменной). 
  Он будет просто удалён сборщиком мусора. Состояние не изменялось — всё в порядке.
- **Отмена после шага 2, но до шага 3:** Это самая опасная ситуация! Мы уже изменили состояние 
  (либо добавили `offerer` в очередь `offerers`, либо удалили `taker`), но эффект `op` ещё не выполнен. 
  Состояние стало **неконсистентным**:
    - Если `op` должно было быть `offerer.get` (блокировка), то `offerer` есть в `State`, 
      но производитель не будет на нём заблокирован (потому что мы ещё не дошли до `.get`).
    - Если `op` должно было быть `taker.complete(i).void`, то `taker` уже удалён из очереди, но потребитель не получит элемент.
- **Отмена во время выполнения `op`:** Если `op` — это `offerer.get` (блокирующий вызов), 
  то отмена может произойти, пока волокно ждёт на `Deferred`. 
  Это нормально, но нужно корректно удалить `offerer` из состояния.

### Решение: `F.uncancelable` и `Poll[F]`

Cats Effect [предоставляет механизм `uncancelable`](typeclasses/monadcancel.md) для защиты критических секций от отмены, 
но с возможностью «пробросить» отмену в определённые места.

```dotty
F.uncancelable { poll =>
  // Код внутри этого блока НЕ может быть отменён, за исключением мест,
  // где явно используется `poll(...)`
}
```

**Принцип работы:**

- Весь блок `uncancelable` защищён от отмены.
- Внутри блока можно использовать `poll(someEffect)`, чтобы сделать `someEffect` **отменяемым** — отмена может произойти внутри этого под-эффекта.
- Это позволяет, например, защитить модификацию состояния, но сделать блокировку на `Deferred.get` отменяемой.

### Исправленный производитель с поддержкой отмены

```dotty
import cats.effect.*
import cats.effect.std.Console
import cats.syntax.all.*
import cats.effect.syntax.all.*  // для .onCancel
import scala.collection.immutable.Queue

def producer[F[_]: {Async, Console}](
    id: Int,
    counterR: Ref[F, Int],
    stateR: Ref[F, State[F, Int]]
): F[Unit] =
  def offer(i: Int): F[Unit] =
    Deferred[F, Unit].flatMap { offerer =>
      // Защищаем критическую секцию от отмены
      Async[F].uncancelable { poll =>
        stateR.modify {
          // Сценарий 1: Есть ожидающие потребители
          case State(queue, capacity, takers, offerers) if takers.nonEmpty =>
            val (taker, rest) = takers.dequeue
            State(queue, capacity, rest, offerers) -> taker.complete(i).void

          // Сценарий 2: Нет ждущих потребителей, очередь не заполнена
          case State(queue, capacity, takers, offerers)
              if queue.size < capacity =>
            State(queue.enqueue(i), capacity, takers, offerers) ->
              Async[F].unit

          // Сценарий 3: Нет ждущих потребителей, очередь заполнена
          case State(queue, capacity, takers, offerers) =>
            // Функция очистки: удаляем offerer из очереди, если отмена произойдёт
            val cleanup = stateR.update { s =>
              s.copy(offerers = s.offerers.filter(_._2 ne offerer))
            }
            // Возвращаем блокирующий эффект, обёрнутый в poll (отменяемый)
            State(queue, capacity, takers, offerers.enqueue(i -> offerer)) ->
              poll(offerer.get).onCancel(cleanup)
        }.flatten
      }
    }

  for
    i <- counterR.getAndUpdate(_ + 1)
    _ <- offer(i)
    _ <- Async[F].whenA(i % 100000 == 0)(
      Console[F].println(s"Производитель $id произвёл $i элементов")
    )
    _ <- producer(id, counterR, stateR)
  yield ()
end producer
```

**Что изменилось?**

1. **`Async[F].uncancelable { poll => ... }`** — вся критическая секция (чтение и модификация состояния) защищена от отмены. 
   Отмена не может произойти между `modify` и выполнением `op`.
2. **В сценарии 3 (блокировка производителя):**
    - Вместо `offerer.get` мы используем `poll(offerer.get)`. Это делает саму блокировку **отменяемой**.
    - Добавлен `cleanup` — функция, которая удаляет `offerer` из очереди `offerers`, если отмена всё же произойдёт во время блокировки.
    - `.onCancel(cleanup)` означает: «Если этот эффект (`poll(offerer.get)`) будет отменён, выполни `cleanup`».

**Гарантии:**

- Состояние изменяется **атомарно** и без возможности отмены в неподходящий момент.
- Блокировка может быть прервана (например, по таймауту).
- При отмене блокировки состояние корректно очищается.

### Исправленный потребитель с поддержкой отмены

Потребитель требует аналогичной обработки. Блокирующий вызов здесь — `taker.get`, 
а очистка должна удалить `taker` из очереди `takers`.

```dotty
def consumer[F[_]: {Async, Console}](
    id: Int,
    stateR: Ref[F, State[F, Int]]
): F[Unit] =
  val take: F[Int] =
    Deferred[F, Int].flatMap { taker =>
      Async[F].uncancelable { poll =>
        stateR.modify {
          // Сценарий 1: Очередь не пуста, нет ожидающих производителей
          case State(queue, capacity, takers, offerers)
              if queue.nonEmpty && offerers.isEmpty =>
            val (i, rest) = queue.dequeue
            State(rest, capacity, takers, offerers) -> Async[F].pure(i)

          // Сценарий 2: Очередь не пуста, есть ожидающие производители
          case State(queue, capacity, takers, offerers) if queue.nonEmpty =>
            val (i, rest)               = queue.dequeue
            val ((move, release), tail) = offerers.dequeue
            State(rest.enqueue(move), capacity, takers, tail) ->
              release.complete(()).as(i)

          // Сценарий 3: Очередь пуста, но есть ожидающие производители
          case State(queue, capacity, takers, offerers)
              if offerers.nonEmpty =>
            val ((i, release), rest) = offerers.dequeue
            State(queue, capacity, takers, rest) -> release.complete(()).as(i)

          // Сценарий 4: Очередь пуста и нет ожидающих производителей — блокируемся
          case State(queue, capacity, takers, offerers) =>
            // Функция очистки: удаляем taker из очереди при отмене
            val cleanup = stateR.update { s =>
              s.copy(takers = s.takers.filter(_ ne taker))
            }
            State(queue, capacity, takers.enqueue(taker), offerers) ->
              poll(taker.get).onCancel(cleanup)
        }.flatten
      }
    }

  for
    i <- take
    _ <- Async[F].whenA(i % 100000 == 0)(
      Console[F].println(s"Потребитель $id обработал $i элементов")
    )
    _ <- consumer(id, stateR)
  yield ()
```

**Симметрия:** Код производителя и потребителя теперь структурно идентичны:

- `uncancelable` защищает модификацию состояния.
- `poll` делает блокировку на `Deferred.get` отменяемой.
- `onCancel(cleanup)` обеспечивает согласованность состояния при отмене.

### Почему это безопасно?

| Сценарий                                                                     | Гарантия                                                                                                   |
|:-----------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------|
| **Отмена до `modify`**                                                       | Состояние не изменилось — ничего не нужно чистить.                                                         |
| **Отмена во время `modify`**                                                 | `modify` является атомарной операцией `Ref` и не может быть отменена.                                      |
| **Отмена сразу после `modify`, но до выполнения `op`**                       | Защищено `uncancelable` — такой ситуации не возникает.                                                     |
| **Отмена во время `op`, если `op` — неблокирующий (`unit` или `complete`)**  | Эти операции выполняются мгновенно; отмена не успевает произойти.                                          |
| **Отмена во время `op`, если `op` — блокирующий (`get`)**                    | `poll` делает блокировку отменяемой. При отмене выполняется `cleanup`, удаляющий `Deferred` из состояния.  |

**Ключевой вывод:** Реализация стала немного сложнее, но приобрела **критически важное свойство** — устойчивость к отмене. 
В реальных приложениях (где таймауты, graceful shutdown, обработка ошибок — это норма) такая защита необходима.

Полная реализация с поддержкой отмены доступна по [ссылке][source].

## Заключение

| Этап                                | Ключевой вывод                                                                     |
|:------------------------------------|:-----------------------------------------------------------------------------------|
| **Мотивация**                       | Функциональные эффекты (`F[_]`) инкапсулируют побочные эффекты.                    |
| **Классы типов**                    | Ограничение возможностей через классы типов — это документирование и безопасность. |
| **Resource**                        | `Resource` гарантирует освобождение ресурсов даже при отмене.                      |
| **Неэффективная очередь**           | Так делать нельзя (100% CPU, последовательная работа).                             |
| **Эффективная очередь (unbounded)** | Семантическая блокировка без потребления CPU.                                      |
| **Ограниченная очередь (bounded)**  | Обратное давление (backpressure) и защита от OOM.                                  |
| **Отменяемость**                    | Код устойчив к отмене, таймаутам, graceful shutdown.                               |
