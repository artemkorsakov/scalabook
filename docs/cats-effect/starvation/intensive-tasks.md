# Вычислительно-ресурсоемкие задачи

## Проблема: не только блокировка вызывает голодание

Хотя жесткая блокировка потоков — это самый простой и очевидный способ «захватить» все потоки в вычислительном пуле 
(как в примере с `Thread.sleep`), это далеко не единственный способ. 
Следующая программа аналогичным образом лишит ваше приложение вычислительных ресурсов, но уже без единого блокирующего вызова:

```dotty
import cats.effect.*
import cats.syntax.all.*

object StarveThyselfAgain extends IOApp.Simple:
  val run = (0 until 100).toList.parTraverse_ { i =>
    IO.println(s"running #$i") >> IO(while true do {}) // Бесконечный цикл!
  }
```

В этом примере, как и в случае с `Thread.sleep`, все вычислительные потоки будут полностью захвачены. 
Однако разница принципиальна: вместо ожидания (`BLOCKED`), потоки находятся в состоянии `RUNNABLE`, бесконечно выполняя код. 
Это **не блокировка**, а **монополизация CPU**.

В реальных приложениях, конечно, подобных очевидных ловушек нет. Вместо этого проблемы могут выглядеть так:

- Серия криптографических операций (особенно асимметричная криптография, которая на порядки ресурсоемче симметричной).
- Интенсивные численные расчеты (симуляции, обработка сигналов).
- Обработка больших коллекций внутри одного этапа `IO`.
- Или что-то, незаметно спрятанное внутри операции `map` или `flatMap`.

Ключевое отличие от блокировки в том, что вычислительно-емкие действия часто **не имеют побочных эффектов**. 
Это просто чистые функции. Именно это делает их коварными: нет явного `IO.blocking`, нет нативного вызова, нет видимого «греха».

## Диагностика: как найти «прожорливый» код

В отличие от блокирующих задач (где достаточно одного дампа потоков), поиск CPU-интенсивных задач сложнее. 
Поток не будет в состоянии `BLOCKED`, он всё время будет `RUNNABLE`. Нам нужно понять, _на что тратится время_.

### 1. Серия дампов потоков (Classic)

Сделайте **несколько дампов потоков** (`kill -3 <pid>` или `Ctrl+\`) с интервалом в 1-2 секунды.

- **Что искать:** Потоки `io-compute-*`, которые **в каждом дампе** находятся в состоянии `RUNNABLE` 
  и **каждый раз** имеют трассировку стека, указывающую на одни и те же методы вашего кода.
- **Почему это работает:** Если один и тот же поток постоянно выполняет один и тот же код, 
  это сильный признак того, что этот код выполняется очень долго, не уступая управление.

### 2. Асинхронный профилировщик (Async Profiler)

Более современный и точный метод — это использование асинхронного профилировщика 
(например, `async-profiler`, встроенный в IntelliJ IDEA Ultimate или доступный как отдельный инструмент). 
Он сэмплирует стеки вызовов с высокой частотой и строит flamegraph.

- **Что искать:** «Толстые» полосы в flamegraph, соответствующие вашему коду, выполняемому в потоках `io-compute-*`.
- **Преимущество:** Дает точную картину того, какой код потребляет больше всего CPU, без необходимости гадать.

## Решение: «Три кита» справедливости

В отличие от блокирующих задач (где решение — `IO.blocking`), для CPU-интенсивных задач нет единого простого ответа. 
Проблема заключается в фундаментальном противоречии:

- **Блокировка (`BLOCKED`):** Поток продвигается вперед, **если есть время** (ОС даст ему CPU, когда данные будут готовы).
- **Вычисления (`RUNNABLE`):** Поток продвигается вперед, только **если есть свободное физическое ядро CPU**.

Если все ваши вычислительные потоки заняты тяжелыми вычислениями, 
вы **не можете** просто создать новые потоки (как это делает `IO.blocking`), 
потому что физические ресурсы (ядра CPU) конечны. 
Дополнительные потоки только усугубят конкуренцию и нагрузку на планировщик ОС.

Решение для обеспечения **справедливости** (то есть отзывчивости приложения) 
в условиях высокой вычислительной нагрузки обычно состоит из трех шагов, которые следует применять последовательно.

### 1. Увеличение детализации этапов (Granularity)

Среда выполнения Cats Effect предполагает (для целей планирования), 
что каждый этап `IO` (например, `map`, `flatMap`, `delay`) имеет **примерно одинаковую стоимость**. 
Если у вас есть один огромный этап, это нарушает это предположение.

**Как увеличить детализацию:**

Разделите один тяжелый этап на несколько более мелких.

```dotty
// Проблемный код: все вычисления внутри одного map
data.map: d =>
  val x = computeX(d) // Долго
  val y = computeY(d) // Тоже долго
  x + y
```

**Исправление:** Разделите на два этапа с помощью `flatMap`.

```dotty
// Исправленный код: два этапа, между которыми Cats Effect может выполнить планирование
data.flatMap: d =>
  IO.pure(computeX(d)).map: x =>  // Этап 1
    x + computeY(d)               // Этап 2
```

**Предостережение:** Увеличение детализации приводит к **увеличению выделения памяти** (больше объектов `IO`) 
и, как следствие, к снижению **пропускной способности** (throughput). 
Золотая середина — это баланс: каждый этап должен быть достаточно большим, 
чтобы накладные расходы на управление `IO` не доминировали, но достаточно маленьким, чтобы не вызывать голодание.

### 2. Добавление `IO.cede` (Yielding)

Среда выполнения Cats Effect по умолчанию делит непрерывную работу на **задачи (tasks)**. 
Одна задача состоит из 1024 этапов `IO` (это значение можно настроить). 
Это сделано для снижения накладных расходов на планирование.

Проблема возникает, когда _один_ этап (`IO(...)`, `map`) выполняется дольше, чем остальные 1023 этапа вместе взятые. 
Решение — принудительно разбить эту работу на отдельные задачи с помощью `IO.cede`. 
`cede` — это точка кооперативной уступки, которая говорит планировщику: 
«Сделай паузу в текущей задаче и дай возможность поработать другим». Она действует как **естественная граница задачи**.

**Основной паттерн:**

```dotty
val expensiveThing: IO[A] = IO(veryLongComputation())

// Добавляем cede ДО и ПОСЛЕ дорогой операции
val fairThing = IO.cede *> expensiveThing.guarantee(IO.cede)
// или, если expensiveThing может быть отменен:
val fairThing = IO.cede *> expensiveThing <* IO.cede
```

**Диагностика: нужно ли использовать `cede`?**

Простой эксперимент с `timed` поможет понять, насколько дорог ваш этап по сравнению с эталонным (`IO.unit`).

```dotty
def isTooExpensive[A](fa: IO[A]): IO[Boolean] =
  IO.unit.timed.flatMap { case (baseline, _) =>
    fa.timed.flatMap { case (cost, _) =>
      IO.println(s"Базовая стоимость: $baseline, Стоимость fa: $cost").as(cost >
        baseline * 1024)
    }
  }
```

Если `isTooExpensive(expensiveThing)` возвращает `true`, это верный признак того, что нужен `cede`.

## Справедливость против пропускной способности

В мире планирования вычислительных задач существует фундаментальное противоречие, 
которое лежит в основе любого решения о распределении ресурсов: 
противоречие между **справедливостью** (fairness) и **пропускной способностью** (throughput). 
Понимание этого компромисса является ключом к созданию отзывчивых и эффективных приложений, особенно в среде Cats Effect.

### Максимальная пропускная способность (Maximum Throughput)

**Что это такое?** Это подход, при котором планировщик **никогда не прерывает задачи**. 
Каждая задача, получив доступ к CPU, выполняется до своего полного завершения. 
Задачи обрабатываются, возможно, в порядке их поступления (FIFO), но без каких-либо вытеснений.

**Как это выглядит в коде (идеализированно):**

```dotty
// Воображаемый планировщик без прерываний
def processQueue(queue: List[Task]): Unit = queue.foreach(_.run())
```

**Плюсы:**

- **Максимальная эффективность:** Нет накладных расходов на переключение контекста 
  (сохранение/восстановление состояния, переключение между задачами). CPU тратит всё время на полезную работу.
- **Минимальное время выполнения фиксированного набора задач:** 
  Если у вас есть ровно 100 задач и больше ничего не поступает, этот подход выполнит их быстрее всего.

**Минусы:**

- **Полная неотзывчивость:** Пока обрабатывается начальная очередь задач, 
  приложение _не будет реагировать_ на новые события (новые сетевые соединения, таймеры, ввод пользователя). 
  Оно «зависает» до тех пор, пока все старые задачи не будут завершены.
- **«Ловушка производительности»:** На первый взгляд кажется, что это самый быстрый способ. 
  Но для интерактивных систем (веб-серверы, GUI, микросервисы) это **неприемлемо**. 
  Пользователь не заметит, что сервер обработал 100 запросов за 100 мс, если он получил ответ только на 101-й запрос через 5 секунд.

### Максимальная справедливость (Maximum Fairness)

**Что это такое?** Это подход, при котором планировщик пытается предоставить **равные кванты времени CPU** всем готовым к выполнению задачам. 
Он активно переключается между задачами, чтобы ни одна из них не «голодала». 
Новые задачи получают CPU практически мгновенно, часто за счет _приостановки_ старых задач.

**Как это выглядит:**
Планировщик с квантованием времени (round-robin): каждая задача выполняется 1 мс, затем переключается на следующую.

**Плюсы:**

- **Отзывчивость:** Приложение реагирует на новые запросы практически мгновенно. Пользовательский интерфейс не «зависает».
- **Предсказуемость:** Хвостовые задержки (p99, p999) значительно ниже, так как ни одна задача не может монополизировать CPU надолго. 
  Все задачи прогрессируют равномерно.

**Минусы:**

- **Снижение общей пропускной способности:** Частые переключения между задачами создают накладные расходы (overhead). 
  Один и тот же фиксированный набор задач в системе со справедливым планированием будет выполняться **дольше**, 
  чем в системе с планированием для максимальной пропускной способности.
- **Менее эффективное использование кэшей CPU:** Постоянное переключение приводит к «охлаждению» кэшей процессора (L1/L2), что замедляет выполнение.

> **«Справедливость — это форма приоритизации. Вы ставите приоритет на отзывчивость вашего приложения, а не на его производительность.»**

## Компромисс на практике: выбор стратегии

Проектировщик приложения и среды выполнения (например, Cats Effect) постоянно балансирует между этими двумя крайностями.

- **Пакетная обработка (Batch processing):** Обработка терабайта логов за ночь. Здесь важна _пропускная способность_. 
  Справедливость не нужна, так как нет интерактивных пользователей, ожидающих ответа.
- **Веб-сервер (Web server):** Здесь критична _отзывчивость_ (маленький p99). Пользователи ждут свои запросы. 
  Справедливость (чтобы ни один запрос не «голодал») важнее, чем максимальная пропускная способность.

**Cats Effect по умолчанию настроен на баланс в пользу справедливости и отзывчивости.** 
Планировщик с перераспределением задач (work-stealing) и автоматические точки `cede` призваны гарантировать, 
что даже при высокой нагрузке приложение останется отзывчивым. 
Но этого может быть недостаточно для экстремально тяжелых задач.

### Крайний случай: неделимая тяжелая задача

Теперь представим, что `expensiveThing` — это **неделимая** вычислительно-емкая задача, например, подписание JWT, 
проверка сложного доказательства или симуляция. Её нельзя разбить на этапы. 
`IO.cede` мы добавили до и после, но это не решает проблему: пока `expensiveThing` выполняется, она занимает CPU.

Если у вас 8 ядер CPU, и вы обрабатываете 16 параллельных запросов, каждый из которых запускает `expensiveThing`, 
то все 8 вычислительных потоков будут полностью заняты. Приложение станет **неотзывчивым**. 
Новые соединения не будут приниматься, таймеры не будут срабатывать. Возникнет **голодание (starvation)**.

Что делать? Единственное решение — **искусственно ограничить параллелизм** выполнения этой тяжелой задачи.

### Стратегия ограничения: Глобальный семафор

Семафор позволяет ограничить количество волокон, которые могут одновременно получить разрешение на выполнение `expensiveThing`.

```dotty
import cats.effect.IO
import cats.effect.std.Semaphore

def handleRequest(throttle: Semaphore[IO], request: Request): IO[Unit] = 
  val fairWork = IO.cede *> expensiveThing(request).guarantee(IO.cede)
  throttle.permit.use(_ => fairWork)
```

**Почему `throttle.permit.use`?** 
Он автоматически освобождает разрешение (permit) после завершения `fairWork`, даже если произошла ошибка или отмена.

**Выбираем `n = computeWorkerThreadCount / 2`.** Это эмпирическое правило. Оно гарантирует, что:

1. Какое-то количество потоков (половина) всегда остается доступным для приема новых соединений, 
   обработки таймеров и других «легких» задач.
2. Оставшиеся потоки выполняют тяжелую работу. Если их несколько, они будут конкурировать за CPU.

**Последствия:**

- **Увеличение p50 (медианной задержки):** Запросы начинают ждать в очереди семафора.
- **Улучшение p99 (хвостовой задержки):** Сервер остается отзывчивым, 
  и самые медленные запросы выполняются существенно быстрее, чем в случае, когда все потоки заблокированы тяжелой работой. 
  Распределение задержек становится _более предсказуемым_.

В контексте микросервисов это приводит к компромиссу: 
вы **намеренно** жертвуете пиковой производительностью (увеличиваете p50), 
чтобы **гарантировать** предсказуемую отзывчивость и низкий p99.

### Стратегия фоновой обработки: Ограниченная очередь

Если `expensiveThing` не обязана завершиться _до_ отправки ответа клиенту, лучшая стратегия — вообще не выполнять её синхронно. 
Отправьте задачу в очередь и ответьте клиенту немедленно.

```dotty
object Backgrounding extends IOApp.Simple:
  val run =
    val rsrc =
      for
        workQueue <- Queue.bounded[IO, IO[Unit]](8096).toResource
        // Один фоновый воркер
        _ <- workQueue.take.flatMap(_.voidError).foreverM.background
        _ <- acceptRequest.toResource.flatMap(r =>
          handleRequest(workQueue, r).background
        )
      yield ()
    rsrc.useForever

  def handleRequest(queue: Queue[IO, IO[Unit]], r: Request): IO[Unit] =
    val fairWork = IO.cede *> expensiveThing(r).guarantee(IO.cede)
    queue.offer(fairWork) *> respond(r) // Ответ отправляется немедленно!
```

**Преимущества:**

- Ответ клиенту не задерживается вообще (`respond` выполняется сразу).
- Ограниченная очередь (`bounded`) создает обратное давление (backpressure): 
  если очередь заполнена, `queue.offer` семантически заблокируется, что замедлит `handleRequest` 
  и, следовательно, ограничит скорость приема новых запросов.

**Улучшение: несколько фоновых воркеров**

Можно запустить несколько воркеров, чтобы увеличить пропускную способность фоновой обработки, 
но опять же, не превысив разумный лимит.

```dotty
// Запускаем, например, половину от числа ядер воркеров
_ <- workQueue.take
  .flatMap(_.voidError)
  .foreverM
  .background
  .replicateA_(computeWorkerThreadCount / 2)
```

Это параллелизм _на уровне приложения_, который вы полностью контролируете.

## Заключение и следующий шаг

Выбор между справедливостью и пропускной способностью — это не техническая проблема, а **бизнес-требование**. 
Понимая компромисс, вы можете сознательно его регулировать.

- **Для синхронных тяжелых API:** Используйте **семафор**, чтобы ограничить параллелизм, жертвуя `p50` ради улучшения `p99`.
- **Для фоновых задач:** Используйте **ограниченную очередь**, чтобы отделить обработку от ответа клиенту и создать контролируемый backpressure.

Эти паттерны настолько распространены, что для их эффективной реализации часто имеет смысл перейти 
от низкоуровневых примитивов Cats Effect к [библиотеке Fs2](https://fs2.io/#/) (Functional Streams for Scala). 
Fs2 предоставляет высокоуровневые, композируемые и безопасные абстракции для конкурентной обработки потоков данных, 
включая готовые инструменты для ограничения параллелизма (`parEvalMap`), буферизации (`buffer`), и управления очередями.

Использование Fs2 позволяет выразить сложные конкурентные сценарии более декларативно и с меньшим количеством ошибок, 
чем ручное управление семафорами и очередями.
