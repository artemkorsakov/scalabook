# AtomicCell — безопасная клетка для эксклюзивного доступа

## Что такое `AtomicCell`?

`AtomicCell[F[_], A]` — это **синхронизированная, конкурентная, атомарная ссылка**, которая гарантирует, 
что **только одно волокно** может выполнять _модифицирующую_ операцию в любой момент времени.

Простым языком: это **комната с ключом**. Внутри лежит значение (`A`). 
Взять ключ и войти в комнату может только одно волокно. 
Остальные волокна, желающие изменить значение, выстраиваются в очередь и ждут, пока комната освободится. 
Заглянуть в комнату (`get`) можно без ключа и очереди.

`AtomicCell` можно представить как удобную, готовую комбинацию двух примитивов:

- **`Ref[F, A]`** — для хранения значения.
- **`Mutex[F]`** — для обеспечения эксклюзивного доступа.

### Базовый интерфейс

```dotty
abstract class AtomicCell[F[_], A]:
  /** Просто читает текущее значение. Не блокирует и не изменяет состояние. */
  def get: F[A]

  /** Заменяет значение. Блокирует волокно на время замены. */
  def set(a: A): F[Unit]

  /** Атомарно изменяет состояние и возвращает произвольное значение. Чтение →
    * вычисление → запись происходят под одной блокировкой.
    */
  def modify[B](f: A => (A, B)): F[B]

  /** Как `modify`, но функция `f` возвращает эффект `F[(A, B)]`. Позволяет
    * выполнять эффекты (например, IO-вызовы) внутри критической секции.
    */
  def evalModify[B](f: A => F[(A, B)]): F[B]

  /** Обновляет значение, используя функцию с эффектом. */
  def evalUpdate(f: A => F[A]): F[Unit]

  // ... и многое другое: update, evalUpdateAndGet, modifyEither, и т.д.
```

### `AtomicCell` vs `Ref`

Это ключевое сравнение, которое нужно понять.

| Операция                  | `Ref[F, A]`                                                                       | `AtomicCell[F, A]`                                                                                       |
|:--------------------------|:----------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------|
| **`get`**                 | Мгновенно, без блокировки.                                                        | Мгновенно, без блокировки.                                                                               |
| **`set`**                 | Мгновенно.                                                                        | **Блокирует** волокно до захвата мьютекса.                                                               |
| **`update` (быстрое)**    | `ref.update(_ + 1)` — неблокирующий CAS-цикл.                                     | `cell.update(_ + 1)` — блокировка + изменение.                                                           |
| **`update` (медленное)**  | `ref.update(doHeavyStuff)` — CAS-цикл может повторяться, отменяя тяжёлую работу.  | `cell.update(doHeavyStuff)` — блокировка, тяжёлая работа выполняется **один раз**, другие волокна ждут.  |
| **`modify` с эффектами**  | ❌ Нет. Нужно комбинировать `Ref` + `Mutex` вручную.                               | ✅ `evalModify` позволяет выполнить `IO` внутри изменения.                                                |

**Главное правило выбора:**

- Используйте **`Ref`**, когда операции изменения **быстрые, неблокирующие** и могут быть безопасно повторены (CAS-цикл).
- Используйте **`AtomicCell`**, когда операция изменения **"дорогая" или эффектная** (сетевой вызов, тяжёлое вычисление) 
  и её нежелательно выполнять несколько раз из-за оптимистичных блокировок.

## Глубокое погружение: `evalModify` и гарантии

Самая мощная функция `AtomicCell` — это `evalModify`. Она решает проблему, которую `Ref` решить не может.

### Проблема с `Ref` для операций с эффектом

Представьте, что у вас есть `Ref[IO, Data]`, и вы хотите обновить его на основе результата внешнего вызова.

```dotty
// ПРОБЛЕМА: Не делайте так!
def updateData(ref: Ref[IO, Data], newId: String): IO[Unit] =
  ref.update { currentData =>
    // Это НЕ сработает! update не принимает IO-эффекты внутри.
    // Предположим, это тяжелое вычисление или IO.sleep
    val newData = heavyComputation(currentData, newId)
    newData
  }
```

Но что, если `heavyComputation` — это на самом деле `IO` (например, запрос в базу данных)? 
`Ref` не позволяет выполнять эффекты внутри `update`.

Единственный способ с `Ref` — это использовать гонку (race condition):

```dotty
// НЕБЕЗОПАСНО: Гонка с Ref
def updateDataBad(ref: Ref[IO, Data], newId: String): IO[Unit] =
  for
    current <- ref.get            // поток 1 читает A
    _       <- IO.sleep(1.second) // имитируем работу
    newData <- compute(current, newId)
    _       <- ref.set(newData)   // поток 1 записывает B
  yield ()
// Если в это время другой поток изменил ref, изменение Потока 1 будет потеряно!
```

Это приводит к **состоянию гонки** (lost update). `AtomicCell` решает эту проблему элегантно.

### Решение с `AtomicCell`: `evalModify`

```dotty
def updateData(cell: AtomicCell[IO, Data], newId: String): IO[Unit] =
  cell.evalModify { currentData =>
    // Теперь мы ВНУТРИ блокировки. Только одно волокно здесь.
    for newData <- compute(currentData, newId) // Безопасно выполняем IO-эффект
    yield (newData, ()) // (новое_состояние, возвращаемое_значение)
  }
```

**Гарантии `evalModify`:**

1. **Эксклюзивность:** Волокно, вошедшее в `evalModify`, **монопольно владеет** доступом к `AtomicCell`. 
   Никакое другое волокно не может выполнять `set`, `modify` или `evalModify` до тех пор, пока текущее не завершится.
2. **Атомарность:** Весь блок внутри `evalModify` (чтение → эффектное вычисление → запись) выполняется как единое, 
   неделимое действие с точки зрения других модифицирующих операций.
3. **Отсутствие повторов:** В отличие от CAS-цикла в `Ref`, **результат `compute` не будет отброшен**. 
   Он будет записан гарантированно.

## Реальный пример: Генератор случайных данных с побочными эффектами

Рассмотрим код:

```dotty
import cats.effect.IO
import cats.effect.std.AtomicCell

trait Data

class RandomDataGenerator(cell: AtomicCell[IO, Data]):

  /** Генерирует новое случайное значение на основе предыдущего. */
  def next: IO[Data] =
    cell.evalUpdateAndGet(generate) // Обновляем и возвращаем новое значение

  /** Эффектная функция генерации, например, обращается к базе данных или
    * внешнему API.
    */
  private def generate(previous: Data): IO[Data] = ???
```

**Почему здесь `AtomicCell` необходим?**

Представьте, что `generate` делает следующее:

1.  Запрашивает у базы данных новый "seed".
2.  Производит сложные криптографические вычисления.
3.  Сохраняет результат в кеш.

Если бы мы использовали `Ref`, мы бы столкнулись с проблемой "гонки" или многократного выполнения дорогой операции. 
`AtomicCell` гарантирует, что:

- Каждый вызов `next` будет выполняться строго последовательно.
- Вызовы `next` не будут мешать друг другу.
- Дорогая операция `generate` выполнится **ровно один раз** за одно изменение состояния.

## Пример из реального мира: Баланс банковского счета

Представьте себе банковский счет. Операции списания и зачисления должны быть строго последовательными, чтобы избежать ошибок.

```dotty
import cats.effect.IO
import cats.effect.std.AtomicCell

case class Account(balance: Long)

class Bank(cell: AtomicCell[IO, Account]):

  /** Списать сумму, но только если баланс позволяет. */
  def withdraw(amount: Long): IO[Boolean] =
    cell.evalModify { account =>
      if account.balance >= amount then
        // Имитируем проверку фрода, запрос к внешней системе...
        val fraudCheck = IO.sleep(100.millis).as(true)
        fraudCheck.map {
          case true => (Account(account.balance - amount), true)
          // Мошенничество: не списываем, но и состояние не меняем
          case false => (account, false)
        }
      else
        IO.pure((account, false)) // Недостаточно средств
    }

  /** Зачислить сумму. */
  def deposit(amount: Long): IO[Unit] =
    cell.evalUpdate(account => IO.pure(Account(account.balance + amount)))

  def getBalance: IO[Long] = cell.get.map(_.balance)
end Bank
```

**Ключевые моменты:**

- `evalModify` в `withdraw` атомарно проверяет баланс, **возможно ждёт ответа от внешнего сервиса**, и затем обновляет баланс.
- Во время ожидания ответа от сервиса фрода, **другие волокна не могут изменить баланс**. Это критично для корректности.
- С `Ref` такую логику реализовать было бы крайне сложно и подвержено ошибкам.

## Важные характеристики и поведение

### 1. Блокировка только для **модифицирующих** операций

- `get` **никогда не блокируется**. Это мгновенный, неблокирующий вызов.
- `set`, `update` (и все `eval*` варианты) **блокируют** волокно, пока мьютекс не будет захвачен.

### 2. Справедливость блокировки

`AtomicCell` обычно обеспечивает **справедливую** (FIFO) очередь ожидания. 
Волокна, пытающиеся изменить состояние, выстраиваются в очередь в порядке поступления. 
Это предотвращает "голодание" (starvation).

### 3. Отменяемость

Блокировка на `AtomicCell` **является отменяемой**. Если волокно, ожидающее в очереди, было отменено, 
оно корректно удаляется из очереди ожидания, и право на захват мьютекса переходит к следующему.

```dotty
// Пример: волокно будет удалено из очереди при отмене
val waitingFiber = cell.update(dosomething).start
waitingFiber.cancel // ожидающее волокно корректно покинет очередь
```

### 4. «Ленивое» получение для `evalModify`

Обратите внимание: внутри `evalModify` вы **не должны** выполнять очень долгие или бесконечные операции (например, `IO.never`), 
так как это заблокирует **все** другие модифицирующие операции навсегда.

## `AtomicCell` в сравнении с альтернативами

| Сценарий                                         | Лучший выбор                      | Почему                                                                  |
|:-------------------------------------------------|:----------------------------------|:------------------------------------------------------------------------|
| Простой счётчик, инкремент без I/O               | `Ref`                             | Неблокирующий CAS, максимальная производительность.                     |
| Счётчик с обращением к БД при каждом инкременте  | `AtomicCell`                      | Тяжёлая операция должна быть выполнена один раз в эксклюзивном режиме.  |
| Кеш, который обновляется из внешнего источника   | `AtomicCell` (с `evalUpdate`)     | Гарантирует, что обновление кеша не будет потеряно.                     |
| Нужно просто разделять неизменяемое состояние    | `Ref`                             | `get` достаточно, блокировка не нужна.                                  |
| Сложная координация с очередью и сигналами       | `Queue`, `Deferred`, `Semaphore`  | `AtomicCell` — это примитив "один слот".                                |

## Итог: Когда использовать `AtomicCell`?

✅ **Используйте `AtomicCell`, если:**

- Операция изменения состояния включает в себя **эффекты** (I/O, внешние вызовы, `IO.sleep`).
- Вы хотите **блокирующего, эксклюзивного** доступа для модификации ("критическая секция").
- Вам нужна **гарантия**, что тяжёлое вычисление для нового значения выполнится **один раз**, без повторных попыток в CAS-цикле.
- Вы портируете код, который раньше использовал `synchronized` или `Lock` из Java.

❌ **Не используйте `AtomicCell`, если:**

- Вам нужна максимальная производительность для очень простых, быстрых операций (`x = x + 1`). `Ref` будет быстрее.
- Достаточно `get` и простого `set` без атомарных изменений.
- Вам нужна неэксклюзивная, просто атомарная ссылка.

`AtomicCell` — это мощный и безопасный инструмент, который заполняет пробел между быстрым, 
но "оптимистичным" `Ref` и ручным, многословным управлением `Mutex` + `Ref`. 
Он идеален для координации доступа к разделяемым ресурсам, когда операции изменения являются "дорогими".
