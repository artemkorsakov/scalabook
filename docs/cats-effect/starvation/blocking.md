# Блокирующие задачи

Самый простой и очевидный источник нехватки ресурсов CPU — это **выполнение блокирующих задач в пуле вычислительных потоков**. 
Причина проста: вычислительный пул имеет фиксированный размер (как правило, равный количеству ядер процессора). 
Если хотя бы один из его потоков блокируется (например, на операции ввода-вывода), его вычислительная мощность безвозвратно теряется. 
Если блокируются _все_ потоки, ваше приложение полностью останавливается.

В реальных приложениях проблема скрывается в глубинах сторонних библиотек, 
особенно тех, что написаны для Java в эпоху, когда господствовала блокирующая модель ввода-вывода.

- **Типичные подозреваемые:**
    - JDBC-вызовы (базы данных).
    - Чтение/запись файлов (`FileInputStream`, `FileOutputStream`, `RandomAccessFile`, `nio.FileChannel` в синхронном режиме).
    - Сетевые вызовы (старые `HttpURLConnection`, `Socket`).
    - Работа с DNS (`java.net.URL`, `InetAddress.getByName`).
    - Любые вызовы `Thread.sleep()`, `Object.wait()`, `synchronized` блоки.
    - Многие операции с `java.nio.*` в синхронном (не `Selector`-ном) режиме.

**Как только проблемный код найден, исправление следующее:** замените `IO(...)` на `IO.blocking(...)`или `IO.interruptible(...)`. 
`IO.blocking` перенаправит выполнение задачи в специальный, неограниченный пул блокирующих потоков, 
не затрагивая вычислительный пул. 
`IO.interruptible` делает то же самое, но также позволяет Cats Effect прервать (через `Thread.interrupt()`) 
заблокированную операцию в случае отмены волокна.

## Детектор блокирующих потоков (Blocked Thread Detection)

Если ваше приложение — это `IOApp`, Cats Effect предоставляет **встроенный, 
но выключенный по умолчанию инструмент для обнаружения блокирующих потоков**. 
Это самый простой способ диагностики подобных проблем.

**Как это включить:**

```dotty
import cats.effect.IOApp

object Example extends IOApp.Simple:
  // Включаем детектор блокирующих потоков
  override protected def blockedThreadDetectionEnabled = true

  val run: IO[Unit] = ??? // Ваша программа
```

**Принцип работы:**

1. Благодаря пулу work-stealing, несколько потоков `io-compute-*` работают вместе.
2. Детектор создаёт фоновый поток-наблюдатель.
3. Этот наблюдатель периодически (каждые несколько секунд) **случайным образом** выбирает один из живых потоков `io-compute-*`.
4. Он проверяет состояние этого потока. Если поток находится в состоянии `BLOCKED` или `WAITING` 
   (что указывает на то, что он заблокирован на уровне JVM/ОС), 
   детектор **печатает его трассировку стека** в стандартный поток ошибок (`stderr`).

**Анализ результатов:**

Допустим, вы увидели что-то подобное:

```
[WARNING] A compute thread has been blocked for at least N ms (possibly due to a blocking call).

"io-compute-5" #21 prio=5 os_prio=0 cpu=2.31ms elapsed=41.71s tid=0x00007fa7a4d6c000 nid=0xc6e runnable
  java.lang.Thread.State: RUNNABLE
  at java.io.FileInputStream.readBytes(Native Method)
  at java.io.FileInputStream.read(FileInputStream.java:...)
  at myapp.LegacyFileReader.readNextBlock(LegacyFileReader.scala:42)
  at myapp.DataProcessor.process(DataProcessor.scala:...)
  ...
```

Трассировка стека напрямую указывает на код, который следует обернуть в `IO.blocking`. 
В данном случае, это вызов `readBytes` внутри `LegacyFileReader`. 
Вы идёте в своё приложение и находите место, откуда вызывается `LegacyFileReader.readNextBlock`, 
и оборачиваете его в `IO.blocking`.

```dotty
// Было (плохо)
def processFile: IO[Unit] = IO {
  legacyReader.readNextBlock()
}

// Стало (хорошо)
def processFile: IO[Unit] = IO.blocking {
  legacyReader.readNextBlock()
}
```

**Важные замечания по детектору:**

- **Это случайный, а не детерминированный процесс.** Выбор потока случаен. 
  Детектор не гарантирует обнаружение _всех_ блокирующих вызовов, но с высокой вероятностью найдет часто встречающиеся.
- **Он дорогой.** Сама процедура проверки потока нетривиальна и потребляет ресурсы. Именно поэтому он **отключен по умолчанию**.
- **Используйте его в тестовой/стендовой среде, а не в продакшене.** 
  Включайте его локально или на staging-окружении для отладки, но выключайте на production-серверах.

## Альтернативный метод: дампы потоков (Thread Dumps)

Если вы не используете `IOApp` или по какой-то причине не можете включить детектор, **дампы потоков** — это мощный ручной метод диагностики.

**Как сделать дамп:**

- **В терминале (Unix/Linux/Mac):** Нажмите `Ctrl + \` (обратный слеш) в консоли, где запущена JVM.
- **Через сигнал ОС:** Используйте команду `kill -3 <pid>` (где `<pid>` — идентификатор процесса вашего приложения).
- **В Windows:** Нажмите `Ctrl + Break`.

В любом случае JVM напечатает полный дамп всех потоков и их трассировки стека в стандартный поток ошибок (`stderr`).

**Анализ результатов:**

Сделайте **несколько дампов** с интервалом в несколько секунд. Затем ищите потоки с именем `io-compute-*`. 
Если в любом из дампов **хотя бы один** такой поток находится в состоянии `BLOCKED` или `WAITING`, это тревожный сигнал. 
Изучите его трассировку стека, чтобы найти проблемный код.

_Пример вывода (фрагмент):_

```
"io-compute-2" #21 daemon prio=5 os_prio=0 cpu=3.21ms elapsed=10.31s tid=0x00007f9a3c011000 nid=0x3a4e waiting for monitor entry  [0x00007f9a38a7e000]
   java.lang.Thread.State: BLOCKED (on object monitor)
	at java.lang.ClassLoader.loadClass(ClassLoader.java:...)
	- waiting to lock <0x00000000deadbeef> (a java.lang.Object)
	at com.example.LegacyLibrary.initialize(LegacyLibrary.java:42)
```

Здесь видно, что поток заблокирован на синхронизированном методе внутри `LegacyLibrary.initialize`. 
Это классический блокирующий вызов, который нужно обернуть в `IO.blocking`.

**Ограничения дампов потоков:**

- В отличие от встроенного детектора, трассировка стека **не будет дополнена** информацией о волокнах Cats Effect. 
  Вы увидите только тот код, который был обернут в `IO.delay` или `IO(...)`. Однако, этого достаточно, чтобы найти источник проблемы.
- Это ручной и неавтоматизированный процесс.

## Файловый I/O и DNS: особые предупреждения

Важно осознавать, какие операции по умолчанию являются блокирующими на целевой платформе.

- **Файловый I/O:**
    - **macOS и Linux:** **Все** операции с файловой системой (чтение, запись, открытие, закрытие) 
      являются блокирующими на уровне ядра. Даже `FileChannel` в синхронном режиме блокируется.
    - **Windows:** Большинство операций с локальной файловой системой (NTFS) являются **неблокирующими**, 
      но операции с сетевыми дисками (SMB) — блокирующими. В целях переносимости, считайте любой файловый I/O блокирующим.
- **Сеть и DNS:**
    - Операции с сокетами (`Socket`) — блокирующие.
    - **`java.net.URL` и `InetAddress`:** При вызове `equals`, `hashCode`, или даже конструктора `new URL(...)` 
      **может выполняться блокирующий DNS-запрос** для разрешения имени хоста. Это крайне коварный источник блокировок!

Именно поэтому в предупреждении о голодании (`starvation`) особо упоминаются "операции с файловой системой или сетевые вызовы". 
Это самые частые и трудноуловимые причины проблем.

**Рекомендация:** Если ваш код взаимодействует с файловой системой, DNS, JDBC или любым другим потенциально блокирующим API, 
по умолчанию используйте `IO.blocking`. 
Лучше немного снизить производительность за счёт переключения контекста, чем полностью остановить приложение.

## Злоупотребление `IO.blocking` и другие виды голодания

Хотя оборачивание блокирующих вызовов в `IO.blocking` решает проблему блокировки вычислительного пула, это не панацея.

1. **Давление на блокирующий пул:** `IO.blocking` переносит задачу в отдельный, кэшируемый пул потоков, 
   который может динамически расширяться. Если создаётся чрезмерное количество блокирующих задач, 
   этот пул может начать потреблять много памяти (каждый поток — ~1 МБ стека) и создавать значительную нагрузку на планировщик ОС. 
   Это, в свою очередь, также может привести к голоданию, но уже другого рода.
2. **Неверное использование `interruptible`:** `IO.interruptible` может вызвать `Thread.interrupt()` 
   в заблокированном потоке, если волокно было отменено. Однако не все блокирующие методы корректно обрабатывают прерывания. 
   Некоторые могут игнорировать их или даже ломать состояние. Используйте `interruptible` с осторожностью, хорошо протестировав.
3. **CPU-интенсивные задачи:** Даже неблокирующие, но очень долгие CPU-задачи также могут монополизировать поток и вызвать голодание. 
   Для них не поможет `blocking`, нужно использовать `IO.cede` для кооперативной уступки.

**Итог:** Начните поиск проблем с включения `blockedThreadDetectionEnabled` в вашем `IOApp` (или с ручных дампов потоков). 
Обнаружив блокирующий код, оберните его в `IO.blocking`. Если проблема сохраняется, 
переходите к [анализу CPU-интенсивных задач](intensive-tasks.md) и общей архитектуры параллелизма.
