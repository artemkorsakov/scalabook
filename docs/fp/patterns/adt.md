# Алгебраические типы данных

## Что такое алгебраические типы данных?

Представьте, что у вас есть конструктор типа данных, который позволяет создавать новые типы, комбинируя существующие. 
Это и есть алгебраические типы данных (АТД).

**Простая аналогия**:

- У вас есть базовые "кирпичики" (простые типы)
- Вы можете склеивать их разными способами (операции)
- Получаете сложные структуры (алгебраические типы)

АТД бывают четырех основных видов:

## Единичный тип (Unit) - "одиночный контейнер"

```dotty
// Единичный тип - имеет только одно возможное значение
type UnitType = Unit
val unitValue: UnitType = () // Единственное значение этого типа

// Аналогия: коробка, в которой всегда лежит один и тот же предмет
// Или страница с одной-единственной записью
```

**Зачем нужен?**

- Обозначает "отсутствие значимой информации"
- Как пустая страница в блокноте
- В математике соответствует числу 1 (один возможный вариант)

## Нулевой тип (Nothing) - "пустой контейнер"

```dotty
// Нулевой тип - не имеет ни одного значения
type Void = Nothing

// Аналогия: пустая коробка, в которую нельзя ничего положить
// Или страница, на которой вообще нельзя писать

// НЕЛЬЗЯ создать значение этого типа!
val impossible: Void = ... // Ошибка!  Type Mismatch Error!
```

**Зачем нужен?**

- Обозначает "невозможность"
- Используется для обработки ошибок и исключительных ситуаций
- В математике соответствует числу 0 (ноль возможных вариантов)

## Тип-произведение (Product Type) - "комбинация всего"

```dotty
// Тип-произведение - содержит значения всех составляющих типов одновременно
type IntPair = (Int, Int) // Должен содержать и первое число, и второе

val product: IntPair = (42, 100) // оба значения обязательны

// Аналогия: анкета, где нужно заполнить все поля
// Или коробка с двумя отделениями - оба должны быть заполнены
```

**Как работает:**

- Количество возможных значений = произведение вариантов каждого типа
- Если `Int` имеет \\(2^{32}\\) значений, то `IntPair` имеет \\(2^{32} \times 2^{32}\\) значений
- Как умножение в математике: Int × Int

**Другие примеры:**

```dotty
case class Person(name: String, age: Int) // и имя, и возраст
type Triple = (Boolean, Int, String) // и булево, и число, и строку
```

## Тип-сумма (Sum Type) - "выбор одного из вариантов"

```dotty
// Тип-сумма - представляет значение одного из возможных типов
// "Баланс может быть либо положительным, либо отрицательным"
enum Balance:
  case Positive(amount: Int) // Вариант 1
  case Negative(amount: Int) // Вариант 2

// Использование:
val positive: Balance = Balance.Positive(100) // Выбрали "положительный" вариант
val negative: Balance = Balance.Negative(50)  // Выбрали "отрицательный" вариант

// Аналогия: форма с вариантами "да/нет" - можно выбрать только один
// Или развилка дороги - можно пойти только по одной из дорог
```

**Как работает:**

- Количество возможных значений = сумма вариантов каждого типа
- Если `Positive` имеет \\(2^{32}\\) значений, `Negative` имеет \\(2^{32}\\) значений, 
  то `Balance` имеет \\(2^{32} + 2^{32}\\) значений
- Как сложение в математике: Int + Int

## Комбинации на практике

**Пример 1: Сложный тип данных**

Пользователь может быть либо гостем, либо зарегистрированным пользователем:

```dotty
enum User:
  // Простой вариант (единичный тип)
  case Guest
  // Тип-произведение внутри типа-суммы!
  case RegisteredUser(name: String, email: String, age: Int)
```

**Пример 2: Дерево (рекурсивный АТД)**

Двоичное дерево может быть либо пустым, либо узлом с двумя поддеревьями:

```dotty
enum Tree[+A]:
  case Empty                                         // Нулевой случай
  case Node(value: A, left: Tree[A], right: Tree[A]) // Рекурсивный случай
```

## Почему "алгебраические"?

Типы в программировании ведут себя как числа в математике! Мы можем:

- **Считать** количество возможных значений типа
- **Складывать** и **умножать** типы
- **Доказывать равенства** между разными типами

### Закон 1: `1 + 0 = 1` (Единица плюс ноль равно единице)

```dotty
// Математика: 1 + 0 = 1
// Типы: Unit + Nothing = тип с одним вариантом

enum OneOrNothing:
  case OnlyOne
// Нет других case классов - это и есть "плюс ноль"

// Проверим на практике:
val onlyPossibleValue: OneOrNothing = OneOrNothing.OnlyOne

// Других значений нет:
// val impossible1: OneOrNothing = ???  // Не существует!
// val impossible2: OneOrNothing = ???  // Не существует!

// Сколько значений? Ровно одно! Как и у Unit
```

**Что здесь происходит:**

- `Unit` (единичный тип) = 1 возможное значение
- `Nothing` (нулевой тип) = 0 возможных значений
- `Unit + Nothing` = 1 + 0 = 1 возможное значение

**Реальная аналогия:**

- У вас есть одна конфета (`OnlyOne`)
- И обещание дать еще нуль конфет (`Nothing`)
- В итоге у вас все равно одна конфета

> Закон обобщается до любого типа: `A + Nothing = A`

### Закон 2: `1 * A = A` (Единица умножить на A равно A)

```dotty
// Математика: 1 × A = A
// Типы: (Unit, Int) эквивалентно просто Int

type UnitTimesInt = (Unit, Int)  // Unit × Int

// Докажем эквивалентность преобразованиями:
def toInt(uti: UnitTimesInt): Int = uti._2  // Просто берем второе значение
def fromInt(i: Int): UnitTimesInt = ((), i) // Добавляем единичное значение

// Проверим:
val number: Int = 42
val wrapped: UnitTimesInt = fromInt(number)  // ((), 42)
val unwrapped: Int = toInt(wrapped)          // 42

// number == unwrapped  
// Ничего не потеряли!
```

**Почему это работает:**

- `Unit` имеет только одно значение `()`
- При умножении `(Unit, Int)` мы получаем пары: `((), 0)`, `((), 1)`, `((), 2)`...
- Но первая часть всегда `()` - она не добавляет информации!
- Фактически это те же самые числа: 0, 1, 2...

**Реальная аналогия:**

- Записывать числа в тетрадь: `(тетрадь, число)`
- Но тетрадь всегда одна и та же - она не меняет числа
- Можно убрать тетрадь и работать только с числами

### Закон 3: `A + A = 2 * A` (Сумма равна произведению)

```dotty
// Математика: Int + Int = 2 × Int
// Типы: TwoInts эквивалентно (Boolean, Int)

// Представление 1: как сумма (сложение)
sealed trait TwoInts
object TwoInts:
  case class First(value: Int) extends TwoInts  // Левый Int
  case class Second(value: Int) extends TwoInts // Правый Int

// Представление 2: как произведение (умножение)
type TwoTimesInt = (Boolean, Int)  // Boolean × Int

// Докажем эквивалентность преобразованиями:
def fromTwoInts(ti: TwoInts): TwoTimesInt = ti match
  case TwoInts.First(value)  => (true, value)  // true означает "из левого"
  case TwoInts.Second(value) => (false, value) // false означает "из правого"

def toTwoInts(ti: TwoTimesInt): TwoInts = ti match
  case (true, value)  => TwoInts.First(value)
  case (false, value) => TwoInts.Second(value)

// Проверим:
val sumStyle: TwoInts = TwoInts.First(100)  // Левое число 100
val productStyle: TwoTimesInt = (true, 100) // То же самое в другом виде

val convertedToProduct: TwoTimesInt = fromTwoInts(sumStyle) // (true, 100)
val convertedBackToSum: TwoInts = toTwoInts(productStyle)   // First(100)
```

**Разберем подробнее:**

**TwoInts (сумма) имеет значения:**

```
First(0), First(1), First(2), ... First(2³²-1)   // 2³² значений
Second(0), Second(1), ... Second(2³²-1)          // еще 2³² значений
```

**Итого:** \\(2^{32} + 2^{32} = 2 \times 2^{32}\\) значений

**TwoTimesInt (произведение) имеет значения:**

```
(true, 0), (true, 1), (true, 2), ... (true, 2³²-1)   // 2³² значений
(false, 0), (false, 1), ... (false, 2³²-1)           // еще 2³² значений
```

**Итого:** \\(2 \times 2^{32}\\) значений - столько же!

**Реальная аналогия:**

- **Сумма**: у вас есть два ящика с числами - можно взять число из левого или правого
- **Произведение**: у вас есть бирка (true/false) и число - бирка говорит, из какого ящика число
- Это две разные формы одной и той же информации!

### Почему это важно на практике?

#### 1. **Оптимизация представления данных**

```dotty
// Либо строгий тип для использования глобально:
enum Result:
  case Success(data: String)
  case Failure(error: String)

// Либо упрощенное представления для локальной области:
type OptimizedResult = (Boolean, String) // true=Success, false=Failure
```

#### 2. **Понимание сложности типов**

```dotty
// Сколько возможных значений?
case class User(premium: Boolean, age: Int, country: String)

// Считаем: 2 (Boolean) × 100 (примерно возраст) × 200 (стран) ≈ 40,000 вариантов
```

#### 3. **Рефакторинг и преобразования**

Можно безопасно преобразовывать:

- `Either[A, A]` ⇔ `(Boolean, A)`
- `Option[A]` ⇔ `Either[Unit, A]`
- И многие другие эквивалентности!

Это помогает выбирать оптимальное представление данных для каждой задачи!

## Рекурсивные типы и списки

Рекурсивный тип - это тип, который определяется **через самого себя**. 
Как матрешка, которая содержит внутри себя такую же матрешку, но меньшего размера.

### Списки: математическая формула `μX.(1 + int*X)`

Давайте разберем эту формулу по частям:

`μX.(1 + int*X)` означает:

- `μX` - "наименьшее решение уравнения X = ..." (рекурсия)
- `1` - пустой список (конец)
- `int*X` - элемент списка и остаток списка
- `+` - либо пустой, либо элемент + остаток

```dotty
// Реализуем эту формулу в коде:
enum IntList:
  // 1 - пустой список (базовый случай рекурсии)
  case Nil

  // int * X - элемент и хвост (рекурсивный случай)
  case Cons(head: Int, tail: IntList)

object IntList:
  // Конструкторы для удобства
  // Пустой список
  def apply(): IntList = Nil
  // Список из одного элемента
  def apply(x: Int): IntList = Cons(x, Nil)
```

### Развернем формулу списка

Исходное уравнение: `X = 1 + int × X`

Подставляем само в себя:

```
X = 1 + int × X
  = 1 + int × (1 + int × X)
  = 1 + int + int × int × X
  = 1 + int + int × int × (1 + int × X)
  = 1 + int + int² + int³ × X
  = ... и так до бесконечности
```

**Что это значит на практике:**

`1 (пустой) + int (один элемент) + int² (два элемента) + int³ (три элемента) + ...`:

- Список может быть: пустым (`1`)
- Или содержать: один элемент (`int`)
- Или содержать: два элемента (`int × int`)
- Или содержать: три элемента (`int × int × int`)
- ... и так далее

### Бинарные деревья: формула `μX.(int + X*X)`

Теперь рассмотрим бинарные деревья:

`μX.(int + X*X)` означает:

- `μX` - рекурсивный тип
- `int` - лист с значением (конец)
- `X*X` - узел с двумя поддеревьями
- `+` - либо лист, либо узел с двумя поддеревьями

```dotty
// Реализация бинарного дерева:
enum BinTree:
  // int - лист со значением
  case Leaf(value: Int)
  // X * X - узел с левым и правым поддеревьями
  case Branch(left: BinTree, right: BinTree)

import BinTree.*

// Пример дерева:
//     •
//    / \
//   1   •
//      / \
//     2   3
val example: BinTree =
  Branch(
    Leaf(1),   // Левое поддерево
    Branch(    // Правое поддерево
      Leaf(2), //   Левое под-поддерево
      Leaf(3)  //   Правое под-поддерево
    )
  )
```

### Развернем формулу дерева

Исходное уравнение: `X = int + X × X`

Подставляем само в себя:

```
X = int + X × X
  = int + (int + X × X) × (int + X × X)
  = int + (int × int) + (int × X × X) + (X × X × int) + (X × X × X × X)
  = ... очень быстро усложняется!
```

**Что это значит на практике:**

- Дерево может быть: простым листом (`int`)
- Или: узлом с двумя листьями (`int × int`)
- Или: узлом с листом и поддеревом (`int × (int × int)`)
- Или: еще более сложными структурами

### Сравнение списков и деревьев

| Аспект             | Список                | Бинарное дерево           |
|--------------------|-----------------------|---------------------------|
| **Формула**        | `μX.(1 + int×X)`      | `μX.(int + X×X)`          |
| **Структура**      | Линейная цепочка      | Иерархическая             |
| **Рекурсия**       | Одна ссылка вперед    | Две ссылки (левый/правый) |
| **Базовый случай** | Пустой список (`Nil`) | Лист (`Leaf`)             |
| **Пример**         | `[1]→[2]→[3]→END`     | Дерево с ветвями          |

## Итого

### Основные преимущества АТД

#### **Безопасность типами**

**Компилятор становится вашим союзником** - он проверяет, что вы обработали все возможные случаи:

```dotty
enum PaymentMethod:
  case Cash
  case Card(number: String)
  case Crypto(wallet: String)

def processPayment(method: PaymentMethod) = method match
  case PaymentMethod.Cash      => println("Принята наличка")
  case PaymentMethod.Card(num) => println(s"Карта: $num")
  // Компилятор предупредит: "match may not be exhaustive"
  // Мы забыли случай Crypto!
```

**Результат:** Невозможно случайно пропустить важный случай обработки.

#### **Точность моделирования**

**Типы точно отражают предметную область** - нельзя создать некорректное состояние:

```dotty
// Плохо: можно создать пользователя без имени и без email одновременно
case class User(name: Option[String], email: Option[String])

// Хорошо: точно описываем возможные состояния
enum UserState:
  case Guest
  case Registered(name: String, email: String)
```

**Результат:** Код ясно выражает бизнес-логику.

#### **Легкость расширения**

**Добавляйте новые операции без изменения существующего кода**:

```dotty
enum Shape:
  case Circle(radius: Double)
  case Rectangle(width: Double, height: Double)

// Можно добавить новую операцию:
def toSvg(shape: Shape): String = shape match
  case Shape.Circle(r)       => s"<circle r='$r'/>"
  case Shape.Rectangle(w, h) => s"<rect width='$w' height='$h'/>"
```

**Результат:** Система легко адаптируется к новым требованиям.

#### **Улучшение читаемости кода**

Типы становятся самодокументируемыми - по сигнатуре функции понятно, что она делает и какие данные принимает.

#### **Композируемость**

Сложные типы строятся из простых, как из кубиков Лего:

```dotty
type UserAction  = Either[LoginCommand, PurchaseCommand]
type UserSession = (UserId, List[UserAction])
```

#### **Упрощение рефакторинга**

При изменении типа данных компилятор точно укажет все места, которые нужно обновить.

### Философский аспект

АТД меняют подход к программированию:

- **Вместо:** "Пишем код и надеемся, что он работает"
- **Получаем:** "Проектируем типы, и код почти пишется сам"

### Итог

Алгебраические типы данных - это не просто технический прием, а **способ мышления**, который позволяет:

- ✅ **Предотвращать ошибки** на этапе компиляции
- ✅ **Ясно выражать** намерения в коде
- ✅ **Строить надежные** системы, которые сложно сломать
- ✅ **Быстро развивать** приложения без страха что-то сломать

> Хорошо спроектированные типы ≈ меньше багов ≈ больше времени на реализацию функциональности! 

АТД превращают компилятор из "надзирателя, который ищет ошибки" в "помощника, который предотвращает ошибки" - и это меняет всё!
