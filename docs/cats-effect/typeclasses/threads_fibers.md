# Потоки и волокна

## Пропасть между потребностями и возможностями

Представьте, что вы разрабатываете современный микросервис, который должен обрабатывать **10,000 одновременных запросов**. 
Каждый запрос требует:

- Чтения данных из базы данных (10 мс)
- Вызова внешнего API (20 мс)
- Вычисления результата (5 мс)
- Отправки ответа (1 мс)

**Сколько потоков вам нужно?**

Если использовать традиционную модель "один поток на запрос", то **10,000 потоков**.

Но JVM не может эффективно работать с 10,000 потоков. 
Это **фундаментальное несоответствие** между тем, что нам нужно (одновременные действия), 
и тем, что может предоставить операционная система (ограниченное количество потоков).

### Цена потоков JVM

#### Память: невидимый убийца

```dotty
// Каждый поток JVM потребляет память
class ThreadMemory:
  def threadCost(): Unit =
    // Стек потока по умолчанию: 1 МБ
    // 1,000 потоков = 1 ГБ памяти только на стеки!
    // 10,000 потоков = 10 ГБ памяти

    // И это не считая:
    // - ThreadLocal переменные
    // - Контекстные данные
    // - Накладные расходы JVM (~1-2 КБ на поток)
    ()
```

**Реальность:**

- 1 поток ≈ 1 МБ памяти
- 10,000 потоков ≈ 10 ГБ RAM
- 100,000 потоков → OutOfMemoryError

#### Переключение контекста: скрытая стоимость

```dotty
class ContextSwitch:
  def cost(): Unit =
    // Переключение контекста потока: ~1-10 микросекунд

    val threads = 10000
    val switchesPerSecond = 100000

    // На 10,000 потоков планировщик ОС будет
    // переключаться между ними миллионы раз в секунду
    // Это может съедать ДО 30% CPU!
    ()
```

#### Проблемы сборщика мусора

```dotty
class GCProblems:
  def explain(): Unit = 
    // Каждый поток имеет:
    // - Стек (1 МБ) — корень для GC
    // - ThreadLocal переменные
    // - Ссылки на объекты

    // GC должен сканировать стеки ВСЕХ потоков
    // 10,000 потоков → 10 ГБ стеков → паузы GC по секундам!
    ()
```

### Несоответствие масштабов

#### Оптимальное количество потоков vs Реальное количество

```dotty
trait ConcurrencyParadox:
  // Теория: оптимальное количество потоков
  def optimalThreads(): Int =
    val cpuCores = Runtime.getRuntime.availableProcessors()
    // Обычно: CPU cores + 1 или CPU cores * 2
    // Для 8-ядерного сервера: 8-16 потоков
    cpuCores + 1

  // Реальность: нужно одновременно обслуживать
  def requiredConcurrency(): Int =
    // Веб-сервер: количество одновременных запросов
    // API-шлюз: количество соединений WebSocket
    // Система обмена сообщениями: количество подписчиков

    100000 // Тысячи, десятки тысяч

  // Разрыв: 16 vs 100,000 → в 6,250 раз!
```

#### Пример: Традиционный сервер Tomcat

```dotty
class TomcatLimitations:
  def explain(): Unit =
    // Tomcat использует пул потоков
    // maxThreads = 200 (обычно)
    // maxConnections = 10,000

    // Что происходит, когда приходит 10,000 запросов?
    // 200 запросов обрабатываются
    // 9,800 ждут в очереди на подключение

    // Время ожидания может быть огромным!
    // При 1 секунде на запрос: последний подождёт ~49 секунд
    ()
```

**Проблема:** Мы вынуждены ограничивать параллелизм не из-за бизнес-требований, а из-за технических ограничений ОС и JVM.

### Традиционные решения и их проблемы

#### Решение 1: Пул потоков

```dotty
class ThreadPoolSolution:
  private val pool = Executors.newFixedThreadPool(200)

  def handleRequest(request: Request): Future[Response] =
    // Проблемы:
    // 1. Блокирующие операции занимают потоки
    // 2. Нужно знать заранее, сколько потоков нужно
    // 3. Сложно масштабировать
    // 4. Ложное разделение (false sharing)

    pool.submit(() => process(request))
```

**Почему это не идеально:**

| Проблема        | Описание                                                                    |
|-----------------|-----------------------------------------------------------------------------|
| **Блокировка**  | Если 200 потоков ждут БД, новые запросы не обрабатываются                   |
| **Сложность**   | Нужно настраивать размер пула (слишком мало → очередь, слишком много → GC)  |
| **Задержки**    | Очереди запросов создают непредсказуемую задержку                           |
| **Ресурсы**     | Каждый поток потребляет память, даже если просто ждёт                       |

#### Решение 2: Асинхронные callback'и

```dotty
class CallbackHell:
  def handleRequest(request: Request, callback: Response => Unit): Unit =
    // "Callback hell" — классическая проблема
    db.query(
      request.id,
      (dbResult, error1) =>
        if error1 != null then
          callback(error1)
        else
          httpClient.call(
            dbResult.url,
            (httpResponse, error2) =>
              if error2 != null then
                callback(error2)
              else
                process(
                  httpResponse,
                  (result, error3) =>
                    // Ещё один уровень...
                    callback(result)
                )
          )
    )
end CallbackHell
```

**Почему это не идеально:**

| Проблема                  | Описание                                     |
|---------------------------|----------------------------------------------|
| **Callback hell**         | Вложенность делает код нечитаемым            |
| **Некомпозируемость**     | Нельзя просто соединить два callback-вызова  |
| **Управление ресурсами**  | Сложно гарантировать закрытие ресурсов       |
| **Ошибки**                | Легко забыть обработать ошибку в callback'е  |

#### Решение 3: CompletableFuture

```dotty
class CompletableFutureExample:
  def handleRequest(request: Request): CompletableFuture[Response] =
    return db.queryAsync(request.id)
      .thenCompose(dbResult -> httpClient.callAsync(dbResult.url))
      .thenApply(httpResponse -> process(httpResponse))
      .exceptionally(error -> handleError(error))
```

**Почему лучше, но всё ещё не идеально:**

| Проблема                     | Описание                                  |
|------------------------------|-------------------------------------------|
| **Отмена**                   | Сложно отменить цепочку операций          |
| **Ресурсы**                  | Нет автоматического управления ресурсами  |
| **Монадическая композиция**  | Не работает с for-comprehension           |
| **Типобезопасность**         | Легко получить ClassCastException         |

### Волокна как решение

#### Что такое волокно?

```dotty
trait Fiber[F[_], E, A]:
  def cancel: F[Unit]
  def join: F[Outcome[F, E, A]]

// Волокно — это "семантический" поток выполнения
// Легковесная абстракция, которая:
// 1. Не привязана к потоку ОС
// 2. Может быть приостановлена и возобновлена
// 3. Автоматически планируется рантаймом
```

#### Волокна в действии

```dotty
import cats.effect.IO

class FiberExample:
  def handleRequest(request: Request): IO[Response] =
    // Волокна настолько лёгкие, что мы можем создавать их миллионами!

    IO.defer:
      // Планируем 100,000 параллельных операций
      (1 to 100000).toList.parTraverse: id =>
        db.query(id).timeout(30.seconds)
```

#### Сравнение: Потоки vs Волокна

| Характеристика        | JVM Thread                | Cats Effect Fiber                 |
|-----------------------|---------------------------|-----------------------------------|
| **Память**            | ~1 МБ                     | ~128 байт                         |
| **Время создания**    | ~1 мс                     | ~100 нс                           |
| **Макс. количество**  | ~10,000                   | Неограниченно (миллионы)          |
| **Отмена**            | Сложная (interrupt)       | Встроенная                        |
| **Переключение**      | Системный вызов (~1 мкс)  | Пользовательский режим (~10 нс)   |
| **Планирование**      | ОС                        | Пользовательское (work stealing)  |


### Реальный пример масштабирования

#### Проблема: WebSocket сервер с 1,000,000 соединений

```dotty
// ❌ Решение на потоках — невозможно
class ThreadBasedWebSocket:
  // 1,000,000 потоков = 1 ТБ памяти
  def onOpen(session: WebSocketSession): Unit =
    new Thread(() =>
      while session.isOpen do
        val message = session.receive() // Блокирующий вызов
        process(message)
    ).start()

// ✅ Решение на волокнах — работает!
import cats.effect.IO
import cats.effect.std.Queue

class FiberBasedWebSocket:
  def onOpen(session: WebSocketSession): IO[Unit] =
    def handleMessages: IO[Unit] =
      for
        message <- session.receiveAsync // Неблокирующий
        _       <- process(message)
      yield ()

    // 1,000,000 волокон ≈ 128 МБ памяти!
    handleMessages.foreverM.start.void
```

### Волокна и отмена

#### Проблема отмены в потоках

```dotty
// ❌ Отмена потока Java — кошмар
class ThreadCancellationProblem:
  def downloadFile(url: String): Unit =
    val thread = new Thread(() =>
      val connection = url.openConnection()
      val stream     = connection.getInputStream()
      // Как отменить это?
      // Thread.interrupt() может не сработать
      // Нет гарантии, что stream закроется
    )
    thread.start()

    // Попытка отменить через 5 секунд
    Thread.sleep(5000)
    thread.interrupt() // ??? Не гарантирует остановку
```

#### Волокна и отмена

```dotty
// ✅ Отмена волокна Cats Effect — гарантированная
import cats.effect.IO
import scala.concurrent.duration.*

class FiberCancellation:
  def downloadFile(url: String): IO[Unit] =
    // Волокно, которое можно отменить
    val download = IO {
      val connection = url.openConnection()
      val stream     = connection.getInputStream()
      // Волокно автоматически проверяет отмену
      // при каждой асинхронной операции
      readStream(stream)
    }

    // Отмена гарантированно сработает через 5 секунд
    download.timeout(5.seconds)
```

### Волокна и композиция

#### Проблема композиции в асинхронном мире

```dotty
// Традиционный асинхронный код нельзя просто скомпоновать
def traditionalAsync(): Unit =
  // Как объединить два асинхронных вызова?
  asyncCall1((result1, err1) =>
    asyncCall2((result2, err2) => {
      // Уже два уровня вложенности...
    })
  )

  // Как распараллелить два вызова?
  asyncCall1(result1 =>
    asyncCall2(result2 => {
      // Они выполняются последовательно!
    })
  )
```

### Волокна решают проблему композиции

```dotty
// С волокнами код выглядит как синхронный!
def fiberComposition[F[_]: Spawn]: F[Unit] =
  for
    // Параллельное выполнение
    fiber1 <- asyncCall1.start
    fiber2 <- asyncCall2.start

    // Ожидание результатов
    result1 <- fiber1.joinWithNever
    result2 <- fiber2.joinWithNever

    // Композиция результатов
    _ <- process(result1, result2)
  yield ()
```

## Ключевые преимущества

1. **Масштабируемость**: Миллионы волокон вместо тысяч потоков
2. **Эффективность**: Наносекундные переключения вместо микросекундных
3. **Простота**: Код выглядит как синхронный, работает как асинхронный
4. **Безопасность**: Встроенная отмена и управление ресурсами
5. **Композиционность**: Легко комбинировать и переиспользовать

Когда использовать волокна:

| Сценарий                              | Потоки             | Волокна                  |
|---------------------------------------|--------------------|--------------------------|
| **CPU-интенсивные задачи**            | ✅ Подходит         | ✅ Подходит               |
| **IO-интенсивные задачи**             | ⚠️ Ограниченно     | ✅ Идеально               |
| **Высокая конкурентность (>10,000)**  | ❌ Не подходит      | ✅ Идеально               |
| **Реальное время**                    | ❌ Непредсказуемо   | ⚠️ Зависит от рантайма   |
| **Распределённые системы**            | ⚠️ Сложно          | ✅ Встроенная поддержка   |

**Волокна — это не просто оптимизация, это парадигмальный сдвиг.** 
Они позволяют писать конкурентный код так же просто, как последовательный, 
но с производительностью и масштабируемостью, недостижимой для традиционных потоков.

## Реальный пример: HTTP сервер на волокнах

Далее разберем рабочий пример **асинхронного HTTP-сервера**, построенного на концепции «волокон». 

```dotty
import cats.effect.{MonadCancel, Spawn}
import cats.effect.syntax.all.*
import cats.syntax.all.*

// Абстракции сервера и соединения
trait Server[F[_]]:
  def accept: F[Connection[F]]

trait Connection[F[_]]:
  def read: F[Array[Byte]]
  def write(bytes: Array[Byte]): F[Unit]
  def close: F[Unit]

// Конечная точка приложения
def endpoint[F[_]: Spawn](
    server: Server[F]
)(body: Array[Byte] => F[Array[Byte]]): F[Unit] =

  // Обработка одного соединения
  def handle(conn: Connection[F]): F[Unit] =
    for
      request  <- conn.read
      response <- body(request)
      _        <- conn.write(response)
    yield ()

  // Обработчик, который принимает соединения и запускает волокна
  val handler = MonadCancel[F].uncancelable: poll =>
    poll(server.accept).flatMap: conn =>
      handle(conn)
        .guarantee(conn.close) // Гарантируем закрытие
        .start                 // Запускаем в отдельном волокне!

  // Бесконечно обрабатываем соединения
  handler.foreverM
end endpoint
```

### Почему это работает? Разбор ключевого фрагмента

```dotty
// Каждый запрос получает СВОЁ волокно
val handler = MonadCancel[F].uncancelable: poll =>
  poll(server.accept).flatMap: conn => // Ждём новое соединение
    handle(conn)
      .guarantee(conn.close) // Гарантия закрытия
      .start                 // ← Волокно на запрос!
```

**Что здесь происходит по шагам:**

1. `server.accept` — блокирующая операция _в смысле эффекта_, но не блокирующая поток ОС. 
   Она приостанавливает текущее волокно до появления нового TCP-соединения.
2. Как только соединение получено, мы передаём его в `handle`, который читает запрос, 
   передаёт в бизнес-логику (`body`) и отправляет ответ.
3. `.guarantee(conn.close)` — обеспечивает **освобождение ресурса** (соединения) при любом исходе: успех, ошибка или отмена.
4. `.start` — **запускает обработку в фоновом волокне**, не дожидаясь её завершения. Текущее волокно сразу возвращается к ожиданию следующего соединения.

**Преимущества такого подхода:**

1. **Масштабируемость** — миллионы одновременных соединений (волокна занимают ~128 байт против ~1 МБ у потоков ОС).
2. **Безопасность** — `guarantee` закрывает соединение даже при отмене (например, если клиент разорвал связь или сервер остановлен).
3. **Простота** — код выглядит как синхронный (последовательный `for`), но внутри работает асинхронно и одновременно.

### Детальный разбор по частям (снизу вверх)

В этом примере происходит _много_ всего, но благодаря возможностям функционального программирования 
мы можем разбить его на крошечные фрагменты. Давайте начнем с самого конца:

```dotty
handler.foreverM
```

#### Что такое `foreverM`?

`foreverM` — это метод, который **повторяет эффект бесконечно**. Он определён для любого `F[A]` и работает так:

- Выполняет `handler`.
- Когда `handler` завершается (успешно или с ошибкой), `foreverM` **запускает его снова**.
- Единственный способ выйти из `foreverM` — это **фатальная ошибка** или **внешняя отмена** (например, при завершении всей программы).

Таким образом, `handler.foreverM` означает: «занимайся обработкой входящих соединений вечно, пока сервер не остановят».

### Анализ `handler`

```dotty
val handler = MonadCancel[F].uncancelable: poll =>
  poll(server.accept).flatMap: conn =>
    handle(conn).guarantee(conn.close).start
```

#### Зачем нужен `uncancelable`?

`uncancelable` — это [механизм защиты](monadcancel.md) критической секции от **прерывания**.
`uncancelable` гарантирует, что внутренний блок `{ ... }` не будет прерван извне. 
Вместо этого отмена будет «отложена» до выхода из блока.

Аргумент `poll` — это функция, которая позволяет [временно разрешить отмену](monadcancel.md) внутри защищённого блока. 
В данном случае `poll(server.accept)` означает: «операция принятия соединения _может_ быть отменена, а вот всё остальное — нет».

> Итог: `uncancelable` делает так, что соединение обязательно попадёт либо в `handle`, 
> либо будет закрыто, но не зависнет в промежуточном состоянии.

#### Разбор `poll(server.accept).flatMap`

- `server.accept` — эффект, который возвращает `Connection[F]`. Это может занять неопределённое время (ждём клиента).
- `poll(...)` разрешает отмену во время ожидания соединения. Это важно, чтобы сервер можно было остановить даже если он ничего не принимает.
- После получения `conn` мы уже внутри `flatMap` — здесь отмена уже заблокирована (действует `uncancelable`).

#### `handle(conn).guarantee(conn.close).start`

- `handle(conn)` — читает запрос, вызывает бизнес-логику, пишет ответ. Это **долгоиграющий** эффект.
- `.guarantee(conn.close)` — обеспечивает закрытие соединения **после** завершения `handle`, независимо от того, успешно оно или с ошибкой. 
  Даже если `handle` выбросит исключение или будет отменён — `close` выполнится.
- `.start` — ключевой момент: мы **не ждём** завершения `handle`. Вместо этого мы:
    1. Запускаем `handle` в новом фоновом волокне.
    2. Получаем объект `Fiber`, который представляет это выполняющееся волокно.
    3. Текущее волокно (то, которое выполняет `handler`) продолжает работу и сразу переходит к следующей итерации цикла `foreverM`.

Таким образом, каждое соединение обрабатывается в **своём собственном волокне**, а главный цикл приёма соединений никогда не блокируется.

### Что будет, если не использовать `.start`?

Если убрать `.start`:

```dotty
val handler = MonadCancel[F].uncancelable: poll =>
  poll(server.accept).flatMap: conn =>
    handle(conn).guarantee(conn.close)  // Нет .start!
```

Сервер будет **обрабатывать соединения последовательно**:

1. Принял соединение.
2. Прочитал запрос.
3. Выполнил бизнес-логику.
4. Отправил ответ.
5. Закрыл соединение.
6. Только после этого перешёл к следующему `accept`.

Это **последовательный сервер** — он не может обслужить второго клиента, пока не закончит с первым. 
Очевидно, это непригодно для реальных задач.

Таким образом, `.start` — это магия, превращающая последовательный код в конкурентный без изменения логики внутри `handle`.
