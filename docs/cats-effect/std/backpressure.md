# Backpressure — Управление потоком данных при перегрузках

`Backpressure` (обратное давление) — это механизм контроля потока, 
который позволяет системе **регулировать скорость обработки входящих задач**, когда ресурсы ограничены. 
Если задача поступает быстрее, чем система может её обработать, `Backpressure` применяет стратегию управления перегрузкой.

Представьте себе:

- **Кофейню**, где бариста может приготовить только 10 чашек кофе в час. 
  Если заходит 20 клиентов, `Backpressure` решает, что делать с "лишними" заказами.
- **Сервер API**, обрабатывающий 1000 запросов в секунду, но база данных выдерживает только 800. 
  `Backpressure` не даст БД "захлебнуться".

```dotty
trait Backpressure[F[_]]:
  /** Запускает эффект f, применяя стратегию ограничения скорости. */
  def metered[A](f: F[A]): F[Option[A]]
```

**Внимание:** `Backpressure` возвращает `F[Option[A]]`, а не `F[A]`. 
Потому что в зависимости от стратегии и текущей нагрузки, эффект может быть **отброшен** — тогда вернётся `None`.

## Две стратегии: `Lossy` и `Lossless`

`Backpressure` можно создать с одной из двух стратегий поведения при переполнении:

### 1. Lossy (с потерями)

> **"Если система перегружена — просто игнорируй новую задачу."**

- Эффект **не будет** выполнен, если в данный момент действует обратное давление.
- Новый вызов возвращает `None` мгновенно, без блокировки.
- Подходит для сценариев, где **можно потерять некоторые данные** без серьёзных последствий.

### 2. Lossless (без потерь)

> **"Если система перегружена — встань в очередь и жди."**

- Эффект **будет выполнен**, но вызывающее волокно **семантически блокируется** до тех пор, пока не освободится ресурс.
- Возвращает `Some(result)`, когда задача наконец выполнена.
- Подходит для сценариев, где **нельзя терять данные** (например, платёжные транзакции, заказы).

## Как это работает под капотом?

`Backpressure` внутри содержит:

- **Счётчик активных задач** (текущая загрузка).
- **Максимальное количество параллельных задач** (limit `n`).
- **Очередь ожидания** (для стратегии `Lossless`).

```
Входящий вызов metered(f)
         │
         ▼
    достигнут лимит?
         │
    ┌────┴────┐
    ❌         ✅
    │         │
    │         └──────► выполнить f
    │                    (активных задач +1)
    │
    ▼
  ┌─────────────────┐
  │  Стратегия?     │
  └─────────────────┘
    │           │
 Lossy       Lossless
    │           │
    ▼           ▼
  вернуть     поставить в очередь
    None       и заблокировать
              волокно
```

Когда задача завершается, счётчик активных задач уменьшается → если есть ожидающие в очереди (Lossless), 
один из них разблокируется и начнёт выполнение.

## Пример 1: Lossless — очередь задач с ограниченным параллелизмом

Допустим, у нас есть сервис, который может обрабатывать не более 2 задач одновременно. 
Мы хотим, чтобы ни одна задача не потерялась.

```dotty
import cats.effect.{IO, IOApp}
import cats.effect.std.Backpressure
import cats.syntax.all.*

import scala.concurrent.duration.*

object LosslessExample extends IOApp.Simple:
  val run: IO[Unit] =
    for
      // Создаём Backpressure с лимитом 2 активных задачи, стратегия Lossless
      backpressure <- Backpressure[IO](Backpressure.Strategy.Lossless, 2)

      // Запускаем 5 "долгих" задач (каждая по 2 секунды)
      fibers <- (1 to 5).toList.traverse { i =>
        backpressure.metered(
          IO.sleep(2.seconds) *> IO.println(s"✅ Задача $i завершена")
        ).start
      }

      // Ждём завершения всех
      _ <- fibers.traverse_(_.join)
    yield ()
    
// Спустя 2 секунды    
// ✅ Задача 1 завершена
// ✅ Задача 2 завершена
// Спустя 2 секунды 
// ✅ Задача 3 завершена
// ✅ Задача 4 завершена
// Спустя 2 секунды 
// ✅ Задача 5 завершена    
```

**Ожидаемое поведение:**

- Первые 2 задачи стартуют сразу.
- Задачи 3, 4, 5 **блокируются** (но не теряются).
- Как только одна из первых двух завершается, третья задача стартует, и так далее.
- В конце **все 5 задач будут выполнены** (Lossless гарантирует это).

## Пример 2: Lossy — телеметрия / метрики (потеря допустима)

Представьте, что мы собираем метрики от миллионов сенсоров, но обрабатывать можем только 10 в секунду. 
Потеря некоторых метрик не страшна — важны лишь те, что успевают обработаться.

```dotty
import cats.effect.{IO, IOApp}
import cats.effect.std.Backpressure
import scala.concurrent.duration.*
import cats.syntax.all.*

object LossyExample extends IOApp.Simple:
  val run: IO[Unit] =
    for
      // Лимит: 3 параллельных метрики, потеря разрешена
      backpressure <- Backpressure[IO](Backpressure.Strategy.Lossy, 3)

      // Симуляция 50 входящих метрик
      _ <- (1 to 50).toList.traverse { i =>
        backpressure.metered(
          IO.sleep(500.millis) *> IO.println(s"📊 Метрика $i обработана")
        ).flatMap {
          case Some(_) => IO.unit // обработано
          case None    => IO.println(s"⚠️ Метрика $i отброшена (перегрузка)")
        }
      }
    yield ()
```

**Результат:** Сначала несколько метрик обработается, но когда лимит 3 достигнут, 
новые вызовы начнут возвращать `None` мгновенно. 
Система не захлёбывается, но часть данных теряется.

## Когда использовать `Backpressure`, а когда — другие примитивы?

| Инструмент                   | Назначение                                | Поведение при перегрузке                                         |
|:-----------------------------|:------------------------------------------|:-----------------------------------------------------------------|
| **`Backpressure.Lossless`**  | Ограничение параллелизма с ожиданием      | Задачи блокируются, но не теряются                               |
| **`Backpressure.Lossy`**     | Ограничение параллелизма с отбрасыванием  | Лишние задачи игнорируются                                       |
| **`Semaphore`**              | Ограничение параллелизма                  | Задачи блокируются, но без понятия "отбрасывания" (все ждут)     |
| **`Queue.bounded`**          | Буферизация задач                         | Очередь ограничена, производитель может блокироваться (`offer`)  |
| **`Queue.dropping`**         | Буферизация с отбрасыванием               | Переполненные элементы отбрасываются                             |
| **`Dispatcher`**             | Запуск из нечистого кода                  | Нет обратного давления — все эффекты запускаются                 |

**Вывод:** `Backpressure` — это специализированный `Semaphore` + дополнительная логика для потока задач, 
где можно либо блокироваться (Lossless), либо отбрасывать (Lossy) новые задачи, когда лимит достигнут.

## Детали реализации и предостережения

### 1. `Backpressure` не является `Resource`

В примерах выше мы создаём `Backpressure` через `Backpressure[IO](strategy, limit)`, 
и он живёт до тех пор, пока есть ссылка на него. При сборке мусора активные задачи и очередь будут потеряны. 
Если нужно гарантированное завершение, оберните в `Resource`:

```dotty
def backpressureResource[F[_]: Concurrent](
    strategy: Backpressure.Strategy,
    limit: Int
): Resource[F, Backpressure[F]] =
  Resource.make(Backpressure[F](strategy, limit))(_ =>
    ???
  ) // остановка не требуется (нет ресурсов)
```

Но на практике `Backpressure` не занимает системных ресурсов (кроме памяти), поэтому `Resource` не обязателен.

### 2. Отмена задач

Если волокно, ожидающее в очереди `Lossless`, будет отменено, оно корректно удалится из очереди, 
и счётчик активных задач не пострадает.

### 3. Гонки при создании

Создание `Backpressure` (через `apply`) дешёвое, но использует `Ref` и `Deferred` под капотом. 
Создавайте его один раз на весь пул задач, а не на каждую метрику.

### 4. Размер очереди для Lossless

`Backpressure` не имеет настраиваемого размера очереди ожидания — она потенциально неограничена. 
Если вы ожидаете огромное количество заблокированных волокон (миллионы), `Lossless` может потребить много памяти. 
В таких случаях рассмотрите `Queue.bounded`.

## Итог

**Ключевая идея:** `Backpressure` — это декларативный способ сказать системе: 
_«Не берись за новую задачу, если мы уже перегружены. Если потерять задачу можно — сразу верни `None`, если нет — встань в очередь и жди»_. 
Это идеальный инструмент для написания **устойчивых к перегрузкам** и **саморегулируемых** приложений.
