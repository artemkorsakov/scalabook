# Tracing — трассировка стека

Трассировка (tracing) — это расширенная функция `IO`, которая предоставляет разработчикам детальную информацию 
о графе выполнения волокна (fiber). Это открывает огромные возможности в области **отладки и интроспекции** — 
не только в локальных средах разработки, но и в критически важных production-окружениях.

### Проблема: асинхронный код убивает трассировку стека

Одной из существенных проблем при работе с асинхронным кодом на JVM является то, 
что **трассировка стека больше не предоставляет ценного контекста** о пути выполнения программы.

Почему так происходит?

```dotty
// Синхронный код — трассировка стека полезна
def syncProgram(): Int =
  val a = computeA()  // строка 5
  val b = computeB(a) // строка 6
  a + b // строка 7
// Ошибка в computeB покажет трассировку: syncProgram -> computeB

// Асинхронный код — трассировка стека теряет контекст
def asyncProgram: IO[Int] =
  for
    a <- IO(computeA())  // стек: IO.map → IOFiber.runLoop → ...
    b <- IO(computeB(a)) // стек: тот же самый, без указания на строки выше
  yield a + b
```

В синхронном мире каждый вызов функции добавляет кадр в стек. При возникновении исключения вы видите чёткую цепочку вызовов. 
В асинхронном мире (и особенно в `Future`, где после каждой операции вставляется асинхронная граница) эта цепочка **теряется**.

`IO` страдает от аналогичной проблемы. Более того, даже при полностью синхронном выполнении программы на `IO`, 
трассировка стека **загрязняется** внутренними методами реализации цикла выполнения `IO` 
(такими как `IOFiber.runLoop`, `IOFiber.execR`, `WorkerThread.run` и т.д.), 
которые не имеют никакого отношения к пользовательскому коду.

### Решение: асинхронная трассировка стека

`IO` решает эту проблему, собирая трассировку стека в различных операциях `IO` по мере выполнения волокна (fiber) 
и объединяя их для получения более целостного, значимого представления о пути выполнения.

Но трассировка в Cats Effect — это не только сбор и объединение кадров стека. Это целый комплекс взаимосвязанных возможностей:

1. **Асинхронная трассировка стека (Async Stack Tracing)**: Сбор кадров стека через асинхронные границы для данного волокна.
2. **Вывод конструктора/комбинатора (Constructor/Combiner Inference)**: Трассировки стека используются для определения того, 
   какой конкретный конструктор или комбинатор `IO` был вызван пользовательским кодом. 
   Например, `void` и `as` — это комбинаторы, производные от `map`, и они должны появляться в трассировке, а не сам `map`. 
   То же самое относится и к конструкторам `IO`, таким как `async` 
   (который внутри состоит из множества низкоуровневых деталей реализации), — 
   ни одна из этих деталей не должна попадать в итоговую трассировку.
3. **Безопасный для JVM и GC кэш трассировочной информации**: Начиная с версии 3.2, 
   Cats Effect использует API платформы `java.lang.ClassValue` — нативное решение для кэширования JVM, которое обеспечивает:
    - **Безопасность загрузчика классов (ClassLoader Safety)**: Длительно работающие приложения Cats Effect 
      полностью учитывают динамические среды загрузки классов, освобождая ссылки на выгруженные классы по указанию JVM, 
      что помогает сборщику мусора.
    - **Бесблокировочные структуры данных (Lock-Free Data Structures)**: Нативные для JVM и JIT-компилятора, 
      что даёт максимальную производительность. 
      Переход на `ClassValue` повысил производительность на 5-10% по сравнению с предыдущей реализацией кэширования.
4. **Улучшения производительности полной (некэшированной) трассировки**: Cats Effect 3 — это полная переработка проекта. 
   Был пересмотрен и оптимизирован процесс сбора информации о трассировке стека, 
   что привело к улучшению производительности **до 5 раз** по сравнению с предыдущим механизмом. 
   Это даёт заметное ускорение отладки в режиме `full` (см. ниже).
5. **Расширенная обработка исключений (Enhanced Exceptions)**: Исключения, возникающие в пользовательском коде, 
   перехватываются средой выполнения Cats Effect. Из них удаляются ненужные внутренние кадры (фреймы реализации `IO`) 
   и добавляется информация об асинхронной трассировке стека, 
   собранная во время выполнения (включая информацию о конструкторах и комбинаторах `IO`). 
   Только после этого обогащённое исключение представляется пользователю.

### Важное предостережение о производительности

Трассировка стека (особенно в режиме `full`) приводит к дополнительным затратам: более высокая загрузка CPU, 
дополнительное потребление памяти и нагрузка на GC. 
**Всегда тестируйте производительность вашего приложения с включённой и выключенной трассировкой** 
перед развертыванием в production!

## Конфигурация трассировки

Режим трассировки стека приложения настраивается системным свойством JVM:

```
-Dcats.effect.tracing.mode=<режим>
```

Для JavaScript используется переменная окружения:

```bash
CATS_EFFECT_TRACING_MODE=<режим>
```

Существует **три режима** трассировки (значения нечувствительны к регистру):

| Режим                        | Описание                                                                                                                                                   | Производительность                                                                  | Когда использовать                                                                                                                 |
|:-----------------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------------------------|
| **`cached`** (по умолчанию)  | Трассировка стека захватывается и **кэшируется** для каждого вызова `map`, `flatMap`, `async` и т.д. Кэш индексируется по ссылке на класс лямбда-функции.  | Высокая (<<30% оверхед в синтетических тестах, в реальных приложениях — незаметно)  | **Production (рекомендуется)** — даёт отличный баланс между полезной информацией и производительностью.                            |
| **`full`**                   | Трассировка стека собирается **при каждом** вызове комбинатора/конструктора `IO`.                                                                          | Низкая (значительное снижение производительности)                                   | **Разработка и отладка** — когда `cached` даёт неточную трассировку (см. предупреждение ниже) или нужна максимальная детализация.  |
| **`none`**                   | Трассировка **полностью отключена**. Все связанные с ней структуры данных и операции удаляются из кода.                                                    | Максимальная (минимальные накладные расходы)                                        | Высокопроизводительные приложения с жёсткими требованиями к задержкам, где информация трассировки не нужна.                        |

### Настройка буфера трассировки

Чтобы предотвратить неограниченное использование памяти, 
информация о трассировке для каждого волокна накапливается во внутреннем буфере. 
Если собрано больше трассировок, чем может вместить буфер, самая старая информация **перезаписывается**.

- **Размер буфера по умолчанию:** `16`
- **Настройка (JVM):** `-Dcats.effect.tracing.buffer.size=<размер>`
- **Настройка (JS):** `CATS_EFFECT_TRACING_BUFFER_SIZE=<размер>`

**Важно:** Значение должно быть **степенью двойки** (2, 4, 8, 16, 32, 64, 128...). 
Если вы укажете другое число, оно будет автоматически округлено до ближайшей степени двойки.

### Пример конфигурации

```bash
# Включить полную трассировку с буфером 1024 (JVM)
java -Dcats.effect.tracing.mode=full -Dcats.effect.tracing.buffer.size=1024 -jar my-app.jar

# Включить кэшированную трассировку с буфером 256 (Node.js)
export CATS_EFFECT_TRACING_MODE=cached
export CATS_EFFECT_TRACING_BUFFER_SIZE=256
node my-app.js
```

### Специфика для Scala.js

- **Рекомендация:** Установите npm-пакет [source-map-support](https://www.npmjs.com/package/source-map-support). 
  Это позволит использовать source maps для получения трассировок стека с **номерами строк исходного Scala-кода**, 
  а не с номерами строк сгенерированного JS-кода.
- **Ограничение:** Трассировка в Scala.js поддерживается **только в режиме `fastLinkJS`** (fastOptJS). 
  В режиме `fullLinkJS` (fullOptJS) трассировка **полностью отключена**, 
  а соответствующий код вырезается из сборки для максимальной производительности.

## Режимы трассировки стека: глубокое погружение

### Режим `none`

- **Что происходит:** Трассировка полностью отключена. Все структуры данных и операции, связанные со сбором информации о стеке, отсутствуют.
- **Размер объектов:** Объекты `IO` и внутренние структуры волокон становятся немного меньше (на ~8-16 байт).
- **Производительность:** Идентична гипотетическому циклу выполнения `IO` без поддержки трассировки.
- **Когда использовать:** Production-среды, где каждый лишний цикл CPU на счету, 
  а информация о трассировке не нужна (например, высокочастотные трейдинговые системы, игровые серверы).

### Режим `cached` (по умолчанию)

**Как работает:**

1. При первом вызове комбинатора (например, `map` на конкретной лямбде) захватывается трассировка стека.
2. Эта трассировка **кэшируется** и привязывается к **классу лямбда-функции**.
3. При последующих вызовах того же комбинатора с той же лямбдой используется кэшированная трассировка.

**Производительность:**

- Синтетические тесты показывают оверхед **менее 30%** для программ с интенсивным использованием `IO` 
  (сочетание синхронных и асинхронных комбинаторов).
- В реальных приложениях, которые выполняют полезную работу (I/O, вычисления), фактический оверхед **значительно ниже**.
- Важно понимать: `IO` даже с включённой трассировкой всё равно **на порядки быстрее** эквивалентной программы на Scala `Future`. 
  Цифры в 30% относятся к микро-бенчмаркам, которые гипертрофируют разницу.

**⚠️ Предупреждение: когда `cached` может давать неточные трассировки**

Кэш индексируется по **ссылке на класс лямбда-функции**. Это приводит к проблемам в следующих случаях:

1. **Композиция монадных трансформеров (Monad Transformer Composition):**
   При использовании `OptionT[IO, *]` или `EitherT[IO, *]` задействованные лямбда-функции могут быть обернуты 
   и повторно использованы таким образом, что нарушается однозначное соответствие между классом лямбда-функции и местом вызова.

2. **Использование именованной функции в нескольких местах:**

```dotty
// Проблема: одна и та же функция multiplyByTwo
// используется в трёх разных местах
def multiplyByTwo(x: Int): Int = x * 2

val program =
  for
    a <- IO(1).map(multiplyByTwo) // Кэш для multiplyByTwo
    b <- IO(2).map(multiplyByTwo) // Используется тот же кэш!
    c <- IO(3).map(multiplyByTwo) // Тот же кэш
  yield (a, b, c)
// Трассировка стека будет показывать ОДИНАКОВЫЙ стек для всех трёх вызовов,
// хотя на самом деле они происходят в разных местах `a`, `b` и `c`.
```

**Рекомендация:** Если вы подозреваете неточности в трассировке (например, видите одинаковые строки для разных вызовов), 
временно переключитесь на режим `full` для отладки.

### Режим `full`

**Как работает:** Трассировка стека захватывается **при каждом** вызове комбинатора/конструктора `IO`. Кэш не используется.

**Производительность:** Значительное снижение производительности по сравнению с `cached`. 
Оверхед может составлять **сотни процентов** для CPU-интенсивных программ.

**Когда использовать:**

- **Исключительно для отладки** в среде разработки.
- Когда `cached` даёт слишком неточные трассировки (например, при активном использовании трансформеров или переиспользуемых функций).
- Для написания тестов, где важна детерминированность трассировок.

**Никогда не используйте `full` в production!**

## Расширенная обработка исключений (Enhanced Exceptions)

### Проблема: «грязные» и бесполезные стектрейсы

Без трассировки (или при `none`) стектрейс исключения, пойманного `IO`, выглядит так:

```
Exception in thread "main" java.lang.Throwable: Boom!
        at Example$.$anonfun$program$5(Main.scala:25)
        at cats.effect.IO.$anonfun$ifM$1(IO.scala:409)
        at cats.effect.IOFiber.runLoop(IOFiber.scala:383)
        at cats.effect.IOFiber.execR(IOFiber.scala:1126)
        at cats.effect.IOFiber.run(IOFiber.scala:125)
        at cats.effect.unsafe.WorkerThread.run(WorkerThread.scala:359)
```

**Что здесь плохо?**

1. **Много шума:** `IOFiber.runLoop`, `execR`, `WorkerThread.run` — это внутренности Cats Effect, 
   не имеющие отношения к пользовательскому коду.
2. **Потерян контекст:** Цепочка вызовов `fib → flatMap → ...` полностью исчезла. 
   Вы видите только самую последнюю операцию (`Example$.$anonfun$program$5`). 
   В сложных асинхронных программах это делает отладку практически невозможной.

### Решение: обогащённые исключения (Enhanced Exceptions)

Когда включена асинхронная трассировка (режимы `cached` или `full`), 
Cats Effect **обогащает** перехваченные исключения кадрами из асинхронной трассировки стека. 
При этом **все внутренние кадры `IO` удаляются**.

**Результат (тот же пример с включённой трассировкой):**

```
Exception in thread "main" java.lang.Throwable: Boom!
        at Example$.$anonfun$program$5(Main.scala:25)
        at apply @ Example$.$anonfun$program$3(Main.scala:24)
        at ifM @ Example$.$anonfun$program$3(Main.scala:25)
        at map @ Example$.$anonfun$program$3(Main.scala:24)
        at apply @ Example$.$anonfun$program$1(Main.scala:23)
        at flatMap @ Example$.$anonfun$program$1(Main.scala:23)
        at apply @ Example$.fib(Main.scala:13)
        at flatMap @ Example$.fib(Main.scala:13)
        ... (ещё много кадров из рекурсивной fib)
        at flatMap @ Example$.program(Main.scala:22)
        at run$ @ Example$.run(Main.scala:10)
```

**Что мы видим теперь?**

- **Чёткая цепочка вызовов:** `program → fib (многократно) → ifM → map → flatMap → apply → exception`.
- **Никаких внутренних кадров `IO`:** Стек чист от реализации.
- **Информативные аннотации:** `apply @`, `flatMap @`, `ifM @` — каждая асинхронная операция помечена комбинатором, который её породил.

Эта информация невероятно полезна для отладки сложных асинхронных программ, 
позволяя быстро локализовать источник ошибки даже через десятки асинхронных границ и монадных трансформеров.

### Конфигурация Enhanced Exceptions

Функция расширенных исключений управляется системным свойством (или переменной окружения):

- **Включено (по умолчанию):** `-Dcats.effect.tracing.exceptions.enhanced=true`
- **Отключено:** `-Dcats.effect.tracing.exceptions.enhanced=false`

### Пример кода для генерации трассировок

```dotty
import cats.effect.{IO, IOApp}
import scala.util.Random

object Example extends IOApp.Simple:
  // Рекурсивная функция для демонстрации глубокого стека
  def fib(n: Int, a: Long = 0, b: Long = 1): IO[Long] =
    IO(a + b).flatMap: b2 =>
      if n > 0 then fib(n - 1, b, b2)
      else IO.pure(b2)

  def program: IO[Unit] =
    for
      x <- fib(20) // Глубокий рекурсивный вызов
      _ <- IO.println(s"The 20th fibonacci number is $x")
      // Генерируем исключение случайным образом
      _ <- IO(Random.nextBoolean()).ifM(
        ifTrue = IO.raiseError(new Throwable("Boom!")),
        ifFalse = IO.unit
      )
    yield ()

  override def run: IO[Unit] = program
end Example
```

## Итог и рекомендации

| Роль                               | Режим                  | Enhanced               | Буфер              | Обоснование                                                                                                                                           |
|:-----------------------------------|:-----------------------|:-----------------------|:-------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Локальная разработка**           | `full` (или `cached`)  | `true` (по умолчанию)  | 64-256             | Максимальная информация для отладки. `full` даёт точные стеки, но медленнее.                                                                          |
| **Production (стандарт)**          | `cached`               | `true`                 | 16 (по умолчанию)  | Лучший баланс. Кэширование даёт хорошую производительность, а enhanced exceptions — ценный контекст для ошибок.                                       |
| **Production (высокая нагрузка)**  | `none`                 | `false`                | N/A                | Если критичны CPU и память, а стектрейсы ошибок можно восстановить другими способами (логирование, метрики).                                          |
| **Отладка кэша (cached)**          | `full` (временно)      | `true`                 | 16                 | Если вы подозреваете, что кэш даёт неточные трассировки, временно включите `full`, чтобы получить точные данные и понять, нужно ли переписывать код.  |
