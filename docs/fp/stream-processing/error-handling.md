# Обработка ошибок в функциональных потоках

В функциональном программировании мы стремимся делать побочные эффекты и ошибки явными 
и управлять ими с помощью классов типов и комбинаторов. 

## Базовый тип `Task`: Отложенные вычисления с ошибками

В основе лежит тип `Task[A]`, представляющий собой **отложенное (ленивое) вычисление**, 
которое при выполнении может либо успешно вернуть значение типа `A`, либо завершиться с исключением (`Throwable`).

**Реализация:** `Task[A]` реализован как обёртка вокруг `IO[Try[A]]`.

- `IO[_]` отвечает за отложенность и возможные побочные эффекты.
- `Try[_]` (который может быть `Success(value)` или `Failure(exception)`) отвечает за явное хранение результата или ошибки.

**Ключевая идея:** `Task` позволяет работать с вычислениями, которые могут завершиться с ошибкой, 
используя обычные комбинаторы (например, `map`, `flatMap`), как будто ошибок не существует, 
до тех пор, пока вы явно не решите их обработать.

**Разбор примера:**

```dotty
// Создание Task, который при выполнении упадёт с NumberFormatException
val a: Task[Int] = Task("asdf".toInt) 

// `map` применяется к "успешному пути". Т.к. `a` упадет, `map` проигнорируется.
val b: Task[Int] = a.map(_ + 1) 

// `attempt` — комбинатор, который "вытаскивает" результат из монадического контекста.    
// Теперь мы имеем не `Task[Int]`, а `Task[Try[Int]]`. 
// Это значит: "вычисление, которое гарантированно завершится успешно, вернув либо успех, либо неудачу". 
val c: Task[Try[Int]] = b.attempt     
                                      
// Запускаем вычисление. `d` будет содержать `Failure(NumberFormatException)`.                          
val d: Try[Int] = c.unsafeRunSync(pool) 
```

**Аналогия с `Try` и `Either`:** `Task` можно рассматривать как асинхронный, ленивый аналог `Try`. 
Он добавляет "канал ошибок" поверх `IO`, так же как `Try` добавляет его поверх обычных вычислений.

## Класс типов `MonadThrow`: Унифицированный интерфейс для ошибок

Чтобы абстрагироваться от конкретного типа эффекта (`Task`, `IO`, `SyncTask` и т.д.), 
который может содержать ошибки, введем класс типов [MonadError](../../typeclass/monad/monad-error.md).

**Назначение:** Описывает возможности [монады](../../typeclass/monad/monad.md) `F`, которая также может:

1.  Создавать вычисление, заведомо завершающееся ошибкой (`raiseError`).
2.  Позволять извлечь результат вычисления в виде `Try` (`attempt`).
3.  Обрабатывать ошибки, преобразуя их в новый эффект (`handleErrorWith`).

**Определение:**

```dotty
trait MonadThrow[F[_]] extends Monad[F]:
  // "Поднять" исключение в контекст эффекта F
  def raiseError[A](t: Throwable): F[A]

  // Извлечь результат из эффекта: превратить F[A] в F[Try[A]]
  extension [A](fa: F[A])
    def attempt: F[Try[A]]

    // Обработать ошибку. Похож на `flatMap`, но для канала ошибок.
    def handleErrorWith(h: Throwable => F[A]): F[A] =
      attempt.flatMap {
        // Если была ошибка, запускаем handler
        case Failure(t) => h(t)
        // Если успех, возвращаем его обратно в контекст F
        case Success(a) => unit(a)
      }
```

## Добавление обработки ошибок в `Stream` и `Pull`

Библиотека потоков построена на двух основных типах:

- `Stream[F, O]` — последовательность выходных значений `O`, создаваемая с помощью эффектов `F`.
- `Pull[F, O, R]` — более низкоуровневая инструкция, описывающая процесс генерации потока или его завершения с результатом `R`.

Чтобы потоки тоже могли обрабатывать ошибки, в `Pull` добавляется новый `case Handle`:

```dotty
enum Pull[+F[_], +O, +R]:
  // Новый конструктор: источник + обработчик ошибок
  case Handle(
      // Исходный Pull
      source: Pull[F, O, R],
      // Функция, вызываемая в случае ошибки в `source`
      handler: Throwable => Pull[F, O, R]
  ) extends Pull[F, O, R]

  // Комбинатор для удобного использования
  def handleErrorWith[F2[x] >: F[x], O2 >: O, R2 >: R](
      handler: Throwable => Pull[F2, O2, R2]
  ): Pull[F2, O2, R2] =
    Pull.Handle(this, handler)
```

Затем этот комбинатор поднимается на уровень `Stream` через метод расширения.

**Важное следствие:** Алгоритм интерпретации (`step`) потока теперь **требует**, 
чтобы тип эффекта `F` имел экземпляр `MonadThrow[F]`, а не просто `Monad[F]`. 
Это потому, что в процессе интерпретации `step` должен уметь ловить и обрабатывать ошибки, 
которые могут возникнуть при выполнении эффектов `F`.

### Общая цель метода `step` для `Pull.Handle`

Метод `step` — это интерпретатор (или машина состояний). Его задача:
**Выполнить один шаг вычисления `Pull` и вернуть результат этого шага.**
Результат может быть одним из трёх вариантов, обёрнутых в эффект `F2`:

1.  `Left(r)` — `Pull` завершился (не обязательно ошибкой!) финальным результатом `R2`.
2.  `Right((o, next))` — `Pull` выдал выходное значение `o` и следующее состояние `next` (оставшийся `Pull`).
3.  _Неявно:_ В эффекте `F2` может произойти ошибка (если `F2` — это `Task`, то может быть выброшено исключение).

Конструктор `Handle(source, handler)` говорит: "Интерпретируй `source`, 
и если во время его интерпретации возникнет ошибка, поймай её и запусти `handler(ошибка)`".

#### Детальный разбор реализации

Разберём код по частям:

```dotty
def step[F2[x] >: F[x], O2 >: O, R2 >: R](
  using F: MonadThrow[F2]
): F2[Either[R2, (O2, Pull[F2, O2, R2])]] =
  this match
    ...
    case Handle(source, f) =>
      source match
        case Handle(s2, g) =>
          s2.handleErrorWith(x =>
            g(x).handleErrorWith(y => f(y))).step
        case other =>
          other.step
            .map:
              case Right((hd, tl)) => Right((hd, Handle(tl, f)))
              case Left(r) => Left(r)
            .handleErrorWith(t => f(t).step)
```

#### Часть 1: Обработка вложенных обработчиков (Left-associatedHandle)

```dotty
case Handle(source, f) => // this - это Handle(source, f)
  source match // Смотрим, что лежит в `source`
    case Handle(s2, g) => // Если источник САМ является обработчиком
      s2.handleErrorWith(x => g(x).handleErrorWith(y => f(y))).step
```

**Проблема:** У нас есть конструкция вида `Handle(Handle(s2, g), f)`. Это похоже на вложенные блоки `try-catch`.

**Цель:** Переписать левоассоциативные обработчики в правоассоциативные. 
Это стандартная практика в функциональных библиотеках для обеспечения стековой безопасности и предсказуемой семантики.

**Аналогия:**

Исходный код: `try { try { s2 } catch { case x => g(x) } } catch { case y => f(y) }`
Мы хотим превратить это в один большой `try` с двумя обработчиками: 
`try { s2 } catch { case x => try { g(x) } catch { case y => f(y) } }`

**Как это работает:**

1. Берем самый внутренний источник `s2`.
2. Говорим: "Если в `s2` возникнет ошибка `x`:
    1. Первым делом передадим её _внутреннему_ обработчику `g(x)`.
    2. Но вычисление `g(x)` тоже может упасть с ошибкой `y`!
    3. Если `g(x)` падает, то ошибку `y` нужно передать уже _внешнему_ обработчику `f(y)`.
3. К результату этого преобразования применяем `.step`, чтобы интерпретировать уже новый, переписанный `Pull`.

**Итог:** Этот случай гарантирует, что вложенные `Handle` будут обработаны в правильном порядке: 
сначала внутренний (`g`), затем внешний (`f`).

#### Часть 2: Обработка "простого" источника

Это самый главный и частый случай, когда `source` — это не `Handle`, а любой другой конструктор `Pull` 
(например, `Output` или `Eval`).

```dotty
case other => // source - это не Handle, а что-то другое (Output, Eval и т.д.)
  other.step // (A) Выполняем шаг исходного Pull
    .map: // (B) Если шаг завершился УСПЕШНО в эффекте F2, мы обрабатываем результат...
      case Right((hd, tl)) => Right((hd, Handle(tl, f))) // ...успех с выходными данными
      case Left(r) => Left(r) // ...успешное завершение
    .handleErrorWith(t => f(t).step) // (C) Если шаг завершился ОШИБКОЙ в эффекте F2
```

Давайте разберём по шагам, что здесь происходит.

**Шаг A: `other.step`**

- Мы запускаем интерпретацию исходного `Pull` (`other`).
- Тип возвращаемого значения: `F2[Either[R2, (O2, Pull[F2, O2, R2])]]`.
- Ключевой момент: этот вызов `.step` может завершиться **успешно** внутри эффекта `F2` (вернув `Left` или `Right`) 
  или **упасть с ошибкой** внутри эффекта `F2` (например, в `Task` это будет `Failure(exception)`).

Дальнейшая обработка разделяется на два пути: **успешный результат** (обрабатывается в `.map`) 
и **ошибка** (обрабатывается в `.handleErrorWith`).

**Шаг B: Успешный путь (обработка в `.map`)**

Метод `.map` применяется к _успешному результату_ внутри `F2`.

```dotty
.map:
  case Right((hd, tl)) => Right((hd, Handle(tl, f)))
  case Left(r) => Left(r)
```

- **Случай `Right((hd, tl))`**: Шаг исходного `Pull` выдал выходные данные `hd` и остаток `tl`.
    - **Что делаем:** Мы должны выдать данные `hd` наружу. Но! Наш обработчик ошибок `f` ещё не использовался. 
      Мы не можем его просто выбросить, ведь ошибка может произойти на _следующем_ шаге при интерпретации `tl`.
    - **Решение:** Мы возвращаем данные `hd` и **продолжаем** обёртывание. 
      Мы говорим: "Следующим состоянием будет `Handle(tl, f)`", 
      то есть оставшуюся часть `tl` нужно интерпретировать с тем же обработчиком `f`.
    - **Аналогия:** Мы успешно прочитали один элемент из файла. Мы его возвращаем, но говорим, 
      что чтение следующего элемента всё ещё должно быть защищено тем же `try-catch`.
- **Случай `Left(r)`**: Исходный `Pull` успешно завершился с результатом `r`.
    - **Что делаем:** Просто возвращаем этот результат `Left(r)`. 
      Обработчик `f` не понадобился, так как завершение было успешным.

**Шаг C: Путь ошибки (обработка в `.handleErrorWith`)**

Метод `.handleErrorWith` перехватывает ошибку, если **Шаг A** упал с ошибкой внутри эффекта `F2`.

```dotty
.handleErrorWith(t => f(t).step)
```

- **`t: Throwable`** — это ошибка, которая возникла при выполнении `other.step`.
- **`f: Throwable => Pull[F2, O2, R2]`** — это обработчик, переданный в конструктор `Handle`.
- **Что происходит:** Мы "падаем" с ошибкой `t`. 
  Вместо того чтобы позволить ошибке распространиться и привести к краху всего потока, 
  мы ловим её и говорим: "Вместо этой ошибки выполни вычисление `f(t)`".
  Но `f(t)` возвращает нам новый `Pull` (например, поток-заглушку или логирующий поток). 
  Нам нужно его не просто вернуть, а **интерпретировать**.
  Поэтому мы берём результат обработчика `f(t)` и немедленно вызываем на нём `.step`.
- **Итог:** Ошибка, возникшая при интерпретации `source`, перехватывается и преобразуется в вычисление, 
  которое запускается вместо неё. Это вычисление, в свою очередь, тоже интерпретируется на этом же шаге.

**Аналогия:** Это точный эквивалент блока `catch` в `try-catch`. В блоке `try` у нас `other.step`. 
Если он падает, управление переходит в блок `catch`, где мы выполняем `f(t).step`.

#### Итог всего алгоритма

Метод `step` для `Handle` делает следующее:

1. **Оптимизация:** Переписывает вложенные обработчики из левой ассоциативности в правую для правильной и предсказуемой обработки.
2. **Интерпретация:** Интерпретирует внутренний источник (`source`).
3. **Обработка результатов:**
    - **Успех с данными:** Возвращает данные и "надвигает" обработчик на хвост вычисления.
    - **Успешное завершение:** Просто возвращает результат завершения.
    - **Ошибка:** Перехватывает ошибку, передаёт её обработчику и интерпретирует _результат работы обработчика_ 
      как следующее состояние всего `Pull`.

Это элегантный и чисто функциональный способ реализовать семантику `try-catch` 
для сложной композиционной структуры данных (`Pull`), используя существующие комбинаторы из класса типов `MonadThrow`.

## Комбинатор `onComplete`

На основе `handleErrorWith` и `raiseError` можно построить полезный комбинатор высшего уровня `onComplete`:

```dotty
enum Pull[+F[_], +O, +R]:
  ...

  case Error(t: Throwable) extends Pull[Nothing, Nothing, Nothing]
    
object Stream:
  def raiseError[F[_], O](t: Throwable): Stream[F, O] =
    Pull.Error(t)

  extension [F[_], O](self: Stream[F, O])
    def onComplete(that: => Stream[F, O]): Stream[F, O] =
      self.handleErrorWith(t => that ++ raiseError(t)) ++ that
```

**Семантика:** Выполнить поток `that` **после** завершения исходного потока `self`, 
**независимо от того, как оно завершилось** (успехом или ошибкой). 
Если `self` завершился ошибкой, эта ошибка будет перевыброшена _после_ выполнения `that`.

### Проблема с управлением ресурсами и `onComplete`

Позволяет ли `onComplete` безопасно получать и освобождать ресурсы, такие как дескрипторы файлов?

**Правильный, но некомпозируемый подход:**

```dotty
// Ресурс открывается и используется в одном непрерывном потоке
Stream.eval(acquire("file")).flatMap { resource =>
  use(resource)        // Поток, использующий ресурс
    .onComplete(Stream.eval(release(resource))) // Освобождение в конце
}
// Это работает, потому что весь "жизненный цикл" ресурса заключен в один `flatMap`.
```

**Проблемный подход (после рефакторинга):**

```dotty
Stream.eval(acquire("file")).flatMap { resource =>
  Stream.eval(Task(source.getLines))    // Часть использования ресурса
    .flatMap(itr => Stream.fromIterator(itr))
    .onComplete(Stream.eval(release(resource))) // Освобождение здесь...
} // ... но flatMap заканчивается, и ресурс `resource` уходит из области видимости!
.mapEval(line => Task(println(line)))   // ... а обработка происходит здесь, снаружи!
```

**Почему это ломается:**

1. **Область видимости:** Переменная `resource` существует только внутри блока `flatMap`. 
   Комбинатор `onComplete` сохраняет её в замыкании, но это опасный паттерн.
2. **Композиция:** Если последующий `.mapEval` выбросит исключение, обработчик `onComplete` **не будет вызван**, 
   так как он был частью внутреннего потока, который уже успешно завершился, передав данные дальше. 
   Ошибка возникнет "снаружи" от области действия `onComplete`.
3. **Раннее завершение:** Если после `onComplete` поставить `.take(10)`, поток завершится после 10 элементов, 
   и `onComplete` (а значит, и `release`) никогда не будет вычислен.

**Вывод:** `onComplete` — не тот инструмент, который дает **гарантированное** освобождение ресурса. 
Для этого нужны более мощные механизмы, например, 
которые управляют жизненным циклом напрямую и являются композируемыми.
Мы рассмотрим этот механизм в следующей главе.

## Последствия для элиминаторов (Eliminators)

Элиминаторы — это функции вроде `runLog` или `compile.toList`, которые запускают поток 
и преобразуют его в одно итоговое значение в эффекте `F` (например, `F[List[O]]`).

**Ключевое изменение:** После добавления обработки ошибок сигнатура элиминаторов должна измениться.

Раньше было:

```dotty
def toList(implicit F: Monad[F]): F[List[O]]
```

Теперь стало:

```dotty
def toList(implicit F: MonadThrow[F]): F[List[O]]
```

Это означает, что мы не сможем запустить `Stream[IO, Int]`, если для `IO` не определен экземпляр `MonadThrow`. 
Это осознанный компромисс: функциональность обработки ошибок требует более строгих ограничений на тип эффекта.

## Специальный случай: потоки без эффектов (`SyncTask`)

Для тестирования или вычислений без эффектов потоки могут интерпретироваться в специальную монаду `TailRec` (для хвостовой рекурсии). 
Но `TailRec` сама по себе не умеет работать с ошибками.

**Решение:** Создать новый тип `SyncTask[A]`, который будет представлять собой `TailRec[Try[A]]`. 
Для этого типа можно легко определить экземпляр `MonadThrow`, "спрятав" `Try` внутрь вычисления `TailRec`. 
Это позволяет использовать всю новую функциональность обработки ошибок и в режиме без эффектов.

```dotty
opaque type SyncTask[A] = TailRec[Try[A]]
```

## Итог

1. **Явность:** Ошибки — это не исключения, а часть типа (`Try` внутри `Task`).
2. **Абстракция:** Классы типов (`MonadThrow`) позволяют писать обобщённый код для обработки ошибок в любых подобных монадах.
3. **Композиция:** Комбинаторы (`handleErrorWith`, `onComplete`) строятся из простых кирпичиков (`attempt`, `flatMap`) 
   и позволяют декларативно описывать логику обработки сбоев.
4. **Компромиссы:** Добавление новой функциональности (ошибки) ужесточает требования к типам 
   (требуется `MonadThrow` вместо `Monad`) и меняет API элиминаторов.
5. **Осторожность с ресурсами:** Не каждый комбинатор подходит для гарантированного управления ресурсами. 
   Нужно использовать правильные абстракции (`bracket`/`Resource`).
