# Копирование файлов

Давайте напишем программу, которая копирует файлы. Сначала мы разработаем чистую функцию, выполняющую копирование, 
а затем встроим её в исполняемое приложение для командной строки.

```dotty
// Что мы хотим в итоге
def copy[F[_]](origin: File, destination: File): F[Long]
```

Функция принимает исходный и целевой файлы, а возвращает **описание** эффекта, 
который при своём выполнении скопирует данные и вернёт количество скопированных байт.

## Проблема: побочные эффекты и чистота

В императивном программировании мы бы написали примерно так:

```dotty
// Императивный подход (НЕ функциональный!)
def copyImperative(src: File, dst: File): Long =
  val in  = new FileInputStream(src)  // побочный эффект!
  val out = new FileOutputStream(dst) // побочный эффект!
  try
    val buffer     = new Array[Byte](8192)
    var bytesRead  = 0
    var totalBytes = 0L
    while {
      bytesRead = in.read(buffer)
      bytesRead != -1
    } do
      out.write(buffer, 0, bytesRead)
      totalBytes += bytesRead
    totalBytes
  finally
    in.close()  // побочный эффект!
    out.close() // побочный эффект!
```

**Проблемы этого подхода для функционального программирования:**

1. **Побочные эффекты в каждом вызове** — чтение, запись, закрытие изменяют внешний мир.
2. **Исключения** — `try/catch` нарушает [ссылочную прозрачность](../fp/fp/pure_function.md).
3. **Неуправляемая отмена** — если процесс копирования нужно прервать, нет безопасного механизма.
4. **Блокировка потоков** — при копировании больших файлов поток ОС заблокирован.

В Cats Effect мы решаем эти проблемы, поднимая побочные эффекты в **описание** (`F[_]`), 
которое сохраняет чистоту и даёт контроль над выполнением.

## Классы типов: определяем необходимые возможности

Функция `copy` будет параметризована эффектом `F[_]`. Но какими возможностями должен обладать `F`? Перечислим требования:

| Требование                | Почему важно                                                   | Какой класс типов нужен                                     |
|:--------------------------|:---------------------------------------------------------------|:------------------------------------------------------------|
| **Работа с ошибками**     | Файл может не существовать, диск переполнен, нет прав доступа  | `MonadError[F, Throwable]`                                  |
| **Отмена выполнения**     | Пользователь нажал Ctrl+C, копирование слишком долгое          | [`MonadCancel[F, Throwable]`](typeclasses/monadcancel.md)   |
| **Блокирующие операции**  | `read`/`write` на уровне ОС блокируют поток                    | [`Sync[F]` (предоставляет `blocking`)](typeclasses/sync.md) |
| **Управление ресурсами**  | Гарантированное закрытие потоков при ошибке или отмене         | [`Resource` (строится на `MonadCancel`)](std/resource.md)   |

### Почему не `IO` везде?

Может возникнуть соблазн сразу зафиксировать `F = IO` и не заморачиваться с классами типов:

```dotty
// ❌ Плохо: слишком конкретный тип
def copy(origin: File, destination: File): IO[Long]
```

**Проблема:** Функция с `IO` говорит: "Я могу всё: запускать волокна, делать тайм-ауты, конкурентные гонки". 
Но для копирования файлов нужен лишь малый поднабор возможностей. Сужение типа до `Sync[F]`:

- **Документирует намерение** — читатель сразу видит: "Здесь будут только синхронные эффекты, никакой магии с волокнами".
- **Облегчает тестирование** — можно подставить фейковый эффект.
- **Защищает от ошибок** — новый разработчик случайно не напишет внутри `copy` вызов `.start` или `.race`, нарушив логику копирования.

**Принцип наименьшей мощности (Least Power Principle):** Используйте самый слабый класс типов, который решает задачу.

Выбираем **`Sync[F]`**. Он предоставляет:

- `F.delay` — обёртка побочного эффекта.
- `F.blocking` — специальная обёртка для блокирующих операций (указывает планировщику выделить отдельный поток).
- Наследует `MonadCancel` и `MonadError`, так что отмена и ошибки уже включены.

```dotty
import cats.effect.Sync
import java.io.File

def copy[F[_]: Sync](origin: File, destination: File): F[Long] = ???
```

## Управление ресурсами: вводим `Resource`

Чтобы открыть файловые потоки и гарантированно закрыть их (даже при ошибке или отмене), используем `Resource[F, A]`.

Создадим отдельные функции для открытия `InputStream` и `OutputStream`:

```dotty
import cats.effect.{Resource, Sync}
import cats.syntax.all.*
import java.io.{File, FileInputStream, FileOutputStream}

def inputStream[F[_]: {Sync, Logger}](
    f: File
): Resource[F, FileInputStream] =
  Resource.make {
    Sync[F].blocking(new FileInputStream(f)) // acquire
  } { inStream =>
    // логируем ошибку, но не даём упасть
    Sync[F].blocking(inStream.close())
      .handleErrorWith { error =>
        Logger[F].error(error)("Не смог закрыть исходный файл")
      } // release
  }

def outputStream[F[_]: {Sync, Logger}](
    f: File
): Resource[F, FileOutputStream] =
  Resource.make {
    Sync[F].blocking(new FileOutputStream(f))
  } { outStream =>
    Sync[F].blocking(outStream.close())
      .handleErrorWith { error =>
        Logger[F].error(error)("Не смог закрыть целевой файл")
      }
  }  
```

**Ключевые моменты:**

- **`Resource.make(acquire)(release)`** — создаёт ресурс. `acquire` выполнится при создании, `release` — при финализации.
- **`Sync[F].blocking`** — помечает операцию как блокирующую, чтобы Cats Effect могла перенести её в специальный пул потоков (не блокируя основные).
- **`.handleErrorWith` в `release`** — ошибка при закрытии не должна "убить" финализацию других ресурсов 
  (например, если закрыть `InputStream` не удалось, `OutputStream` всё равно нужно закрыть).

### Композиция ресурсов

Объединим два ресурса в один кортеж:

```dotty
def inputOutputStreams[F[_]: {Sync, Logger}](
    in: File,
    out: File
): Resource[F, (InputStream, OutputStream)] =
  for
    inStream  <- inputStream(in)
    outStream <- outputStream(out)
  yield (inStream, outStream)  
```

**Гарантии:** если `outStream` открыть не удалось (например, нет прав на запись), то `inStream` будет немедленно закрыт.

## Реализация копирования: композиция ресурсов и логики

После того как мы определили безопасное получение потоков через `Resource`, следующим шагом будет реализация функции `copy`. 
Её задача — связать ресурсы (потоки) и логику копирования, гарантируя, что ресурсы будут освобождены независимо от результата.

```dotty
def copy[F[_]: {Sync, Logger}](
    origin: File,
    destination: File
): F[Long] =
  inputOutputStreams(origin, destination).use { (in, out) =>
    transfer(in, out)   // (*)
  }
```

**Анатомия вызова:**

1. `inputOutputStreams(...)` создаёт `Resource[F, (InputStream, OutputStream)]`. 
   На этом этапе никакие файлы ещё не открыты — это только описание.
2. Вызов `.use` — критическая точка. Именно здесь Cats Effect выполняет `acquire` (открывает потоки) 
   и передаёт их в функцию, которую вы предоставляете `{ (in, out) => ... }`.
3. Внутри блока `use` мы вызываем `transfer(in, out)`, которая выполняет фактическое копирование.
4. **Гарантия:** когда `use` завершится (успешно, с ошибкой или по отмене), 
   Cats Effect **обязательно** выполнит `release` для всех ресурсов, причём в обратном порядке: сначала закроет `out`, потом `in`.

Важные следствия из семантики [`Resource`](std/resource.md):

- Если `in` не удалось открыть (файл не найден), `out` даже не начнёт открываться.
- Если `in` открылся, но `out` открыть не удалось (нет прав на запись), `in` будет **немедленно закрыт** 
  (`release` для `in` отработает автоматически).
- Никакой утечки дескрипторов файлов не происходит — даже в многопоточном конкурентном окружении.

> `transfer` — это новая функция, которая будет выполнять фактическое копирование данных после получения ресурсов (потоков). 
> Когда они больше не нужны, независимо от исхода `transfer` (успеха или неудачи) оба потока будут закрыты. 
> Если какой-то из потоков получить не удалось, то `transfer` запускаться не будет.

## Копирование данных: пишем `transfer`

Функция `transfer` должна:

1. Читать данные из `InputStream` в буфер.
2. Записывать данные из буфера в `OutputStream`.
3. Повторять, пока файл не кончится (`read()` вернёт `-1`).
4. Подсчитывать количество переданных байтов.
5. Делать всё это **без переполнения стека** и с возможностью **отмены** в безопасных точках.

Базовый цикл рекурсивен. Это функциональная замена императивному `while`.

```dotty
def transfer[F[_]: Sync](
    origin: InputStream,
    destination: OutputStream
): F[Long] =
  val buffer = new Array[Byte](1024 * 10) // 10 KB буфер

  def loop(acc: Long): F[Long] = ???

  loop(0L)
```

Детально реализуем `loop`:

```dotty
def loop(acc: Long): F[Long] =
  for
    bytesRead <- Sync[F].blocking(origin.read(buffer, 0, buffer.length))
    // Если прочитано -1 (конец файла), возвращаем накопленную сумму
    result <- if bytesRead == -1 then
      Sync[F].pure(acc) // конец потока, возвращаем результат
    else
      // Записываем прочитанный блок
      Sync[F].blocking(destination.write(buffer, 0, bytesRead)) >>
        loop(acc + bytesRead)
  yield result
```

**Ключевые детали реализации:**

- **`Sync[F].blocking`** используется для всех операций ввода-вывода. 
  Это сигнал планировщику Cats Effect: "Эта операция может блокировать поток ОС". 
  Планировщик [выделяет для таких операций отдельные потоки](typeclasses/sync.md), чтобы не блокировать основные потоки.
- **Рекурсия** — поскольку `F` строится [на отложенных операциях](../fp/external-effects/stack_overflow_error.md), 
  рекурсия безопасна и не ведёт к переполнению стека. 
- **`>>`** — оператор последовательности из Cats. `a >> b` эквивалентно `a.flatMap(_ => b)`, 
  т.е. выполняет `a`, затем `b`, игнорируя результат `a`. Здесь: записали данные → продолжаем рекурсию.
- **Счётчик `acc`** — увеличивается на каждой итерации на количество прочитанных байтов (`amount`).

Если во время работы возникнет какое-либо исключение в `transfer` (например, диск заполнился или пропала сеть), 
то **потоки будут автоматически закрыты `Resource`**. 
Вы даже не должны думать об этом — Cats Effect гарантирует выполнение `release` блоков при любом исходе.

## Работа с отменой: почему это безопасно

[Отмена](typeclasses/monadcancel.md) — мощная, но нетривиальная функция cats-effect. 
Некоторые `F` экземпляры могут быть отменены (например, если они запущены параллельно через `.start` или внутри `.race`). 
Отмена означает, что выполнение будет прервано. Но Cats Effect предоставляет чёткие гарантии.

**Ключевая гарантия:**

Код, обёрнутый в `Sync[F].blocking`, **не может быть отменён посередине**. 
Cats Effect ожидает завершения блокирующей операции (чтения или записи). 
Отмена может произойти **только между** двумя `blocking` вызовами.

Например:

```dotty
for
  a <- Sync[F].blocking(origin.read(buffer))  // Точка отмены: ДО и ПОСЛЕ
  b <- Sync[F].blocking(destination.write(...)) // Точка отмены: ДО и ПОСЛЕ
yield ...
```

Если отмена приходит **во время выполнения** `origin.read(buffer)`, 
Cats Effect подождёт, пока `read()` завершится (вернёт управление),
и только затем прервёт выполнение, перейдя к финализаторам `Resource`.

**Что происходит с ресурсами при отмене?**

К счастью, `Resource` упрощает отмену. Если `F` внутри `Resource.use` отменяется, 
Cats Effect **автоматически запускает освобождение (`release`) всех задействованных ресурсов**. 
В нашем примере это означает, что:

1. Текущий вызов `transmit` может быть отменён после завершения очередной итерации.
2. Управление передаётся в `.use`.
3. `.use` выполняет `release` для `out` (закрывает файл), затем `release` для `in`.
4. Все дескрипторы закрыты, данные не повреждены.

Пользователь программы (например, нажавший Ctrl+C) получает мгновенный отклик, а система остаётся в консистентном состоянии. 
Без `Resource` пришлось бы вручную отслеживать флаг "отменено" и закрывать потоки в `finally` — что подвержено ошибкам.

## Финальная программа: `IOApp`

Теперь, когда у нас есть чистая функция `copy[F[_]]`, мы можем создать конкретную программу для командной строки. 
Для этого используем `IOApp` — "функциональный" эквивалент традиционного `App` из Scala.

`IOApp` позволяет:

- Определить чистую функцию `run: IO[ExitCode]`.
- Автоматически обрабатывать сигналы ОС (Ctrl+C) как отмену `IO`.
- Обеспечить выполнение `IO` с правильным планировщиком и пулом потоков.

### Реализация `run`

```dotty
import cats.effect.*
import cats.syntax.all.*
import org.typelevel.log4cats.Logger
import org.typelevel.log4cats.slf4j.Slf4jLogger

import java.io.*

object CopyFiles extends IOApp:

  // Логгер для IO (имплисит передаётся автоматически)
  private given Logger[IO] = Slf4jLogger.getLogger[IO]

  override def run(args: List[String]): IO[ExitCode] =
    for
      // 1. Валидация аргументов
      _ <- if args.length < 2 then
             IO.raiseError(
               new IllegalArgumentException("Не указаны исходный и целевой файлы")
             )
           else IO.unit

      // 2. Подготовка File объектов
      orig = new File(args.head)
      dest = new File(args(1))

      // 3. Вызов чистой функции копирования
      count <- copy[IO](orig, dest)

      // 4. Логирование результата
      _ <- Logger[IO].info(
        s"$count bytes copied from ${orig.getPath} to ${dest.getPath}"
      )
    yield ExitCode.Success
```

**Что здесь важно:**

- **`args.length`** — проверяем входные параметры. `IO.raiseError` поднимает ошибку внутри `IO`. 
  Поскольку `IO` реализует `MonadError`, дальнейшие шаги (`orig = ...`, `copy`) не будут выполнены, а ошибка будет перехвачена.
- **`copy[IO](orig, dest)`** — вызываем нашу полиморфную функцию, конкретизируя `F = IO`. 
  Благодаря тому, что `IO` реализует экземпляр `Sync`, всё компилируется.
- **`Logger[IO].info`** — логируем результат. Обратите внимание, что логирование само по себе — эффект, и оно встроено в цепочку.

### Почему это лучше, чем `java.nio.file.Files.copy`?

Можно возразить, что использование `IO { java.nio.file.Files.copy(src, dst, options) }` даст `IO` те же характеристики чистоты, что и наша функция.

**Но есть критическое различие:**

- `IO { Files.copy(...) }` — это чёрный ящик, который нельзя отменить. Он будет выполняться до конца, блокируя поток. 
  Нажатие Ctrl+C никак не повлияет на копирование.
- Наш `copy` построен на `Resource` и `Sync[F].blocking`. Его можно **отменить** в любой безопасной точке (между чтениями). 
  При отмене файловые дескрипторы будут закрыты, а система не останется в половинчатом состоянии.

Эта отменяемость становится критичной, если `copy[F]` используется как часть более крупной системы, 
где таймауты или параллельные гонки требуют прерывания долгих операций.

## Итог: как не бояться отмены

1. **Пользуйтесь `Resource` для всего, что можно "открыть и закрыть".** Он автоматически обрабатывает отмену.
2. **Обёртывайте операции ввода-вывода в `Sync[F].blocking`.** Это говорит планировщику, что операцию не следует прерывать до её естественного завершения.
3. **Пишите рекурсивные циклы через `flatMap` (или for-comprehension).** Cats Effect оптимизирует их.
4. **Используйте `IOApp` в конечной программе.** Она свяжет чистые описания с реальным выполнением, обработкой сигналов и пулом потоков.

Итоговая структура программы:

```dotty
object CopyFiles extends IOApp:
  def transfer[F[_]: Sync](in: InputStream, out: OutputStream): F[Long] = // рекурсивный цикл
  def copy[F[_]: Sync](orig: File, dest: File): F[Long] = // Resource.use
  def run(args: List[String]): IO[ExitCode] = // IOApp точка входа
```

Теперь у вас есть не просто функция копирования, а **конкурентно-безопасная, отменяемая и чистая** абстракция, 
которую можно использовать в любой `F`, реализующей `Sync`.
