# Конкуренция за резервные ресурсы (Overcommitment)

> Этот сценарий специфичен для **Kubernetes**, **Amazon ECS** и аналогичных контейнерных развертываний с управлением ресурсами.

В мире контейнерной оркестрации распространена практика **избыточного выделения ресурсов (overcommitment)**. 
Кластеру выделяется определённое количество физических CPU, но контейнерам «обещается» (в лимитах) больше ядер, 
чем есть на самом деле, в расчёте на то, что они не будут использовать их все одновременно.

Допустим, у вас есть физический сервер с 32 ядрами. Вы настраиваете контейнерный оркестратор так, 
чтобы он выделял контейнерам в сумме 64 виртуальных ядра, надеясь, что не все приложения одновременно будут нагружать CPU на 100%. 
Коэффициент избыточного выделения (overcommit factor) здесь равен 2 (или 100% overcommit). 
Это стандартная стратегия _для большинства приложений_, потому что они далеко не всегда используют CPU на полную мощность.

**Проблема:** Cats Effect — это **не** «большинство приложений». 
Приложения на Cats Effect, особенно написанные с учётом всех рекомендаций, 
**очень хорошо** утилизируют все доступные им процессоры. 
Вычислительный пул work-stealing постоянно активен. Если вы дадите Cats Effect приложению лимит в 4 CPU, 
оно будет пытаться использовать **все 4**, причём постоянно.

Теперь представьте, что на одном физическом хосте с 32 ядрами вы разместили 16 контейнеров, 
каждому из которых выделено по 4 CPU (лимит). Но 16 × 4 = 64 ядра, а физически доступно только 32. 
Коэффициент избыточного выделения — 2. Если все 16 приложений Cats Effect одновременно попытаются утилизировать 
свои ядра на 100% (например, в час пик), возникнет **симметричная пиковая нагрузка**. 
Авиакомпания продала билеты на 64 места, а мест в самолёте — 32. Все пассажиры пришли на рейс. 
Это **конкуренция за резервные ресурсы**. 
Ядро ОС вынуждено постоянно переключать контекст между 64 потоками, которые "хотят" работать, но физически могут работать только 32. 
Результат — катастрофическое падение производительности и гарантированное голодание.

**Решение:** **Устраните избыточное выделение ресурсов (overcommitment).** 
Если контейнеру обещано `n` CPU, эти CPU должны быть физически зарезервированы за ним на всё время работы.

Этот совет прекрасно сочетается с предыдущим: **приложениям Cats Effect выгоднее использовать «более высокие» 
(с большим числом CPU) и «менее широкие» (меньше реплик) развертывания.**

**Пример:**

- **Кластер:** 16 хостов, каждый с 64 CPU. Всего доступно 1024 CPU.
- **Плохая конфигурация (с overcommit):** Каждый контейнер получает лимит 4 CPU, вы запускаете 256 контейнеров. 
  Overcommit factor = 1 (максимум). При пиковой нагрузке все 256 контейнеров будут конкурировать за 1024 CPU. Это **не масштабируется**.
- **Хорошая конфигурация (без overcommit):** Каждый контейнер получает лимит 16 CPU. Вы запускаете 64 контейнера. 
  Конкуренции нет. За счёт лучшей локальности кэша и отсутствия переключений контекста, 64 мощных контейнера, 
  вероятно, обработают больший трафик, чем 256 слабых.

## Привязка CPU в Kubernetes (CPU Pinning)

Даже если вы избежали overcommit'а, планировщик ядра Linux всё равно может активно «мешать». 
Он может перемещать рабочие потоки Cats Effect между разными физическими ядрами CPU, 
нарушая **привязку потока к ядру (thread affinity)**, которая так важна для поддержания горячего кэша L1/L2.

В Kubernetes это можно предотвратить, настроив **привязку CPU (CPU Pinning)** для вашего пода:

1. **Настройте политику управления CPU в kubelet:** Установите политику `static`.
2. **Обеспечьте класс QoS `Guaranteed` для пода:** Все контейнеры в поде должны иметь `requests` и `limits` по CPU, равные друг другу.
3. **Запросите целое количество CPU:** В `resources.limits.cpu` и `resources.requests.cpu` укажите целое число (например, `8`, а не `8500m`).

После этого вы увидите в логах kubelet сообщения о назначении CPU (например, `cpumanager updated ...`). 
Это зарезервирует за вашим контейнером изолированные физические ядра, 
к которым не будут допущены другие контейнеры (и даже системные процессы).

## Конфликт процессов (Process Contention)

Все предыдущие советы предполагали **единственный значимо активный процесс** на экземпляре — ваш `java`-процесс Cats Effect. 
Если это не так (например, на одном сервере работают и ваше Java-приложение, и Postgres, и Nginx), 
то ситуация становится **гораздо хуже**. 
Конкуренция за CPU возникает уже не между потоками одного процесса, а между разными процессами. 
Это может привести к **квадратичному снижению производительности**, 
поскольку каждый процесс имеет свой собственный планировщик (Cats Effect внутри JVM и планировщик ОС для Postgres), 
которые не знают друг о друге и активно конфликтуют.

**Диагностика:** Используйте `top`, `htop` или `pidstat`. Если вы видите, что **любой** другой процесс 
(кроме вашего приложения и системных процессов ядра) стабильно потребляет более 5-10% CPU, это верный признак конфликта процессов.

**Решение:** Выделите каждому критичному по задержке приложению **отдельный экземпляр (виртуальную машину, ноду кластера)**. 
Не смешивайте их. В контексте Kubernetes это означает использование `taints` и `tolerations` 
для изоляции рабочих нагрузок или выделение отдельных нод (node pools) для разных типов приложений.
