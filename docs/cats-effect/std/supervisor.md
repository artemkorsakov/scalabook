# Supervisor — Управление жизненным циклом волокон

## Мотивация: проблема со `start` и `background`

[`Spawn`](../typeclasses/spawn.md) предоставляет два основных способа запуска [волокон](../foundation/fibers.md), 
но у каждого есть ограничения:

### 1. `start` — "запустил и забыл"

```dotty
fiber <- fa.start  // Волокно B запущено в фоне
```

**Жизненный цикл:**

```
Жизненный цикл волокна A (создатель)
+-----------------------------------+
|                                   |
|   A запускает B                   |
|   ↓                               |
|   Жизненный цикл волокна B        |
|   +-------------------------+     |
|   |                         |     |
|   |                         |     |
|   +-------------------------+     |
|                                   |
+-----------------------------------+
```

**Проблема:** Волокно `B` живёт **независимо** от `A`. 
Даже если `A` завершится или упадёт с ошибкой, `B` продолжит выполняться в фоне. 
Это может привести к:

- Утечке ресурсов (волокно "висит" вечно)
- Неожиданному поведению при ошибках
- Сложности с отладкой

### 2. `background` — связанный жизненный цикл

```dotty
Resource.eval(fa.background).use { fiber =>
  // используем fiber
}
```

**Жизненный цикл:**

```
Жизненный цикл волокна A (создатель)
+-----------------------------------+
|                                   |
|   Жизненный цикл волокна B        |
|   +-------------------------+     |
|   |   A запускает B         |     |
|   |                         |     |
|   +-------------------------+     |
|                                   |
+-----------------------------------+
```

**Особенность:** Волокно `B` **привязано** к жизненному циклу `A`. 
Когда `A` завершается, `B` **автоматически отменяется**.

**Проблема:** А что, если `B` должно жить **дольше**, чем `A`? Например:

- `A` — HTTP-обработчик запроса, который запускает фоновую задачу
- Задача должна продолжить выполнение даже после того, как ответ отправлен клиенту
- Но мы всё ещё хотим иметь возможность отменить все такие задачи при завершении всего сервера

## Supervisor: Решение для "долгоживущих" фоновых задач

`Supervisor` — это **менеджер волокон**, который:

1. Создаёт и запускает дочерние волокна.
2. Привязывает их жизненный цикл к **своему собственному** жизненному циклу.
3. Позволяет дочерним волокнам **пережить** создателя.
4. Гарантирует их остановку при завершении супервизора.

### Базовый интерфейс

```dotty
trait Supervisor[F[_]]:
  /** Запускает волокно под управлением супервизора. Возвращает волокно, которое
    * можно отменить вручную до завершения супервизора.
    */
  def supervise[A](fa: F[A]): F[Fiber[F, Throwable, A]]

object Supervisor:
  /** Создаёт супервизор как Resource.
    *
    * @param await
    *   - true: ждать завершения всех дочерних волокон при финализации
    *   - false: отменить все дочерние волокна при финализации
    */
  def apply[F[_]](await: Boolean)(using
      F: Concurrent[F]
  ): Resource[F, Supervisor[F]] = ???
```

### Жизненный цикл с Supervisor

```
Жизненный цикл супервизора (ресурса)
+===================================+
|                                   |
|   Жизненный цикл волокна B        |
|   +---------------------------+   |
|   |                           |   |
|   |   A запускает B           |   |
|   |   (через supervise)       |   |
|   |                           |   |
|   +---------------------------+   |
|                                   |
|   Жизненный цикл волокна A        |
|   +---------------------------+   |
|   |                           |   |
|   |                           |   |
|   +---------------------------+   |
|                                   |
+===================================+
```

**Ключевое отличие:** Волокно `A` (создатель) и волокно `B` (дочернее) живут независимо друг от друга, 
но **оба** привязаны к жизненному циклу супервизора. 
Супервизор живёт внутри `Resource.use` — как только он завершается, все дочерние волокна останавливаются.

## Две стратегии завершения

Параметр `await` в конструкторе супервизора определяет, **как** завершаются дочерние волокна при остановке супервизора.

| `await = true`                                                                               | `await = false`                                                               |
|:---------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------|
| **Ожидание** завершения всех активных волокон                                                | **Немедленная отмена** всех активных волокон                                  |
| `Supervisor` дождётся, пока каждое дочернее волокно корректно завершится (успех или ошибка)  | Все дочерние волокна получают сигнал `cancel`                                 |
| Полезно для graceful shutdown (завершение с ожиданием)                                       | Полезно для быстрой остановки (например, при панике или тайм-ауте)            |
| **Риск:** бесконечное волокно (`IO.never`) зависнет навсегда                                 | **Риск:** данные могут быть потеряны, если волокно было в критической секции  |

## Пример 1: Фоновая задача, переживающая HTTP-запрос

```dotty
import cats.syntax.all.*
import cats.effect.{IO, IOApp}
import cats.effect.std.Supervisor

import scala.concurrent.duration.*

object HttpHandler extends IOApp.Simple:

  val run: IO[Unit] =
    Supervisor[IO](await = true).use: supervisor =>
      List(1, 2, 3).traverse(handleRequest(_, supervisor)).void

  private def handleRequest(id: Int, supervisor: Supervisor[IO]): IO[Unit] =
    def longJob: IO[Unit] =
      IO.sleep(1.second) *>
        IO.println(s"Задача $id: началась") *>
        IO.sleep(1.second) *>
        IO.println(s"Задача $id: завершилась")

    for
      // Запускаем долгую фоновую задачу
      _ <- supervisor.supervise(longJob)
      // Ответ отправляем клиенту немедленно
      _ <- IO.println(s"Запрос $id: обработан, ответ отправлен")
    yield ()
end HttpHandler
```

Вывод:

```text
Запрос 1: обработан, ответ отправлен
Запрос 2: обработан, ответ отправлен
Запрос 3: обработан, ответ отправлен
... спустя секунду ...
Задача 1: началась
Задача 2: началась
Задача 3: началась
... спустя секунду ...
Задача 1: завершилась
Задача 2: завершилась
Задача 3: завершилась
```

**Что происходит:**

1. Приходит 3 запроса, каждый запускает фоновую 2-секундную задачу через `supervise`.
2. Ответ отправляется клиенту **мгновенно**.
3. Все 3 фоновые задачи продолжают выполняться независимо.
4. Когда сервер завершает работу, `supervisor.use` завершается, 
   и все фоновые задачи **останавливаются** (ждать или отменить — зависит от `await`).

## Пример 2: Graceful shutdown с ожиданием задач

```dotty
import cats.effect.{IO, Resource}
import cats.effect.std.Supervisor
import scala.concurrent.duration.*

class EmailService(supervisor: Supervisor[IO]):
  def sendBulk(emails: List[Email]): IO[Unit] =
    emails.traverse { email =>
      supervisor.supervise {
        IO.println(s"Отправляю письмо на ${email.address}") *>
          IO.sleep(2.seconds) *>
          email.send()
      }.void
    }.void

val program: Resource[IO, Unit] =
  for
    supervisor <- Supervisor[IO](await = true) // Ждём завершения всех писем
    service = new EmailService(supervisor)
    _ <- Resource.eval(service.sendBulk(bigEmailList))
  yield ()

// При завершении программы supervisor.use дождётся, пока все письма будут отправлены
```

## Пример 3: Быстрая остановка с отменой (anticipating shutdown)

```dotty
val quickShutdown: Resource[IO, Supervisor[IO]] =
  Supervisor[IO](await = false) // При завершении — отменить все фоновые задачи

def longRunningTask(i: Int): IO[Unit] =
  IO.sleep(i.seconds) *> IO.println(s"Запуск $i")

val run = quickShutdown.use { supervisor =>
  for
    // Запускаем 100 фоновых задач
    fibers <- (1 to 100).toList.traverse(i =>
      supervisor.supervise(longRunningTask(i))
    )
    _ <- IO.sleep(5.seconds) // Работаем 5 секунд
  // Supervisor будет закрыт после этого блока принудительно отменив все задачи
  yield ()
}

run.unsafeRunSync()

// Запуск 1
// Запуск 2
// Запуск 3
// Запуск 4
// Запуск 5
```

## Пример 4: Самовосстанавливающийся сервис с супервизором

Супервизор идеально подходит для реализации паттерна "супервизорного дерева" из Erlang/OTP.

```dotty
import cats.effect.{IO, Temporal}
import cats.effect.std.Supervisor
import scala.concurrent.duration.*

class ResilientService(supervisor: Supervisor[IO]):
  def startWorkers: IO[Unit] =
    supervisor.supervise(runWorker("Worker1", runJob)).void *>
      supervisor.supervise(runWorker("Worker2", runJob)).void *>
      supervisor.supervise(runWorker("Worker3", runJob)).void

  private def runWorker(name: String, job: Int => IO[Unit]): IO[Unit] =
    def loop(attempt: Int): IO[Unit] =
      job(attempt).handleErrorWith { error =>
        IO.println(s"Worker $name упал: ${error.getMessage}") *>
          IO.sleep(1.second) *>
          loop(attempt + 1)
      }
    loop(1)

  private def runJob(attempt: Int): IO[Unit] =
    if attempt >= 3 then IO.println("Успех!")
    else
      IO.raiseError(
        new Exception(s"Попытка $attempt отправляется на перезапуск")
      )
end ResilientService

val program: Resource[IO, Unit] =
  for
    supervisor <- Supervisor[IO](await = true)
    service = new ResilientService(supervisor)
    _ <- Resource.eval(service.startWorkers)
  yield ()

// Worker Worker3 упал: Попытка 1 отправляется на перезапуск
// Worker Worker2 упал: Попытка 1 отправляется на перезапуск
// Worker Worker1 упал: Попытка 1 отправляется на перезапуск
// Worker Worker3 упал: Попытка 2 отправляется на перезапуск
// Worker Worker2 упал: Попытка 2 отправляется на перезапуск
// Worker Worker1 упал: Попытка 2 отправляется на перезапуск
// Успех!
// Успех!
// Успех!
```

## Важные нюансы и ограничения

### 1. Бесконечное волокно + `await = true` = вечная блокировка

```dotty
// ⚠️ ОПАСНО: программа зависнет навсегда
Supervisor[IO](await = true).use { supervisor =>
  supervisor.supervise(IO.never)  // бесконечная задача
}.unsafeRunSync()  // никогда не завершится!
```

**Решение:** Используйте `await = false`, если есть риск бесконечных задач, или обеспечьте механизм их корректного завершения.

### 2. Вложенные супервизоры

Супервизоры можно вкладывать друг в друга, создавая иерархии.

```dotty
Supervisor[IO](await = true).use { outer =>
  Supervisor[IO](await = false).use { inner =>
    // outer ждёт inner при своём завершении
    inner.supervise(IO.never) // inner с await=false отменит эту задачу
  }
}
```

### 3. Ручная отмена дочернего волокна

Волокно, запущенное через `supervise`, можно отменить вручную **до** завершения супервизора.

```dotty
supervisor.supervise(longTask).flatMap { fiber =>
  IO.sleep(1.second) *> fiber.cancel // отменяем конкретную задачу
}
```

## Supervisor vs Альтернативы

|                                   | `start`                                | `background`                              | `Supervisor`                                      |
|:----------------------------------|:---------------------------------------|:------------------------------------------|:--------------------------------------------------|
| **Зависимость от создателя**      | Нет (полностью независимо)             | Да (отменяется при завершении создателя)  | Нет (независимо от создателя)                     |
| **Живёт при ошибке создателя**    | Да                                     | Нет                                       | Да                                                |
| **Может быть остановлен внешне**  | Только через `fiber.cancel`            | Автоматически                             | Групповая остановка (при завершении супервизора)  |
| **Привязка к `Resource`**         | Нет                                    | Да (через `background`)                   | Да (супервизор как `Resource`)                    |
| **Graceful shutdown**             | Нужно отслеживать все волокна вручную  | Автоматически                             | Две стратегии (`await` true/false)                |

## Итог: когда использовать Supervisor?

✅ **Используйте `Supervisor`, если:**

- Задача должна пережить создателя (например, фоновый экспорт после отправки HTTP-ответа).
- Вы хотите группировать несколько фоновых задач под общим жизненным циклом.
- Нужно реализовать "супервизорное дерево" для устойчивости к ошибкам.
- Вам нужен graceful shutdown (дождаться завершения задач перед остановкой).
- Проблематично вручную сохранять все волокна и вызывать `traverse(_.cancel)`.

❌ **Не используйте `Supervisor`, если:**

- Задача должна быть привязана к создателю (`background` проще).
- У вас простая программа, где можно использовать `start` и собрать все волокна в список.
- Вы создаёте всего одно-два фоновых волокна — `Supervisor` может быть избыточен.

**Ключевая идея:** `Supervisor` — это менеджер жизненного цикла для "сиротских" волокон, 
которые должны жить своей жизнью, но всё же подчиняться общему правилу остановки при завершении системы. 
Это недостающее звено между "запустил и забыл" (`start`) и "живи вместе со мной" (`background`).
