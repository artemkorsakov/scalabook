# Обработка ошибок

## Основные принципы функционального подхода к генерации и обработке ошибок

В функциональном программировании создание исключений (_exceptions_) рассматривается как побочный эффект (_side effect_), 
что противоречит принципам чистой функциональности. 
Вместо использования механизма исключений, функциональный подход предлагает:

1. Представление ошибок и сбоев в виде обычных возвращаемых значений
2. Использование функций высшего порядка (higher-order functions) для абстрагирования общих паттернов обработки ошибок
3. Реализацию механизмов восстановления после ошибок через композицию функций

Такое решение обладает несколькими ключевыми преимуществами:

- **Безопасность**: явное представление ошибок делает их обработку обязательной
- **Ссылочная прозрачность (_Referential Transparency_)**: сохранение свойства заменяемости выражений
- **Консолидация логики**: возможность централизованной обработки ошибок, аналогично блокам try/catch

## Обзор традиционного подхода с исключениями

Основная проблема исключений в том, что они **нарушают принципы функционального программирования**, 
такие как чистота функций, прозрачность и типобезопасность.

### 1. Нарушение ссылочной прозрачности

**Ссылочная прозрачность** означает, что выражение можно заменить его результатом без изменения поведения программы. 
Исключения нарушают это правило.

- **Зависимость от контекста:** Результат функции зависит не только от её аргументов, 
  но и от состояния системы (например, существует ли файл, доступна ли сеть).

- **Пример:**
  ```dotty
  // НЕПРОЗРАЧНАЯ функция
  def readConfigFile(configPath: String): String =
      val source = scala.io.Source.fromFile(configPath)
      try
        source.mkString
      finally
        source.close()
  ```

  Вызов `readConfigFile("app.conf")`:
    - Если файл существует, он вернёт его содержимое (например, `"port=8080"`).
    - Если файла нет, выбросит `FileNotFoundException`.

  **Проблема:** Мы не можем мысленно заменить вызов функции `readConfigFile("app.conf")` на её результат, 
  не зная контекста (существует файл или нет). Это ломает возможность рассуждать о коде с помощью простой **модели подстановки**.

- **Создание запутанного потока:** Управление потоком выполнения происходит не через комбинацию выражений, 
  а через "прыжки" (`throw` -> `catch`) в разные части кода, что сложнее для анализа.

### 2. Отсутствие типобезопасности

Типобезопасность — это гарантия, что компилятор проверит корректность программы на этапе компиляции. 
Исключения обходят эту систему типов.

- **Скрытые контракты:** Сигнатура функции — это её контракт. Исключения скрывают важнейшую часть этого контракта — возможные ошибки.

  **Пример:**

  ```dotty
  // Контракт функции: Int => Int
  // Реальный контракт: Int => Int ИЛИ throws Exception
  def failingFn(n: Int): Int =
      if n < 0 then throw new Exception("Отрицательное число!")
      else n * 2
  ```

- **Компилятор не поможет:** Компилятор _не_ обязывает вызывающую сторону обрабатывать исключение. Ошибка проявится только в **Runtime**.

  **Пример опасного кода, который скомпилируется:**

  ```dotty
  val result: Int = failingFn(-5) // Компилятор доволен. Типы совпали.
  val finalResult = result + 10   // Эта строка никогда не выполнится для n=-5
  ```

  **Результат выполнения:** Программа аварийно завершится с `Exception: Отрицательное число!`, и компилятор нас не предупредил об этой возможности.

- **Ошибки остаются незамеченными:** Если разработчик забыл, что `failingFn` может бросать исключение, 
  или не посмотрел в её документацию/исходный код, ошибка будет обнаружена только при тестировании или уже у пользователя.

### Ключевой вывод:

Исключения полезны для **критических, невосстановимых ошибок** (например, нехватка памяти), 
которые обрабатываются на самом высоком уровне абстракции.

Однако для **ожидаемых ошибок предметной области** (неверный ввод пользователя, отсутствие данных, сетевая недоступность) 
они — плохой инструмент, так как делают код ненадёжным и непредсказуемым. 

## Альтернативные подходы к обработке ошибок

Рассмотрим практический пример — реализацию функции вычисления среднего значения, которая не определена для пустого списка:

```dotty
def mean(xs: Seq[Double]): Double =
  if xs.isEmpty then
    throw new ArithmeticException("mean of empty list!")
  else xs.sum / xs.length
```

Эта функция является частичной (_partial function_) — она определена не для всех возможных входных данных 
(в данном случае, не для пустых списков).

### Альтернатива 1: Возврат специальных значений

Первый подход предполагает возврат специальных значений:

- Для пустого списка можно вернуть `Double.NaN`
- В других контекстах могут использоваться `null` или другие сигнальные значения

**Проблемы этого подхода**:

1. **Неявное распространение ошибок**:
    - Вызывающий код может забыть проверить специальное значение и не будет предупрежден компилятором, 
      что может привести к тому, что последующий код не будет работать должным образом.
    - Ошибки обнаруживаются значительно позже места их возникновения

2. **Увеличение шаблонного кода**:
    - Требуется множество явных проверок возвращаемых значений на стороне вызова с явными операторами `if` 
      для проверки того, получил ли вызывающий «настоящий» результат
    - Особенно проблематично при цепочках вызовов функций, каждая из которых использует коды ошибок,
      которые должны быть проверены и каким-то образом агрегированы

3. **Ограничения полиморфного кода**:
    - Не для всех типов существуют подходящие сигнальные значения
    - Пример: функция `max[A](xs: Seq[A])(greater: (A,A) => Boolean): A` не может вернуть корректное значение 
      для пустого списка. Здесь также нельзя использовать `null`, поскольку `null` допустим только для непримитивных типов,
      а `A` на самом деле может быть примитивом, таким как `Double` или `Int`.

4. **Нарушение единообразия**:
    - Требует специальных соглашений между функциями: правильное использование функции `mean` потребует, 
      чтобы вызывающие выполняли что-то иное, кроме вызова `mean` и использования результата
    - Усложняет использование с функциями высшего порядка: предоставление функциям специальных политик 
      затрудняет их передачу функциям высшего порядка, которые должны обрабатывать все аргументы единообразно.

### Альтернатива 2: Параметр обработки неопределенного случая

Второй подход предполагает передачу значения по умолчанию — заставить вызывающую программу предоставить аргумент,
который говорит, что делать, если мы не знаем, как обрабатывать ввод:

```dotty
def mean(xs: Seq[Double], onEmpty: Double): Double =
  if xs.isEmpty then onEmpty
  else xs.sum / xs.length
```

**Ограничения этого решения**:

1. **Жесткая привязка к конкретному типу** обработки ошибки
2. **Недостаточная гибкость**:
    - Невозможность прервать вычисление при ошибке. Что, если среднее значение вызывается как часть более крупного вычисления,
      и хотелось бы прервать это вычисление, если среднее значение не определено?
    - Отсутствие механизма выбора альтернативных веток вычислений
3. **Раннее принятие решения** об обработке ошибки, что может быть неоптимально для вызывающего кода

Нам требуется более гибкий механизм, позволяющий отложить решение об обработке ошибки до подходящего уровня абстракции.

## Тип данных Option: безопасное представление отсутствующих значений

### Концепция и базовое определение

Функциональный подход к обработке отсутствующих или неопределенных значений заключается 
в явном указании возможности отсутствия результата через возвращаемый тип. 
Это позволяет передать ответственность за обработку таких случаев вызывающему коду, 
сохраняя при этом типобезопасность и ссылочную прозрачность.

Тип `Option` представляет собой алгебраический тип данных (ADT), определенный следующим образом:

```dotty
enum Option[+A]:
  case Some(get: A)  // Представляет наличие значения типа A
  case None          // Представляет отсутствие значения
```

Ключевые особенности:

- Ковариантность (`+A`) позволяет естественным образом работать с иерархиями типов
- Два варианта: `Some` для существующих значений и `None` для отсутствующих
- Явная модель обработки вместо неявных исключений

### Практическое применение Option

Рассмотрим переработанный пример функции вычисления среднего:

```dotty
import Option.{Some, None}

def mean(xs: Seq[Double]): Option[Double] =
  if xs.isEmpty then 
    None  // Явное указание отсутствия результата
  else 
    Some(xs.sum / xs.length)  // Упаковка результата в Some
```

Преимущества такого подхода:

1. **Полнота функции**: функция определена для всех входных значений
2. **Ясность сигнатуры**: тип возвращаемого значения явно указывает на возможное отсутствие результата
3. **Безопасность**: компилятор требует обработки обоих случаев (`Some`/`None`)

### Основные операции с Option

#### 1. Преобразование значений

`map` и `flatMap` позволяют последовательно работать с возможными значениями:

```dotty
def map[B](f: A => B): Option[B] = this match
  case Some(a) => Some(f(a))
  case None    => None

def flatMap[B](f: A => Option[B]): Option[B] = this match
  case Some(a) => f(a)
  case None    => None
```

Функцию `map` можно использовать для преобразования результата внутри параметра, если он существует.
Можно думать об этом как о продолжении вычислений в предположении, что ошибки не произошло;
это также способ отложить обработку ошибок на более поздний код:

`flatMap` аналогичен, за исключением того,
что функция, предоставляемая для преобразования результата, сама по себе может дать сбой.

Пример использования с иерархией сотрудников:

```dotty
case class Employee(
  name: String,
  department: String,
  manager: Option[Employee]  // Рекурсивное использование Option
)

def lookupByName(name: String): Option[Employee] =
  name match
    case "Jack" => Some(Employee("Jack", "Engineering", None))
    case "Jill" => Some(Employee("Jill", "HR", lookupByName("Jack")))
    case _      => None

// Примеры цепочек вычислений
lookupByName("Jill").map(_.department)  // Преобразование существующего значения
// Some("HR")

lookupByName("Jill").flatMap(_.manager) // Распаковка вложенного Option
// Some(Employee("Jack", "Engineering", None))
```

#### 2. Фильтрация и обработка отсутствующих значений

`filter` можно использовать для преобразования успехов в неудачи,
если успешные значения не соответствуют заданному предикату.

`getOrElse` используется для преобразования из `Option[A]` в `A`,
предоставляя значение по умолчанию на случай ошибки.

`orElse` похож на `getOrElse`, за исключением того, что возвращается другой `Option`, если первый не определен.
Это часто бывает полезно, когда нужно вместе связать возможные неудачные вычисления,
пробуя второе, если первое не удалось.

```dotty
def filter(p: A => Boolean): Option[A] = this match
  case Some(a) if p(a) => Some(a)
  case _               => None

def getOrElse[B >: A](default: => B): B = this match
  case Some(a) => a
  case None    => default

def orElse[B >: A](ob: => Option[B]): Option[B] = this match
  case Some(a) => Some(a)
  case None    => ob
```

Практические примеры:

```dotty
val dept = lookupByName("Jill")
  .map(_.department)
  .filter(_ != "Sales")  // Превращаем Some в None если условие не выполняется
  .getOrElse("Default Department")

// Альтернативный Option при неудаче
lookupByName("Unknown")
  .orElse(lookupByName("Default Employee"))
```

#### 3. Композиция операций

Типичный паттерн работы с `Option` — цепочка преобразований с финальной обработкой:

```dotty
// Получение имени менеджера с обработкой всех возможных отсутствий
val managerName = lookupByName("Jill")
  .flatMap(_.manager)
  .map(_.name)
  .getOrElse("No manager found")
// val managerName: String = Jack  
```

### Рекомендации по использованию

1. **Преимущества перед исключениями**:
    - Сохранение ссылочной прозрачности
    - Явное указание возможных ошибок в типах
    - Композируемость и возможность отложенной обработки

2. **Когда использовать**:
    - Для ожидаемых и обрабатываемых "ошибок" (отсутствие данных, неверные входные параметры)
    - В публичном API для явного указания возможных проблем

3. **Когда не использовать**:
    - Для действительно исключительных ситуаций (ошибки ввода-вывода, фатальные ошибки)
    - Когда отсутствие значения является ошибкой программиста (лучше использовать исключение)

4. **Идиоматические паттерны**:
    ```dotty
    // Преобразование None в исключение
    val result = optionValue.getOrElse(throw new IllegalStateException("Missing required value"))
 
    // Каскадная проверка альтернатив
    val config = readFileConfig()
      .orElse(readEnvConfig())
      .orElse(readDefaultConfig())
    ```

### Сравнение с аналогичными решениями

Для более сложных сценариев, где нужно сохранять информацию об ошибке, рассмотрите использование `Either` или `Try`. 
`Option` лучше всего подходит для простых случаев отсутствия значений, когда дополнительная информация об ошибке не требуется.

Реализуйте функцию безопасного деления,

Это упражнение демонстрирует базовый принцип функциональной обработки ошибок - 
преобразование частичной функции в полную.

```dotty
def safeDivide(a: Double, b: Double): Option[Double] = ???
```

**Примеры:**

```dotty
// Успешное деление
safeDivide(10, 2)   // Some(5.0)
safeDivide(5, 2)    // Some(2.5)

// Деление на ноль
safeDivide(8, 0)    // None
safeDivide(-3, 0)   // None

// Особые случаи
safeDivide(0, 5)    // Some(0.0)
safeDivide(0, 0)    // None (неопределенность)
```

@:note(🔍 Показать решение)

Функция `safeDivide` реализует безопасное деление чисел, возвращая результат в `Some` при ненулевом делителе 
и `None` при делении на ноль, что явно указывает на ошибку без использования исключений. 
Альтернативная версия `safeDivideAlt` делает то же самое через pattern matching, 
проверяя случай нулевого делителя отдельным кейсом — 
оба варианта демонстрируют функциональный подход к обработке ошибок через тип `Option`, 
сохраняя чистоту кода и типобезопасность.

```dotty
def safeDivide(a: Double, b: Double): Option[Double] =
  if b != 0 then Some(a / b) else None

// Альтернативная реализация через pattern matching
def safeDivideAlt(a: Double, b: Double): Option[Double] = 
  b match
    case 0 => None
    case _ => Some(a / b)
```

### Упражнение 3.1.2: Поиск адреса доставки по цепочке зависимостей

В этом упражнении мы будем работать с цепочкой зависимых данных, где информация разбросана по разным сущностям. 
Задача - найти адрес доставки для заказа, используя `flatMap` для безопасной работы с потенциально отсутствующими значениями.

```dotty
case class User(id: Int, name: String, address: Option[String])
case class Order(orderId: Int, userId: Int, product: String, price: Double)

val users = List(
  User(1, "Alice", Some("123 Main St")),
  User(2, "Bob", None)
)

val orders = List(
  Order(100, 1, "Laptop", 999.99),
  Order(101, 2, "Phone", 599.99)
)

// Напишите функцию, которая по id заказа возвращает адрес доставки (используйте flatMap)
def getShippingAddress(orderId: Int): Option[String] = ???
```

**Примеры:**

```dotty
// Заказ с существующим пользователем и адресом
getShippingAddress(100)  // Some("123 Main St")

// Заказ с существующим пользователем без адреса
getShippingAddress(101)  // None

// Несуществующий заказ
getShippingAddress(999)  // None
```

@:note(🔍 Показать решение)

Функция `getShippingAddress` безопасно извлекает адрес доставки по ID заказа, 
используя цепочку операций с `Option`: сначала находим заказ через `find`, 
затем через `flatMap` находим соответствующего пользователя и его адрес. 
Если любой из шагов возвращает `None` (заказ не найден, пользователь не существует или адрес не указан), 
вся цепочка автоматически возвращает `None`, 
что обеспечивает строгую обработку отсутствующих данных без исключений и явных проверок. 
Решение демонстрирует идиоматичную работу с вложенными `Option` через композицию `flatMap`.

```dotty
def getShippingAddress(orderId: Int): Option[String] =
  orders
    // Найти заказ
    .find(_.orderId == orderId)  
    // Распаковать Option[Order]      
    .flatMap(order =>                  
      users
        // Найти пользователя
        .find(_.id == order.userId) 
        // Получить адрес
        .flatMap(_.address)            
    )
```

### Упражнение 3.1.3: Работа с опциональными полями профилей: getEmailOrDefault

Напишите функцию, которая возвращает `email` профиля или `"no-email@example.com"` если `email` отсутствует.

```dotty
case class Profile(id: Int, name: String, email: Option[String], age: Option[Int])

val profiles = List(
  Profile(1, "Alice", Some("alice@example.com"), Some(30)),
  Profile(2, "Bob", None, Some(25)),
  Profile(3, "Charlie", Some("charlie@example.com"), None)
)

def getEmailOrDefault(profile: Profile): String = ???
```

**Примеры:**

```dotty
getEmailOrDefault(profiles(0)) // "alice@example.com"
getEmailOrDefault(profiles(1)) // "no-email@example.com"
```

@:note(🔍 Показать решение)

Функция возвращает email пользователя или стандартное значение `"no-email@example.com"`,
если email отсутствует, используя метод `getOrElse` для безопасной обработки `Option`.
Это гарантирует, что результат всегда будет строкой, исключая необходимость последующих проверок на `None`.

```dotty
def getEmailOrDefault(profile: Profile): String =
```

## Тип данных Either: Расширенная обработка ошибок в функциональном программировании

### Введение в обработку ошибок через значения

В функциональном программировании существует фундаментальный принцип: 
все эффекты, включая ошибки и исключения, должны быть явно представлены в типах возвращаемых значений. 
Такой подход обеспечивает несколько ключевых преимуществ:

1. **Прозрачность** - сигнатура функции явно указывает на возможные ошибки
2. **Безопасность** - компилятор требует обработки всех возможных случаев
3. **Композируемость** - ошибки могут обрабатываться и передаваться через цепочки вызовов

### Ограничения типа Option

Хотя `Option` является простым и полезным инструментом для представления отсутствующих значений, у него есть существенные ограничения:

```dotty
def findUser(id: Int): Option[User] = ...
```

В этом примере, когда функция возвращает `None`, мы не можем определить:

- Существует ли пользователь с таким ID
- Произошла ли ошибка при доступе к базе данных
- Были ли проблемы с подключением к сети

`Option` просто сообщает, что значения нет, но не объясняет причину.

### Тип Either: концепция и определение

`Either` - это алгебраический тип данных, который расширяет возможности `Option`, 
позволяя хранить информацию об ошибках. Его определение:

```dotty
enum Either[+E, +A]:
  case Left(value: E)  // Для хранения информации об ошибке
  case Right(value: A) // Для хранения успешного результата
```

Ключевые особенности:

- Ковариантность по обоим параметрам типа (`+E`, `+A`)
- Два конструктора: `Left` и `Right`
- По соглашению: `Right` означает "правильный" (успешный) результат

### Практическое применение Either

#### Пример 1: Вычисление среднего значения

```dotty
def mean(xs: Seq[Double]): Either[String, Double] =
  if xs.isEmpty then
    Left("Ошибка: невозможно вычислить среднее значение пустого списка")
  else
    Right(xs.sum / xs.length)

// Примеры использования:
mean(Seq(1.0, 2.0, 3.0)) 
// Right(2.0)
mean(Seq.empty)           
// Left("Ошибка: невозможно вычислить среднее значение пустого списка")
```

#### Пример 2: Безопасное выполнение кода с исключениями

```dotty
import scala.util.control.NonFatal

def safeDivide(a: Int, b: Int): Either[Throwable, Int] =
  try Right(a / b)
  catch case NonFatal(ex) => Left(ex)

// Примеры:
safeDivide(10, 2)  // Right(5)
safeDivide(10, 0)  // Left(java.lang.ArithmeticException: / by zero)
```

### Сравнение с Option

| Характеристика     | Option              | Either                         |
|--------------------|---------------------|--------------------------------|
| Хранение ошибки    | Нет (только `None`) | Да (произвольный тип в `Left`) |
| Сигнатура          | `Option[A]`         | `Either[E, A]`                 |
| Успешный результат | `Some(value)`       | `Right(value)`                 |
| Ошибка             | `None`              | `Left(error)`                  |
| Информативность    | Низкая              | Высокая                        |

### Расширенные примеры использования

#### Обработка нескольких ошибок

```dotty
case class ValidationError(message: String)

def validateAge(age: Int): Either[ValidationError, Int] =
  if age < 0 then Left(ValidationError("Возраст не может быть отрицательным"))
  else if age > 120 then Left(ValidationError("Слишком большой возраст"))
  else Right(age)

def createUser(name: String, age: Int): Either[ValidationError, User] =
  for
    validAge <- validateAge(age)
    // Другие проверки...
  yield User(name, validAge)
```

#### Композиция Either

```dotty
def parseNumber(s: String): Either[String, Int] =
  try Right(s.toInt)
  catch case _: NumberFormatException => Left(s"Невозможно преобразовать '$s' в число")

def calculate(a: String, b: String): Either[String, Int] =
  for
    num1 <- parseNumber(a)
    num2 <- parseNumber(b)
    result <- safeDivide(num1, num2).left.map(_ => "Деление на ноль")
  yield result

// Примеры:
calculate("10", "2")  // Right(5)
calculate("10", "0")  // Left("Деление на ноль")
calculate("a", "2")   // Left("Невозможно преобразовать 'a' в число")
```

### Рекомендации по использованию

1. **Когда использовать Either**:
    - Когда важно передавать информацию об ошибке
    - Для валидации входных данных
    - При работе с внешними системами (базы данных, API)

2. **Когда использовать Option**:
    - Когда причина отсутствия значения не важна
    - Для простых случаев "значение есть/нет"

3. **Best Practices**:
    - Используйте осмысленные типы ошибок (не только `String`)
    - Создавайте иерархии ошибок для сложных сценариев
    - Документируйте возможные ошибки в ScalaDoc

### Упражнение 3.2.1: Безопасное вычисление квадратного корня

Реализуйте функцию вычисления квадратного корня, которая явно обрабатывает случай с отрицательными числами, 
возвращая информативное сообщение об ошибке вместо выбрасывания исключения. 
Функция должна сохранять ссылочную прозрачность и явно указывать возможную ошибку в типе возвращаемого значения.

```dotty
def safeSqrt(x: Double): Either[String, Double] = ???
```

**Примеры:**

```dotty
safeSqrt(16.0)   // Right(4.0)
safeSqrt(0.0)    // Right(0.0)
safeSqrt(-9.0)   // Left("Отрицательное число")
safeSqrt(2.25)   // Right(1.5)
```

@:note(🔍 Показать решение)

Функция `safeSqrt` реализует безопасное вычисление квадратного корня, 
возвращая `Right` с результатом для неотрицательных чисел 
и `Left` с сообщением "Отрицательное число" для отрицательных входных данных. 
Это демонстрирует типичный функциональный подход к обработке ошибок через тип `Either`, где:

- Успешный результат оборачивается в `Right`
- Ошибка с описанием возвращается в `Left`
- Проверка условия выполняется явно перед вычислением
- Сохраняется ссылочная прозрачность (одинаковые входные данные всегда дают одинаковый результат)
- Исключения заменяются на явное возвращение значения-ошибки

```dotty
def safeSqrt(x: Double): Either[String, Double] =
  if x < 0 then 
    Left("Отрицательное число")
  else 
    Right(Math.sqrt(x))
```

### Упражнение 3.2.2: Валидация возраста с Either

Реализуйте функцию парсинга и валидации возраста из строки, которая обрабатывает все возможные ошибки: 
некорректный формат числа и выход за допустимые границы значений (от 1 до 120). 
Функция должна возвращать понятные сообщения об ошибках в `Left` и валидный возраст в `Right`.

```dotty  
def parseAge(s: String): Either[String, Int] = ???  
```

**Примеры:**

```dotty
parseAge("25")      // Right(25)
parseAge("150")     // Left("Возраст должен быть от 1 до 120")
parseAge("abc")     // Left("Некорректный формат возраста")
parseAge("0")       // Left("Возраст должен быть от 1 до 120")
parseAge("")        // Left("Некорректный формат возраста")
```

@:note(🔍 Показать решение)

Функция `parseAge` реализует безопасный парсинг и валидацию возраста из строки,
используя `Either` для обработки возможных ошибок. 
Сначала она пытается преобразовать строку в число через `toIntOption`, 
возвращая ошибку формата при неудаче, затем проверяет диапазон возраста (1-120), 
возвращая соответствующую ошибку при выходе за границы, 
и только при успешном прохождении всех проверок возвращает валидный возраст в `Right`. 
Решение демонстрирует каскадную проверку условий с явным возвратом ошибок, типичную для функционального подхода.

```dotty
def parseAge(s: String): Either[String, Int] =
  s.toIntOption match
    case None => Left("Некорректный формат возраста")
    case Some(age) if age < 1 || age > 120 =>
      Left("Возраст должен быть от 1 до 120")
    case Some(age) => Right(age)
```

### Упражнение 3.2.3: Валидация пользователя с Either: createUser

Реализуйте две версии функции создания пользователя с разными стратегиями обработки ошибок: 
первая возвращает первую обнаруженную ошибку, вторая собирает все ошибки валидации. 
Упражнение демонстрирует композицию `Either` и разные подходы к валидации сложных данных.

Реализуйте функцию `createUser`, которая:

- Принимает имя (не пустое) и возраст (строку)
- Использует `parseAge` из предыдущего упражнения
- Возвращает `Right(User)` если все проверки пройдены
- Возвращает `Left` с описанием первой ошибки  

```dotty  
case class User(name: String, age: Int)  
  
def createUser(name: String, ageStr: String): Either[String, User] = ???   
```  

**Примеры:**

```dotty
createUser("Alice", "30") // Right(User("Alice", 30))
createUser("", "25")      // Left("Имя не может быть пустым")
createUser("Bob", "abc")  // Left("Некорректный формат возраста")
createUser("", "abc")     // Left("Имя не может быть пустым")
```

@:note(🔍 Показать решение)

Функция `createUser` реализует базовую валидацию пользователя, проверяя имя на пустоту 
и используя `parseAge` для валидации возраста, возвращая первую обнаруженную ошибку в `Left`. 

```dotty
def createUser(name: String, ageStr: String): Either[String, User] =

    Left("Имя не может быть пустым")
  else
    parseAge(ageStr).map(age => User(name, age))
```

### Упражнение 3.2.4: Валидация пользователя с Either: createUserDetailed

Улучшенная версия `createUser`:

- Собирает ВСЕ ошибки валидации (имени и возраста)
- Использует `Either` с типом ошибки `List[String]  `

```dotty  
case class User(name: String, age: Int)  
  
def createUserDetailed(name: String, ageStr: String): Either[List[String], User] = ???  
```  

**Примеры:**

```dotty
createUserDetailed("Alice", "30")
// Right(User("Alice", 30))
createUserDetailed("", "abc")
// Left(List("Имя не может быть пустым", "Некорректный формат возраста"))
createUserDetailed("", "150")
// Left(List("Имя не может быть пустым", "Возраст должен быть от 1 до 120"))
```

@:note(🔍 Показать решение)

Расширенная версия `createUserDetailed` применяет более продвинутую стратегию валидации:
с помощью `Either.cond` проверяет имя и комбинирует с результатом `parseAge`, собирая все возможные ошибки в список.
Решение демонстрирует два подхода к обработке ошибок - "fail-fast" (первая ошибка)
и "полную валидацию" (все ошибки), используя сопоставление с шаблоном для композиции `Either`-значений.
Обе функции возвращают либо валидного пользователя в `Right`,
либо список ошибок в `Left`, сохраняя типобезопасность.

```dotty
def createUserDetailed(
    name: String,
    ageStr: String
): Either[List[String], User] =
  val nameValid =
    Either.cond(name.nonEmpty, name, List("Имя не может быть пустым"))
  val ageValid = parseAge(ageStr).left.map(_ :: Nil)

  (nameValid, ageValid) match
    case (Right(n), Right(a))     => Right(User(n, a))
    case (Left(nErr), Left(aErr)) => Left(nErr ++ aErr)
    case (Left(err), _)           => Left(err)
    case (_, Left(err))           => Left(err)
```
