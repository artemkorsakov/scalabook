# Tagless Final

## Введение

Метод Tagless Final (интерпретаторы без тегов или "F с дыркой") — это архитектурный паттерн для построения программ. 
Его главная цель — разделить описание того, _что_ делает программа, от описания того, _как_ она это делает.

- **Что делает программа (DSL):** Вы описываете бизнес-логику на языке, который сами создаёте 
  (предметно-ориентированный язык, DSL), используя абстрактные интерфейсы (алгебры). 
  Ваш код на этом этапе говорит: "Мне нужно увеличить счётчик" или "получить список товаров", 
  но не говорит, как именно это произойдёт.
- **Как это делает программа (Интерпретация):** Отдельно вы пишете реализации (интерпретаторы), 
  которые объясняют, как эти абстрактные команды превращаются в конкретные действия: "увеличить счётчик в Redis" 
  или "получить товары из PostgreSQL".

**Ключевые преимущества:**

- **Решаем ["Проблему выражений"](https://en.wikipedia.org/wiki/Expression_problem):** 
  Легко добавлять новые операции (новые функции в интерфейс) и новые способы выполнения (новые интерпретаторы).
- **Тестируемость:** Для тестов вы можете подменить "боевые" интерпретаторы (работа с БД) 
  на "тестовые" (работа с данными в памяти), не меняя саму бизнес-логику.
- **Композируемость:** Небольшие алгебры (для счётчика, для товаров) легко объединяются в более сложные программы.

**Сравнение с [Free Monad](../../typeclass/monad/free-monads.md):** Оба подхода решают схожие задачи. 
Tagless Final считается более эффективным на этапе выполнения (меньше накладных расходов) 
и часто более простым для понимания в Scala из-за прямого использования возможностей языка (трейтов).

## Алгебры

**Алгебра** — это сердце Tagless Final. По сути, это **абстрактный API** для определённой предметной области.

```dotty
trait Counter[F[_]]:
  def incr: F[Unit] // Команда: "Сделай увеличение счётчика"
  def get: F[Int]   // Запрос: "Дай мне текущее значение счётчика"
```

**Ключевые моменты:**

- **`F[_]` (Конструктор типа):** Это "дыра" для эффекта. `F[_]` — это не конкретный тип (как `Int`), 
  а "форма" типа, которая принимает один тип. Например, `IO[Int]`, `Future[Int]`, `Option[Int]` подходят под форму `F[_]`. 
  Это позволяет алгебре быть независимой от конкретной библиотеки эффектов (`cats-effect IO`, `ZIO`, `Monix Task`) 
  или контекста (`Future`, `Id` для симуляции).
- **Это не класс типов (Type Class):** Хотя внешне похоже (трейт с параметром типа `F[_]`), это просто интерфейс.
    - **Класс типов** (например, `trait Monad[F[_]]`) описывает _возможности_ типа `F` (как с ним можно работать: `flatMap`, `pure`). 
      Он обычно один на весь проект для данного `F`.
    - **Алгебра** описывает _бизнес-операции_ в предметной области. 
      Для одной алгебры (`Counter`) может быть множество реализаций (интерпретаторов).
- **Почему без ограничений (`F[_]: Monad`)?** 
  Алгебра должна описывать только то, _что_ нужно сделать, а не _какие возможности_ для этого нужны. 
  Ограничения (например, `Monad`) — это требования к тому, как можно комбинировать операции. 
  Эти требования относятся к этапу _использования_ алгебры (в программах), а не к её определению. 
  Добавив `Monad` в алгебру, вы неявно говорите: "Все возможные реализации этой алгебры могут работать только в контексте `Monad`", 
  что излишне сужает область применения.

**Итог:** Алгебра — это максимально абстрактный, чистый контракт для вашего бизнес-домена.

## Интерпретаторы

**Интерпретатор** — это мост между абстрактным миром алгебры и конкретным миром реализации. 
Если алгебра — это **что**, то интерпретатор — **как**.

### Два типа интерпретаторов: Боевой vs Тестовый

#### Боевой (Production) интерпретатор

```dotty
object Counter:
  case class RedisKey(value: String)

  def make[F[_]: Functor](
      key: RedisKey,
      cmd: RedisCommands[F, String, Int]
  ): Counter[F] =
    new Counter[F]:
      def incr: F[Unit] =
        cmd.incr(key.value).void  // Вызов реального Redis
      def get: F[Int] =
        cmd.get(key.value).map(_.getOrElse(0))  // Чтение из реального Redis
```

**Что здесь происходит:**

- Интерпретатор принимает зависимость `RedisCommands` — это клиент для работы с Redis
- Каждый метод алгебры (`incr`, `get`) маппится на конкретную операцию Redis
- `key.value` — конкретный ключ в Redis, где хранится наш счётчик
- `map(_.getOrElse(0))` — преобразует `Option[Int]` из Redis в `Int` со значением по умолчанию

**Зачем ограничение `Functor`?**
Оно нужно только для операции `map` в методе `get`. Мы используем [минимально необходимое ограничение](../../typeclass/monad.md).

#### Тестовый интерпретатор

```dotty
def testCounter[F[_]](ref: Ref[F, Int]): Counter[F] =
  new Counter[F]:
    def incr: F[Unit] = ref.update(_ + 1)  // Обновляем значение в памяти
    def get: F[Int]   = ref.get  // Читаем из памяти
```

**Ключевые отличия:**

- **Нет внешних зависимостей** (Redis, база данных) — только `Ref[F, Int]`
- **Работает полностью в памяти** — идеально для тестов
- **Изолированное состояние** — каждый тест может создать свой `Ref`
- **Быстрый** — нет сетевых вызовов

**Что такое `Ref[F, Int]`?**
Это потокобезопасная изменяемая ячейка памяти, которая:

- Хранит значение типа `Int`
- Предоставляет атомарные операции (`update`, `get`)
- Существует только в рамках одного выполнения программы

### Полиморфизм интерпретаторов

**Почему оба интерпретатора полиморфны по `F[_]`?**

```dotty
// Оба работают с любым F[_]
def make[F[_]: Functor](...): Counter[F]
def testCounter[F[_]](...): Counter[F]
```

**Преимущества:**

1. **Гибкость тестирования:**

   ```dotty
   // В тестах можем использовать IO
   Ref[IO].of(0).map: ref =>
     testCounter[IO](ref)
   ```

2. **Независимость от рантайма:**
    - Та же алгебра может работать с `cats-effect IO`, `ZIO`, `Monix Task`
    - Переключение между эффект-системами не требует изменения бизнес-логики

### Практические рекомендации

**Для боевых интерпретаторов:**

1. Всегда инкапсулируйте внешние ресурсы (БД, HTTP-клиенты)
2. Используйте `Resource` или `Managed` для управления жизненным циклом - 
   подробнее в разделе ["Обеспечение безопасности ресурсов"](../stream-processing/resource.md)
3. Логируйте ошибки, но не внутри интерпретатора (используйте алгебру логирования)

**Для тестовых интерпретаторов:**

1. Храните состояние в памяти (`Ref`, `AtomicRef`, коллекции)
2. Делайте интерпретаторы максимально простыми
3. Добавляйте методы для инспекции состояния (только в тестовой сборке):
   ```dotty
   // Только в тестах!
   trait TestCounter[F[_]] extends Counter[F]:
       def getInternalState: F[Int] // Для проверок в тестах
   ```

**Итог:** Интерпретаторы — это место, где абстракция встречается с реальностью. 
Правильно спроектированный интерпретатор скрывает все технические детали, 
предоставляя чистое, тестируемое и переиспользуемое API для вашей бизнес-логики.

## Программы

**Программа** — это слой, где из кирпичиков-алгебр строится здание бизнес-логики. 
Это место, где абстракции начинают _работать вместе_ для решения реальных задач.

```dotty
class ItemsCounter[F[_]: Apply](counter: Counter[F], items: Items[F]):
  def addItem(item: Item): F[Unit] =
    // Сначала добавить товар, потом увеличить счётчик
    items.add(item) *> counter.incr 
```

**Характеристики программ:**

1.  **Они композитные:** Используют одну или несколько алгебр.
2.  **Они содержат бизнес-правила:** Правило "при добавлении товара увеличивать счётчик" живёт именно здесь.
3.  **Они вводят ограничения классов типов:** Поскольку программы _комбинируют_ эффекты 
   (например, используют `*>` для последовательного выполнения), им нужно указать, 
   какие возможности от `F[_]` им требуются ([`Apply`, `Bind`, `Monad`](../../typeclass/monad.md)).
4.  **Принцип наименьшей мощности:** Это золотое правило. Используйте самое слабое ограничение, которое позволяет сделать работу.
    - Нужно просто выполнить два действия одно за другим? [`Apply`](../../typeclass/monad/apply.md) (метод `*>`) достаточно.
    - Нужен результат первого действия, чтобы решить, что делать вторым? Понадобится [`Bind`](../../typeclass/monad/bind.md) (метод `flatMap`).
    - Используя минимально необходимое ограничение, вы делаете программу максимально гибкой и переиспользуемой в разных контекстах.

**Чистота бизнес-логики:** Что значит "чистая"?

- В программе не должно быть прямых вызовов к базе данных, файловой системе или внешним API. Всё это скрыто за алгебрами.
- Даже логирование должно идти через алгебру (например, `Logger[F]`). 
  Это позволяет в тестах подставить "немой" интерпретатор, который ничего не логирует.
- Программа описывает _последовательность шагов_ в терминах предметной области, а не технических деталей.

**Способы записи программ:**

1.  **Классы:** Хорошо для логики, которая имеет своё состояние (зависимости в виде алгебр) и несколько методов.
2.  **Функции:** Идеально для одноразовых или небольших сценариев.
3.  **Композиция программ:** Крупные программы могут собираться из более мелких, создавая иерархию.

Tagless Final — это чёткое разделение ответственности:

```dotty
trait Counter[F[_]]:
  def incr: F[Unit]
  def get: F[Int]
  
object Counter:
  def make[F[_]: Functor](key: RedisKey, cmd: RedisCommands[F, String, Int]): Counter[F] = ???
  
class ItemsCounter[F[_]: Apply](counter: Counter[F], items: Items[F]):
  def addItem(item: Item): F[Unit] = ??? 
```

1.  **Алгебра (`trait Counter`):** **_определяет_**, _что_ можно делать. (Спецификация)
2.  **Интерпретатор (`object Counter.make`):** **_реализует_**, _как_ это делать. (Исполнитель)
3.  **Программа (`class ItemsCounter`):** **_использует_** алгебры, чтобы описать _бизнес-процесс_. (Сценарий/Режиссёр)

Это разделение даёт невероятную гибкость, тестируемость и поддерживаемость кода, особенно в больших и сложных проектах.

## Почему интерпретаторы без тегов?

> "Ограничения освобождают, свободы сдерживают." — [Рунар Бьярнасон](https://www.youtube.com/watch?v=GqmsQeSzMdw)

**Параметричность** — это концепция, которая показывает, как **ограничения типов делают код более предсказуемым**.

#### Пример 1: Специфичная функция (мало ограничений)

```dotty
def specific(a: Int): Int
```

Сколько правильных реализаций может быть у этой функции? Бесконечно много! Вот лишь несколько:

```dotty
// Вариант 1
def specific(a: Int): Int = 0

// Вариант 2
def specific(a: Int): Int = a * 5

...
```

**Проблема:** Тип `Int → Int` слишком широкий. Функция может делать что угодно с числом, и компилятор не поможет нам понять, что именно.

#### Пример 2: Параметричная функция (сильные ограничения)

```dotty
def parametric[A](a: A): A
```

Сколько правильных реализаций может быть у этой функции? Только одна! (не считая бесконечной рекурсии)

```dotty
def parametric[A](a: A): A = a
```

**Почему так происходит?**

- Компилятор не знает ничего о типе `A`
- Нельзя создать значение типа `A` из ничего (не знаем конструктор)
- Нельзя преобразовать `A` в другой тип (не знаем операций)
- Единственное, что можно — вернуть то, что получили

### Параметричность в Tagless Final

Теперь посмотрим, как это работает в Tagless Final:

#### Пример без параметричности (прямой `IO`):

```dotty
class UserService:
  def createUser(name: String): IO[User] =
    // Может делать что угодно!
    for 
      _ <- logToFile(s"Creating user: $name") // Побочный эффект №1
      user = User(name)
      _ <- saveToDatabase(user)         // Побочный эффект №2
      _ <- sendWelcomeEmail(user.email) // Побочный эффект №3
      _ <- updateAnalytics()            // Побочный эффект №4 (кто это добавил?!)
    yield user
```

**Проблемы:**

1. Неясно, что делает функция
2. Сложно тестировать (нужно мокать всё)
3. Легко добавить скрытые побочные эффекты

#### Пример с параметричностью (Tagless Final):

```dotty
class UserService[F[_]: Monad: Logger](
    dbService: Database,
    emailService: EmailService
):
  def createUser(name: String): F[User] =
    for
      _ <- Logger[F].info(s"Creating user: $name") // Только логгирование
      user = User(name)
      _ <- dbService.save(user)                 // Только сохранение в БД
      _ <- emailService.sendWelcome(user.email) // Только отправка email
    // Нельзя добавить updateAnalytics() - нет сервиса для аналитики
    yield user
```

**Преимущества:**

1. **Явные зависимости:** Видно все побочные эффекты
2. **Ограниченная мощность:** Нельзя добавить "скрытые" эффекты
3. **Легко тестировать:** Можно подменить реализации

Параметричность связана с важной математической концепцией — 
[Theorems for free](https://people.mpi-sws.org/~dreyer/tor/papers/wadler.pdf). 
Грубо говоря:

> Если функция имеет полиморфный тип, то её поведение ограничено этим типом.

**Пример на практике:**

```dotty
// Полиморфная функция
def mystery[F[_], A](fa: F[A]): F[A]

// Что можно сказать о mystery, зная только её тип?
// Теорема говорит: она не может:
// 1. Заглянуть внутрь F[A] (не знает про A)
// 2. Создать новое значение A (не знает конструктор)
// 3. Изменить структуру F (не знает про F)
// Единственное, что может — вернуть fa
```

В Tagless Final это означает, что если у нас есть:

```dotty
def program[F[_]: Monad: Counter]: F[Unit]
```

Мы знаем, что `program`:

- Может использовать только операции из `Monad` и `Counter`
- Не может делать неожиданных вещей (HTTP-запросы, чтение файлов и т.д.)

### Сравнение с альтернативами

| Подход            | Параметричность | Тестируемость        | Безопасность                     |
|-------------------|-----------------|----------------------|----------------------------------|
| **Прямой `IO`**   | Нет             | Сложно (много моков) | Низкая (можно делать что угодно) |
| **Free Monad**    | Да              | Хорошо               | Высокая (но сложный синтаксис)   |
| **Tagless Final** | Да              | Отлично              | Высокая (простой синтаксис)      |

### Реальный пример: Эволюция кода

**Версия 1 (наивная):**

```dotty
def checkout(userId: UserId): IO[Order] =
  // 100 строк кода со смешанными эффектами
  // Сложно тестировать, легко сломать
```

**Версия 2 (с зависимостями):**

```dotty
class CheckoutService(
  db: Database,
  payment: PaymentGateway,
  email: EmailService,
  analytics: Analytics
):
  def checkout(userId: UserId): IO[Order] =
    // Лучше, но всё ещё прямой IO
```

**Версия 3 (Tagless Final):**

```dotty
class CheckoutService[F[_]: Monad](
    dbService: Database,
    paymentService: PaymentService
    emailService: EmailService
):
  def checkout(userId: UserId): F[Order] =
    // Чистая бизнес-логика
    // Все эффекты явно объявлены
    // Легко тестировать
    for
      user  <- dbService.getUser(userId)
      order <- createOrder(user)
      _     <- paymentService.process(order)
      _     <- emailService.sendReceipt(user.email, order)
    yield order
```

### Зачем всё это?

1. **Безопасность через ограничения:** Компилятор не даст сделать что-то неявное
2. **Тестируемость:** Легко подменять реализации
3. **Модульность:** Компоненты слабо связаны
4. **Композируемость:** Мелкие части собираются в большие системы
5. **Сопровождаемость:** По типу функции видно её возможности

**Философский итог:** Tagless Final — это не просто техника программирования. 
Это **дисциплина мышления**, которая учит нас:

- Декомпозировать проблемы на маленькие части
- Явно объявлять намерения
- Доверять композиции больше, чем наследованию
- Ценить ограничения, которые защищают от ошибок

## Резюме

**Tagless Final** — это архитектурный паттерн, который разделяет _что делает программа_ (бизнес-логику) от _как она это делает_ (реализацию). 
Он основан на трёх компонентах: **алгебры** (абстрактные интерфейсы предметной области, полиморфные по типу эффекта `F[_]`), 
**программы** (чистая бизнес-логика, использующая алгебры) 
и **интерпретаторы** (конкретные реализации алгебр для production и тестов).

Ключевые преимущества — **тестируемость** (логика неизменна, подменяются только интерпретаторы), 
**параметричность** (ограничения типов предотвращают скрытые эффекты) и **модульность** (чёткие границы между компонентами). 
Паттерн особенно эффективен для сложных приложений с высокими требованиями к сопровождению, 
обеспечивая предсказуемость и безопасность через ограничения типов.
