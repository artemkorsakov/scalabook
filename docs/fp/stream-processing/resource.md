# Обеспечение безопасности ресурсов

## Введение в проблему

`Stream` (в контексте библиотек функционального программирования, таких как **fs2** или **ZIO Streams**) — 
это не просто последовательность данных. Это абстракция над _процессом_, который может потреблять ресурсы. 
Ресурсы в программировании — это всё, что имеет ограниченную доступность и требует корректного освобождения:

- **Файлы**: Дескрипторы файлов (количество которых в системе ограничено).
- **Сетевые соединения**: Сокеты.
- **Подключения к БД**: Connection pool'ы.
- **Потоки ввода-вывода**.

Если такие ресурсы не закрывать, возникает их утечка, что может привести к исчерпанию лимитов операционной системы, 
ошибкам `Too many open files` и деградации производительности приложения.

### Анализ проблемы на примере файла

Представим, что у нас есть `lines: Stream[Task, String]`. Под капотом этот стрим держит открытый файловый дескриптор.

**Цель:** гарантировать, что дескриптор файла будет закрыт _независимо_ от того, как завершится работа с потоком.

**Наивный подход (который не работает):**

```dotty
val fileStream: Stream[Task, String] = openFile("data.txt") // Предположим, что это есть
val result: Task[List[String]] = fileStream.take(5).compile.toList // Берём только 5 строк
```

Проблема: после получения 5 строк поток `take(5)` завершается, но интерпретатор не знает, 
что нужно вызвать закрытие файла, так как исходный `fileStream` не был исчерпан (в файле могло быть 1000 строк). 
Дескриптор остается открытым.

### Таксономия завершения потоков

Чтобы правильно обработать закрытие ресурса, нужно учесть все три сценария завершения потока:

1.  **Нормальное завершение (Истощение):**
    - **Что происходит:** Поток дошел до своего естественного конца (например, достиг End Of File).
    - **Действие:** Ресурс нужно закрыть.

2.  **Раннее завершение (Прерывание):**
    - **Что происходит:** Поток-потребитель решил, что ему достаточно данных. Классические примеры — `.take(n)`, `.find(p)`, `.takeWhile(p)`.
    - **Проблема:** Источник (`lines`) еще не исчерпан и "готов" emit'ить больше данных, но его больше никто не слушает.
    - **Действие:** Ресурс нужно закрыть _немедленно_, а не ждать окончания всей программы.

3.  **Ненормальное завершение (Ошибка):**
    - **Что происходит:** Во время обработки потока было выброшено исключение (например, ошибка парсинга строки из файла).
    - **Действие:** Ресурс нужно закрыть, _и только после этого_ пробросить ошибку дальше по цепочке. 
      Это гарантирует, что утечка ресурса не усложнит отладку основной ошибки.

### Принципы (Guidelines) управления ресурсами

Формализуем два фундаментальных правила, которым должна следовать реализация `Stream`:

1.  **Принцип ответственности производителя:**
    - _"Производитель должен освободить все базовые ресурсы, как только он узнает, что у него больше нет значений для создания."_
    - **Объяснение:** Поток, владеющий ресурсом (наш `lines`), сам знает, как его закрыть (через функцию `release`). 
      Именно он должен взять на себя ответственность за его освобождение в момент, когда его работа завершена (по любой из трех причин).

2.  **Принцип ответственности интерпретатора:**
    - _"Любой поток `s`, который потребляет значения из другого потока `t`, 
      должен гарантировать, что действия по очистке `t` выполняются до остановки `s`."_
    - **Объяснение:** Операции вроде `take`, `flatMap` или `compile.toList` не просто трансформируют данные. 
      Они управляют _исполнением_ (interpretation) потока. 
      Если такая операция решает прервать потребление данных из upstream-источника (`t`), 
      она обязана просигнализировать этому источнику, что пора выполнить cleanup, 
      прежде чем завершить свою собственную работу.

## Конструктор `resource`

Вместо того чтобы вручную и небезопасно комбинировать `acquire` и `release` с помощью `flatMap` и `handleErrorWith`, 
предлагается абстракция верхнего уровня.

**Сигнатура:**

```dotty
def resource[F[_], R](acquire: F[R])(release: R => F[Unit]): Stream[F, R]
```

- `acquire: F[R]` — эффект приобретения ресурса (например, `Task[File]`).
- `release: R => F[Unit]` — функция освобождения ресурса (например, `f => Task(f.close())`).
- **Возвращает:** `Stream[F, R]` — поток, который emit'ит ровно один элемент — приобретенный ресурс `R`, 
  и гарантирует выполнение `release` при завершении.

**Как это используется для чтения файла:**

```dotty
def fileLines(path: String): Stream[Task, String] = {
  // 1. Создаём Stream, управляющий ресурсом File
  val fileResource: Stream[Task, File] = Stream.resource {
    Task(Source.fromFile(path)) // acquire
  } { source =>
    Task(source.close())        // release
  }

  // 2. "Вытягиваем" данные из ресурса, преобразуя File в Stream[String]
  fileResource.flatMap { file =>
    // Создаём поток строк из файла.
    // Теперь этот внутренний поток защищён гарантией,
    // что release действие будет вызвано, если его потребление прекратится.
    Stream.fromIterator(file.getLines())
  }
}

// Использование безопасно при любом сценарии

// Раннее завершение
val first5: Task[List[String]] = fileLines("big.txt").take(5).compile.toList 
// Нормальное завершение
val all: Task[List[String]] = fileLines("big.txt").compile.toList   
// Ошибка         
val failed: Task[List[String]] = fileLines("big.txt").map(_ => throw Err).compile.toList 
```

Во всех трех случаях файл будет гарантированно закрыт.

### Детали реализации (Как это может работать внутри)

Ключевая идея — интерпретатор потока должен вести **"регистр окончания"** (finalization register) или стек действий по очистке. 
Это внутреннее состояние, недоступное пользователю напрямую.

1.  **Компиляция:**
    - Когда интерпретатор встречает `Stream.resource(acquire)(release)`, он выполняет эффект `acquire`.
    - Полученный ресурс `R` помещается в регистр окончания вместе с функцией `release`.
    - Ресурс `R` emit'ится дальше по потоку.

2.  **Интерпретация и Очистка:**
    - При нормальном завершении: интерпретатор, дойдя до конца, просматривает регистр 
      и выполняет все `release`-действия в порядке LIFO (последний приобретенный — первый освобожденный).
    - При раннем завершении или ошибке: интерпретатор немедленно прекращает обработку последующих значений 
      и переходит к фазе _очистки_, выполняя все зарегистрированные `release`-действия.

3.  **Композиция:**
    - Если внутри `flatMap` открывается новый ресурс, его `release`-действие добавляется в стек. 
      Это гарантирует корректную вложенность: ресурсы закрываются в порядке, обратном их открытию.

> Лучше не зацикливаться на деталях реализации конкретной библиотеки. 
> Концепция `Resource` как монадической обертки для жизни ресурса — 
> это идиоматический и безопасный паттерн в функциональном программировании, 
> и его точная реализация (через `Bracket` в cats-effect, `ZManaged` в ZIO и т.д.) может варьироваться, но семантика остается неизменной.

## Концепция Scope (Области видимости)

`Scope` — это центральная абстракция для управления жизненным циклом ресурсов в потоковой обработке. 
Можно представить `Scope` как **контекст выполнения**, который:

1. Отслеживает приобретённые ресурсы
2. Гарантирует их освобождение в правильном порядке
3. Обеспечивает безопасность даже при прерываниях и ошибках

Каждая область может находиться в одном из двух состояний:

- **Открытая (Open)**:
    - Активно управляет ресурсами
    - Может иметь зарегистрированные финализаторы
    - Может содержать вложенные подобласти
    - Готова к выполнению операций

- **Закрытая (Closed)**:
    - Завершила свою работу
    - Все финализаторы уже выполнены
    - Не принимает новые операции

Области образуют древовидную структуру:

```
Root Scope
├── Subscope 1 (финализатор A)
│   ├── Subscope 1.1 (финализатор B)
│   └── Subscope 1.2 (финализатор C)
└── Subscope 2 (финализатор D)
```

### Регистрация финализаторов

`Scope` тип должен быть параметризован типом эффекта `F`.

```dotty
// Концептуальный интерфейс
trait Scope[F[_]]:
  def openSubscope(finalizer: F[Unit]): F[Scope[F]]
  def close: F[Unit]
```

При открытии подобласти регистрируется финализатор — эффект типа `F[Unit]`, который будет выполнен при закрытии области.

### Процесс закрытия Scope

Закрытие области выполняется в строго определённом порядке:

1. **Рекурсивное закрытие подобластей**: Сначала закрываются все вложенные области
2. **Выполнение финализаторов**: Затем выполняется собственный финализатор области
3. **LIFO порядок**: Ресурсы освобождаются в порядке, обратном их приобретению

```dotty
// Псевдокод процесса закрытия
def closeScope(scope: Scope): F[Unit] =
  for
    _ <- scope.subscopes.traverse(closeScope) // Закрываем все подобласти
    _ <- scope.finalizer                      // Выполняем финализатор
  yield ()
```

## Реализация Ref: Функциональная ссылка

В функциональном программировании нельзя просто использовать изменяемые переменные. 
`Ref` предоставляет безопасный способ работы с изменяемым состоянием в контексте эффектов `F[_]`.

### Базовая структура

```dotty
final class Ref[F[_], A] private (
  // Низкоуровневое атомарное хранилище
  underlying: AtomicReference[A],
  // Способ преобразования побочных эффектов в эффект F
  delay: [A] => (() => A) => F[A]
):
```

### Ключевые методы

#### 1. `get: F[A]`

Читает текущее значение атомарно:

```dotty
def get: F[A] = delay(() => underlying.get)
// Преобразует: () => A (побочный эффект) в F[A] (эффект)
```

#### 2. `set(a: A): F[Unit]`

Устанавливает новое значение атомарно:

```dotty
def set(a: A): F[Unit] = delay(() => underlying.set(a))
```

#### 3. `modify[B](f: A => (A, B)): F[B]`

Атомарно преобразует значение и возвращает результат:

```dotty
def modify[B](f: A => (A, B)): F[B] = delay: () =>
  @annotation.tailrec
  def loop(): B =
    val oldA = underlying.get           // Читаем текущее значение
    val (newA, result) = f(oldA)        // Вычисляем новое значение и результат
    if underlying.compareAndSet(oldA, newA) then
      result                            // Успешно обновили
    else
      loop()                            // Повторяем при конкуренции
      
  loop()
```

**Как работает Compare-And-Set (CAS):**

```java
// AtomicReference.compareAndSet(expect, update)
// "Если текущее значение == expect, установить update и вернуть true"
// Иначе вернуть false и повторить операцию
```

### Создание Ref

```dotty
object Ref:
  def apply[F[_], A](initial: A)(using F: Monad[F]): Ref[F, A] =
    new Ref(
      new AtomicReference[A](initial),
      [A] => (th: () => A) => F.unit(()).map(_ => th())
    )
```

Здесь `F.unit(())` создаёт минимальный эффект, а `map(_ => th())` "подвешивает" побочный эффект в контексте `F`.

## Интеграция Scope и Ref

Используя `Ref` and `modify`, мы можем реализовать `Scope` как конечный автомат с состояниями `Open` and `Closed`:

```dotty
class Scope[F[_]](
  parent: Option[Scope[F]],     // Ссылка на родительскую область
  val id: Id,                   // Уникальный идентификатор области
  state: Ref[F, Scope.State[F]] // Атомарная ссылка на состояние
)(using F: MonadThrow[F]):      // Контекст: монада с возможностью выбрасывания ошибок
  import Scope.State

  // Интерфейсные методы
  def open(finalizer: F[Unit]): F[Scope[F]] = ???  // Создание подобласти
  def close: F[Unit] = ???                         // Закрытие области
```

### Модель состояния Scope

```dotty
object Scope:
  // ADT (Algebraic Data Type) для представления состояния
  enum State[F[_]]:
    case Open(
      finalizer: F[Unit],         // Финализатор этой области
      subscopes: Vector[Scope[F]] // Активные подобласти
    ) extends State[F]

    case Closed() extends State[F] // Закрытое состояние
    
  def root[F[_]](using F: MonadThrow[F]): Scope[F[_]] =
    new Scope(None, new Id, Ref(State.Open(F.unit(()), Vector.empty)))
```

### Детальная реализация метода `open`

```dotty
def open(finalizer: F[Unit]): F[Scope[F]] =
  state  // Ref[F, State[F]]
    .modify:  // Атомарная модификация состояния
      // Случай 1: Область открыта - можно создавать подобласти
      case State.Open(myFinalizer, subscopes) =>
        // Создаем новую подобласть
        val sub = new Scope(
          Some(this),           // Родитель - текущая область
          new Id,               // Новый уникальный ID
          Ref(State.Open(finalizer, Vector.empty)) // Начальное состояние
        )

        // Возвращаем: новое состояние + эффект с созданной подобластью
        State.Open(myFinalizer, subscopes :+ sub) -> F.unit(sub)

      // Случай 2: Область закрыта - пробуем создать в родительской
      case State.Closed() =>
        val next = parent match
          case None =>
            // Корневая область закрыта - ошибка
            F.raiseError(new RuntimeException("корневая область уже закрыта"))
          case Some(p) =>
            // Рекурсивно пытаемся создать в родительской области
            p.open(finalizer)

        // Возвращаем текущее состояние (остается Closed) + эффект создания
        State.Closed() -> next
    .flatten  // Преобразуем F[F[Scope[F]]] в F[Scope[F]]
```

### Детальная реализация метода `close`

```dotty
def close: F[Unit] =
  state
    .modify:
      // Случай 1: Закрытие открытой области
      case State.Open(finalizer, subscopes) =>
        // Подготавливаем список действий для выполнения:
        // 1. Закрытие всех подобластей (в обратном порядке)
        // 2. Выполнение финализатора текущей области
        val finalizers = (subscopes.reverseIterator.map(_.close) ++
          Iterator(finalizer)).toList

        // Функция для безопасного выполнения всех финализаторов
        def go(rem: List[F[Unit]], error: Option[Throwable]): F[Unit] =
          rem match
            case Nil =>
              // Все финализаторы выполнены
              error match
                case None => F.unit(())         // Успех
                case Some(t) => F.raiseError(t) // Были ошибки

            case hd :: tl =>
              // Выполняем очередной финализатор с обработкой ошибок
              hd.attempt.flatMap: res =>
                go(tl, error orElse res.toEither.swap.toOption)

        // Переходим в состояние Closed и возвращаем действие закрытия
        State.Closed() -> go(finalizers, None)

      // Случай 2: Область уже закрыта - ничего не делаем
      case State.Closed() =>
        State.Closed() -> F.unit(())
    .flatten
```

#### Критически важные аспекты реализации close

##### 1. **Порядок закрытия (LIFO)**

```dotty
subscopes.reverseIterator.map(_.close) ++ // Сначала закрываем подобласти
Iterator(finalizer)                       // Затем текущий финализатор
```

**Почему `reverse`?** Чтобы соблюсти принцип "последний пришел - первый ушел".

##### 2. **Гарантия выполнения всех финализаторов**

```dotty
hd.attempt.flatMap: res =>  // attempt: F[A] => F[Either[Throwable, A]]
  go(tl, error orElse res.toEither.swap.toOption)
```

**Логика обработки ошибок:**

- `attempt` превращает потенциально падающий эффект в безопасный
- `error orElse ...` накапливает первую ошибку, но продолжает выполнение
- Все финализаторы выполняются, даже если некоторые падают

##### 3. **Сохранение первой ошибки**

```dotty
error orElse res.toEither.swap.toOption
```

Сохраняем первую произошедшую ошибку, но продолжаем выполнение остальных финализаторов.

### Особенности обработки ошибок

#### Стратегия "восходящего делегирования"

При закрытой области метод `open` делегирует создание родительской области:

```dotty
case State.Closed() =>
  parent match
    case None    => F.raiseError(...) // Критическая ошибка
    case Some(p) => p.open(finalizer) // Рекурсивное делегирование
```

Это создает элегантный механизм, где области могут "просить" родительские области создать ресурсы, когда сами уже закрыты.

#### Гарантия завершения

Метод `close` гарантирует, что:

1. Все подобласти будут закрыты
2. Все финализаторы будут выполнены
3. Первая ошибка будет проброшена, но не остановит выполнение остальных финализаторов

Эта реализация обеспечивает надежное управление ресурсами в функциональных потоках, 
полностью соответствующее принципам функционального программирования и предоставляющее строгие гарантии безопасности.

## Интеграция Scope в Stream и Pull

Начнем с создания двух новых конструкторов в `Pull` перечислении:

### Расширение алгебры Pull

#### Новые конструкторы Pull

```dotty
// Создание новой области видимости
case OpenScope[+F[_], +O, +R](
  source: Pull[F, O, R],       // Вычисление внутри новой области
  finalizer: Option[F[Unit]]   // Финализатор для новой области
) extends Pull[F, O, R]

// Работа в существующей области видимости
case WithScope[+F[_], +O, +R](
  source: Pull[F, O, R],       // Вычисление внутри указанной области
  scopeId: Id,                 // ID области для выполнения
  returnScopeId: Id            // ID области для возврата после завершения
) extends Pull[F, O, R]
```

Эти новые конструкторы подразумевают, что интерпретатор (т.е. `fold` и `step`)
должен отслеживать активную область и разрешать `step` изменять текущую область.
Чтобы разрешить изменения активной области, нам нужно изменить результат `step`, включив новую активную область.

Давайте введем новый тип, представляющий результат шага:

### Модель результата выполнения Step

#### Новая модель StepResult

```dotty
enum StepResult[F[_], +O, +R]:
  // Завершение вычисления
  case Done(scope: Scope[F], result: R)

  // Вывод элемента и продолжение вычисления
  case Out(scope: Scope[F], head: O, tail: Pull[F, O, R])
```

**Почему это важно:** Каждый шаг выполнения теперь явно указывает, в какой области должно продолжаться вычисление.

### Модифицированный алгоритм fold

#### Обновленная структура интерпретатора

```dotty
def fold[F2[x] >: F[x], R2 >: R, A](init: A)(f: (A, O) => A)(
  using F: MonadThrow[F2]
): F2[(R2, A)] =
  // Создаем корневую область
  val scope = Scope.root[F2]

  // Рекурсивная функция обработки
  def go(currentScope: Scope[F2], p: Pull[F2, O, R2], acc: A): F2[(R2, A)] =
    p.step(currentScope).flatMap:
      case StepResult.Done(_, r) =>
        // Вычисление завершено, возвращаем результат
        F.unit((r, acc))

      case StepResult.Out(nextScope, hd, tl) =>
        // Получен элемент, продолжаем обработку
        go(nextScope, tl, f(acc, hd))

  // Запускаем вычисление с гарантией закрытия области
  go(scope, this, init).attempt.flatMap:
    case Success(result) =>
      scope.close.flatMap(_ => F.unit(result))
    case Failure(error) =>
      scope.close.flatMap(_ => F.raiseError(error))
```

### Реализация step для OpenScope

#### Логика обработки OpenScope

```dotty
case OpenScope(source, finalizer) =>
  // Создаем новую подобласть с финализатором
  val finalizerEffect = finalizer.getOrElse(F.unit(()))

  scope.open(finalizerEffect).flatMap: newSubscope =>
    // Выполняем source в контексте новой области
    val wrappedSource = WithScope(source, newSubscope.id, scope.id)
    wrappedSource.step(newSubscope)
```

**Последовательность действий:**

1. Создаем новую подобласть с указанным финализатором
2. Оборачиваем исходное вычисление в `WithScope`
3. Выполняем вычисление в контексте новой области

### Реализация step для WithScope

Изменение `step` для `WithScope` немного сложнее.
Сначала мы ищем в дереве областей целевую область,
а затем используем эту область для пошагового выполнения исходного потока.
Если в результате получается `Done`, то закрываем целевую область и ищем область, в которую нужно вернуться.
В противном случае распространяем `WithScope` по оставшемуся потоку, возвращенному в `Out`:

```dotty
case WithScope(source, scopeId, returnScopeId) =>
  // Поиск целевой области
  scope.findScope(scopeId).flatMap:
    case Some(targetScope) =>
      // Область найдена, выполняем в ней (targetScope)
      executeInScope(targetScope, closeAfterUse = true)
      
    case None =>
      // Область не найдена, используем текущую (scope)
      executeInScope(scope, closeAfterUse = false)

  private def executeInScope(execScope: Scope[F], closeAfterUse: Boolean): F[StepResult[F, O, R]] =
    source.step(execScope).attempt.flatMap:
      // Случай 1: Успешное получение элемента
      case Success(StepResult.Out(resultScope, hd, tl)) =>
        F.unit(StepResult.Out(
          resultScope,
          hd,
          WithScope(tl, scopeId, returnScopeId) // Продолжаем в той же области
        ))

      // Случай 2: Успешное завершение
      case Success(StepResult.Done(resultScope, r)) =>
        findReturnScope(resultScope).flatMap: returnScope =>
          if closeAfterUse then
            execScope.close.flatMap: _ =>
              F.unit(StepResult.Done(returnScope, r))
          else
            F.unit(StepResult.Done(returnScope, r))

      // Случай 3: Ошибка выполнения
      case Failure(error) =>
        if closeAfterUse then
          execScope.close.flatMap: _ => 
            F.raiseError(error)
        else
          F.raiseError(error)

  private def findReturnScope(currentScope: Scope[F]): F[Scope[F]] =
    currentScope.findScope(returnScopeId).map(_.getOrElse(currentScope))  
```

### Гарантии безопасности

#### 1. Гарантия закрытия областей

```dotty
// Все области закрываются даже при ошибках
.attempt.flatMap:
  case Success(result) => scope.close.flatMap(_ => F.unit(result))
  case Failure(error) => scope.close.flatMap(_ => F.raiseError(error))
```

#### 2. Правильный порядок закрытия (LIFO)

```dotty
// WithScope гарантирует закрытие в правильном порядке
case Success(StepResult.Done(resultScope, r)) =>
  findReturnScope(resultScope).flatMap: returnScope =>
    if closeAfterUse then
      execScope.close.flatMap(_ => F.unit(StepResult.Done(returnScope, r)))
```

#### 3. Обработка ошибок в финализаторах

```dotty
// Финализаторы выполняются даже при ошибках в основном вычислении
case Failure(error) =>
  if closeAfterUse then
    execScope.close.flatMap(_ => F.raiseError(error))
```

### Детали механизма поиска областей

Метод `findScope` предназначен для поиска области видимости (`Scope`) по её уникальному идентификатору в дереве областей. 
Это критически важный механизм для:

1. **Управления ресурсами** - поиск области, в которой был зарегистрирован ресурс
2. **Обеспечения безопасности** - корректного закрытия областей в правильном порядке
3. **Поддержки вложенности** - работы с иерархической структурой областей видимости

```dotty
final class Scope[F[_]](parent: Option[Scope[F]], val id: Id, state: Ref[F, Scope.State[F]])(using F: MonadThrow[F]):
  import Scope.State

  def findScope(target: Id): F[Option[Scope[F]]] = ...

  def findThisOrSubScope(target: Id): F[Option[Scope[F]]] = ...
```

#### Основной метод `findScope`

```dotty
def findScope(target: Id): F[Option[Scope[F]]] =
  // 1. Сначала ищем в текущей области и её поддереве
  findThisOrSubScope(target).flatMap:
    case Some(s) =>
      // 2. Если нашли - возвращаем успех
      F.unit(Some(s))
    case None =>
      // 3. Если не нашли - делегируем поиск родителю
      parent match
        case Some(p) => p.findScope(target)  // Рекурсивный вызов
        case None    => F.unit(None)         // Дошли до корня - не нашли
```

#### Вспомогательный метод `findThisOrSubScope`

```dotty
def findThisOrSubScope(target: Id): F[Option[Scope[F]]] =
  // 1. Проверяем текущую область
  if id == target then F.unit(Some(this))
  else
    // 2. Если не совпадает - ищем в подобластях
    state.get.flatMap: // Атомарно читаем состояние
      case State.Open(_, subscopes) =>
        // 3. Рекурсивно ищем в каждой подобласти
        def go(rem: List[Scope[F]]): F[Option[Scope[F]]] =
          rem match
            case Nil =>
              F.unit(None) // Все подобласти проверены - не нашли
            case hd :: tl =>
              hd.findThisOrSubScope(target).flatMap:
                case Some(s) =>
                  F.unit(Some(s)) // Нашли в текущей подобласти
                case None =>
                  go(tl)          // Продолжаем поиск в остальных
        go(subscopes.toList) // Запускаем обход подобластей

      case State.Closed() =>
        F.unit(None) // Область закрыта - поиск невозможен      
```

## Реализация конструктора `resource`

Благодаря вышеописанным изменениям мы можем реализовать `resource` в терминах `Eval` и `OpenScope`:

```dotty
def resource[F[_], R](acquire: F[R])(release: R => F[Unit]): Stream[F, R] =
  // 1. Выполняем эффект приобретения ресурса
  Pull.Eval(acquire).flatMap(r =>
    // 2. Создаем новую область видимости с финализатором
    Pull.OpenScope(
      // 3. Эмитим приобретенный ресурс
      Pull.Output(r),
      // 4. Регистрируем функцию освобождения
      Some(release(r))
    )
  )
```

#### Как это работает:

1. **Acquire Phase**: `Pull.Eval(acquire)` выполняет эффект получения ресурса
2. **Resource Emission**: `Pull.Output(r)` передает ресурс ниже по течению
3. **Finalizer Registration**: `Some(release(r))` регистрирует функцию очистки
4. **Scope Isolation**: `OpenScope` создает изолированную область для управления ресурсом

### Введение оператора `scope` для раннего завершения

Однако всё ещё нужно сделать одну вещь для обработки раннего завершения:
всякий раз, когда мы потенциально можем отбросить остаток потока, мы должны сделать это в новой области.
Это гарантирует, что все ресурсы будут выделены подобластям,
и все поддерево области будет закрыто в самое ближайшее подходящее время.

Давайте добавим для `Stream` метод расширения `scope`, открывающую новую область действия,
а затем введем такие области действия для любых операций,
которые могут частично выполнять потоки — таких операций, как `take`, `takeWhile` и так далее:

#### Реализация метода `scope`

```dotty
def scope: Stream[F, O] =
  // Создаем новую область без специфичного финализатора
  Pull.OpenScope(self, None)
```

#### Применение в операциях раннего завершения

```dotty
def take(n: Int): Stream[F, O] =
  // 1. Берем n элементов из исходного потока
  // 2. Игнорируем остаток (.void)
  // 3. Оборачиваем в новую область видимости
  self.take(n).void.scope
```

#### Почему это важно:

**Без `scope`:**

```dotty
// Проблема: ресурсы, выделенные после take(5), не освобождаются
lines("big.txt").take(5).compile.toList
// Файл остается открытым!
```

**Со `scope`:**

```dotty
// Решение: создаем изолированную область для операции take
lines("big.txt").take(5).scope.compile.toList
// Все ресурсы корректно освобождаются
```

#### Механизм работы:

1. **Создание области**: `take(n)` создает новую область видимости
2. **Частичное выполнение**: Поток выполняется до n-го элемента
3. **Завершение области**: Когда `take` завершается, вся его область закрывается
4. **Очистка ресурсов**: Все ресурсы, выделенные в области, освобождаются

## Полный пример: Конвертация файлов с гарантией безопасности

Собрав все эти части вместе, мы можем вернуться к примеру конвертации файла,
на этот раз используя эффективную версию `Stream`:

#### 1. Безопасное чтение файла

```dotty
def file(path: String): Stream[Task, Source] =
  Stream.resource(
    // Acquire: открываем файл
    Task(Source.fromFile(path))
  )(
    // Release: гарантированно закрываем
    s => Task(s.close())
  )

def lines(path: String): Stream[Task, String] =
  file(path).flatMap: source =>
    // Преобразуем Source в поток строк
    Stream.eval(Task(source.getLines))
      .flatMap(Stream.fromIterator)
```

#### 2. Безопасная запись в файл

```dotty
def fileWriter(path: String): Stream[Task, BufferedWriter] =
  Stream.resource(
    // Acquire: создаем writer
    Task(Files.newBufferedWriter(Paths.get(path)))
  )(
    // Release: гарантированно закрываем
    w => Task(w.close())
  )

def writeLines(path: String): Pipe[Task, String, Unit] =
  lines =>
    fileWriter(path).flatMap: writer =>
      // Для каждой строки выполняем запись
      lines.mapEval(line => Task {
        writer.write(line)
        writer.newLine()
      })
```

#### 3. Конвейер преобразований

```dotty
val conversion: Pipe[Task, String, String] =
  trimmed andThen      // Удаляем пробелы
  nonEmpty andThen     // Игнорируем пустые строки
  nonComment andThen   // Игнорируем комментарии
  asDouble andThen     // Парсим в Double
  toCelsius andThen    // Конвертируем в Celsius
  toString             // Преобразуем обратно в String
```

#### 4. Полная интеграция

```dotty
def convert(inputFile: String, outputFile: String): Task[Unit] =
  lines(inputFile)                // Безопасное чтение
    .pipe(conversion)             // Применяем преобразования
    .pipe(writeLines(outputFile)) // Безопасная запись
    .run                          // Запускаем вычисление
```

### Ключевые преимущества архитектуры

#### 1. **Сквозная безопасность ресурсов**

```dotty

// Даже при ошибках в середине обработки
```

#### 2. **Композируемость**

```dotty

  .take(1000)        // Раннее завершение безопасно

  .map(_.toUpperCase)
```

#### 3. **Изоляция областей видимости**

```dotty

  .scope  // Изолируем всю цепочку
  .compile
  .toList
```

#### 4. **Гарантии выполнения финализаторов**

- ✅ LIFO порядок закрытия
- ✅ Обработка ошибок в финализаторах
- ✅ Атомарность операций
- ✅ Thread-safe выполнение

#### Иерархия областей для `take(5)`

```
Root Scope
└── Take Scope (создана take(5).scope)
    ├── Resource Scope 1 (файл input.txt)
```

#### Процесс закрытия:

Эта архитектура обеспечивает промышленный уровень надежности управления ресурсами в функциональных потоках, 
полностью соответствуя принципам функционального программирования.

## Динамическое распределение ресурсов

Динамическое распределение ресурсов — это паттерн, при котором программа во время выполнения:

1. Читает конфигурацию или метаданные из входного потока
2. На основе этих данных приобретает новые ресурсы
3. Выполняет преобразования с использованием этих ресурсов
4. Гарантированно освобождает все ресурсы по завершении

### Сценарий 1: Объединение нескольких файлов

#### Постановка задачи

Имеется файл `fahrenheits.txt` со списком путей к другим файлам:

```
data/file1.txt
data/file2.txt
data/file3.txt
```

Нужно:

1. Прочитать каждый файл из списка
2. Объединить их содержимое в единый поток
3. Преобразовать температуры в градусы Цельсия
4. Записать результат в `celsius.txt`

#### Реализация с гарантией безопасности

```dotty
def convertAll(inputFile: String, outputFile: String): Task[Unit] =
  // 1. Читаем файл со списком путей
  lines(inputFile)
    // 2. Для каждого пути создаем поток строк файла
    .flatMap(filePath => lines(filePath))
    // 3. Применяем цепочку преобразований
    .pipe(conversion)
    // 4. Записываем результат в выходной файл
    .pipe(writeLines(outputFile))
    // 5. Запускаем выполнение
    .run
```

#### Как работает flatMap в этом контексте:

```dotty
// Концептуальное представление
val dynamicStream: Stream[Task, String] =
  lines("fahrenheits.txt").flatMap: filePath =>
    // Для каждого filePath создается НОВЫЙ поток с собственными ресурсами
    lines(filePath) // Этот поток безопасно управляет файловым дескриптором
```

#### Жизненный цикл ресурсов:

1. **Открытие `fahrenheits.txt`** - читаем список файлов
2. **Последовательное открытие файлов** - для каждого пути в списке:
    - Открывается файловый дескриптор
    - Читается содержимое
    - Дескриптор закрывается после чтения
3. **Непрерывный поток данных** - данные из всех файлов объединяются
4. **Гарантированное закрытие** - даже при ошибках все дескрипторы закрываются

### Сценарий 2: Multi-sink output (Запись в несколько файлов)

#### Постановка задачи

Для каждого файла из `fahrenheits.txt`:

1. Прочитать его содержимое
2. Преобразовать температуры
3. Создать соответствующий выходной файл
4. Записать результат в файл с суффиксом `.celsius`

#### Реализация

```dotty
def convertMultisink(inputFile: String): Task[Unit] =
  // 1. Читаем файл со списком путей
  lines(inputFile).flatMap: file =>
    // 2. Для каждого файла создаем отдельный pipeline:
    lines(file)                            // Читаем исходный файл
      .pipe(conversion)                    // Применяем преобразования
      .pipe(writeLines(file + ".celsius")) // Пишем в новый файл
  .run // Запускаем выполнение
```

#### Ключевые особенности:

**Параллельная обработка ресурсов:**

```dotty
// Для каждого входного файла создается независимая цепочка:
// File1: lines("file1.txt") → conversion → writeLines("file1.txt.celsius")
// File2: lines("file2.txt") → conversion → writeLines("file2.txt.celsius")
// File3: lines("file3.txt") → conversion → writeLines("file3.txt.celsius")
```

**Гарантии безопасности:**

- Каждый файл открывается и закрывается в своей области видимости
- Ошибка в одном файле не влияет на обработку других
- Все ресурсы освобождаются даже при падении всего pipeline

### Механизм работы flatMap с ресурсами

#### Под капотом flatMap:

```dotty
def flatMap[F[_], O, R](s: Stream[F, O])(f: O => Stream[F, R]): Stream[F, R] =
  // Создаем новую область видимости для каждого элемента
  s.map(f).flatten.scope // Важно: каждый вложенный поток в своей области
```

#### Иерархия областей видимости:

```
Корневой Scope
├── Scope для fahrenheits.txt
│   ├── Scope для file1.txt (открыт → обработан → закрыт)
│   ├── Scope для file2.txt (открыт → обработан → закрыт)
│   └── Scope для file3.txt (открыт → обработан → закрыт)
└── Scope для celsius.txt (если в первом сценарии)
```

#### Процесс выполнения:

1. **Чтение метаданных**: Открывается `fahrenheits.txt`, читаются пути
2. **Динамическое создание ресурсов**: Для каждого пути:
    - Создается новая область видимости
    - Открывается файловый дескриптор
    - Данные обрабатываются и передаются ниже по течению
    - Область закрывается, дескриптор освобождается
3. **Непрерывность потока**: Данные из всех файлов последовательно передаются дальше

### Пример с обработкой ошибок

```dotty
def robustConvertMultisink(inputFile: String): Task[Unit] =
  lines(inputFile)
    .attempt // Преобразуем ошибки в значения
    .flatMap {
      case Right(filePath) =>
        lines(filePath)
          .pipe(conversion)
          .pipe(writeLines(filePath + ".celsius"))
          .handleErrorWith: e =>
            Stream.eval(Task(println(s"Error processing $filePath: $e")))
      case Left(error) =>
        Stream.eval(Task(println(s"Error reading input: $error")))
    }
    .run
```

Эта архитектура демонстрирует мощь функциональных потоков для работы с динамическими ресурсами, 
обеспечивая при этом высочайший уровень безопасности и надежности.
