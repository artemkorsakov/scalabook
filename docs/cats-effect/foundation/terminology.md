# Асинхронность, Одновременность и Параллелизм

## Введение

В большинстве императивных языков программирования (включая Scala) термины **«асинхронный»** (asynchronous), 
**«одновременный»** (concurrent) и **«параллельный»** (parallel) часто используются как взаимозаменяемые. 
Это приводит к путанице, особенно при работе с такими фреймворками, как Cats Effect, 
где каждое из этих понятий имеет строго определённое значение, 
и их различие становится критически важным для правильного проектирования систем.

Давайте подробно разберём каждое понятие, их взаимосвязи и то, как Cats Effect реализует соответствующие механизмы.

## Асинхронность (Asynchronous) — как производится значение

### Определение

**Асинхронность** — это противоположность **синхронности**. 
Она описывает **способ**, которым данный эффект производит своё значение (или ошибку).

Важно понять: асинхронность — это **деталь реализации** конкретного эффекта, а не модель организации вычислений в целом. 
Она ничего не говорит о том, выполняется ли эффект одновременно с другими или последовательно.

### Синхронные эффекты

Синхронные эффекты в Cats Effect создаются с помощью методов:

- `IO.apply` (или что то же самое `IO.delay`)
- `IO.blocking`
- `IO.interruptible`
- `IO.interruptibleMany`

Они работают привычным образом: возвращают результат или бросают ошибку через `throw`.

```dotty
import cats.effect.IO

// Синхронный эффект: блокирует текущий поток на 500 мс
val syncDelay: IO[Unit] = IO {
  Thread.sleep(500) // Внимание: блокирует поток ОС!
}
```

**Проблема синхронных блокировок**: `Thread.sleep` не возвращает управление потоку JVM до истечения задержки. 
Это означает, что **дефицитный ресурс** (поток операционной системы) тратится впустую на всё время ожидания. 
Если у вас 1000 одновременных запросов, каждый из которых делает такую блокировку, 
вам понадобится 1000 потоков ОС, что приведёт к огромным накладным расходам.

### Асинхронные эффекты

Асинхронные эффекты создаются с помощью `IO.async` (или упрощённого `IO.async_`). 
Они производят результат через **обратный вызов (callback)**, где:

- Успешный результат передаётся как `Right(value)`
- Ошибка передаётся как `Left(exception)`

```dotty
import java.util.concurrent.{Executors, TimeUnit}
import cats.effect.IO

val scheduler = Executors.newScheduledThreadPool(1)

// Асинхронный эффект: не блокирует поток
val asyncDelay: IO[Unit] = IO.async_ { callback =>
  scheduler.schedule(
    new Runnable:
      def run(): Unit = callback(Right(()))
    ,
    500,
    TimeUnit.MILLISECONDS
  )
  () // Финализатор (необязательный)
}
```

**Что здесь происходит?**

1. `IO.async_` регистрирует `callback`.
2. Планировщик получает задачу выполнить `callback` через 500 мс.
3. Метод `async_` **возвращает управление немедленно**.
4. Поток ОС, на котором выполнялся этот код, освобождается и может делать другую работу.
5. Через 500 мс планировщик вызывает `callback` на каком-то потоке (часто из пула).

**Ключевое преимущество**: Базовый поток ОС **не тратится впустую** на ожидание. 
Он может быть перенаправлен для выполнения другой работы.

### Сравнение синхронных и асинхронных эффектов

| Характеристика          | Синхронный (Thread.sleep)      | Асинхронный (ScheduledExecutor)       |
|-------------------------|--------------------------------|---------------------------------------|
| Возврат управления      | Только после завершения        | Немедленно                            |
| Использование потока ОС | Блокирует на всё время         | Освобождает сразу                     |
| Масштабируемость        | Плохая (нужен поток на задачу) | Отличная (один поток на много задач)  |
| Сложность написания     | Простая (знакомый код)         | Сложная (ручное управление колбэками) |

### Роль волокон: устранение сложности асинхронности

Главная проблема асинхронных эффектов — **сложность работы с обратными вызовами**. 
В классическом асинхронном программировании (Node.js, Netty) код быстро превращается в «ад обратных вызовов» (callback hell).

**Волокна Cats Effect полностью устраняют этот недостаток.** 
Для внешнего кода оба примера выше выглядят одинаково:

```dotty
// И синхронный, и асинхронный эффект имеют один и тот же тип!
val delay: IO[Unit] = ???  // Неважно, как он реализован внутри

// Использование одинаково для обоих
for
  _ <- delay
  _ <- IO.println("Прошло 500 мс")
yield ()
```

Разница между `return/throw` и обратным вызовом **полностью инкапсулирована** на уровне определения эффекта. 
Остальная часть вашего приложения не знает и не должна знать, является ли эффект синхронным или асинхронным. 
В этом — **огромная мощь волокон**.

### Важное уточнение

> **Ничто в определении «асинхронный» не подразумевает «одновременный» или «параллельный».**

Асинхронный эффект может быть выполнен **последовательно** с другими эффектами — 
это просто деталь того, как он получает своё значение. Вы можете написать:

```dotty
// Всё выполняется последовательно, несмотря на асинхронность внутри
for
  _ <- asyncDelay1   // Асинхронный
  _ <- asyncDelay2   // Тоже асинхронный
  _ <- IO.println("Done")
yield ()
```

Здесь `asyncDelay2` начнётся **только после** завершения `asyncDelay1`. 
Асинхронность не означает автоматического распараллеливания.

## Одновременность (Concurrency) — независимость потоков управления

### Определение

В терминологии Cats Effect **одновременное выполнение** означает, 
что два или более действий **независимы по своему потоку управления**. 
Это противоположность **последовательному выполнению**, где действия строго упорядочены.

Важнейший нюанс: **одновременные действия не обязаны выполняться параллельно**. 
Среда выполнения может решить выполнять их последовательно на одном ядре, 
и это всё равно будет корректной реализацией «одновременности». 
Параллельность — это лишь возможная оптимизация.

### Как выразить одновременность в Cats Effect

Самый простой способ — использовать операторы вида `parTupled`, `parMapN`, `parTraverse`:

```dotty
// Два независимых вызова сервисов
val serviceA: IO[Response] = callServiceA(params1)
val serviceB: IO[Response] = callServiceB(params2)

// Одновременное выполнение (среда может распараллелить)
val both: IO[(Response, Response)] = (serviceA, serviceB).parTupled
```

Запись `parTupled` — это **инструкция среде выполнения**: 
«Эти два эффекта независимы, их можно вычислять одновременно (возможно, параллельно, если есть свободные ядра)». 
Cats Effect **никогда не предполагает** возможность параллельного выполнения самостоятельно — 
вы должны явно указать это с помощью соответствующих операторов.

### Низкоуровневые примитивы: `start` и `join`

Вся высокоуровневая одновременность в Cats Effect построена на двух фундаментальных примитивах:

- `start` — запускает волокно в фоне, возвращает `Fiber`
- `join` — ожидает завершения волокна и возвращает его результат

```dotty
val fiber: Fiber[IO, Response] = serviceA.start  // Запускаем в фоне
val resultA: IO[Response] = fiber.join           // Ожидаем результат

// То же самое, что parTupled, но вручную:
val bothManual: IO[(Response, Response)] = 
  for
    fiberA <- serviceA.start
    fiberB <- serviceB.start
    resultA <- fiberA.join
    resultB <- fiberB.join
  yield (resultA, resultB)
```

Эти примитивы значительно быстрее и безопаснее, чем аналогичные операции с потоками Java.

### Структурированная одновременность (Structured Concurrency)

**Структурированная одновременность** — это подход, при котором все параллельные операции образуют **замкнутую иерархию**:

- Любая операция, запускающая параллельные действия, должна гарантировать их завершение, прежде чем двигаться дальше.
- Результаты параллельной операции доступны **только после её полного завершения** и **только родительскому элементу**.

**Пример структурированной одновременности**:

```dotty
// Результат недоступен, пока оба сервиса не завершатся
val result: IO[(Response, Response)] = (serviceA, serviceB).parTupled

// Внутри этого блока ответы A и B уже доступны
result.flatMap { case (respA, respB) =>
  processBoth(respA, respB)
}
```

**Преимущества структурированной одновременности:**

- Нет «утекших» волокон (запущенных, но потерянных)
- Легче рассуждать о времени жизни ресурсов
- Автоматическая отмена при ошибках
- Более предсказуемое поведение

**Инструменты Cats Effect для структурированной одновременности:**

- `parTupled`, `parMapN`, `parTraverse` — основные операторы
- `background` — для задач, которые должны жить дольше родителя, но с контролем
- `Supervisor` — для управления набором долгоживущих волокон
- `Dispatcher` — для интеграции с callback-кодом

### Неструктурированная одновременность

Иногда структурированная одновременность слишком ограничивающая. 
Cats Effect **не запрещает** неструктурированную одновременность, когда это необходимо:

```dotty
// Запускаем волокно и не ждём его
val fiber: Fiber[IO, Unit] = longRunningTask.start

// Родитель завершается, а волокно продолжает жить (возможно, это нужно)
// Но это может привести к "утечке" волокна, если потерять ссылку
```

**Риски неструктурированной одновременности:**

- Утечки волокон (потеря ссылки на `Fiber`)
- Ресурсы не освобождаются
- Сложнее отладка и тестирование

**Рекомендация**: По возможности используйте структурированные инструменты (`background`, `Supervisor`), а не голые `start`.

### Общее конкурентное состояние: Ref и Deferred

`Ref` (атомарная ссылка) и `Deferred` (однократный promise) — это **неструктурированные** инструменты для моделирования общего состояния:

```dotty
val counter: IO[Ref[IO, Int]] = IO.ref(0)

// Неструктурированно: любое волокно может изменить счётчик в любое время
counter.update(_ + 1)
```

Эти примитивы **не навязывают структуру** и могут приводить к сложной для понимания логике. 
Однако они являются строительными блоками для мощных абстракций высокого уровня:

- `Queue` — очередь
- `Semaphore` — семафор
- `Hotswap` — горячая замена ресурсов
- `Resource` — управление ресурсами

**Вывод**: Cats Effect **поощряет структурированную одновременность** 
и предоставляет множество гибких инструментов для её достижения, 
но не препятствует неструктурированным подходам, когда они действительно нужны.

> Более подробно вышеописанные примитивы будут разобраны позднее.

## Параллельность (Parallelism) — деталь реализации среды выполнения

### Определение

**Параллельное выполнение** означает, что два процесса выполняются **одновременно на разных физических ядрах** (или процессорах). 
Это **исключительно деталь реализации среды выполнения и оборудования**.

Параллельность тесно связана с одновременностью, но это не одно и то же:

- **Одновременность** — это **семантика** (независимость потоков управления)
- **Параллельность** — это **физическая реальность** (одновременное выполнение на разных ядрах)

### Когда одновременное не равно параллельному

#### Сценарий 1: JavaScript (однопоточная среда)

JavaScript выполняется в одном потоке. Даже если вы определили эффекты как одновременные:

```dotty
// На JVM это может выполниться параллельно
// На JavaScript — строго последовательно на одном потоке
(serviceA, serviceB).parTupled
```

Это **не означает**, что `parTupled` бесполезен в JavaScript! 
Среда выполнения всё равно знает, что `serviceA` и `serviceB` независимы, 
и может чередовать их выполнение (кооперативная многозадачность), 
но физической параллельности не будет.

#### Сценарий 2: Больше волокон, чем потоков

Cats Effect на JVM обычно создаёт количество потоков, 
соответствующее количеству **физических ядер** (например, 8 потоков на 8-ядерном процессоре). 
Волокон могут быть **миллионы**:

```dotty
// Запускаем 1 000 000 одновременных волокон
val fibers = (1 to 1_000_000).map(_ -> task.start)
```

Одновременно (физически) на 8 ядрах могут выполняться только **8 волокон**. Остальные будут ждать в очереди. 
С точки зрения семантики, все 1 000 000 волокон считаются «одновременными», 
но физически они выполняются последовательно, когда приходит их очередь.

### Справедливость (Fairness) и предотвращение захвата потока

Волокнам **предотвращается «захват»** своего несущего потока. 
Cats Effect гарантирует, что одно волокно не может бесконечно долго занимать поток ОС, блокируя другие волокна.

**Механизмы справедливости:**

1. **Асинхронные эффекты** — при выполнении асинхронной операции волокно добровольно уступает поток.
2. **Искусственная кооперативность** — если волокно выполняет слишком много последовательных синхронных эффектов 
   без «уступки», среда выполнения **вставляет искусственную точку уступки** (предотвращает голодание).

```dotty
// Плохо: длинная цепочка синхронных эффектов без уступки
def badLoop: IO[Unit] = (1 to 1000000).foldLeft(IO.unit): (acc, i) =>
  acc *> IO(compute(i)) // Может заблокировать другие волокна

// Хорошо: Cats Effect автоматически вставит точки уступки
// Но можно и явно:
def goodLoop: IO[Unit] = (1 to 1000000).foldLeft(IO.unit): (acc, i) =>
  acc *> IO(compute(i)) *> IO.cede // Явно уступаем поток
```

`IO.cede` — явная инструкция «уступить поток другим волокнам». 
Обычно не нужна, так как Cats Effect вставляет уступки автоматически.

## Сводная таблица: сравнение понятий

| Понятие              | Что определяет?                                 | Противоположность                          | Кто контролирует?                         | Пример                      |
|----------------------|-------------------------------------------------|--------------------------------------------|-------------------------------------------|-----------------------------|
| **Асинхронность**    | Способ получения значения (callback vs return)  | Синхронность                               | Разработчик (при определении эффекта)     | `IO.async_`                 |
| **Одновременность**  | Независимость потоков управления                | Последовательность                         | Разработчик (через `parTupled`, `start`)  | `(a, b).parTupled`          |
| **Параллельность**   | Физическое выполнение на разных ядрах           | Последовательное выполнение на одном ядре  | Среда выполнения + ОС + железо            | Зависит от количества ядер  |

## Практические рекомендации

### Когда использовать асинхронные эффекты

- **Всегда**, когда это возможно для I/O операций (сеть, диск, таймеры)
- Cats Effect предоставляет асинхронные версии многих операций из коробки
- Для блокирующих операций используйте `IO.blocking`

### Когда использовать одновременность

- **Всегда**, когда задачи независимы (можно ускорить выполнение)
- Используйте высокоуровневые операторы: `parTraverse`, `parSequence`, `parMapN`
- Избегайте `start` без структурированных обёрток (`background`, `Supervisor`)

### Ожидания от параллельности

- **Не полагайтесь** на физический параллелизм для корректности
- Код должен работать правильно даже на одном ядре
- Рассматривайте параллельность как **оптимизацию**, а не гарантию

## Заключение

Понимание различий между асинхронностью, одновременностью и параллельностью важно для эффективной работы с Cats Effect. 
Эти концепции, хотя и взаимосвязаны, описывают разные аспекты выполнения программы:

- **Асинхронность** — как (callback vs return)
- **Одновременность** — что (независимость задач)
- **Параллельность** — где (на каких ядрах)

Cats Effect предоставляет мощные и безопасные инструменты для работы со всеми тремя аспектами, 
позволяя писать корректный, производительный и масштабируемый код.
