# Потоковая обработка и инкрементный ввод-вывод

## Введение

Представим задачу: необходимо определить, содержит ли файл больше сорока тысяч непустых строк.

### Проблемы императивного подхода

В обычном (императивном) стиле эта задача часто выглядит так:

```dotty
import cats.effect.IO
import scala.io.Source

def linesGt40k(filename: String): IO[Boolean] = IO:
  // Открываем файл
  val src = Source.fromFile(filename)
  try
    var count = 0
    // Получаем "читалку" строк из файла
    val lines: Iterator[String] = src.getLines()
    // Пока не насчитали 40000 и есть еще строки
    while count <= 40000 && lines.hasNext do
      // Читаем следующую строку
      val row = lines.next
      // Увеличиваем счетчик, если строка не пустая
      count += (if row.nonEmpty then 1 else 0)
    count > 40000   // Возвращаем результат
  finally src.close // Обязательно закрываем файл!
```

**Что здесь хорошо:**

- Мы не загружаем весь файл в память сразу
- Можем остановиться досрочно, когда насчитали 40000 строк

**Что здесь представляет опасность:**

1. **Легко забыть закрыть файл** - если убрать `finally`, файл останется открытым
2. **Код сложно переиспользовать** - если захотим сделать другую проверку, придется копировать весь этот код
3. **Смешана логика и управление ресурсами** - трудно понять, где заканчивается работа с файлом и начинается подсчет строк
4. **Ошибки могут произойти в любом месте** - если что-то пойдет не так в середине, файл может не закрыться

### Идея функционального подхода

В функциональном программировании код выглядит как цепочка преобразований:

```dotty
// В идеальном мире мы бы хотели писать так:
linesFromFile("file.txt")
  .filter(_.nonEmpty)         // убрать пустые строки
  .take(40000)                // взять первые 40000 строк
  .exists(_.startsWith("//")) // ещё проверка, например: проверить, есть ли комментарии
  ...
  // дополнительные проверки и обработки
```

Такой код:

- **Понятный** - читается как инструкция сверху вниз
- **Составной** - можно легко менять отдельные шаги
- **Безопасный** - не нужно беспокоиться о деталях работы с файлом

### Почему просто реализовать `linesFromFile` - плохая идея?

Давайте попробуем сделать простую версию:

```dotty
def linesFromFile(filename: String): IO[LazyList[String]] = IO:
  val src = Source.fromFile(filename)
  // Создаем ленивую коллекцию строк
  LazyList.from[String](src.getLines()).appendedAll:
    src.close() // Пытаемся закрыть файл в конце
    LazyList.empty
```

**Проблемы этого подхода:**

1. **Когда закроется файл?** - только когда мы прочитаем **все** строки до конца
2. А если прочитаем только часть, файл останется открытым!
3. **Повторное использование** - если попробуем прочитать файл второй раз, он уже будет закрыт
4. **Неожиданные сюрпризы** - эффекты (открытие/закрытие файла) происходят в неочевидные моменты

Нужно решение, которое работает как вышеприведенный "идеальный" пример, но при этом:

1. **Ресурсы в безопасности** - файлы закрываются автоматически, даже если произошла ошибка
2. **Можно комбинировать** - простые операции собираются в сложные цепочки
3. **Работает по частям** - не загружает все данные в память сразу
4. **Предсказуемое** - точно знаем, когда происходят операции с внешним миром

### Как это выглядит на практике?

Представьте, что у нас есть специальный инструмент для работы с потоками данных:

```dotty
// Создаем безопасный поток из файла
Stream.resource(openFile("data.txt")) { file =>
  // Описываем цепочку преобразований
  Stream.fromIterator(file.lines)   // Берем строки из файла
    .filter(_.nonEmpty)             // Фильтруем пустые
    .take(40000)                    // Берем первые 40000
    .exists(_.startsWith("foo"))    // Проверяем условие
}
// Запускаем всю цепочку
.compile.toList 
```

**Что здесь происходит по шагам:**

1. `Stream.resource` - гарантирует, что файл будет закрыт в любом случае
2. `Stream.fromIterator` - создает поток данных из строк файла
3. `.filter`, `.take`, `.exists` - описываем какие преобразования нужно сделать
4. `.compile.toList` - запускаем всю описанную цепочку операций

> **Ключевая идея:** мы сначала **описываем** что хотим сделать, а потом **запускаем** это описание.

### Что это дает?

1. **Безопасность** - не нужно помнить о закрытии файлов
2. **Читаемость** - код выглядит как понятная цепочка операций
3. **Переиспользование** - можно легко менять отдельные шаги
4. **Эффективность** - данные обрабатываются постепенно, а не все сразу
5. **Предсказуемость** - точно знаем, когда происходит работа с внешним миром

Такой подход позволяет писать код, который одновременно:

- Красивый и понятный (как в функциональном программировании)
- Безопасный и эффективный (как в хорошем императивном коде)
- Легко изменяемый и составной (_composable_)

Функциональные потоковые библиотеки (например, [Functional Streams for Scala (FS2)](https://fs2.io)) позволяют:

- Сохранять композиционность чистого кода
- Автоматически управлять ресурсами
- Эффективно обрабатывать большие/бесконечные потоки
- Избегать скрытых побочных эффектов

Это дает преимущества функционального подхода даже для IO-интенсивных задач.

## Простые потоковые преобразования

Давайте разберем концепцию потоковых преобразований.

Потоковый процессор - это преобразователь данных, который:

- Принимает поток (последовательность) входных данных
- Обрабатывает их по мере поступления
- Возвращает новый поток выходных данных

Примеры потоков:

- Строки из файла
- HTTP-запросы к серверу
- Координаты кликов мыши
- Показания датчиков

### Тип данных `Pull`

Представьте, что вам нужно обработать огромный файл в 100 ГБ. 
Загрузка всего файла в память (в `List` или `Array`) невозможна. 
Потоковая обработка решает эту проблему, позволяя обрабатывать данные по частям, по мере их поступления.

**`Pull[O, R]`** — это функциональная абстракция для описания таких потоковых операций. 
Это не данные, а _план вычислений_, который выполняется лениво.

```dotty
enum Pull[+O, +R]:
  case Result[+R](result: R) extends Pull[Nothing, R]
  case Output[+O](value: O)  extends Pull[O, Unit]
  case FlatMap[X, +O, +R](
      source: Pull[O, X],
      f: X => Pull[O, R]
  ) extends Pull[O, R]

  def flatMap[O2 >: O, R2](
      f: R => Pull[O2, R2]
  ): Pull[O2, R2] =
    Pull.FlatMap(this, f)

  def >>[O2 >: O, R2](next: => Pull[O2, R2]): Pull[O2, R2] =
    flatMap(_ => next)

  def map[R2](f: R => R2): Pull[O, R2] =
    flatMap(r => Result(f(r)))
end Pull
```

Тип `Pull` имеет два фундаментальных параметра:

- **`O` (Output)** — тип элементов, которые мы _выдаём_ наружу в процессе работы (например, строки файла).
- **`R` (Result)** — тип _финального результата_, который мы возвращаем после завершения всех выходных операций 
  (например, количество обработанных байт, статус закрытия файла).

Проще говоря: `Pull` выдает ноль или более значений типа `O` и в конце возвращает одно значение типа `R`.

**Аналогия:** Представьте себе конвейер на фабрике (`Pull`). 
Он может:

1.  Выпускать готовые товары (`Output[O]`) на ленту.
2.  В конце своей работы сообщить итоговый отчет: "Произведено 1000 единиц, брак 2%" (`Result[R]`).

### Результат: `Result[+R](result: R)`

Это конечная точка вычисления. Говорит: "Все, обработка завершена. Вот итоговый результат".

```dotty
val done: Pull[Nothing, Int] = Pull.Result(42)
// Процесс завершился с результатом 42: Result(42)
val unitDone: Pull[Nothing, Unit] = Pull.Result(())
// Процесс завершился без значимого результата: Result(())
```

### Выдача: `Output[+O](value: O)`

Это основное действие для генерации элемента потока. 
Говорит: "Я выдаю один элемент `value`, а затем продолжу работу". 
Так как после вывода элемента процесс должен продолжаться, его результирующий тип — `Unit`.

```dotty
val hello: Pull[String, Unit] = Pull.Output("Hello") // Выдаем одну строку в поток
// Тип: Выдает String, а в конце возвращает Unit (пустой результат).
```

### Комбинация: `FlatMap[X, +O, +R](source: Pull[O, X], f: X => Pull[O, R])`

Это самый важный случай. 
Он позволяет _последовательно комбинировать_ операции `Pull`.
Это механизм, с помощью которого мы собираем сложные пайплайны из простых шагов.

**Как читать `FlatMap`?**

"Сначала выполни вычисление `source`. Когда оно завершится и вернет некоторое значение `X` (типа `X`), 
передай это значение в функцию `f`, чтобы получить следующее вычисление `Pull[O, R]`, и выполни его."

**Простой пример:**

```dotty
// Шаг 1: Процесс, который выдает число 1.
val step1: Pull[Int, Unit] = Pull.Output(1)

// Шаг 2: Функция, которая принимает результат предыдущего шага (но тут он Unit)
// и решает, что делать дальше.
val step2: Unit => Pull[Int, Unit] = (_: Unit) => Pull.Output(2)

// Комбинация: Сначала step1, затем step2(результат step1)
val combined: Pull[Int, Unit] = Pull.FlatMap(step1, step2)
// Эквивалентно более простой записи через `flatMap`:
val combinedSimple: Pull[Int, Unit] = step1.flatMap(step2)
```

Этот процесс выдаст `1`, а затем выдаст `2`.

## Комбинаторы

Когда мы работаем с потоковыми преобразованиями, нам постоянно нужно:

1. **Преобразовывать** результаты вычислений
2. **Комбинировать** несколько операций в последовательности
3. **Создавать** сложные пайплайны из простых компонентов

Для этого в `Pull` реализованы три основных комбинатора: `flatMap`, `map` и `>>`.

### Комбинатор `flatMap`: Последовательное выполнение

`flatMap` позволяет создать **последовательность операций**,
где результат первой операции становится входным параметром для следующей.

**Сигнатура:**

```dotty
def flatMap[O2 >: O, R2](f: R => Pull[O2, R2]): Pull[O2, R2]
```

**Как читать:**

"Возьми результат текущего `Pull` (типа `R`), передай его в функцию `f`, и выполни тот `Pull`, который вернет эта функция."

```dotty
Pull.Result(1).flatMap: x =>
  Pull.Result(x * 2)
```

**Пошаговое выполнение:**

1. Исходный `Pull` — `Result(1)`. Он сразу завершается с результатом `1`
2. Функция `f` принимает этот результат: `x = 1`
3. Функция возвращает новый `Pull`: `Result(1 * 2) = Result(2)`
4. Итоговый процесс завершается с результатом `2`

### Комбинатор `map`: Простое преобразование

`map` — это упрощенная версия `flatMap`, которая позволяет **только преобразовать** конечный результат, 
не производя новых побочных эффектов (выводов).

**Сигнатура:**

```dotty
def map[R2](f: R => R2): Pull[O, R2]
```

**Как читать:**

"Когда текущий `Pull` завершится с результатом `R`, преобразуй его в `R2` с помощью функции `f`."

```dotty
Pull.Result(1).map(_ * 2)
```

**Пошаговое выполнение:**

1. Исходный `Pull` — `Result(1)`
2. `map(_ * 2)` преобразует этот результат: `1 * 2 = 2`
3. Новый `Pull` будет завершаться с результатом `2`

**Отличие от `flatMap`:**

```dotty
// map: только преобразует результат
Pull.Result(3).map(_ + 1) // Result(4)

// flatMap: может создавать новые операции
Pull.Result(3).flatMap(x => Pull.Result(x + 1)) // Result(4)
// Результат тот же, но механизм разный
```

### Комбинатор `>>` (then): Последовательное выполнение действий

Оператор `>>` (произносится "then" — "затем") выполняет два процесса **последовательно**, полностью игнорируя результат первого.

**Сигнатура:**

```dotty
def >>[O2 >: O, R2](next: => Pull[O2, R2]): Pull[O2, R2]
```

**Как читать:**

"Выполни текущий процесс, а затем выполни процесс `next`."

**Ключевые особенности:**

1. **Игнорирует результат** первого процесса
2. **Сохраняет все выходные данные** обоих процессов
3. **Ленивый параметр** — `next` вычисляется только когда нужно

**Идеально для цепочек действий, где важен только вывод (`O`), а не промежуточные результаты.**

```dotty
val writeHeader: Pull[String, Unit] = Pull.Output("## Header")
val writeLine1: Pull[String, Unit] = Pull.Output("First line")
val writeLine2: Pull[String, Unit] = Pull.Output("Second line")

// Сборка пайплайна: вывести заголовок, а затем первую строку, а затем вторую строку.
val pipeline: Pull[String, Unit] = writeHeader >> writeLine1 >> writeLine2
```

**Эквивалент через `flatMap`:**

```dotty
// writeHeader >> writeLine1 эквивалентно:
writeHeader.flatMap(_ => writeLine1)

// Полный пайплайн:
writeHeader.flatMap(_ => writeLine1.flatMap(_ => writeLine2))
```

**Почему `>>` полезен?**

- **Упрощает код** — не нужно придумывать имена для неиспользуемых результатов
- **Улучшает читаемость** — явно показывает последовательность действий
- **Работает с side-effects** — идеален для цепочек операций ввода-вывода

## План и его исполнение

`Pull[O, R]` — это не данные, а **план вычислений**. 
Сам по себе он ничего не делает — он только описывает, какие операции нужно выполнить. 
Методы `step`, `fold` и `toList` — это разные способы **исполнить** этот план.

### Метод `.step`: Пошаговое выполнение плана

Метод `.step` — это базовый механизм выполнения, который обрабатывает план **по одному шагу за раз**. 
Это низкоуровневая операция, на основе которой построены все остальные.

**Сигнатура:** `def step: Either[R, (O, Pull[O, R])]`

- **`Left(r: R)`** -> План выполнен _полностью_. Финальный результат — `r`.
- **`Right((o: O, next: Pull[O, R]))`** -> План еще не завершен:
    - На этом шаге выдано значение `o`.
    - А также `next` — продолжение плана для следующих шагов.

**Детальный разбор алгоритма step**

```dotty
def step: Either[R, (O, Pull[O, R])] = this match
  // Базовые случаи:
  case Result(r) => Left(r)  // Завершаем с результатом
  case Output(o) => Right(o, Pull.Result(())) // Выдаем значение и завершаемся
  
  // Рекурсивный случай: раскрываем FlatMap
  case FlatMap(source, f) =>
    source match
      // Оптимизация: устраняем вложенные FlatMap (закон ассоциативности)
      case FlatMap(s2, g) =>
        s2.flatMap(x => g(x).flatMap(y => f(y))).step
      
      // Обрабатываем источник FlatMap
      case other => other.step match
          case Left(r)         => f(r).step // Источник завершился, применяем f
          case Right((hd, tl)) => Right((hd, tl.flatMap(f))) // Продолжаем
```

**Пример пошагового разбора:**

```dotty
val ourPull: Pull[Int, Unit] = Pull.Output(1) >> Pull.Output(2)

// Шаг 1
val step1: Either[Unit, (Int, Pull[Int, Unit])] = ourPull.step
// step1 = Right((1, Pull.Output(2)))
// Значение: 1. Следующий шаг: процесс Pull.Output(2).

// Шаг 2 (выполняем `next` из шага 1)
val nextPull: Pull[Int, Unit]                   = Pull.Output(2)
val step2: Either[Unit, (Int, Pull[Int, Unit])] = nextPull.step
// step2 = Right((2, Result(())))
// Значение: 2. Следующий шаг: процесс Result(()).

// Шаг 3 (выполняем `next` из шага 2)
val finalPull: Pull[Int, Unit]                  = Pull.Result(())
val step3: Either[Unit, (Int, Pull[Int, Unit])] = finalPull.step
// step3 = Left(()) // Процесс завершен.
```

**Зачем нужен такой сложный алгоритм для FlatMap?**

Алгоритм обеспечивает **корректное выполнение** цепочек операций:

1. **Ленивость** — вычисления происходят только когда нужно
2. **Стекобезопасность** — избегаем глубокой рекурсии
3. **Сохранение семантики** — гарантируем правильный порядок выполнения

### Метод `.fold`: Универсальное свертывание потока

Метод `fold` использует `step` для последовательной обработки всех элементов:

```dotty
@annotation.tailrec
final def fold[A](init: A)(f: (A, O) => A): (R, A) =
  step match
    case Left(r)         => (r, init)               // Процесс завершен
    case Right((hd, tl)) => tl.fold(f(init, hd))(f) // Продолжаем
```

**Ключевые особенности:**

- **Хвостовая рекурсия** — работает без переполнения стека
- **Инкрементальность** — обрабатывает элементы по одному
- **Универсальность** — подходит для любых операций свертывания

#### Визуализация работы fold

```dotty
val p = Pull.Output(1) >> Pull.Output(2)
p.fold(0)(_ + _)
```

**Итерация 1:**

- `p.step` → `Right((1, Pull.Output(2)))`
- `init = 0`, `hd = 1`
- `f(0, 1) = 1` (новый аккумулятор)
- Рекурсия: `Pull.Output(2).fold(1)(_ + _)`

**Итерация 2:**

- `Pull.Output(2).step` → `Right((2, Result(())))`
- `init = 1`, `hd = 2`
- `f(1, 2) = 3` (новый аккумулятор)
- Рекурсия: `Result(()).fold(3)(_ + _)`

**Итерация 3:**

- `Result(()).step` → `Left(())` (завершение)
- Результат: `((), 3)`

### Метод `.toList`: Специализированное преобразование

Метод `toList` — это специализированная версия `fold` для построения списка:

```dotty
def toList: List[O] =
  fold(List.newBuilder[O])((bldr, o) => bldr += o)(1).result
```

**Эквивалентная реализация (для понимания):**

```dotty
def toListSimple: List[O] =
  @annotation.tailrec
  def loop(current: Pull[O, Any], acc: List[O]): List[O] =
    current.step match
      case Left(_) => acc.reverse // Разворачиваем, т.к. добавляли в начало
      case Right((hd, tl)) => loop(tl, hd :: acc)

  loop(this, Nil)
```

#### Примеры использования

**Простое преобразование:**

```dotty
val p = Pull.Output(1) >> Pull.Output(2) >> Pull.Output(3)
p.toList // List(1, 2, 3)
```

**С пустым результатом:**

```dotty
val empty = Pull.Result("done")
empty.toList // List()
```

**Со сложными типами:**

```dotty
case class Person(name: String, age: Int)
val people = Pull.Output(Person("Alice", 30)) >> Pull.Output(Person("Bob", 25))
people.toList // List(Person("Alice", 30), Person("Bob", 25))
```

#### Важные ограничения:

1. **Потребление памяти** — все элементы загружаются в память
2. **Бесконечные потоки** — вызов `toList` на бесконечном потоке никогда не завершится
3. **Только выходные данные** — финальный результат `R` игнорируется

### Упражнение 11.1.1: Числа Фибоначчи

> [Репозиторий с упражнениями и инструкцией по выполнению][sample]

**Задача:**

Реализуйте метод, который выдает заданное количество чисел Фибоначчи в выходной поток, а в конце возвращает строку с n-м числом.

```dotty
def fib(n: Int): Pull[Int, String] = ???
```

**Ожидаемое поведение:**

```dotty
fib(5).toList         // Должно вернуть: List(0, 1, 1, 2, 3)
fib(5).fold(0)(_ + _) // Должно вернуть: ("5-е число Фибоначчи - это 3", 7)
```

@:note(🔍 Показать решение)

**Объяснение решения:**

1. Используем рекурсивный подход с аккумуляторами
2. На каждом шаге выводим текущее число Фибоначчи
3. Когда доходим до n-го числа, завершаемся с результатом-строкой
4. Обрабатываем краевые случаи (n ≤ 0, n = 1)

Это решение демонстрирует всю мощь комбинаторов `Pull` — мы создаем ленивый поток данных,
который вычисляется только по мере необходимости!

```dotty
def fib(n: Int): Pull[Int, String] =
  def fibHelper(remaining: Int, current: Int, next: Int): Pull[Int, String] =
    if remaining == 1 then
      Pull.Output(current) >>
        Pull.Result(s"$n-е число Фибоначчи - это $current")
    else
      Pull.Output(current) >>
        fibHelper(remaining - 1, next, current + next)

  if n <= 0 then Pull.Result("n должно быть положительным числом")
  else if n == 1 then
    Pull.Output(0) >> Pull.Result("1-е число Фибоначчи - это 0")
  else Pull.Output(0) >> fibHelper(n - 1, 1, 1)
```

## Практический пример: Чтение файла

Давайте реализуем функцию `fileLines`.

```dotty
// Предположим, есть функция, которая читает одну строку из файла.
// Она возвращает `None` при достижении конца файла (EOF).
def readLine(file: File): Option[String] = ???

def fileLines(file: File): Pull[String, Unit] =
  // Пытаемся прочитать строку
  readLine(file) match
    case None =>
      // Файл закончился, завершаем процесс с пустым результатом.
      Pull.Result(())
    case Some(line) =>
      // Мы прочитали строку! Наш план:
      // 1. Выдать эту строку в поток (Output).
      // 2. А ТОГДА (>>) запустить этот же процесс (fileLines) рекурсивно
      //    для чтения следующих строк.
      Pull.Output(line) >> fileLines(file)

// Использование
val fileProcessor: Pull[String, Unit] = fileLines(new File("data.txt"))
// Пока мы только описали процесс. Ни одна строка еще не прочитана!
```

**Ключевой вывод:** `fileLines` не читает файл сразу. 
Он строит _цепочку действий_ (`Output >> Output >> ... >> Result`), которую можно выполнить лениво, в том числе и не полностью.

## Преимущества `Pull`

1. **Композиционность (Composability)**: Маленькие, простые процессы (`Output`, `Result`) 
   легко комбинируются с помощью `flatMap` и `>>` в сложные пайплайны. Это чистый, функциональный дизайн.
2. **Ленивость (Laziness) & Инкрементальность (Incremental Processing)**: `Pull` описывает _что делать_, а не делает это немедленно. 
   Исполнение управляется через `.step` или `.fold`, что позволяет обрабатывать данные по частям, без потребления всей памяти.
3. **Безопасность ресурсов (Resource Safety)**: Поскольку исполнением управляем мы, 
   мы можем гарантировать, что файлы будут закрыты, а соединения разорваны в нужный момент 
   (например, вставив логику в `Result` или используя `try`/`finally` в `.fold`).
4. **Тестируемость (Testability)**: Легко тестировать отдельные шаги, 
   так как это просто значения данных (`case class`), а не побочные эффекты.

`Pull` — это мощный низкоуровневый строительный блок для создания библиотек потоковой обработки (как, например, FS2 или ZIO Streams). 
Вы работаете не с потоками данных напрямую, а с планами их обработки.

### Почему это полезно?

1. **Ленивость** - данные обрабатываются по мере необходимости
2. **Композиционность** - можно комбинировать простые операции
3. **Безопасность** - контроль над выполнением

`Pull` дает нам:

- Простой способ описывать потоковые преобразования
- Возможность комбинировать операции
- Контроль над выполнением без лишних эффектов

Это фундамент для построения более сложных потоковых API в функциональном стиле.
