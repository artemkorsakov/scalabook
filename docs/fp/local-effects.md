# Локальные эффекты и изменяемое состояние

## Введение в концепцию

Функциональное программирование основывается на принципе **ссылочной прозрачности**, 
который гласит, что выражение можно заменить его результатом без изменения поведения программы. 
Это приводит нас к понятию **чистых функций** - функций, 
которые не имеют побочных эффектов и зависят только от своих аргументов.

Однако в реальных программах иногда необходимо работать с изменяемым состоянием. 
Рассмотрим, как это можно делать, сохраняя чистоту функций на внешнем уровне.

## Углубленное понимание ссылочной прозрачности

### Определения

1. **Ссылочная прозрачность**:
    - Выражение `e` ссылочно прозрачно, если во всей программе `p` каждое вхождение `e` 
      можно заменить результатом его вычисления без изменения смысла `p`.
    - *Проще говоря*: если везде, где вы видите `someExpression`, 
      вы можете заменить его на его результат, и программа будет работать так же.

2. **Чистота функции**:
    - Функция `f` чистая, если для всех ссылочно прозрачных `x` выражение `f(x)` также ссылочно прозрачно.
    - *Проще говоря*: чистая функция всегда возвращает один и тот же результат 
      для одних и тех же аргументов и не имеет побочных эффектов.

### Важное уточнение

Эти определения **не запрещают** использование мутации внутри функции, если она не видна снаружи. 
Это ключевой момент для понимания.

## Пример: чистая быстрая сортировка с внутренней мутацией

Рассмотрим реализацию быстрой сортировки на Scala:

```dotty
def quicksort(xs: List[Int]): List[Int] =
  if xs.isEmpty then xs
  else
    // 1. Создаем изменяемый массив из входного списка
    val arr = xs.toArray

    // 2. Вспомогательная функция для обмена элементов
    def swap(x: Int, y: Int) =
      val tmp = arr(x)
      arr(x) = arr(y)
      arr(y) = tmp

    // 3. Функция разделения массива
    def partition(n: Int, r: Int, pivot: Int) =
      val pivotVal = arr(pivot)
      swap(pivot, r)
      var j = n
      for i <- n until r if arr(i) < pivotVal do
        swap(i, j)
        j += 1
      swap(j, r)
      j

    // 4. Основная рекурсивная функция сортировки
    def qs(n: Int, r: Int): Unit =
      if n < r then
        val pi = partition(n, r, n + (n - r) / 2)
        qs(n, pi - 1)
        qs(pi + 1, r)

    // 5. Запускаем сортировку
    qs(0, arr.length - 1)
    // 6. Возвращаем результат как неизменяемый список
    arr.toList
```

### Почему эта функция чистая?

1. **Локальность мутации**:
    - Все изменения происходят внутри массива `arr`, который создается внутри функции
    - Никакая внешняя часть программы не имеет доступа к `arr`

2. **Детерминированность**:
    - Для одного и того же входного списка функция всегда вернет одинаковый результат
    - Нет зависимости от внешнего состояния

3. **Отсутствие побочных эффектов**:
    - Функция не изменяет ничего вне своей области видимости
    - Не взаимодействует с внешним миром (файлами, сетью и т.д.)

### Разбор компонентов

1. **`swap`**:
    - Имеет побочный эффект (меняет элементы массива)
    - Но является приватной для `quicksort`
    - Ее эффекты не видны снаружи

2. **`partition`**:
    - Использует изменяемую переменную `j`
    - Но эта переменная видна только внутри `partition`
    - Все изменения остаются локальными

3. **`qs`**:
    - Рекурсивно изменяет массив
    - Но опять же - изменения ограничены областью видимости `quicksort`

## Принципы работы с локальными эффектами

1. **Инкапсуляция**:
    - Все изменяемые объекты должны создаваться внутри функции
    - Никакие ссылки на них не должны "утекать" наружу

2. **Ограниченная область видимости**:
    - Мутация должна быть видна только в ограниченной области
    - Вспомогательные функции с эффектами должны быть приватными

3. **Чистый интерфейс**:
    - Входные параметры не должны изменяться
    - Результат должен быть новым, неизменяемым значением

### Когда это полезно?

1. **Алгоритмы, требующие мутации**:
    - Сортировки (как в примере выше)
    - Алгоритмы на графах
    - Оптимизации производительности

2. **Временные структуры данных**:
    - Когда нужно временно использовать изменяемую структуру для эффективности
    - Но конечный результат преобразуется в неизменяемую форму

3. **Постепенная миграция к функциональному стилю**:
    - Можно начать с инкапсуляции эффектов
    - Затем постепенно переходить к более чистым решениям

### Выводы

1. **Чистые функции могут содержать локальные эффекты**, если они правильно инкапсулированы.
2. **Ключевой критерий** - невозможность наблюдать эффекты извне функции.
3. **Это мощный инструмент**, который сочетает преимущества функционального подхода с практической эффективностью.

Таким образом, функциональное программирование не требует полного отказа от мутаций, 
а лишь их строгого контроля и инкапсуляции. 
Это делает ФП более практичным и гибким подходом к разработке программного обеспечения.

## Тип данных для безопасной работы с изменяемым состоянием

### Проблема ограничения области видимости эффектов

Когда мы работаем с изменяемым состоянием в функциональном программировании, важно гарантировать, что:

1. Изменения состояния не видны снаружи определенной области
2. Невозможно случайно "упустить" изменяемые данные наружу

Рассмотрим пример с быстрой сортировкой (`quicksort`) из предыдущего раздела. 
Там мы использовали изменяемый массив внутри функции, но гарантировали чистоту за счет того, что:

- Массив создавался внутри функции
- Никакие ссылки на него не передавались наружу

Однако такой подход полагается только на дисциплину программиста. 
Хотелось бы, чтобы компилятор помогал проверять эти условия.

### Решение: тип ST для контролируемого состояния

Мы создадим специальный тип `ST[S, A]`, который будет:

- Представлять вычисление с внутренним изменяемым состоянием
- Гарантировать, что состояние не "утечет" наружу
- Позволять комбинировать такие вычисления

#### Базовое определение

```dotty
// Специальный тип, скрывающий детали реализации
opaque type ST[S, A] = S => (A, S)

object ST:
  // Преобразование результата вычисления
  extension [S, A](self: ST[S, A])
    def map[B](f: A => B): ST[S, B] =
      s =>
        val (a, s1) = self(s)
        (f(a), s1)

    // Последовательное выполнение двух вычислений
    def flatMap[B](f: A => ST[S, B]): ST[S, B] =
      s =>
        val (a, s1) = self(s)
        f(a)(s1)

  // Создание простого вычисления без эффектов
  def apply[S, A](a: => A): ST[S, A] =
    lazy val memo = a
    s => (memo, s)

  // Создание вычисления с эффектом
  def lift[S, A](f: S => (A, S)): ST[S, A] = f
end ST
```

### Как это работает

1. **Параметр типа `S`**:
    - Это "метка" для определенного вида изменяемого состояния
    - Не содержит реальных данных, только тип
    - Помогает компилятору отслеживать область видимости

2. **Ограничения**:
    - Нет способа получить реальное состояние напрямую
    - Все операции с состоянием происходят внутри `ST`

3. **Композиция**:
    - Методы `map` и `flatMap` позволяют последовательно выполнять операции
    - Результат одного вычисления можно передать в следующее

### Почему это безопасно?

1. **Изоляция состояния**:
    - Каждое вычисление работает только со своим состоянием
    - Невозможно передать состояние между разными `ST`-вычислениями

2. **Контроль области видимости**:
    - Компилятор проверяет, что состояние не используется вне разрешенной области
    - Если попытаться "украсть" состояние, код не скомпилируется

3. **Чистый интерфейс**:
    - Снаружи `ST` выглядит как обычное функциональное вычисление
    - Все эффекты скрыты внутри

### Преимущества перед другими подходами

1. **По сравнению с ручной инкапсуляцией**:
    - Компилятор помогает находить ошибки
    - Нет риска случайно нарушить инкапсуляцию

2. **По сравнению с `IO`**:
    - Более точное ограничение возможностей
    - Явно показывает, что работаем только с локальным состоянием
    - Лучшая производительность

## Работа с изменяемыми ссылками в ST

### Основные операции с изменяемыми ячейками

Для безопасной работы с изменяемым состоянием в функциональном стиле нам нужны три базовые операции:

1. **Создание** новой изменяемой ячейки
2. **Запись** значения в ячейку
3. **Чтение** значения из ячейки

Реализуем эти операции с помощью типа `ST`, 
который гарантирует, что все изменения останутся локальными.

### Реализация изменяемой ссылки (STRef)

```dotty
// Класс для работы с изменяемой ячейкой
final class STRef[S, A] private (private var cell: A):
  // Чтение значения из ячейки
  def read: ST[S, A] = ST(cell)

  // Запись нового значения в ячейку
  def write(a: => A): ST[S, Unit] =
    ST.lift[S, Unit]: s =>
      cell = a
      ((), s)

object STRef:
  // Создание новой изменяемой ячейки
  def apply[S, A](a: A): ST[S, STRef[S, A]] =
    ST(new STRef[S, A](a))
```

#### Как это работает:

1. **STRef** - это обертка вокруг обычной переменной (`var`)
2. **read** возвращает вычисление, которое при выполнении вернет текущее значение
3. **write** возвращает вычисление, которое при выполнении обновит значение
4. **apply** - единственный способ создать новую ячейку

Тип `S` здесь играет важную роль:

- Это "метка", которая связывает ячейку с определенной областью видимости
- Не содержит реальных данных, только обеспечивает безопасность типов
- Гарантирует, что ячейка не будет использована вне разрешенного контекста

### Пример программы с изменяемыми ячейками

Рассмотрим простую программу, которая:

1. Создает две ячейки с начальным значением 1
2. Читает их значения
3. Записывает в каждую ячейку значение другой ячейки + 1
4. Возвращает конечные значения

```dotty
for
  r1 <- STRef[Nothing, Int](1)  // Создаем первую ячейку
  r2 <- STRef[Nothing, Int](1)  // Создаем вторую ячейку
  x  <- r1.read                 // Читаем из первой ячейки
  y  <- r2.read                 // Читаем из второй ячейки
  _  <- r1.write(y + 1)         // Записываем в первую ячейку (y+1)
  _  <- r2.write(x + 1)         // Записываем во вторую ячейку (x+1)
  a  <- r1.read                 // Читаем новое значение из первой
  b  <- r2.read                 // Читаем новое значение из второй
yield (a, b)
```

#### Особенности примера:

1. Мы используем `Nothing` как тип-метку, так как он подходит для простых примеров
2. Все операции выполняются последовательно благодаря `for`-нотации
3. Программа пока не может быть выполнена - нужен специальный механизм запуска

#### Почему это безопасно?

1. **Инкапсуляция**:
    - Прямой доступ к переменной `cell` невозможен извне
    - Все операции проходят через `ST`-вычисления

2. **Контроль области видимости**:
    - Ячейка привязана к определенному контексту (тип `S`)
    - Невозможно случайно передать ячейку в другой контекст

3. **Чистый интерфейс**:
    - Снаружи работа с `STRef` выглядит как чистое вычисление
    - Все эффекты скрыты внутри `ST`-действий

## Безопасное выполнение операций с изменяемым состоянием

### Как безопасно работать с изменяемым состоянием

При использовании `ST` для работы с изменяемым состоянием важно соблюдать два ключевых принципа:

1. Все изменения состояния должны быть временными и локальными
2. Никакие ссылки на изменяемые объекты не должны "утекать" наружу

Рассмотрим разницу между этими двумя типами операций:

```dotty
ST[S, STRef[S, Int]]  // Опасная операция - возвращает изменяемую ссылку
ST[S, Int]            // Безопасная операция - возвращает просто значение
```

### Гарантии безопасности

Система типов Scala помогает нам обеспечить безопасность через следующие механизмы:

1. **Привязка изменяемых объектов к контексту**:
    - Каждый `STRef` помечен тем же типом `S`, что и содержащее его `ST`-действие
    - Это предотвращает передачу ссылок между разными контекстами

2. **Проверка возвращаемых значений**:
    - Запрещено возвращать изменяемые объекты из `ST`-действий
    - Можно возвращать только простые значения (`Int`, `String` и т.д.)

### Запуск ST-действий

Для безопасного выполнения `ST`-действий мы используем специальную функцию `run`:

```dotty
object ST:
  def run[A](action: [s] => () => ST[s, A]): A =
    val computation: ST[Unit, A] = action[Unit]()
    computation(())(0)  // Выполняем вычисление с фиктивным состоянием
```

### Как это работает:

1. **Полиморфная функция**:
    - Действие должно быть полиморфным по типу `s`
    - Это гарантирует, что оно не зависит от конкретного типа состояния

2. **Фиктивное состояние**:
    - При выполнении передается `Unit` как фиктивное состояние
    - Так как действие полиморфно, оно не может реально использовать это состояние

3. **Извлечение результата**:
    - Возвращается только конечное значение типа `A`
    - Все промежуточные изменяемые объекты остаются внутри

### Пример безопасного выполнения

```dotty
// Создаем безопасное действие
val safeAction = [s] =>
  () =>
    for
      cell <- STRef[s, Int](10) // Создаем ячейку
      _    <- cell.write(20)    // Меняем значение
      x    <- cell.read         // Читаем значение
    yield x * 2 // Возвращаем результат

// Выполняем действие
val result = ST.run(safeAction) // Результат: 40
```

### Почему это безопасно?

**Невозможно вернуть изменяемый объект**:

```dotty
// Такой код не скомпилируется:
val p: [s] => () => ST[s, STRef[Nothing, Int]] =
[s] => () => STRef(1)

// -- [E007] Type Mismatch Error: -------------------------------------------------
// 2 |  [s] => () => STRef(1)
//   |               ^^^^^^^^
//   |               Found:    Example.ST[Any, Example.STRef[Any, Int]]
//   |               Required: Example.ST[s, Example.STRef[Nothing, Int]]
```

Важно то, что тип `s` привязан в момент вызова полиморфной функции
и может даже вызываться несколько раз с разными типами.
Мы не можем знать этот тип, пока функция не будет вызвана.

Как следствие, тот факт, что мы не можем получить `STRef` на выходе из `ST` действия,
гарантирует, что если у нас есть `STRef`, то мы находимся внутри `ST` действия,
которое создало его, поэтому всегда можно безопасно изменить ссылку.

**Все изменения изолированы**:

- Каждое действие работает со своим собственным состоянием
- Невозможно передать состояние между разными вызовами

**Чистый результат**:

- Функция `run` возвращает обычное неизменяемое значение
- Все побочные эффекты остаются внутри выполнения

### Преимущества такого подхода

1. **Безопасность**:
    - Компилятор проверяет корректность работы с состоянием
    - Невозможно случайно нарушить правила

2. **Производительность**:
    - Можно использовать реальную мутацию внутри
    - Снаружи сохраняется чисто функциональный интерфейс

3. **Удобство**:
    - Позволяет писать императивный код внутри функциональной обертки
    - Сохраняет все преимущества функционального подхода

Такой механизм дает нам возможность использовать изменяемое состояние там, где это необходимо, 
сохраняя при этом все гарантии функционального программирования.

## Работа с изменяемыми массивами

### Создание безопасного интерфейса для массивов

Для практического использования изменяемого состояния часто требуются массивы. 
Реализуем безопасный интерфейс для работы с ними:

```dotty
import scala.reflect.ClassTag

// Класс-обертка для изменяемого массива
final class STArray[S, A] private (private var value: Array[A]):
  
  // Получение размера массива
  def size: ST[S, Int] = ST(value.size)

  // Запись элемента по индексу
  def write(i: Int, a: A): ST[S, Unit] =
    ST.lift[S, Unit]: s =>
      value(i) = a
      ((), s)

  // Чтение элемента по индексу
  def read(i: Int): ST[S, A] = ST(value(i))

  // Преобразование в неизменяемый список
  def freeze: ST[S, List[A]] = ST(value.toList)

object STArray:
  // Создание нового массива заданного размера
  def apply[S, A: ClassTag](
      sz: Int,
      v: A
  ): ST[S, STArray[S, A]] =
    ST(new STArray[S, A](Array.fill(sz)(v)))
```

### Особенности реализации:

1. **Безопасный конструктор**:
    - Массив создается только через метод `apply` объекта-компаньона
    - Возвращается не сам массив, а действие `ST`, которое его создает

2. **Ограниченный доступ**:
    - Все операции с массивом возвращают `ST`-действия
    - Прямой доступ к массиву извне невозможен

3. **Преобразование в неизменяемый вид**:
    - Метод `freeze` позволяет получить список элементов
    - Гарантирует, что массив не будет изменяться после преобразования

### Требования к типам элементов

Scala требует специальной информации для создания массивов произвольных типов:

- Параметр `A: ClassTag` обеспечивает возможность создания массива для типа `A`
- Стандартная библиотека предоставляет необходимые `ClassTag`'и для базовых типов

### Преимущества подхода:

1. **Безопасность**:
    - Компилятор предотвращает утечку ссылок на массив
    - Все изменения изолированы внутри `ST`-действий

2. **Производительность**:
    - Внутри используется настоящий изменяемый массив
    - Снаружи сохраняется чисто функциональный интерфейс

3. **Композируемость**:
    - Отдельные операции можно комбинировать в более сложные
    - Сохраняется последовательность выполнения

### Упражнение 10.1.1: Реализация метода fill для STArray

> [Репозиторий с упражнениями и инструкцией по выполнению][sample]

**Задача:**

Добавить метод `fill` к классу `STArray`, который заполняет массив значениями из переданной `Map`,
где ключи представляют индексы, а значения - элементы для записи.

```dotty
final class STArray[S, A] private (private var value: Array[A]):
  // ... другие методы ...
  
  def fill(xs: Map[Int, A]): ST[S, Unit] = ???
```

**Примеры:**

```dotty
// Создаем массив размером 3 с начальным значением 0
val arrayAction = STArray[Unit, Int](3, 0)

// Программа для заполнения массива
val program = [S] => () =>
  for
    arr <- arrayAction
    _ <- arr.fill(Map(0 -> 10, 2 -> 30)) // Заполняем индексы 0 и 2
    result <- arr.freeze
  yield result

// Выполняем программу
val result = ST.run(program) // Результат: List(10, 0, 30)
```

@:note(🔍 Показать решение)

Метод `fill` последовательно записывает значения из переданной `Map` в массив, 
используя `foldRight` для объединения операций записи: 
начиная с пустого действия `ST[S, Unit](())`, для каждой пары (индекс, значение) 
он добавляет операцию `write` через `flatMap`, 
гарантируя порядок выполнения и безопасность типов благодаря системе `ST`.

```dotty
def fill(xs: Map[Int, A]): ST[S, Unit] =
  xs.foldRight(ST[S, Unit](())):
    case ((k, v), st) => st.flatMap(_ => write(k, v))
```

@:@

### Чисто функциональная быстрая сортировка на месте

Компоненты для `quicksort` теперь легко писать в `ST`.
Например, функцию `swap`, которая меняет местами два элемента массива,
можно определить как метод в `STArray`:

```dotty
def swap(i: Int, j: Int): ST[S, Unit] =
  for
    x <- read(i)     // Читаем значение по индексу i
    y <- read(j)     // Читаем значение по индексу j
    _ <- write(i, y) // Записываем y в позицию i
    _ <- write(j, x) // Записываем x в позицию j
  yield ()
```

### Упражнение 10.1.2: Реализация partition и qs

Напишите чисто функциональные версии `partition` и `qs`:

```dotty
def partition[S](a: STArray[S, Int], l: Int, r: Int, pivot: Int): ST[S, Int] = ???
def qs[S](a: STArray[S, Int], l: Int, r: Int): ST[S, Unit] = ???
```

##### `partition`

@:note(🔍 Показать решение)

Функция `partition` реализует этап разделения в быстрой сортировке: 
сначала опорный элемент (`pivot`) перемещается в конец массива, 
затем последовательно просматриваются элементы от `l` до `r-1` — если элемент меньше опорного, 
он меняется местами с элементом на текущей границе (`j`), которая увеличивается после каждого обмена. 
В конце опорный элемент возвращается на свою окончательную позицию (между меньшими и большими элементами), 
которая и возвращается как результат. 
Вся работа с изменяемым состоянием (чтение/запись в массив, счётчик границы) 
инкапсулирована в `ST`-действиях, сохраняя ссылочную прозрачность.

```dotty
def partition[S](
    a: STArray[S, Int], // Рабочий массив
    l: Int,             // Левая граница
    r: Int,             // Правая граница
    pivot: Int          // Индекс опорного элемента
): ST[S, Int] = // Возвращает новую позицию pivot
  for
    vp <- a.read(pivot)    // Читаем значение опорного элемента
    _  <- a.swap(pivot, r) // Перемещаем pivot в конец
    j  <- STRef(l)         // Создаем изменяемую ссылку для границы
    _ <- (l until r).foldLeft(ST[S, Unit](()))((s, i) =>
      for
        _  <- s
        vi <- a.read(i) // Читаем текущий элемент
        _ <- if vi < vp then // Если элемент меньше опорного
          for
            vj <- j.read          // Читаем текущую границу
            _  <- a.swap(i, vj)   // Меняем местами
            _  <- j.write(vj + 1) // Увеличиваем границу
          yield ()
        else ST[S, Unit](()) // Иначе ничего не делаем
      yield ()
    )
    x <- j.read       // Читаем финальную позицию
    _ <- a.swap(x, r) // Возвращаем pivot на место
  yield x // Возвращаем новую позицию pivot
```

@:@

##### `qs`

@:note(🔍 Показать решение)

Функция `qs` реализует рекурсивный алгоритм быстрой сортировки в рамках `ST`:
если границы корректны (`l < r`), она выбирает средний элемент как опорный
через `partition`, рекурсивно сортирует левую и правую части относительно опорного элемента,
а в базовом случае (когда сортировать нечего) возвращает "пустое" действие.
Все операции с изменяемым массивом инкапсулированы в `ST`-действиях, что сохраняет чистоту функции,
позволяя при этом эффективно модифицировать массив на месте.

```dotty
def qs[S](a: STArray[S, Int], l: Int, r: Int): ST[S, Unit] =
  if l < r then // Если есть что сортировать
    for
      pi <- partition(a, l, r, l + (r - l) / 2) // Разделяем массив
      _  <- qs(a, l, pi - 1)                    // Сортируем левую часть
      _  <- qs(a, pi + 1, r)                    // Сортируем правую часть
    yield ()
  else ST[S, Unit](()) // Базовый случай рекурсии
```

@:@

### quicksort

Теперь по написанным компонентам можно собрать `quicksort`:

```dotty
def qs[S](a: STArray[S,Int], l: Int, r: Int): ST[S, Unit] =
  if l < r then  // Если есть что сортировать
    for
      pi <- partition(a, l, r, l + (r - l) / 2) // Разделяем массив
      _ <- qs(a, l, pi - 1)                     // Сортируем левую часть
      _ <- qs(a, pi + 1, r)                     // Сортируем правую часть
    yield ()
  else ST[S, Unit](())  // Базовый случай рекурсии
```

## Чистота в программировании зависит от контекста

### 1. Ненаблюдаемые эффекты и локальность

В предыдущих разделах обсуждалось, что некоторые эффекты (например, изменение данных) 
могут быть "невидимыми" для программы, если они ограничены локальной областью видимости.  

**Пример**: Если функция изменяет временную переменную, но не возвращает и не передает её наружу, 
внешний код не сможет заметить эти изменения.

### 2. Ссылочная прозрачность под микроскопом

Ссылочная прозрачность — это свойство выражения, 
позволяющее заменить его на результат вычисления без изменения поведения программы.  
Но в Scala есть нюансы:

#### Пример с классом `Foo`:

```dotty
case class Foo(s: String)

// Сравнение по значению
val b = Foo("hello") == Foo("hello")  // true 
// Сравнение по ссылке (как в Java)
val c = Foo("hello") eq Foo("hello")  // false
```

**Проблема**:  

Каждый вызов `Foo("hello")` создает новый объект в памяти. 
Это технически побочный эффект (выделение памяти), 
но большинство программ его не замечают, так как не используют `eq`.

#### Ключевой вывод:

- **Конструкторы в Scala не являются полностью прозрачными** из-за создания новых объектов.
- Но если программа не проверяет ссылки (через `eq`), этот эффект "невидим".

### 3. Уточненное определение ссылочной прозрачности

> Выражение `e` прозрачно для программы `p`, если все его использования в `p` 
> можно заменить результатом вычисления `e` без изменения смысла `p`.

**Что это значит?**  

Чистота зависит от:

1. **Контекста программы** (какие эффекты она может наблюдать).
2. **Критериев эквивалентности** (что считаем "одинаковым" поведением).

### 4. Что считать побочным эффектом?

#### Пример с методом `timesTwo`:

```dotty
def timesTwo(x: Int): Int =
  if x < 0 then println("Negative!")  // Побочный эффект
  x * 2
```

- Замена `timesTwo(2)` на `4` сохранит результат, но "спрячет" вывод в консоль.
- **Важно**: Нужно решить, учитывать ли вывод в консоль как часть поведения программы.

## Заключение

**Главные идеи**

1. **Локальные изменения допустимы**, если они не влияют на внешний код.
2. **Чистота — это соглашение**:
    - Какие эффекты считаем важными?
    - Как определяем, что две программы ведут себя "одинаково"?
3. **Инструменты Scala помогают контролировать сложность**:
    - `ST` — для изолированных мутаций.
    - `IO` — для явного управления операциями ввода-вывода.
    - Можно создавать собственные механизмы для специфичных задач.

**Итого**

- **Функциональный код — не про запрет изменений**, а про их предсказуемость.
- **Решение о чистоте принимается на основе требований** программы.
- **Система типов Scala** — мощный инструмент для выражения этих решений.
