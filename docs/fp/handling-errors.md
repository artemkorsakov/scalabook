# Обработка ошибок

## Основные принципы функционального подхода к генерации и обработке ошибок

В функциональном программировании создание исключений (_exceptions_) рассматривается как побочный эффект (_side effect_), 
что противоречит принципам чистой функциональности. 
Вместо использования механизма исключений, функциональный подход предлагает:

1. Представление ошибок и сбоев в виде обычных возвращаемых значений
2. Использование функций высшего порядка (higher-order functions) для абстрагирования общих паттернов обработки ошибок
3. Реализацию механизмов восстановления после ошибок через композицию функций

Такое решение обладает несколькими ключевыми преимуществами:

- **Безопасность**: явное представление ошибок делает их обработку обязательной
- **Ссылочная прозрачность (_Referential Transparency_)**: сохранение свойства заменяемости выражений
- **Консолидация логики**: возможность централизованной обработки ошибок, аналогично блокам try/catch

## Обзор традиционного подхода с исключениями

Основная проблема исключений в том, что они **нарушают принципы функционального программирования**, 
такие как чистота функций, прозрачность и типобезопасность.

### 1. Нарушение ссылочной прозрачности

**Ссылочная прозрачность** означает, что выражение можно заменить его результатом без изменения поведения программы. 
Исключения нарушают это правило.

- **Зависимость от контекста:** Результат функции зависит не только от её аргументов, 
  но и от состояния системы (например, существует ли файл, доступна ли сеть).

- **Пример:**
  ```dotty
  // НЕПРОЗРАЧНАЯ функция
  def readConfigFile(configPath: String): String =
      val source = scala.io.Source.fromFile(configPath)
      try
        source.mkString
      finally
        source.close()
  ```

  Вызов `readConfigFile("app.conf")`:
    - Если файл существует, он вернёт его содержимое (например, `"port=8080"`).
    - Если файла нет, выбросит `FileNotFoundException`.

  **Проблема:** Мы не можем мысленно заменить вызов функции `readConfigFile("app.conf")` на её результат, 
  не зная контекста (существует файл или нет). Это ломает возможность рассуждать о коде с помощью простой **модели подстановки**.

- **Создание запутанного потока:** Управление потоком выполнения происходит не через комбинацию выражений, 
  а через "прыжки" (`throw` -> `catch`) в разные части кода, что сложнее для анализа.

### 2. Отсутствие типобезопасности

Типобезопасность — это гарантия, что компилятор проверит корректность программы на этапе компиляции. 
Исключения обходят эту систему типов.

- **Скрытые контракты:** Сигнатура функции — это её контракт. Исключения скрывают важнейшую часть этого контракта — возможные ошибки.

  **Пример:**

  ```dotty
  // Контракт функции: Int => Int
  // Реальный контракт: Int => Int ИЛИ throws Exception
  def failingFn(n: Int): Int =
      if n < 0 then throw new Exception("Отрицательное число!")
      else n * 2
  ```

- **Компилятор не поможет:** Компилятор _не_ обязывает вызывающую сторону обрабатывать исключение. Ошибка проявится только в **Runtime**.

  **Пример опасного кода, который скомпилируется:**

  ```dotty
  val result: Int = failingFn(-5) // Компилятор доволен. Типы совпали.
  val finalResult = result + 10   // Эта строка никогда не выполнится для n=-5
  ```

  **Результат выполнения:** Программа аварийно завершится с `Exception: Отрицательное число!`, и компилятор нас не предупредил об этой возможности.

- **Ошибки остаются незамеченными:** Если разработчик забыл, что `failingFn` может бросать исключение, 
  или не посмотрел в её документацию/исходный код, ошибка будет обнаружена только при тестировании или уже у пользователя.

### Ключевой вывод:

Исключения полезны для **критических, невосстановимых ошибок** (например, нехватка памяти), 
которые обрабатываются на самом высоком уровне абстракции.

Однако для **ожидаемых ошибок предметной области** (неверный ввод пользователя, отсутствие данных, сетевая недоступность) 
они — плохой инструмент, так как делают код ненадёжным и непредсказуемым. 

## Альтернативные подходы к обработке ошибок

Рассмотрим практический пример — реализацию функции вычисления среднего значения, которая не определена для пустого списка:

```dotty
def mean(xs: Seq[Double]): Double =
  if xs.isEmpty then
    throw new ArithmeticException("mean of empty list!")
  else xs.sum / xs.length
```

Эта функция является частичной (_partial function_) — она определена не для всех возможных входных данных 
(в данном случае, не для пустых списков).

### Альтернатива 1: Возврат специальных значений

Первый подход предполагает возврат специальных значений:

- Для пустого списка можно вернуть `Double.NaN`
- В других контекстах могут использоваться `null` или другие сигнальные значения

**Проблемы этого подхода**:

1. **Неявное распространение ошибок**:
    - Вызывающий код может забыть проверить специальное значение и не будет предупрежден компилятором, 
      что может привести к тому, что последующий код не будет работать должным образом.
    - Ошибки обнаруживаются значительно позже места их возникновения

2. **Увеличение шаблонного кода**:
    - Требуется множество явных проверок возвращаемых значений на стороне вызова с явными операторами `if` 
      для проверки того, получил ли вызывающий «настоящий» результат
    - Особенно проблематично при цепочках вызовов функций, каждая из которых использует коды ошибок,
      которые должны быть проверены и каким-то образом агрегированы

3. **Ограничения полиморфного кода**:
    - Не для всех типов существуют подходящие сигнальные значения
    - Пример: функция `max[A](xs: Seq[A])(greater: (A,A) => Boolean): A` не может вернуть корректное значение 
      для пустого списка. Здесь также нельзя использовать `null`, поскольку `null` допустим только для непримитивных типов,
      а `A` на самом деле может быть примитивом, таким как `Double` или `Int`.

4. **Нарушение единообразия**:
    - Требует специальных соглашений между функциями: правильное использование функции `mean` потребует, 
      чтобы вызывающие выполняли что-то иное, кроме вызова `mean` и использования результата
    - Усложняет использование с функциями высшего порядка: предоставление функциям специальных политик 
      затрудняет их передачу функциям высшего порядка, которые должны обрабатывать все аргументы единообразно.

### Альтернатива 2: Параметр обработки неопределенного случая

Второй подход предполагает передачу значения по умолчанию — заставить вызывающую программу предоставить аргумент,
который говорит, что делать, если мы не знаем, как обрабатывать ввод:

```dotty
def mean(xs: Seq[Double], onEmpty: Double): Double =
  if xs.isEmpty then onEmpty
  else xs.sum / xs.length
```

**Ограничения этого решения**:

1. **Жесткая привязка к конкретному типу** обработки ошибки
2. **Недостаточная гибкость**:
    - Невозможность прервать вычисление при ошибке. Что, если среднее значение вызывается как часть более крупного вычисления,
      и хотелось бы прервать это вычисление, если среднее значение не определено?
    - Отсутствие механизма выбора альтернативных веток вычислений
3. **Раннее принятие решения** об обработке ошибки, что может быть неоптимально для вызывающего кода

Нам требуется более гибкий механизм, позволяющий отложить решение об обработке ошибки до подходящего уровня абстракции.

## Тип данных Option: безопасное представление отсутствующих значений

### Концепция и базовое определение

Функциональный подход к обработке отсутствующих или неопределенных значений заключается 
в явном указании возможности отсутствия результата через возвращаемый тип. 
Это позволяет передать ответственность за обработку таких случаев вызывающему коду, 
сохраняя при этом типобезопасность и ссылочную прозрачность.

Тип `Option` представляет собой алгебраический тип данных (ADT), определенный следующим образом:

```dotty
enum Option[+A]:
  case Some(get: A)  // Представляет наличие значения типа A
  case None          // Представляет отсутствие значения
```

Ключевые особенности:

- Ковариантность (`+A`) позволяет естественным образом работать с иерархиями типов
- Два варианта: `Some` для существующих значений и `None` для отсутствующих
- Явная модель обработки вместо неявных исключений

### Практическое применение Option

Рассмотрим переработанный пример функции вычисления среднего:

```dotty
import Option.{Some, None}

def mean(xs: Seq[Double]): Option[Double] =
  if xs.isEmpty then 
    None  // Явное указание отсутствия результата
  else 
    Some(xs.sum / xs.length)  // Упаковка результата в Some
```

Преимущества такого подхода:

1. **Полнота функции**: функция определена для всех входных значений
2. **Ясность сигнатуры**: тип возвращаемого значения явно указывает на возможное отсутствие результата
3. **Безопасность**: компилятор требует обработки обоих случаев (`Some`/`None`)

### Основные операции с Option

#### 1. Преобразование значений

`map` и `flatMap` позволяют последовательно работать с возможными значениями:

```dotty
def map[B](f: A => B): Option[B] = this match
  case Some(a) => Some(f(a))
  case None    => None

def flatMap[B](f: A => Option[B]): Option[B] = this match
  case Some(a) => f(a)
  case None    => None
```

Функцию `map` можно использовать для преобразования результата внутри параметра, если он существует.
Можно думать об этом как о продолжении вычислений в предположении, что ошибки не произошло;
это также способ отложить обработку ошибок на более поздний код:

`flatMap` аналогичен, за исключением того,
что функция, предоставляемая для преобразования результата, сама по себе может дать сбой.

Пример использования с иерархией сотрудников:

```dotty
case class Employee(
  name: String,
  department: String,
  manager: Option[Employee]  // Рекурсивное использование Option
)

def lookupByName(name: String): Option[Employee] =
  name match
    case "Jack" => Some(Employee("Jack", "Engineering", None))
    case "Jill" => Some(Employee("Jill", "HR", lookupByName("Jack")))
    case _      => None

// Примеры цепочек вычислений
lookupByName("Jill").map(_.department)  // Преобразование существующего значения
// Some("HR")

lookupByName("Jill").flatMap(_.manager) // Распаковка вложенного Option
// Some(Employee("Jack", "Engineering", None))
```

#### 2. Фильтрация и обработка отсутствующих значений

`filter` можно использовать для преобразования успехов в неудачи,
если успешные значения не соответствуют заданному предикату.

`getOrElse` используется для преобразования из `Option[A]` в `A`,
предоставляя значение по умолчанию на случай ошибки.

`orElse` похож на `getOrElse`, за исключением того, что возвращается другой `Option`, если первый не определен.
Это часто бывает полезно, когда нужно вместе связать возможные неудачные вычисления,
пробуя второе, если первое не удалось.

```dotty
def filter(p: A => Boolean): Option[A] = this match
  case Some(a) if p(a) => Some(a)
  case _               => None

def getOrElse[B >: A](default: => B): B = this match
  case Some(a) => a
  case None    => default

def orElse[B >: A](ob: => Option[B]): Option[B] = this match
  case Some(a) => Some(a)
  case None    => ob
```

Практические примеры:

```dotty
val dept = lookupByName("Jill")
  .map(_.department)
  .filter(_ != "Sales")  // Превращаем Some в None если условие не выполняется
  .getOrElse("Default Department")

// Альтернативный Option при неудаче
lookupByName("Unknown")
  .orElse(lookupByName("Default Employee"))
```

#### 3. Композиция операций

Типичный паттерн работы с `Option` — цепочка преобразований с финальной обработкой:

```dotty
// Получение имени менеджера с обработкой всех возможных отсутствий
val managerName = lookupByName("Jill")
  .flatMap(_.manager)
  .map(_.name)
  .getOrElse("No manager found")
// val managerName: String = Jack  
```

### Рекомендации по использованию

1. **Преимущества перед исключениями**:
    - Сохранение ссылочной прозрачности
    - Явное указание возможных ошибок в типах
    - Композируемость и возможность отложенной обработки

2. **Когда использовать**:
    - Для ожидаемых и обрабатываемых "ошибок" (отсутствие данных, неверные входные параметры)
    - В публичном API для явного указания возможных проблем

3. **Когда не использовать**:
    - Для действительно исключительных ситуаций (ошибки ввода-вывода, фатальные ошибки)
    - Когда отсутствие значения является ошибкой программиста (лучше использовать исключение)

4. **Идиоматические паттерны**:
    ```dotty
    // Преобразование None в исключение
    val result = optionValue.getOrElse(throw new IllegalStateException("Missing required value"))
 
    // Каскадная проверка альтернатив
    val config = readFileConfig()
      .orElse(readEnvConfig())
      .orElse(readDefaultConfig())
    ```

### Сравнение с аналогичными решениями

Для более сложных сценариев, где нужно сохранять информацию об ошибке, рассмотрите использование `Either` или `Try`. 
`Option` лучше всего подходит для простых случаев отсутствия значений, когда дополнительная информация об ошибке не требуется.

Реализуйте функцию безопасного деления, 
которая использует тип `Option` для явного представления возможности ошибки деления на ноль. 
Это упражнение демонстрирует базовый принцип функциональной обработки ошибок - 
преобразование частичной функции в полную.

```dotty
def safeDivide(a: Double, b: Double): Option[Double] = ???
```

**Примеры:**

```dotty
// Успешное деление
safeDivide(10, 2)   // Some(5.0)
safeDivide(5, 2)    // Some(2.5)

// Деление на ноль
safeDivide(8, 0)    // None
safeDivide(-3, 0)   // None

// Особые случаи
safeDivide(0, 5)    // Some(0.0)
safeDivide(0, 0)    // None (неопределенность)
```

@:note(🔍 Показать решение)

Функция `safeDivide` реализует безопасное деление чисел, возвращая результат в `Some` при ненулевом делителе 
и `None` при делении на ноль, что явно указывает на ошибку без использования исключений. 
Альтернативная версия `safeDivideAlt` делает то же самое через pattern matching, 
проверяя случай нулевого делителя отдельным кейсом — 
оба варианта демонстрируют функциональный подход к обработке ошибок через тип `Option`, 
сохраняя чистоту кода и типобезопасность.

```dotty
def safeDivide(a: Double, b: Double): Option[Double] =
  if b != 0 then Some(a / b) else None

// Альтернативная реализация через pattern matching
def safeDivideAlt(a: Double, b: Double): Option[Double] = 
  b match
    case 0 => None
    case _ => Some(a / b)
```

### Упражнение 3.1.2: Поиск адреса доставки по цепочке зависимостей

В этом упражнении мы будем работать с цепочкой зависимых данных, где информация разбросана по разным сущностям. 
Задача - найти адрес доставки для заказа, используя `flatMap` для безопасной работы с потенциально отсутствующими значениями.

```dotty
case class User(id: Int, name: String, address: Option[String])
case class Order(orderId: Int, userId: Int, product: String, price: Double)

val users = List(
  User(1, "Alice", Some("123 Main St")),
  User(2, "Bob", None)
)

val orders = List(
  Order(100, 1, "Laptop", 999.99),
  Order(101, 2, "Phone", 599.99)
)

// Напишите функцию, которая по id заказа возвращает адрес доставки (используйте flatMap)
def getShippingAddress(orderId: Int): Option[String] = ???
```

**Примеры:**

```dotty
// Заказ с существующим пользователем и адресом
getShippingAddress(100)  // Some("123 Main St")

// Заказ с существующим пользователем без адреса
getShippingAddress(101)  // None

// Несуществующий заказ
getShippingAddress(999)  // None
```

@:note(🔍 Показать решение)

Функция `getShippingAddress` безопасно извлекает адрес доставки по ID заказа, 
используя цепочку операций с `Option`: сначала находим заказ через `find`, 
затем через `flatMap` находим соответствующего пользователя и его адрес. 
Если любой из шагов возвращает `None` (заказ не найден, пользователь не существует или адрес не указан), 
вся цепочка автоматически возвращает `None`, 
что обеспечивает строгую обработку отсутствующих данных без исключений и явных проверок. 
Решение демонстрирует идиоматичную работу с вложенными `Option` через композицию `flatMap`.

```dotty
def getShippingAddress(orderId: Int): Option[String] =
  orders
    // Найти заказ
    .find(_.orderId == orderId)  
    // Распаковать Option[Order]      
    .flatMap(order =>                  
      users
        // Найти пользователя
        .find(_.id == order.userId) 
        // Получить адрес
        .flatMap(_.address)            
    )
```

### Упражнение 3.1.3: Работа с опциональными полями профилей: getEmailOrDefault

Напишите функцию, которая возвращает `email` профиля или `"no-email@example.com"` если `email` отсутствует.

```dotty
case class Profile(id: Int, name: String, email: Option[String], age: Option[Int])

val profiles = List(
  Profile(1, "Alice", Some("alice@example.com"), Some(30)),
  Profile(2, "Bob", None, Some(25)),
  Profile(3, "Charlie", Some("charlie@example.com"), None)
)

def getEmailOrDefault(profile: Profile): String = ???
```

**Примеры:**

```dotty
getEmailOrDefault(profiles(0)) // "alice@example.com"
getEmailOrDefault(profiles(1)) // "no-email@example.com"
```

@:note(🔍 Показать решение)

Функция возвращает email пользователя или стандартное значение `"no-email@example.com"`,
если email отсутствует, используя метод `getOrElse` для безопасной обработки `Option`.
Это гарантирует, что результат всегда будет строкой, исключая необходимость последующих проверок на `None`.

```dotty
def getEmailOrDefault(profile: Profile): String =
  profile.email.getOrElse("no-email@example.com")
```

## Тип данных Either: Расширенная обработка ошибок в функциональном программировании

### Введение в обработку ошибок через значения

В функциональном программировании существует фундаментальный принцип: 
все эффекты, включая ошибки и исключения, должны быть явно представлены в типах возвращаемых значений. 
Такой подход обеспечивает несколько ключевых преимуществ:

1. **Прозрачность** - сигнатура функции явно указывает на возможные ошибки
2. **Безопасность** - компилятор требует обработки всех возможных случаев
3. **Композируемость** - ошибки могут обрабатываться и передаваться через цепочки вызовов

### Ограничения типа Option

Хотя `Option` является простым и полезным инструментом для представления отсутствующих значений, у него есть существенные ограничения:

```dotty
def findUser(id: Int): Option[User] = ...
```

В этом примере, когда функция возвращает `None`, мы не можем определить:

- Существует ли пользователь с таким ID
- Произошла ли ошибка при доступе к базе данных
- Были ли проблемы с подключением к сети

`Option` просто сообщает, что значения нет, но не объясняет причину.

### Тип Either: концепция и определение

`Either` - это алгебраический тип данных, который расширяет возможности `Option`, 
позволяя хранить информацию об ошибках. Его определение:

```dotty
enum Either[+E, +A]:
  case Left(value: E)  // Для хранения информации об ошибке
  case Right(value: A) // Для хранения успешного результата
```

Ключевые особенности:

- Ковариантность по обоим параметрам типа (`+E`, `+A`)
- Два конструктора: `Left` и `Right`
- По соглашению: `Right` означает "правильный" (успешный) результат

### Практическое применение Either

#### Пример 1: Вычисление среднего значения

```dotty
def mean(xs: Seq[Double]): Either[String, Double] =
  if xs.isEmpty then
    Left("Ошибка: невозможно вычислить среднее значение пустого списка")
  else
    Right(xs.sum / xs.length)

// Примеры использования:
mean(Seq(1.0, 2.0, 3.0)) 
// Right(2.0)
mean(Seq.empty)           
// Left("Ошибка: невозможно вычислить среднее значение пустого списка")
```

#### Пример 2: Безопасное выполнение кода с исключениями

```dotty
import scala.util.control.NonFatal

def safeDivide(a: Int, b: Int): Either[Throwable, Int] =
  try Right(a / b)
  catch case NonFatal(ex) => Left(ex)

// Примеры:
safeDivide(10, 2)  // Right(5)
safeDivide(10, 0)  // Left(java.lang.ArithmeticException: / by zero)
```

### Сравнение с Option

| Характеристика     | Option              | Either                         |
|--------------------|---------------------|--------------------------------|
| Хранение ошибки    | Нет (только `None`) | Да (произвольный тип в `Left`) |
| Сигнатура          | `Option[A]`         | `Either[E, A]`                 |
| Успешный результат | `Some(value)`       | `Right(value)`                 |
| Ошибка             | `None`              | `Left(error)`                  |
| Информативность    | Низкая              | Высокая                        |

### Расширенные примеры использования

#### Обработка нескольких ошибок

```dotty
case class ValidationError(message: String)

def validateAge(age: Int): Either[ValidationError, Int] =
  if age < 0 then Left(ValidationError("Возраст не может быть отрицательным"))
  else if age > 120 then Left(ValidationError("Слишком большой возраст"))
  else Right(age)

def createUser(name: String, age: Int): Either[ValidationError, User] =
  for
    validAge <- validateAge(age)
    // Другие проверки...
  yield User(name, validAge)
```

#### Композиция Either

```dotty
def parseNumber(s: String): Either[String, Int] =
  try Right(s.toInt)
  catch case _: NumberFormatException => Left(s"Невозможно преобразовать '$s' в число")

def calculate(a: String, b: String): Either[String, Int] =
  for
    num1 <- parseNumber(a)
    num2 <- parseNumber(b)
    result <- safeDivide(num1, num2).left.map(_ => "Деление на ноль")
  yield result

// Примеры:
calculate("10", "2")  // Right(5)
calculate("10", "0")  // Left("Деление на ноль")
calculate("a", "2")   // Left("Невозможно преобразовать 'a' в число")
```

### Рекомендации по использованию

1. **Когда использовать Either**:
    - Когда важно передавать информацию об ошибке
    - Для валидации входных данных
    - При работе с внешними системами (базы данных, API)

2. **Когда использовать Option**:
    - Когда причина отсутствия значения не важна
    - Для простых случаев "значение есть/нет"

3. **Best Practices**:
    - Используйте осмысленные типы ошибок (не только `String`)
    - Создавайте иерархии ошибок для сложных сценариев
    - Документируйте возможные ошибки в ScalaDoc

```dotty
    Either.cond(name.nonEmpty, name, List("Имя не может быть пустым"))
  val ageValid = parseAge(ageStr).left.map(_ :: Nil)

    case (Right(n), Right(a))     => Right(User(n, a))
    case (Left(nErr), Left(aErr)) => Left(nErr ++ aErr)
    case (Left(err), _)           => Left(err)
```

## Ior: Инклюзивная обработка ошибок и предупреждений

### Введение в инклюзивные логические отношения

В функциональном программировании часто возникает необходимость передавать не только успешные результаты или ошибки, 
но и **предупреждения** (warnings) — важную информацию, которая не является критичной, но может быть полезной для вызывающего кода. 
Стандартный тип `Either` (исключающее ИЛИ) не позволяет одновременно вернуть и результат, 
и дополнительную информацию об ошибке — он представляет только **один из двух вариантов**.

Тип `Ior` (сокращение от "inclusive-or" — инклюзивное ИЛИ) решает эту проблему, 
позволяя хранить **либо** значение типа `A`, **либо** значение типа `B`, **либо оба значения одновременно**.

### Тип Ior: концепция и определение

`Ior` — это алгебраический тип данных, представляющий инклюзивное отношение между двумя типами:

```dotty
enum Ior[+A, +B]:
  case Left(value: A)          // Только значение типа A
  case Right(value: B)         // Только значение типа B
  case Both(left: A, right: B) // Одновременно A и B
```

Ключевые особенности:

- Три конструктора: `Left`, `Right` и `Both`
- Ковариантность по обоим параметрам типа (`+A`, `+B`)
- **Правостороннее смещение** (right-biased): операции `map` и `flatMap` работают с правой стороной (тип `B`)
- Аналогия с `Either`, но с дополнительной возможностью хранить оба значения

| Характеристика  | Either                           | Ior                                              |
|-----------------|----------------------------------|--------------------------------------------------|
| Варианты        | `Left(error)` или `Right(value)` | `Left(a)`, `Right(b)` или `Both(a, b)`           |
| Семантика       | Исключающее ИЛИ (либо A, либо B) | Инклюзивное ИЛИ (либо A, либо B, либо оба)       |
| Хранение ошибки | Только ошибка                    | Ошибка или предупреждение + результат            |
| Информативность | Ограниченная                     | Расширенная (возможность передавать доп. данные) |

### Практическое применение Ior

В дальнейшем будет использоваться реализация Ior из библиотеки [cats-effect](../cats-effect/index.md).

#### Создание значений Ior

```dotty
import cats.data.*

// Создание через фабричные методы:
val right = Ior.right[String, Int](3)
// Right(3) - успешный результат
val left = Ior.left[String, Int]("Error")
// Left("Error") - только ошибка
val both = Ior.both("Warning", 3)
// Both("Warning", 3) - предупреждение + результат

// Создание через синтаксис (требует импорта):
import cats.syntax.all.*

val rightSyntax = 3.rightIor      // Ior.right(3)
val leftSyntax  = "Error".leftIor // Ior.left("Error")
```

#### Пример 1: Валидация с накоплением предупреждений

Классический пример использования `Ior` — валидация данных, 
когда мы хотим накапливать **предупреждения** (некритичные замечания), 
но останавливаемся только на **критических ошибках**:

```dotty
import cats.syntax.all.*
import cats.data.{NonEmptyChain as Nec, Ior}

// Тип для накопления ошибок/предупреждений
type Failures = Nec[String]

case class Username(value: String) extends AnyVal
case class Password(value: String) extends AnyVal
case class User(name: Username, pw: Password)

def validateUsername(u: String): Failures Ior Username =
  if u.isEmpty then
    // Критическая ошибка - только Left
    Nec.one("Имя пользователя не может быть пустым").leftIor
  else if u.contains(".") then
    // Предупреждение + успешный результат
    Ior.both(Nec.one("Использование точки в имени устарело"), Username(u))
  else
    // Успех без предупреждений
    Username(u).rightIor

def validatePassword(p: String): Failures Ior Password =
  if p.length < 8 then
    // Критическая ошибка
    Nec.one("Пароль слишком короткий").leftIor
  else if p.length < 10 then
    // Предупреждение + успешный результат
    Ior.both(Nec.one("Пароль должен быть длиннее"), Password(p))
  else
    Password(p).rightIor

def validateUser(name: String, password: String): Failures Ior User =
  (validateUsername(name), validatePassword(password)).mapN(User.apply)
```

#### Пример 2: Обработка результатов валидации

```dotty
validateUser("John", "password12")
// Right(User(Username("John"), Password("password12"))) - успех без предупреждений

validateUser("john.doe", "password")
// Both(
//   Chain(Использование точки в имени устарело, Пароль должен быть длиннее),
//   User(Username(john.doe),Password(password))
// )

validateUser("jane", "short")
// Left(Ошибка: пароль слишком короткий)
```

#### Извлечение значений

Для извлечения данных из `Ior` используется метод `fold`, который принимает три функции — по одной для каждого случая:

```dotty
validateUser("john.doe", "password").fold(
  // Только ошибки
  errorNec => s"Ошибка: ${errorNec.head}",
  // Только успех
  user => s"Успех: $user",
  // Предупреждения + успех
  (warnings, user) =>
    s"Предупреждение: ${user.name.value}; Следующие предупреждения обнаружены: ${warnings.head}"
)
// "Предупреждение: john.doe; Следующие предупреждения обнаружены: Использование точки в имени устарело"

validateUser("John", "password12").fold(
  errorNec => s"Ошибка: ${errorNec.head}",
  user => s"Успех: $user",
  (warnings, user) =>
    s"Предупреждение: ${user.name.value}; Следующие предупреждения обнаружены: ${warnings.head}"
)
// "Успех: User(Username(John),Password(password12))"
```

### Использование с NonEmptyChain

Для `Ior` существует специализированный псевдоним с `NonEmptyChain` для накопления ошибок на левой стороне:

```dotty
import cats.data.NonEmptyChain

type IorNec[B, A] = Ior[NonEmptyChain[B], A]
```

Это позволяет удобно накапливать несколько ошибок или предупреждений:

```dotty
import cats.syntax.all.*
import cats.data.{ IorNec, NonEmptyChain}

val left: IorNec[String, Int] = Ior.fromEither("Ошибка".leftNec[Int])
// Ior.left(NonEmptyChain("Ошибка"))
```

### Преобразования

`Ior` поддерживает преобразование в другие типы данных. Важно: **все преобразования отбрасывают левое значение, если присутствует Both**:

```dotty
// Both превращается в Either.Right, теряя предупреждение
Ior.both("Предупреждение", 42).toEither
// Right(42)

// Right превращается в Either.Right
Ior.right[String, Int](42).toEither
// Right(42)

// Left превращается в Either.Left
Ior.left[String, Int]("Ошибка").toEither
// Left("Ошибка")
```

### Рекомендации по использованию

#### 1. Когда использовать Ior

- **Валидация с предупреждениями**: когда нужно вернуть и результат, и нефатальные замечания
- **Системы с накоплением ошибок**: когда ошибки накапливаются, но не останавливают вычисления
- **Логирование**: когда нужно вернуть результат вместе с диагностической информацией
- **API с предупреждениями**: когда спецификация API позволяет возвращать предупреждения

#### 2. Когда использовать Either

- **Критические ошибки**: когда ошибка останавливает дальнейшие вычисления
- **Исключительные ситуации**: когда нужна только ошибка или только результат
- **Простая обработка ошибок**: когда информация о предупреждениях не требуется

### Сравнение с Option и Either

| Характеристика                           | Option                 | Either             | Ior                          |
|------------------------------------------|------------------------|--------------------|------------------------------|
| Варианты                                 | `Some`/`None`          | `Left`/`Right`     | `Left`/`Right`/`Both`        |
| Информация об ошибке                     | Нет                    | Да                 | Да (включая предупреждения)  |
| Одновременный результат и предупреждение | Нет                    | Нет                | Да (`Both`)                  |
| Семантика                                | Есть/нет               | Либо `А`, либо `B` | Либо `А`, либо `B`, либо оба |
| Применение                               | Отсутствующее значение | Ошибка             | Ошибка + предупреждение      |
| Накопление ошибок                        | Нет                    | Нет                | Да (с `Semigroup`)           |

### Заключение

`Ior` — это мощный инструмент для сценариев, где недостаточно простого `Either`. 
Он позволяет явно передавать как ошибки, так и предупреждения, сохраняя при этом возможность работать с успешными результатами. 
Это делает его идеальным выбором для:

- API, возвращающих предупреждения вместе с данными
- Валидации с частичным успехом
- Систем, где предупреждения не должны останавливать выполнение

## Validated: Накопление ошибок при валидации

### Введение в проблему накопления ошибок

Представьте, что вы заполняете веб-форму для регистрации аккаунта. Вы вводите имя пользователя и пароль и отправляете форму. 
В ответ приходит сообщение, что имя пользователя не может содержать дефисы. Вы исправляете и отправляете снова. 
Теперь сообщение, что не могут быть специальные символы. Снова исправляете и отправляете. 
Пароль должен содержать хотя бы одну заглавную букву. Исправляете, отправляете. Пароль должен содержать хотя бы одну цифру.

Было бы гораздо удобнее получать **все ошибки одновременно**. 
Проверка имени на дефисы может выполняться независимо от проверки на специальные символы, 
равно как и проверка пароля на различные требования. 
Некорректно заполненное поле в конфигурации может проверяться отдельно от другого поля.

Именно для таких сценариев существует тип `Validated`.

### Тип Validated: концепция и определение

`Validated` — это алгебраический тип данных, представляющий результат вычисления, 
который может быть либо успешным (`Valid`), либо содержать ошибку (`Invalid`). 
В отличие от `Either`, `Validated` предназначен для **накопления ошибок** при помощи `Applicative` и **не является монадой**.

#### Структура типа

```dotty
sealed abstract class Validated[+E, +A] extends Product with Serializable

final case class Valid[+A](a: A)   extends Validated[Nothing, A]
final case class Invalid[+E](e: E) extends Validated[E, Nothing]
```

#### Сравнение с Either

| Характеристика | Either                     | Validated                        |
|----------------|----------------------------|----------------------------------|
| Семантика      | Первая ошибка (fail-fast)  | Все ошибки (error-accumulation)  |
| Монада         | Да (есть `flatMap`)        | Нет (только `Applicative`)       |
| Композиция     | For-comprehension          | `mapN`, `tupleN`                 |
| Тип ошибки     | Одна ошибка                | Множество ошибок (с `Semigroup`) |
| Применение     | Последовательная валидация | Параллельная валидация           |

### Первый подход: Fail-fast с Either

Рассмотрим пример валидации регистрационной формы с использованием `Either`. Наша модель данных:

```dotty
final case class RegistrationData(
    username: String,
    password: String,
    firstName: String,
    lastName: String,
    age: Int
)
```

Модель ошибок:

```dotty
sealed trait DomainValidation:
  def errorMessage: String

case object UsernameHasSpecialCharacters extends DomainValidation:
  def errorMessage: String =
    "Имя пользователя не может содержать специальные символы."

case object PasswordDoesNotMeetCriteria extends DomainValidation:
  def errorMessage: String =
    "Пароль должен содержать минимум 10 символов, включая заглавную и строчную буквы, цифру и специальный символ."

case object FirstNameHasSpecialCharacters extends DomainValidation:
  def errorMessage: String =
    "Имя не может содержать пробелы, цифры или специальные символы."

case object LastNameHasSpecialCharacters extends DomainValidation:
  def errorMessage: String =
    "Фамилия не может содержать пробелы, цифры или специальные символы."

case object AgeIsInvalid extends DomainValidation:
  def errorMessage: String = "Возраст должен быть от 18 до 75 лет."
```

Реализация валидатора с `Either`:

```dotty
import cats.syntax.all.*

sealed trait FormValidator:
  def validateUserName(userName: String): Either[DomainValidation, String] =
    Either.cond(
      userName.matches("^[a-zA-Z0-9]+$"),
      userName,
      UsernameHasSpecialCharacters
    )

  def validatePassword(password: String): Either[DomainValidation, String] =
    Either.cond(
      password.matches(
        "(?=^.{10,}$)((?=.*\\d)|(?=.*\\W+))(?![.\\n])(?=.*[A-Z])(?=.*[a-z]).*$"
      ),
      password,
      PasswordDoesNotMeetCriteria
    )

  def validateFirstName(firstName: String): Either[DomainValidation, String] =
    Either.cond(
      firstName.matches("^[a-zA-Z]+$"),
      firstName,
      FirstNameHasSpecialCharacters
    )

  def validateLastName(lastName: String): Either[DomainValidation, String] =
    Either.cond(
      lastName.matches("^[a-zA-Z]+$"),
      lastName,
      LastNameHasSpecialCharacters
    )

  def validateAge(age: Int): Either[DomainValidation, Int] =
    Either.cond(
      age >= 18 && age <= 75,
      age,
      AgeIsInvalid
    )

  def validateForm(
      username: String,
      password: String,
      firstName: String,
      lastName: String,
      age: Int
  ): Either[DomainValidation, RegistrationData] =
    for
      validatedUserName  <- validateUserName(username)
      validatedPassword  <- validatePassword(password)
      validatedFirstName <- validateFirstName(firstName)
      validatedLastName  <- validateLastName(lastName)
      validatedAge       <- validateAge(age)
    yield RegistrationData(
      validatedUserName,
      validatedPassword,
      validatedFirstName,
      validatedLastName,
      validatedAge
    )
end FormValidator

object FormValidator extends FormValidator
```

Проблема: for-comprehension **прерывается на первой ошибке** (fail-fast). 
Если несколько полей невалидны, мы увидим только первую ошибку:

```dotty
FormValidator.validateForm(
  username = "fakeUs3rname",
  password = "password",
  firstName = "John",
  lastName = "Doe",
  age = 15
)
// Left(UsernameHasSpecialCharacters) - только первая ошибка!
```

### Встреча с Validated и Applicative

Для накопления всех ошибок мы используем `Validated` с `NonEmptyChain`:

```dotty
import cats.data.*
import cats.data.Validated.*
import cats.syntax.all.*

sealed trait FormValidatorNec:
  type ValidationResult[A] = ValidatedNec[DomainValidation, A]

  private def validateUserName(userName: String): ValidationResult[String] =
    if userName.matches("^[a-zA-Z0-9]+$") then userName.validNec
    else UsernameHasSpecialCharacters.invalidNec

  private def validatePassword(password: String): ValidationResult[String] =
    if password.matches(
        "(?=^.{10,}$)((?=.*\\d)|(?=.*\\W+))(?![.\\n])(?=.*[A-Z])(?=.*[a-z]).*$"
      )
    then password.validNec
    else PasswordDoesNotMeetCriteria.invalidNec

  private def validateFirstName(firstName: String): ValidationResult[String] =
    if firstName.matches("^[a-zA-Z]+$") then firstName.validNec
    else FirstNameHasSpecialCharacters.invalidNec

  private def validateLastName(lastName: String): ValidationResult[String] =
    if lastName.matches("^[a-zA-Z]+$") then lastName.validNec
    else LastNameHasSpecialCharacters.invalidNec

  private def validateAge(age: Int): ValidationResult[Int] =
    if age >= 18 && age <= 75 then age.validNec
    else AgeIsInvalid.invalidNec

  def validateForm(
      username: String,
      password: String,
      firstName: String,
      lastName: String,
      age: Int
  ): ValidationResult[RegistrationData] =
    (
      validateUserName(username),
      validatePassword(password),
      validateFirstName(firstName),
      validateLastName(lastName),
      validateAge(age)
    ).mapN(RegistrationData.apply)
end FormValidatorNec

object FormValidatorNec extends FormValidatorNec
```

#### Ключевые изменения

1. **`ValidatedNec[DomainValidation, A]`** — псевдоним для `Validated[NonEmptyChain[DomainValidation], A]`
2. **`.validNec` и `.invalidNec`** — комбинаторы для подъёма в `ValidatedNec`
3. **`.mapN(...)`** — applicative синтаксис для накопления ошибок
4. **`NonEmptyChain`** — структура данных, гарантирующая наличие хотя бы одного элемента

#### Результат работы

```dotty
// Успешная валидация
FormValidatorNec.validateForm(
  username = "Joe",
  password = "Passw0r$1234",
  firstName = "John",
  lastName = "Doe",
  age = 21
)
// Valid(RegistrationData(Joe,Passw0r$1234,John,Doe,21))

// Валидация с ошибками - ВСЕ ошибки собраны!
FormValidatorNec.validateForm(
  username = "Joe%%%",
  password = "password",
  firstName = "John",
  lastName = "Doe",
  age = 21
)
// Invalid(Chain(UsernameHasSpecialCharacters, PasswordDoesNotMeetCriteria))
```

### Накопление ошибок: Semigroup

`Validated` накапливает ошибки с помощью [`Semigroup`](../typeclass/monoid/semigroup.md). 
`NonEmptyChain` по умолчанию имеет экземпляр `Semigroup`, объединяющий две цепочки:

```dotty
NonEmptyChain.one[DomainValidation](UsernameHasSpecialCharacters) |+|
NonEmptyChain[DomainValidation](FirstNameHasSpecialCharacters, LastNameHasSpecialCharacters)
```

Вы можете определить собственный способ комбинирования ошибок, предоставив свою реализацию `Semigroup`.

### Преобразования: Validated ↔ Either

#### Из Either в Validated

```dotty
FormValidator.validateUserName("Joe%%%").toValidatedNec
// Invalid(NonEmptyChain(UsernameHasSpecialCharacters))
```

#### Из Validated в Either

```dotty
FormValidatorNec.validateForm(
  username = "Joe",
  password = "Passw0r$1234",
  firstName = "John",
  lastName = "Doe",
  age = 21
).toEither
// Right(RegistrationData(Joe,Passw0r$1234,John,Doe,21))

FormValidatorNec.validateForm(
  username = "Joe123#",
  password = "password",
  firstName = "John",
  lastName = "Doe",
  age = 5
).toEither
// Left(Chain(UsernameHasSpecialCharacters, PasswordDoesNotMeetCriteria, AgeIsInvalid))
```

### Практический пример: Парсинг конфигурации

Рассмотрим более сложный пример — парсинг конфигурационного файла:

```dotty
import cats.data.*
import cats.syntax.all.*
import cats.Semigroup

// Класс типов Read для парсинга значений
trait Read[A]:
  def read(s: String): Option[A]

object Read:
  def apply[A: Read as r]: Read[A] = r

  given Read[String] =
    (s: String) => Some(s).filter(_.nonEmpty)

  given Read[Int] =
    (s: String) =>
      if s.matches("-?[0-9]+") then Some(s.toInt)
      else None

// Модель ошибок
sealed abstract class ConfigError
final case class MissingConfig(field: String) extends ConfigError
final case class ParseError(field: String)    extends ConfigError

// Конфигурация
case class Config(map: Map[String, String]):
  def parse[A: Read](key: String): Validated[ConfigError, A] =
    map.get(key) match
      case None        => Validated.Invalid(MissingConfig(key))
      case Some(value) =>
        Read[A].read(value) match
          case None    => Validated.Invalid(ParseError(key))
          case Some(a) => Validated.Valid(a)
```

#### Параллельная валидация

```dotty
import cats.data.*
import cats.syntax.all.*
import Read.given

case class ConnectionParams(url: String, port: Int)

val config = Config(Map(("endpoint", ""), ("port", "not an int")))

given Semigroup[NonEmptyChain[ConfigError]] =
  SemigroupK[NonEmptyChain].algebra[ConfigError]

// Собираем все ошибки
val result = (
  config.parse[String]("endpoint").toValidatedNec,
  config.parse[Int]("port").toValidatedNec
).mapN(ConnectionParams.apply)
// Invalid(Chain(ParseError(endpoint), ParseError(port)))
```

### Почему Validated не является монадой?

Если бы `Validated` был монадой, он имел бы метод `flatMap`. 
Однако `flatMap` подразумевает последовательную (fail-fast) обработку, 
что противоречит основной цели `Validated` — накоплению ошибок.

```dotty
import cats.Monad

// Попытка создать Monad для Validated (не работает правильно)
given validatedMonad[E]: Monad[[A] =>> Validated[E, A]] =
  new Monad[[A] =>> Validated[E, A]]:
    def flatMap[A, B](fa: Validated[E, A])(f: A => Validated[E, B])
        : Validated[E, B] =
      fa match
        case Validated.Valid(a)       => f(a)
        case i @ Validated.Invalid(_) => i

    def pure[A](x: A): Validated[E, A] = Validated.Valid(x)

    @annotation.tailrec
    def tailRecM[A, B](a: A)(f: A => Validated[E, Either[A, B]])
        : Validated[E, B] =
      f(a) match
        case Validated.Valid(Right(b)) => Validated.Valid(b)
        case Validated.Valid(Left(a))  => tailRecM(a)(f)
        case i @ Validated.Invalid(_)  => i
        
given validatedApplicative[E: Semigroup as semi]
    : Applicative[[A] =>> Validated[E, A]] =
  new Applicative[[A] =>> Validated[E, A]]:
    def pure[A](x: A): Validated[E, A] =
      Validated.valid(x)

    def ap[A, B](ff: Validated[E, A => B])(fa: Validated[E, A])
        : Validated[E, B] =
      (ff, fa) match
        case (Validated.Valid(f), Validated.Valid(a)) =>
          Validated.Valid(f(a))
        case (i @ Validated.Invalid(_), Validated.Valid(_)) => i
        case (Validated.Valid(_), i @ Validated.Invalid(_)) => i
        case (Validated.Invalid(e1), Validated.Invalid(e2)) =>
          Validated.Invalid(semi.combine(e1, e2))        
```

Согласно [законам монады](../typeclass/monad/monad.md) должно выполняться следующее:

```dotty
fab.ap(fa) <-> fab.flatMap(f => fa.map(f))
```

Проблема: Закон выше не выполняется, `flatMap` и `ap` (applicative) становятся **неконсистентными**:

```dotty
val fab = Validated.invalidNec[String, Int => Double]("Ошибка 1")
val fa  = Validated.invalidNec[String, Int]("Ошибка 2")

// При использовании Monad (fail-fast)
val monad = validatedMonad[NonEmptyChain[String]]
monad.ap(fab)(fa)
// Invalid(Ошибка 1) - первая ошибка
monad.flatMap(fab)(f => fa.map(f))
// Invalid(Ошибка 1) - первая ошибка

// При использовании Applicative (накопление)
val applicative = validatedApplicative[NonEmptyChain[String]]
applicative.ap(fab)(fa)
// Invalid(Ошибка 1, Ошибка 2) - обе ошибки
```

**Вывод**: `Validated` не может быть монадой, так как это нарушило бы законы `FlatMap`.

### Validated vs Either: когда что использовать

| Сценарий                                              | Рекомендация            |
|-------------------------------------------------------|-------------------------|
| Нужно накопить все ошибки                             | Используйте `Validated` |
| Нужна последовательная валидация (зависимые проверки) | Используйте `Either`    |
| Работа в for-comprehension                            | Используйте `Either`    |
| Параллельная проверка независимых полей               | Используйте `Validated` |
| API, требующее все ошибки сразу                       | Используйте `Validated` |
| Первая ошибка останавливает процесс                   | Используйте `Either`    |

### Последовательная валидация внутри Validated

Иногда внутри накопительной валидации требуется последовательная проверка. `Validated` предоставляет методы:

#### `andThen` (аналог flatMap)

```dotty
def positive(field: String, i: Int): Validated[ConfigError, Int] =
  if i >= 0 then Validated.Valid(i)
  else Validated.Invalid(ParseError(field))

val houseNumber = config.parse[Int]("house_number").andThen { n =>
  positive("house_number", n)
}
// Invalid(MissingConfig(house_number))
```

#### `withEither` (временное преобразование)

```dotty
def positiveEither(field: String, i: Int): Either[ConfigError, Int] =
  if i >= 0 then Right(i)
  else Left(ParseError(field))

val houseNumber = config.parse[Int]("house_number").withEither {
  (either: Either[ConfigError, Int]) =>
    either.flatMap { i =>
      positiveEither("house_number", i)
    }
}
// Invalid(MissingConfig(house_number))
```

### Заключение

`Validated` — это мощный инструмент для сценариев, требующих накопления ошибок. 
В отличие от `Either`, он не является монадой, но предоставляет богатые возможности для параллельной валидации через `Applicative`. 
Его использование особенно оправдано при:

- Валидации форм с множеством полей
- Парсинге конфигурации
- Проверке входных данных API
- Любых сценариях, где важно сообщить пользователю обо всех проблемах сразу
