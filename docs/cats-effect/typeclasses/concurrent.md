# Concurrent — параллельное состояние и синхронизация

`Concurrent[F[_]]` (или `GenConcurrent[F[_], E]` с явным типом ошибки) — это класс типов, который **расширяет `Spawn`** 
и добавляет возможность **выделять и манипулировать параллельным состоянием** в параллельной среде.

В иерархии Cats Effect `Concurrent` находится между `Spawn` и `Temporal`:

```
MonadError[F, E]
    ↓
MonadCancel[F, E]    ← можно отменять вычисления
    ↓
Spawn[F, E]          ← можно создавать параллельные волокна
    ↓
Concurrent[F, E]     ← добавляются примитивы синхронизации (Ref, Deferred)
    ↓
Temporal[F, E]       ← возможностью приостанавливать выполнение потока
    ↓
Async[F]             ← работа с callback-based API
    ↓
IO                   ← конкретная реализация
```

**Ключевая идея:** `Concurrent` предоставляет два фундаментальных строительных блока для программирования одновременных задач:

1. **`Ref[F, A]`** — [атомарная, неизменяемая ссылка](concurrent/ref.md) на значение типа `A`
2. **`Deferred[F, A]`** — [однократный контейнер для значения](concurrent/deferred.md), позволяющий волокнам ожидать его появления

Используя эти два примитива, можно построить **любые одновременные структуры данных**: семафоры, очереди, барьеры, таймеры, блокировки и т.д.

## Полная сигнатура класса типов

```dotty
trait Concurrent[F[_], E] extends Spawn[F, E]:

  /** Создаёт атомарную ссылку на начальное значение. */
  def ref[A](a: A): F[Ref[F, A]]

  /** Создаёт пустой однократный контейнер.
    *
    * Используется для блокировки волокна до того момента, пока другое волокно
    * не предоставит значение через `complete`.
    */
  def deferred[A]: F[Deferred[F, A]]

  /** Запоминает эффект, обеспечивая его однократное выполнение.
    *
    * Первый вызов возвращённого эффекта выполняет оригинальный `fa` и кеширует
    * результат (или ошибку). Все последующие вызовы возвращают кешированное
    * значение без повторного выполнения.
    *
    * Если несколько волокон одновременно обращаются к запомненному эффекту,
    * `fa` выполняется только один раз.
    */
  def memoize[A](fa: F[A]): F[F[A]]

  /** Параллельно применяет функцию к элементам структуры с ограничением
    * параллелизма.
    *
    * Одновременно выполняется не более `n` задач. Порядок результатов в
    * выходной структуре соответствует порядку входных элементов.
    */
  def parTraverseN[T[_]: Traverse, A, B](n: Int)(ta: T[A])(f: A => F[B])
      : F[T[B]]

  /** Параллельно применяет функцию к элементам структуры с ограничением
    * параллелизма, игнорируя результаты.
    *
    * Эквивалент `parTraverseN`, но результат каждого применения отбрасывается.
    * Эффективен, когда важны только побочные эффекты.
    */
  def parTraverseN_[T[_]: Foldable, A, B](n: Int)(ta: T[A])(f: A => F[B])
      : F[Unit]

  /** Параллельно выполняет эффекты из структуры с ограничением параллелизма.
    *
    * Принимает структуру, содержащую эффекты, и выполняет их параллельно, но не
    * более `n` одновременно. Возвращает структуру результатов в том же порядке.
    */
  def parSequenceN[T[_]: Traverse, A](n: Int)(tma: T[F[A]]): F[T[A]]

  /** Параллельно выполняет эффекты из структуры с ограничением параллелизма,
    * игнорируя результаты.
    */
  def parSequenceN_[T[_]: Foldable, A](n: Int)(tma: T[F[A]]): F[Unit]

  /** Параллельно повторяет эффект заданное число раз с ограничением
    * параллелизма.
    *
    * Выполняет эффект `ma` `replicas` раз, но не более `n` раз одновременно.
    * Результаты собираются в список.
    */
  def parReplicateAN[A](n: Int)(replicas: Int, ma: F[A]): F[List[A]]
```

> В реальном коде `parTraverseN` и `parSequenceN` обычно доступны через синтаксис `list.parTraverseN(n)(f)`, 
> но их реализация опирается на `Concurrent`.

### `Ref` — атомарная изменяемая ссылка

`Ref[F, A]` — это **конкурентно-безопасная** ссылка на значение типа `A` в контексте эффекта `F`. 
Она предоставляет операции для атомарного чтения, записи и изменения значения.
[Подробнее в соответствующем разделе.](concurrent/ref.md)

### `Deferred` — однократное обещание

`Deferred[F, A]` — это **однократный контейнер**, который изначально пуст и может быть заполнен ровно один раз. Волокна могут:

- Ожидать заполнения через `.get` (семантическая блокировка)
- Заполнить значение через `.complete(a)`

**Ключевое свойство:** если несколько волокон одновременно вызывают `complete`, только одно успешно заполнит `Deferred`, 
остальные получат ошибку или будут проигнорированы.

[Подробнее в соответствующем разделе.](concurrent/deferred.md)

## `memoize` — кеширование результатов эффектов

### Что делает `memoize`?

```dotty
def memoize[A](fa: F[A]): F[F[A]]
```

`memoize` — это **одновременный кеш** для эффекта:

- Первый запуск выполняет `fa` и сохраняет результат (или ошибку)
- Все последующие запуски возвращают сохранённый результат без повторного выполнения
- Если несколько волокон одновременно запрашивают запомненный эффект, `fa` выполнится **только один раз**

### Детальный пример

```dotty
import cats.effect.{IO, IOApp}
import cats.effect.unsafe.implicits.global

val action: IO[String] =
  IO.println("🔥 Тяжёлые вычисления...") *>
    IO.sleep(1.second) *>
    IO.pure("результат")

// Без memoize: выполняется каждый раз
val withoutMemo =
  for
    r1 <- action
    r2 <- action
    r3 <- action
  yield List(r1, r2, r3)
  
// Вывод: "🔥 Тяжёлые вычисления..." трижды!
withoutMemo.unsafeRunSync()
// 🔥 Тяжёлые вычисления...
// 🔥 Тяжёлые вычисления...
// 🔥 Тяжёлые вычисления...
// List(результат, результат, результат)

// С memoize: выполняется один раз
val withMemo =
  for
    memoized <- action.memoize
    r1       <- memoized
    r2       <- memoized
    r3       <- memoized
  yield List(r1, r2, r3)
  
// Вывод: "🔥 Тяжёлые вычисления..." единожды!
withMemo.unsafeRunSync()
// 🔥 Тяжёлые вычисления...
// List(результат, результат, результат)
```

### Реальный пример: кеширование конфигурации

```dotty
class ConfigCache[F[_]: {Concurrent, Sync}]:
  private val configLoader: F[F[Config]] =
    loadConfigFromFile().memoize

  private def loadConfigFromFile(): F[Config] =
    Sync[F].delay {
      println("📂 Загрузка конфигурации из файла...")
      // Тяжёлая операция
      Config("localhost", 8080, "secret-key")
    }

  def getConfig: F[Config] =
    configLoader.flatMap(identity)

// Использование
val program =
  val cache = new ConfigCache[IO]

  for
    conf1 <- cache.getConfig // Загружает из файла
    conf2 <- cache.getConfig // Берёт из кеша
    conf3 <- cache.getConfig // Берёт из кеша
  yield ()
```

### `memoize` vs ручное кеширование через `Ref`

| Аспект                        | `memoize`                      | Ручное кеширование через `Ref`  |
|-------------------------------|--------------------------------|---------------------------------|
| **Сложность**                 | Минимальная                    | Нужно управлять состоянием      |
| **Гонка при первом запуске**  | Обработана автоматически       | Легко допустить ошибку          |
| **Кеширование ошибок**        | Да (ошибка также сохраняется)  | По желанию                      |
| **Очистка кеша**              | Нет (нужен свой механизм)      | Полный контроль                 |
| **Производительность**        | Оптимизирован                  | Зависит от реализации           |

## Атомарная машина состояний: `CountDownLatch`

Давайте реализуем **классический примитив синхронизации** — `CountDownLatch`.

`CountDownLatch` (защёлка обратного отсчёта) создаётся с начальным числом `n`. Волокна могут:

- **Ждать** (`await`) — заблокироваться, пока счётчик не станет 0
- **Освобождать** (`release`) — уменьшить счётчик на 1; 
- Когда счётчик достигает 0, все ожидающие волокна разблокируются

### Моделирование состояния

```dotty
sealed trait State[F[_]]
case class Awaiting[F[_]](
    latches: Int,             // Сколько ещё защёлок нужно освободить
    signal: Deferred[F, Unit] // Сигнал для пробуждения ожидающих
) extends State[F]
case class Done[F[_]]() extends State[F] // Финальное состояние
```

Здесь мы определяем алгебраический тип данных для представления двух возможных состояний защёлки. 
`Awaiting` — активное состояние, хранящее оставшееся количество защёлок (`latches`) 
и `Deferred`-канал для уведомления ожидающих волокон. 
`Done` — терминальное состояние, означающее, что защёлка закрыта и все ожидающие уже разблокированы. 
Такой подход позволяет моделировать конечный автомат конкурентного примитива.

### Реализация `CountDownLatch`

```dotty
class CountDownLatch[F[_]: Concurrent](state: Ref[F, State[F]]):
  /** Ожидание, пока счётчик не станет 0. Если защёлка уже закрыта (Done) —
    * возвращается немедленно.
    */
  def await: F[Unit] =
    state.get.flatMap:
      // Ещё не готовы — ждём сигнала
      case Awaiting(_, signal) => signal.get
      // Уже готово
      case Done() => Concurrent[F].unit

  /** Освобождает одну защёлку. Когда счётчик достигает 0, пробуждает все
    * ожидающие волокна.
    */
  def release: F[Unit] =
    Concurrent[F].uncancelable { _ =>
      state.modify {
        case Awaiting(n, signal) if n > 1 =>
          // Уменьшаем счётчик, сигнал ещё не отправляем
          (Awaiting(n - 1, signal), Concurrent[F].unit)

        case Awaiting(_, signal) =>
          // Последняя защёлка — закрываем защёлку и пробуждаем всех
          (Done(), signal.complete(()).void)

        case d @ Done() =>
          // Уже закрыто — ничего не делаем
          (d, Concurrent[F].unit)
      }.flatten
    }
end CountDownLatch
```

Основная логика примитива реализована через атомарные операции над `Ref`.

**Метод `await`**: просто читает текущее состояние. 
Если защёлка в состоянии `Awaiting` — вызывающий поток блокируется на `signal.get`. 
Если уже `Done` — завершается мгновенно.

**Метод `release`**: обёрнут в `uncancelable` для защиты критической секции от отмены. 
С помощью `state.modify` атомарно обновляем состояние:

- Если осталось больше 1 защёлки (`n > 1`) — уменьшаем счётчик, сигнал не отправляем
- Если это последняя защёлка (`n == 1`) — переходим в `Done` и отправляем сигнал через `signal.complete`, пробуждая все ожидающие волокна
- Если уже в `Done` — ничего не делаем

`modify` возвращает эффект, который затем разворачивается через `.flatten`. 
Благодаря `uncancelable` гарантируется, что переходы между состояниями будут атомарными даже при внешних отменах.

### Использование `CountDownLatch`

```dotty
object LatchDemo extends IOApp.Simple:
  def run: IO[Unit] =
    for
      signal <- Concurrent[IO].deferred[Unit]
      state  <- Concurrent[IO].ref[State[IO]](Awaiting(3, signal))
      latch = new CountDownLatch[IO](state)
  
      // Запускаем 3 рабочих волокна
      _ <- (1 to 3).toList.traverse { id =>
        (
          for
            _ <- IO.sleep((id * 500).millis)
            _ <- IO.println(s"Рабочий $id: готов!")
            _ <- latch.release
          yield ()
        ).start
      }
  
      // Главное волокно ждёт всех
      _ <- IO.println("Главный: ожидаю всех рабочих...")
      _ <- latch.await
      _ <- IO.println("Главный: все готовы! Начинаем работу!")
    yield ()
    end for
  end run
```

**Вывод:**

```
Главный: ожидаю всех рабочих...
Рабочий 1: готов!
Рабочий 2: готов!
Рабочий 3: готов!
Главный: все готовы! Начинаем работу!
```

Демонстрация работы `CountDownLatch` в реальном сценарии.

**Инициализация:** Сначала создаются `Deferred[Unit]` для сигнала 
и `Ref[State]` с начальным состоянием `Awaiting(3, signal)`, затем инстанс `CountDownLatch`.

**Запуск рабочих:** Для каждого из 3 рабочих волокон запускается отдельное волокно с задержкой (`id * 500 мс`), 
затем распечатывается сообщение о готовности и вызывается `latch.release()`.

**Ожидание:** Главное волокно вызывает `latch.await()` и блокируется до тех пор, пока все 3 рабочих не вызовут `release`.

**Разблокировка:** Когда последний (третий) рабочий вызывает `release`, счётчик достигает 0, 
`signal.complete` пробуждает главное волокно, и оно продолжает выполнение с финальным сообщением.

**Ключевое наблюдение:** Задержки рабочих (500ms, 1000ms, 1500ms) демонстрируют, 
что главное волокно ждёт завершения всех, независимо от порядка их готовности. 
Это классический сценарий использования защёлки — координация начала операции после выполнения нескольких предусловий.

### Почему именно `Ref` и `Deferred`?

`Ref` и `Deferred` — это **минимальные** примитивы, из которых можно построить всё остальное:

| Примитив        | Аналогия                     | Что позволяет                         |
|-----------------|------------------------------|---------------------------------------|
| **`Ref`**       | Атомарная переменная         | Атомарное чтение/изменение состояния  |
| **`Deferred`**  | Promise / CompletableFuture  | Ожидание события (semantic blocking)  |

**Из них строится:**

- `Semaphore` (семафор) — `Ref[(Long, Deferred[F, Unit])]`
- `Queue` (очередь) — `Ref[Vector[A]]` + `Deferred[F, Unit]` для сигналов
- `Mutex` (мьютекс) — `Ref[Boolean]` + `Deferred[F, Unit]` для блокировки
- `CyclicBarrier` — `Ref` состояния + `Deferred` для пробуждения

### Альтернативный подход: почему не `AtomicReference` и `Lock`?

В Java мы использовали бы `AtomicReference` и `Lock/ReentrantLock`. Но в Cats Effect:

1. **`AtomicReference`** не работает с `F` — он небезопасен из-за `null` и не интегрирован с отменой
2. **`Lock`** — блокирует потоки ОС, что убивает масштабируемость
3. **`Object.wait/notify`** — требует `synchronized` и блокирует потоки

`Ref` и `Deferred` дают **легковесную, отменяемую, безопасную по ресурсам** альтернативу.

## Продвинутый паттерн: пул воркеров (workers pool)

Теперь, используя все знания, построим **пул воркеров** на базе `Ref` и `Deferred`:

```dotty
import cats.effect.{Concurrent, Deferred, Ref, Resource}
import cats.syntax.all._
import scala.collection.immutable.Queue

class WorkerPool[F[_]: Concurrent, A](workers: Int):
  private case class State(
    queue: Queue[A],
    waiting: Option[Deferred[F, A]]  // волокно, ожидающее задачу
  )

  private val state: F[Ref[F, State]] =
    Concurrent[F].ref(State(Queue.empty, None))

  // Добавить задачу в очередь
  def submit(a: A): F[Unit] =
    state.flatMap { ref =>
      ref.modify {
        case State(queue, Some(waiting)) =>
          // Есть ожидающий воркер — передаём задачу напрямую
          (State(queue, None), waiting.complete(a).void)

        case State(queue, None) =>
          // Нет ожидающих — кладём в очередь
          (State(queue.enqueue(a), None), Concurrent[F].unit)
      }.flatten
    }

  // Забрать задачу (воркер вызывает этот метод)
  private def take: F[A] =
    Concurrent[F].deferred[A].flatMap { waiting =>
      state.flatMap { ref =>
        ref.modify {
          case State(queue, None) if queue.nonEmpty =>
            // Есть задача в очереди — отдаём немедленно
            val (a, newQueue) = queue.dequeue
            (State(newQueue, None), a.pure[F])

          case State(queue, None) if queue.isEmpty =>
            // Нет задач — регистрируем ожидание
            (State(queue, Some(waiting)), waiting.get)

          case State(queue, Some(_)) =>
            // Не должно случиться (waiting всегда None при some)
            (State(queue, None), Concurrent[F].canceled >> take)
        }.flatten
      }
    }

  // Запустить воркеров
  def start(workerTask: A => F[Unit]): Resource[F, Unit] =
    (1 to workers).toList.traverse { _ =>
      (take.flatMap(workerTask)).foreverM.start
    }.flatMap { fibers =>
      Resource.eval(fibers.traverse_(_.join))
    }

// Использование
val program = for
  pool <- Resource.eval(Concurrent[IO].delay(new WorkerPool[IO, String](3)))
  _ <- pool.start(task => IO.println(s"Обрабатываю: $task"))
  _ <- pool.submit("Задача 1")
  _ <- pool.submit("Задача 2")
  _ <- pool.submit("Задача 3")
  _ <- pool.submit("Задача 4")
  _ <- IO.sleep(2.seconds)
yield ()
```

## Итог: что даёт `Concurrent`?

| Возможность                         | Ключевой примитив                                                |
|-------------------------------------|------------------------------------------------------------------|
| **Атомарное состояние**             | `Ref` — ссылка с атомарными обновлениями                         |
| **Ожидание событий**                | `Deferred` — однократный сигнал                                  |
| **Кеширование результатов**         | `memoize` — ленивое однократное выполнение                       |
| **Ограниченный параллелизм**        | `parTraverseN` — контроль числа одновременных задач              |
| **Сложные конкурентные структуры**  | `Ref` + `Deferred` для реализации семафоров, очередей, барьеров  |

**Главная идея:** `Concurrent` предоставляет минимальный, 
но достаточный набор примитивов для построения **любого** конкурентного кода в функциональном стиле. 
Если вам нужно управлять состоянием, синхронизировать волокна или 
ограничивать параллелизм — `Concurrent` даёт все необходимые инструменты.

В реальных приложениях вы будете использовать `Concurrent` постоянно:

- `Ref` для счётчиков, кешей, флагов
- `Deferred` для координации между волокнами
- `Semaphore` (построенный на `Concurrent`) для ограничения параллелизма
- `memoize` для дорогих операций
- `Queue` для обмена сообщениями между волокнами

И всё это — с полной поддержкой отмены, безопасностью ресурсов и потрясающей масштабируемостью.
