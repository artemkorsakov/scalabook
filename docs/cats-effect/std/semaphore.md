# Semaphore — Счётный семафор для контроля параллелизма

**Семафор** — это классический примитив синхронизации, 
который контролирует доступ к общему ресурсу с помощью счётчика **разрешений** (permits). 
Представьте себе турникет в метро, который пропускает только `n` человек в минуту, а остальные вынуждены ждать.

- **Счётчик разрешений** — неотрицательное целое число, показывающее, сколько потоков (волокон) могут одновременно получить доступ.
- **Acquire (получение)** — уменьшает счётчик на 1. Если разрешений нет (счётчик = 0), волокно **блокируется** и ждёт.
- **Release (освобождение)** — увеличивает счётчик на 1, пробуждая одно из ожидающих волокон.

### Базовый интерфейс

```dotty
abstract class Semaphore[F[_]]:
  /** Текущее количество доступных разрешений (неблокирующая операция). */
  def available: F[Long]

  /** Запрашивает одно разрешение. Блокируется, если нет доступных. */
  def acquire: F[Unit]

  /** Возвращает одно разрешение обратно, увеличивая счётчик. */
  def release: F[Unit]

  // ... и многое другое: tryAcquire, count, withPermit, etc.
```

## Семантическая блокировка (а не блокировка потока)

Ключевая особенность семафора в Cats Effect — **семантическая блокировка**:

- Когда волокно вызывает `acquire` и ждёт разрешение, **системный поток не блокируется**.
- Вместо этого волокно приостанавливается, а поток OS переключается на выполнение другого волокна.
- Это позволяет масштабироваться до **миллионов одновременных ожидающих волокон**, 
  в отличие от традиционных `Semaphore` из `java.util.concurrent`.

**Важно:** Блокирующая операция `acquire` полностью **отменяема**. 
Если ожидающее волокно отменить, оно будет корректно удалено из очереди ожидания, и счётчик не "потеряет" разрешение.

## Пример из документации: Три процесса борются за ресурс

В этом примере три процесса (`R1`, `R2`, `R3`) одновременно пытаются получить доступ к **одному** (`available = 1`) ресурсу. 
Семафор гарантирует, что в любой момент времени работать может только один из них.

```dotty
import cats.effect.{IO, Temporal}
import cats.effect.std.{Console, Semaphore}
import cats.syntax.all.*
import scala.concurrent.duration.*

class PreciousResource[F[_]: {Temporal, Console as console}](
    name: String,
    semaphore: Semaphore[F]
):
  def use: F[Unit] =
    for
      // 1. Смотрим, сколько разрешений доступно
      availableBefore <- semaphore.available
      _               <- console.println(s"$name >> Доступно: $availableBefore")

      // 2. Запрашиваем разрешение (уменьшаем счётчик)
      _                     <- semaphore.acquire // если 0, волокно блокируется
      availableAfterAcquire <- semaphore.available
      _                     <-
        console.println(s"$name >> НАЧАЛО | Доступно: $availableAfterAcquire")

      // 3. Симулируем работу с ресурсом (задержка 3 секунды)
      //    По завершению, разрешение будет автоматически возвращено через `release`
      _ <- console.println(s"$name >> Работаю...")

      // 4. Возвращаем разрешение с задержкой:
      _                     <- Temporal[F].sleep(3.seconds) // Имитация работы
      _                     <- semaphore.release
      availableAfterRelease <- semaphore.available
      _                     <- console.println(
        s"$name >> ЗАВЕРШЕНО | Доступно: $availableAfterRelease"
      )
    yield ()
end PreciousResource

val program: IO[Unit] =
  for
    sem <- Semaphore[IO](1) // Создаём семафор с 1 разрешением
    r1 = new PreciousResource[IO]("R1", sem)
    r2 = new PreciousResource[IO]("R2", sem)
    r3 = new PreciousResource[IO]("R3", sem)
    _ <- List(r1.use, r2.use, r3.use).parSequence.void
  yield ()
```

### Возможный вывод (порядок может отличаться)

```
R1 >> Доступно: 1
R3 >> Доступно: 1
R2 >> Доступно: 1
R2 >> НАЧАЛО | Доступно: 0
R2 >> Работаю...
R1 >> НАЧАЛО | Доступно: 0
R3 >> НАЧАЛО | Доступно: 0
R2 >> ЗАВЕРШЕНО | Доступно: 0
R1 >> Работаю...
R1 >> ЗАВЕРШЕНО | Доступно: 0
R3 >> Работаю...
R3 >> ЗАВЕРШЕНО | Доступно: 1
```

### Анализ происходящего

1. **Начало гонки**: Все три волокна одновременно вызывают `use`.
2. **Чтение `available`**: `R1`, `R2` и `R3` видят `1`.
3. **Acquire**: `R2` быстрее всех выполняет `acquire`, захватывает единственное разрешение, счётчик становится `0`.
4. **Блокировка**: `R1` и `R3` теперь не могут выполнить `acquire` и **семантически блокируются**, вставая в очередь ожидания.
5. **Работа**: `R2` работает 3 секунды, затем вызывает `release`, увеличивая счётчик до `1`.
6. **Пробуждение**: Ожидающие волокна (`R1` и `R3`) просыпаются. Порядок зависит от политики очереди (обычно FIFO). 
   Допустим, `R1` захватывает разрешение следующим, а `R3` продолжает ждать.
7. **Завершение**: Процесс повторяется, пока все не отработают.

## Продвинутые методы

Современный `Semaphore` предоставляет множество полезных методов:

| Метод                           | Описание                                                                                                                           |
|:--------------------------------|:-----------------------------------------------------------------------------------------------------------------------------------|
| `tryAcquire`                    | Неблокирующая попытка получить разрешение. Возвращает `Boolean`.                                                                   |
| `available`                     | Текущее количество разрешений.                                                                                                     |
| `count`                         | Аналогично `available`, когда разрешения доступны, но возвращает количество ожидающих (отрицательное число), когда разрешений нет. |
| `acquireN(n)`                   | Запрашивает `n` разрешений.                                                                                                        |
| `releaseN(n)`                   | Возвращает `n` разрешений.                                                                                                         |

### Пример с `acquireN` и `releaseN`

```dotty
// Семафор с 5 разрешениями
for
  sem <- Semaphore[IO](5)
  // Запрашиваем 3 разрешения сразу
  _ <- sem.acquireN(3)
  // Теперь доступно 2
  _ <- sem.acquireN(2)
  // Теперь доступно 0
  _ <- sem.releaseN(4)
// Доступно 4
yield ()
```

## Пример: Ограничение параллелизма HTTP-запросов

Реальный сценарий: вам нужно отправить 1000 запросов к внешнему API, но он принимает не более 10 одновременно.

```dotty
import cats.effect.{IO, IOApp}
import cats.effect.std.Semaphore
import cats.syntax.all.*

object ApiClient extends IOApp.Simple:
  def fetchUrl(url: String): IO[String] =
    IO.pure(s"Data from $url") // имитация запроса

  def run: IO[Unit] =
    val urls = (1 to 1000).map(i => s"https://api.example.com/data/$i").toList

    Semaphore[IO](10).flatMap {
      semaphore => // максимум 10 одновременных запросов
        urls.parTraverse { url =>
          semaphore.permit.use { _ =>
            fetchUrl(url)
          }
        }.flatMap(IO.println)
    }
```

**Результат:** Будет активно не более 10 одновременных запросов, остальные будут дожидаться освобождения семафора.

## Семафор с динамическим количеством разрешений

Семафор не обязан быть статическим. 
Вы можете увеличивать количество доступных разрешений в рантайме, вызывая `release` без соответствующего `acquire`.

```dotty
for
  sem <- Semaphore[IO](0) // начинаем без разрешений
  // Добавляем 5 разрешений
  _ <- sem.releaseN(5)
// Теперь доступно 5
yield ()
```

## Сравнение с другими примитивами

| Примитив         | Назначение             | Разрешения          | Множественный доступ    |
|:-----------------|:-----------------------|:--------------------|:------------------------|
| **`Semaphore`**  | Контроль параллелизма  | Счётный (n)         | Да (до n волокон)       |
| **`Mutex`**      | Взаимное исключение    | 0 или 1             | Нет (только 1 волокно)  |
| **`Deferred`**   | Однократный сигнал     | Однократный         | Нет (просыпает всех)    |
| **`Queue`**      | Буферизация данных     | Зависит от ёмкости  | Да (producer-consumer)  |

## Итог: когда использовать `Semaphore`?

✅ **Используйте семафор, если нужно:**

- Ограничить количество одновременных обращений к ресурсу (API, БД, файловая система).
- Реализовать паттерн "пул соединений" (connection pool).
- Контролировать утилизацию ресурсов в высоконагруженной системе.
- Оркестрировать доступ к разделяемому состоянию с небинарной блокировкой.

❌ **Не используйте семафор, если:**

- Нужно, чтобы ресурс принадлежал только одному волокну — используйте `Mutex`.
- Нужно подождать один единственный сигнал — используйте `Deferred`.
- Нужна асинхронная очередь сообщений — используйте `Queue`.

**Ключевая идея:** `Semaphore` — это незаменимый инструмент для борьбы с перегрузкой системы. 
Он позволяет выдерживать пиковые нагрузки, не захлёбываясь, 
и является фундаментальным строительным блоком для многих конкурентных структур в Cats Effect.
