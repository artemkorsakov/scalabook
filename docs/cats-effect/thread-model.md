# Модель потоков в Cats Effect

Cats Effect — это мощный инструмент для создания высокопроизводительных, конкурентных систем на Scala. 
Однако для его эффективного использования необходимо понимать базовую модель потоков и то, как [волокна](foundation/fibers.md) 
планируются поверх потоков операционной системы.

## Основные цели модели потоков

Ключевые принципы многопоточности в Cats Effect были детально описаны в [gist Даниэля Спивака](https://gist.github.com/djspiewak/46b543800958cf61af6efa8e072bfd5c). 
Вот краткое изложение этих принципов.

### Архитектура пулов потоков

Оптимальная конфигурация для Cats Effect приложения на JVM:

1.  **Вычислительный пул (compute pool)**
    - Размер: примерно равен количеству доступных процессорных ядер.
    - Назначение: выполнение **неблокирующих**, вычислительных операций волокон.
    - _Примечание:_ В зависимости от приложения, вы можете получить лучшую производительность, 
      оставив одно или два ядра свободными для сборки мусора или других системных нужд.
2.  **Блокирующий пул (blocking pool)**
    - Размер: неограниченный, кэширующий пул потоков.
    - Назначение: выполнение **блокирующих операций** ввода-вывода (работа с файлами, JDBC-запросы, чтение из сокетов и т.д.).
3.  **Пул для асинхронного ввода-вывода (async I/O)**
    - Размер: 1-2 высокоприоритетных потока.
    - Назначение: обработка асинхронных событий ввода-вывода (например, из `java.nio.channels`). 
      Сами эти события должны немедленно перенаправляться в вычислительный пул для дальнейшей обработки.

**Главная цель** — минимизировать количество дорогостоящих переключений контекста потоков и максимизировать время, 
в течение которого вычислительный пул выполняет полезную работу.

### Почему не `scala.concurrent.ExecutionContext.global`?

Важно понимать, что `scala.concurrent.ExecutionContext.global` — это **плохой выбор** для вычислительного пула в Cats Effect. Причины:

- Его архитектура (`ForkJoinPool`) предполагает, что в нём будут выполняться блокирующие операции, 
  поэтому он может **выделять дополнительные потоки** для их "маскировки", увеличивая накладные расходы.
- Нет способа запретить библиотекам в вашем classpath планировать выполнение произвольного кода на этом экзекуторе, 
  что делает его ненадёжной основой.

## Цикл выполнения `IO`: как это работает под капотом

Чтобы понять модель потоков, нужно понять, как выполняется `IO`. Упрощённая модель `IO` может выглядеть так:

```dotty
sealed abstract class IO[A]:
  def flatMap[B](f: A => IO[B]): IO[B] = FlatMap(this, f)
  def unsafeRun(): A                   = this match
    case Pure(a)        => a
    case Suspend(thunk) => thunk()
    case FlatMap(io, f) => f(io.unsafeRun()).unsafeRun()

case class Pure[A](a: A)                           extends IO[A]
case class Suspend[A](thunk: () => A)              extends IO[A]
case class FlatMap[A, B](io: IO[B], f: B => IO[A]) extends IO[A]
```

Эта модель опускает обработку ошибок, асинхронность и стекобезопасность, но хорошо иллюстрирует главное: 
`unsafeRun()` — это **цикл, интенсивно использующий CPU**, который рекурсивно "разворачивает" вложенные структуры `IO`.

В реальном Cats Effect этот цикл выполняется для каждого волокна (fiber), 
которое по сути является экземпляром живого `IO`-вычисления.

### Волокна (Fibers)

Волокна — это **легковесные, логические потоки выполнения**. Они не привязаны напрямую к потокам ОС:

- Волокна выполняются по схеме **`m:n`**: множество волокон (`m`) могут быть запланированы на меньшем количестве потоков ОС (`n`).
- Они создаются с помощью методов `IO#start`, `IO.race`, `IO.parTraverse` и других.

**Важно:** Волокна используют **кооперативную многозадачность**. 
Это означает, что волокно **добровольно** должно передавать управление процессору, чтобы другие волокна могли выполняться.
В противном случае одно волокно может "захватить" ядро CPU.

К счастью, волокна автоматически уступают управление на **асинхронных границах**, 
таких как ожидание результата от `Deferred.get`, `IO.sleep`, или чтение из очереди `Queue.take`. 
Однако, если волокно выполняет **длительную CPU-интенсивную операцию** без таких границ, оно может монополизировать поток:

```dotty
// Опасно! Может заблокировать поток вычислений.
def calculate(data: Vector[BigInt]): IO[BigInt] =
  IO(longSubTaskA(data))
    .map(xs => longSubTaskB(xs))
    .map(ys => longSubTaskC(ys)) // Нет точек уступки управления.
```

Если у вас есть такие операции, явно добавьте точку уступки с помощью `IO.cede`. 
Это даст возможность другим волокнам выполниться на том же потоке.

```dotty
// Безопасно: между этапами даём шанс другим волокнам.
def calculate(data: Vector[BigInt]): IO[BigInt] =
  IO(longSubTaskA(data)).flatMap { xs =>
    IO.cede.map { _ =>
      longSubTaskB(xs)
    }
  }.map(ys => longSubTaskC(ys))
```

## Блокирующие вызовы: как их правильно обрабатывать

Прямым следствием из описанной модели является то, что **выполнение блокирующего кода в вычислительном пуле — это катастрофа**.

Представьте сервер на узле с 2 CPU. Если вы выполните блокирующий вызов, например:

```dotty
IO(Source.fromFile(path).getLines().mkString)
```

то на время его выполнения **одно из двух ядер будет полностью занято ожиданием**. 
Это сразу снижает общую производительность приложения вдвое. Два таких блокирующих вызова практически остановят обработку.

**Решение:** перенаправляйте блокирующие операции в специальный блокирующий пул, 
и после их завершения возвращайте результат обратно в вычислительный пул.

## Семантическая блокировка: не путать с блокировкой потока

Нам также часто нужно, чтобы волокно **логически ожидало** выполнения какого-либо условия 
(например, появления элемента в очереди). 
Но мы не можем использовать для этого обычные Java/Scala-блокировки (`synchronized`, `Lock`, `BlockingQueue`), 
так как они остановят целый поток ОС.

Вместо этого Cats Effect предоставляет концепцию **семантической блокировки**. 
Волокно приостанавливает свою работу и передаёт управление, 
но при этом **поток ОС остаётся свободным** для выполнения других волокон.

Классический пример — `IO.sleep(duration)`. **Никогда** не используйте `IO(Thread.sleep(duration))` (блокировка потока), 
всегда используйте `IO.sleep` (семантическая блокировка).

Фундаментом для произвольных семантических блокировок является `Deferred` — однократное, потокобезопасное "обещание".

```dotty
trait Deferred[F[_], A]:
  // семантически блокируется, пока значение не появится
  def get: F[A]
  // устанавливает значение, пробуждает ожидающие волокна
  def complete(a: A): F[Boolean]
```

На основе `Deferred` построены все остальные примитивы синхронизации: `Semaphore`, `Queue`, `Mutex` и т.д.

## Cats Effect 3

### Асинхронные эффекты

**CE3** представляет новый класс типов `Async` с семантикой, похожей на монаду-ридер:

```dotty
trait Async[F[_]]:
  // Выполнить `fa` на указанном ExecutionContext, ВЕРНУТЬСЯ обратно
  def evalOn[A](fa: F[A], ec: ExecutionContext): F[A]

  // Получить текущий ExecutionContext (обычно вычислительный пул)
  def executionContext: F[ExecutionContext]
```

Важно, что после выполнения блока `evalOn` выполнение **автоматически возвращается** в пул, заданный `executionContext`. 
Это делает код более предсказуемым и безопасным.

### Блокирующие операции

**CE3** предоставляет встроенные методы:

- `IO.blocking(thunk)` / `Sync[F].blocking(thunk)`: выполнить `thunk` в блокирующем пуле, дождаться результата.
- `IO.interruptible(thunk)`: аналогично `blocking`, но попытаться прервать `thunk` через `Thread.interrupt()` при отмене волокна.

```dotty
// В CE3 всё просто
IO.println("Вычислительный пул") >>
  IO.blocking(println("Блокирующий пул")) >>
  IO.println("Снова вычислительный пул")
```

### Пул потоков, перехватывающих задачи (Work-Stealing Pool)

CE3 поставляется с собственной высокопроизводительной реализацией пула потоков, work-stealing pool. 
Он обладает ключевыми преимуществами:

1. **Очередь задач на каждое ядро:** Вместо одной глобальной очереди, разделяемой всеми потоками, 
   этот пул использует отдельную очередь для каждого ядра. Это **значительно снижает конкуренцию** за доступ к очереди, 
   что критично для систем с большим числом ядер (64+).
2. **Привязка к потоку (locality):** Пул старается перепланировать только что уступившее волокно на тот же самый поток ОС. 
   Это позволяет сохранять "теплые" кэши процессора (L1/L2) и избегать дорогостоящих промахов кэша при переключении.
3. **Автоматическая уступка (Auto-yielding):** Чтобы предотвратить случайную монополизацию CPU одним волокном, 
   пул может автоматически вставлять вызовы `IO.cede` после определённого количества выполненных итераций цикла `IO`.

## Заключение

Понимание модели потоков Cats Effect — залог написания высокопроизводительных, надёжных и предсказуемых приложений.

- **Используйте правильные пулы:** вычислительный пул для CPU-работы, блокирующий пул для I/O.
- **Избегайте блокировок потоков:** отдавайте предпочтение семантическим блокировкам (`Deferred`, `IO.sleep`).
- **Помечайте блокировки:** используйте `IO.blocking` для любых операций, которые могут заблокировать поток ОС.
- **Уступайте управление:** для долгих CPU-операций вставляйте `IO.cede`, чтобы сохранить отзывчивость системы.
- **Доверяйте `IOApp`:** он автоматически настраивает для вас оптимальные пулы потоков.

Следуя этим принципам, вы сможете создавать системы, способные выдерживать огромные нагрузки, оставаясь при этом чистыми и композируемыми.
