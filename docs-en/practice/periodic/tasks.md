# Generating Periodic Tasks

Periodic tasks are **instances** of periodic templates, created for a specific date.
If the step "Review presentation" (daily) is a template,
then a **periodic task** is "15.03.2026 - Daily task" with a plan `[1. Review presentation]`, created for March 15.
Each day the system generates a new task from the template, and the user works with it like any regular task: checks off steps, completes it, edits the plan.

This is a key distinction: **template** (what to do) and **instance** (when to do it).
A template is configured once in settings; instances are automatically created on schedule.

## `PeriodicTask` Model

```dotty
final case class PeriodicTask(
    id: PeriodicTaskId,
    userId: UserId,
    periodicType: PeriodicType,
    date: LocalDate,
    plan: Plan,
    completed: Boolean
)
```

**Fields breakdown:**

| Field            | Type           | Purpose                                      |
| ---------------- | -------------- | -------------------------------------------- |
| **`id`**         | `PeriodicTaskId` | Unique instance identifier                 |
| **`userId`**     | `UserId`       | Task owner                                   |
| **`periodicType`** | `PeriodicType` | Period type (`Daily`, `Weekly`, ...)         |
| **`date`**       | `LocalDate`    | Date for which the task is created           |
| **`plan`**       | `Plan`         | Execution plan (list of steps)               |
| **`completed`**  | `Boolean`      | Whether the task is fully completed          |

**Why `date` instead of `startDate`/`endDate`?** Because a periodic task is tied to **a specific date**.
It does not span a week — it is created for Monday and should be completed on Monday.
`LocalDate` is the precise model: "task for March 15".

**Why `completed: Boolean` instead of a status?** Because a periodic task has **two states**: open and completed.
Statuses `InProgress`, `Planned`, `KnowledgeBase` are for project tasks with a long lifecycle.
A periodic task lives one day (or one week) — it doesn't need an intermediate status. `Boolean` is simpler and more accurate.

**Why is `plan` a `Plan` and not just a list of strings?**
Because a periodic task may have a **hierarchical plan** with nested steps.
`Plan` provides the same structure as regular tasks: `PlanStep` with number, text, and a flag.
This uniformity means the user works with the plan identically in both task types.

### `PeriodicTaskId`

```dotty
object PeriodicTask:
  type PeriodicTaskId = PeriodicTaskId.T
  object PeriodicTaskId extends PdpUUID
```

**Breakdown:**

- **`PeriodicTaskId`** — a refined type over `UUID`.
  Protects against accidental confusion: `PeriodicTaskId` and `UserId` are both `UUID`, but incompatible at the compiler level.

## `CreatePeriodicTask` DTO

```dotty
final case class CreatePeriodicTask(
    userId: UserId,
    periodicType: PeriodicType,
    date: LocalDate,
    plan: Plan
)
```

DTO for creating an instance. Differs from `PeriodicTask` by the absence of `id` — ID is generated by the DB (`DEFAULT gen_random_uuid()`).

## `PeriodicTaskService`

```dotty
private[services] trait PeriodicTaskService[F[_]]:
  def create(newItem: CreatePeriodicTask): F[PeriodicTaskId]
  def get(id: PeriodicTaskId, userId: UserId): F[Option[PeriodicTask]]
  def getByUser(userId: UserId): F[Vector[PeriodicTask]]
  def update(item: PeriodicTask): F[Boolean]
  def delete(id: PeriodicTaskId): F[Boolean]
```

**Method breakdown:**

- **`create`** — creates an instance and returns the ID.
- **`get`** — gets an instance by ID **with owner verification**: takes `userId`
  and filters by `user_id`. Returns `Option` because it may not exist (or may belong to another user).
- **`getByUser`** — gets all user instances. Used for **filtering incomplete tasks** and **checking if a task for this date has already been created**.
- **`update`** — updates an instance. Returns `Boolean` — whether it was found.
- **`delete`** — deletes an instance.

**Why no `updateAll`?** Because periodic tasks are **not reordered**.
Their order is determined by **date** and **period type**, not manual sorting.
`updateAll` is only needed for plan steps (where the user sets order), not for instances.

**Why no `reorder`?** Similarly:
instances are ordered by `(periodicType.ordinal, date)` — this is a **natural order** that does not require manual management.

## Database Migration

```dotty
private val createPeriodicTasksTable: Fragment =
  sql"""CREATE TABLE IF NOT EXISTS periodic_tasks (
       id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
       user_id UUID NOT NULL,
       periodic_type PeriodicTypeEnum NOT NULL,
       date DATE NOT NULL,
       plan VARCHAR[] NOT NULL,
       completed BOOLEAN NOT NULL DEFAULT FALSE
       );"""
```

**Columns breakdown:**

| Column            | Type                               | Purpose                                                      |
| ----------------- | ---------------------------------- | ------------------------------------------------------------ |
| **`id`**          | `UUID DEFAULT gen_random_uuid()`   | Primary key. PostgreSQL generates UUID automatically.        |
| **`user_id`**     | `UUID NOT NULL`                    | Owner. `NOT NULL` — a task always belongs to someone.        |
| **`periodic_type`** | `PeriodicTypeEnum NOT NULL`        | Period type. Same enum as in `periodic_steps`.               |
| **`date`**        | `DATE NOT NULL`                    | Task date. `DATE`, not `TIMESTAMP` — day-level precision.    |
| **`plan`**        | `VARCHAR[] NOT NULL`               | String array. Each string is a JSON-serialized `PlanStep`.   |
| **`completed`**   | `BOOLEAN NOT NULL`                 | Completion flag.                                             |

**Why `gen_random_uuid()`?** Because UUID is generated **on the database side**. This is more reliable than generating in Scala:

- No risk of collisions during parallel inserts.
- No need to pass ID from the application.
- `RETURNING id` returns the generated ID.

**Why `VARCHAR[]` instead of `JSONB`?**
Because `Plan` is serialized as an **array of JSON strings** — each string is a `PlanStep` in JSON.
`VARCHAR[]` is simpler for Doobie: `Meta[Plan]` is already implemented via `unliftedStringArrayType`.
`JSONB` would require additional configuration.

**Why `DATE` instead of `TIMESTAMP`?** Because a periodic task is tied to a **day**, not a point in time.
`DATE` is more compact and more accurately reflects the model. `LocalDate` in Scala maps to `DATE` in PostgreSQL.

## `PostgreSQLPeriodicTaskService` Implementation

### `create`

```dotty
def create(newItem: CreatePeriodicTask): F[PeriodicTaskId] =
  sql"""INSERT INTO periodic_tasks (user_id, periodic_type, date, plan, completed)
        VALUES (${newItem.userId}, ${newItem.periodicType}::PeriodicTypeEnum, ${newItem.date}, ${newItem.plan}, false)
        RETURNING id"""
    .query[PeriodicTaskId]
    .unique
    .transact(xa)
```

**Breakdown:**

- **`INSERT`** — inserts an instance.
- **`${newItem.periodicType}::PeriodicTypeEnum`** — cast to enum.
- **`${newItem.plan}`** — Doobie automatically serializes `Plan` to `VARCHAR[]` via `Meta[Plan]`.
- **`RETURNING id`** — returns the generated UUID.

### `get`

```dotty
def get(id: PeriodicTaskId, userId: UserId): F[Option[PeriodicTask]] =
  sql"""SELECT id, user_id, periodic_type, date, plan, completed FROM periodic_tasks WHERE id = $id AND user_id = $userId"""
    .query[PeriodicTask]
    .option
    .transact(xa)
```

Returns `Option[PeriodicTask]`. Doobie deserializes `VARCHAR[]` to `Plan` via `Meta[Plan]`.
The query filters by both `id` and `user_id` — so the service itself guarantees that a user
cannot get another user's task.

### `getByUser`

```dotty
def getByUser(userId:UserId): F[Vector[PeriodicTask]] =
  sql"""SELECT id, user_id, periodic_type, date, plan, completed FROM periodic_tasks WHERE user_id = $userId"""
    .query[PeriodicTask]
    .to[Vector]
    .transact(xa)
```

Returns **all** user instances. Filtering by `completed` and **checking for existence** is performed in `PeriodicTaskLifecycleService`.

**Why not filter in SQL?**

- **`getTasks`** — filters `completed == false` after creating missing tasks.
- **`createTask`** — checks if there is already a task for this date: `tasks.exists(task => task.periodicType == periodicType && task.date == date)`. This check does not depend on `completed`.

If SQL filtered by `completed == false`, this `exists` check would not see completed tasks — and would create duplicates. Therefore, filtering is at the service level.

### `update`

```dotty
def update(item: PeriodicTask): F[Boolean] =
  sql"""UPDATE periodic_tasks
       SET user_id = ${item.userId}, periodic_type = ${item.periodicType}::PeriodicTypeEnum, date = ${item.date}, plan = ${item.plan}, completed = ${item.completed}
       WHERE id = ${item.id}"""
    .update
    .run
    .transact(xa)
    .map(_ > 0)
```

Updates all fields of the instance. `.map(_ > 0)` — `true` if the row was updated.

### `delete`

```dotty
def delete(id: PeriodicTaskId): F[Boolean] =
  sql"""DELETE FROM periodic_tasks WHERE id = $id"""
    .update.run.transact(xa).map(_ > 0)
```

Deletes the instance. `.map(_ > 0)` — `true` if the row was deleted.

## Date Generation: `PeriodicDates`

```dotty
final case class PeriodicDates(
    daily: LocalDate,
    weekly: LocalDate,
    monthly: LocalDate,
    quarterly: LocalDate,
    yearly: LocalDate
)

object PeriodicDates:
  def apply(now: LocalDate): PeriodicDates =
    val month = now.getMonthValue
    val year  = now.getYear

    val startOfTheWeek    = now.minusDays(now.getDayOfWeek.getValue - 1)
    val startOfTheMonth   = now.withDayOfMonth(1)
    val quarterStartMonth = ((month - 1) / 3) * 3 + 1
    val startOfTheQuarter = LocalDate.of(year, quarterStartMonth, 1)
    val startOfTheYear    = now.withDayOfYear(1)

    PeriodicDates(
      daily = now,
      weekly = startOfTheWeek,
      monthly = startOfTheMonth,
      quarterly = startOfTheQuarter,
      yearly = startOfTheYear
    )
```

**Purpose:** for each periodicity, computes the **date to which the task belongs**.
This is the key to **deduplication**: tasks are created **at the start of the period**, not the current date.

**Breakdown:**

- **`daily = now`** — a daily task is created for **today**.
- **`weekly = startOfTheWeek`** — a weekly task is for **Monday of the current week**.
- **`monthly = startOfTheMonth`** — a monthly task is for the **first day of the current month**.
- **`quarterly = startOfTheQuarter`** — a quarterly task is for the **first day of the current quarter**.
- **`yearly = startOfTheYear`** — an annual task is for **January 1st of the current year**.

**Quarter formula:**

```dotty
val quarterStartMonth = ((month - 1) / 3) * 3 + 1
```

- **`(month - 1) / 3`** — integer division: `0` for Q1, `1` for Q2, `2` for Q3, `3` for Q4.
- **`* 3`** — converts to `0`, `3`, `6`, `9`.
- **`+ 1`** — shifts by 1: `1`, `4`, `7`, `10`.

**Example:** `month = 5` (May) → `(5 - 1) / 3 = 1` → `1 * 3 = 3` → `3 + 1 = 4` → April (Q2).

## DTO `PeriodicTaskCard`

```dotty
final case class PeriodicTaskCard(
    id: PeriodicTaskId,
    name: String,
    periodicType: PeriodicType,
    date: LocalDate,
    plan: List[PlanRowCard],
    progress: Double,
    completedCount: Int,
    count: Int
)
```

**Fields breakdown:**

| Field              | Purpose                                         |
| ------------------ | ----------------------------------------------- |
| **`id`**           | ID for link `/periodic_task/{id}`               |
| **`name`**         | Generated name (`15.03.2026 - Daily task`)      |
| **`periodicType`** | Period type                                     |
| **`date`**         | Task date                                       |
| **`plan`**         | Plan as `List[PlanRowCard]`                     |
| **`progress`**     | Progress in percent (0.00–100.00)               |
| **`completedCount`** | Number of completed steps                     |
| **`count`**        | Total number of steps                           |

### Factory Method `apply`

```dotty
object PeriodicTaskCard:
  private val formatter = DateTimeFormatter.ofPattern("dd.MM.yyyy")

  def apply(task: PeriodicTask): PeriodicTaskCard =
    PeriodicTaskCard(
      id = task.id,
      name = s"${task.date.format(formatter)} - ${task.periodicType.show}",
      periodicType = task.periodicType,
      date = task.date,
      plan = task.plan.steps.map(row =>
        PlanRowCard(
          number = row.number.value,
          step = row.step.value,
          completed = row.completed
        )
      ),
      progress = math.round(task.plan.progress * 10000.0) / 100.0,
      completedCount = task.plan.steps.count(_.completed),
      count = task.plan.steps.length
    )
```

**Step-by-step breakdown:**

1. **`name`** — `s"${task.date.format(formatter)} - ${task.periodicType.show}"`:
    - Date is formatted as `dd.MM.yyyy`.
    - Type is displayed via `Show` ("Daily task").
    - Result: `"15.03.2026 - Daily task"`.

2. **`plan`** — converting `PlanStep` to `PlanRowCard`:
    - `row.number.value` — number as a string (`"1.2.3"`).
    - `row.step.value` — step text.
    - `row.completed` — flag.

3. **`progress`** — `math.round(task.plan.progress * 10000.0) / 100.0`:
    - `plan.progress` — a fraction from 0.0 to 1.0.
    - `* 10000.0` — converts to a cents-level integer.
    - `math.round` — rounds.
    - `/ 100.0` — converts to percentage with two decimal places.

   **Example:** `progress = 0.3333` → `3333.0` → `3333` → `33.33`.

4. **`completedCount`** — number of completed steps.

5. **`count`** — total number of steps.

**Why `math.round(... * 10000.0) / 100.0` instead of just `* 100`?**
Because `* 100` gives `33.33333333333333` — ugly in the UI. Rounding to cents gives `33.33` — readable.
Same formula as in `calculateProgress`, but for `Plan.progress` (which returns `Double`, not counted via `FiniteDuration`).

## `PeriodicTaskLifecycleService`

This is the **key service** — it decides which tasks to create and provides operations on instances.

```dotty
final case class PeriodicTaskLifecycleService[F[_]: MonadThrow](
    periodicTaskService: PeriodicTaskService[F],
    settingsService: SettingsService[F]
):
```

**Dependency breakdown:**

- **`periodicTaskService`** — working with instances in the DB.
- **`settingsService`** — loading templates (`getSteps`).

### `getTasks`

```dotty
def getTasks(userId: UserId): F[Vector[PeriodicTaskCard]] =
  val dates = PeriodicDates(LocalDate.now())

  for
    tasks            <- periodicTaskService.getByUser(userId)
    periodicSettings <- settingsService.getSteps(userId)
    settings = periodicSettings.groupBy(_.periodicType)
    maybeDailyTask <- createTask(tasks, settings, PeriodicType.Daily, dates.daily, userId)
    maybeWeeklyTask <- createTask(tasks, settings, PeriodicType.Weekly, dates.weekly, userId)
    maybeMonthlyTask <- createTask(tasks, settings, PeriodicType.Monthly, dates.monthly, userId)
    maybeQuarterlyTask <- createTask(tasks, settings, PeriodicType.Quarterly, dates.quarterly, userId)
    maybeYearlyTask <- createTask(tasks, settings, PeriodicType.Yearly, dates.yearly, userId)
  yield (
    tasks ++ maybeDailyTask ++ maybeWeeklyTask ++ maybeMonthlyTask ++
      maybeQuarterlyTask ++ maybeYearlyTask
  )
    .withFilter(_.completed == false)
    .map(PeriodicTaskCard.apply)
    .sortBy(t => (t.periodicType.ordinal, t.date))
end getTasks
```

**Step-by-step breakdown:**

**1. Computing dates:**

```dotty
val dates = PeriodicDates(LocalDate.now())
```

For each periodicity — the date to which the task belongs. This is the **key to deduplication**.

**2. Loading existing tasks and templates:**

```dotty
tasks            <- periodicTaskService.getByUser(userId)
periodicSettings <- settingsService.getSteps(userId)
settings = periodicSettings.groupBy(_.periodicType)
```

- **`tasks`** — all user instances (including completed ones).
- **`periodicSettings`** — all user templates.
- **`settings`** — templates grouped by type. This speeds up access: `settings(Daily)` — all daily templates.

**3. Creating missing tasks:**

```dotty
maybeDailyTask <- createTask(tasks, settings, PeriodicType.Daily, dates.daily, userId)
...
```

`createTask` is called for each type. It returns:

- **`Some(task)`** — if a task was created.
- **`None`** — if there was nothing to create (no templates or a task for this date already exists).

**4. Combining:**

```dotty
tasks ++ maybeDailyTask ++ maybeWeeklyTask ++ maybeMonthlyTask ++
  maybeQuarterlyTask ++++ maybeYearlyTask
```

Only just-created tasks are added to existing ones. `++` for `Option` works as "add if `Some`".

**5. Filtering completed:**

```dotty
.withFilter(_.completed == false)
```

The user sees only **open** tasks.

**6. Converting to cards:**

```dotty
.map(PeriodicTaskCard.apply)
```

Each `PeriodicTask` is transformed into a `PeriodicTaskCard` — a UI model.

**7. Sorting:**

```dotty
.sortBy(t => (t.periodicType.ordinal, t.date))
```

- **First by period type** (`Daily` → `Weekly` → ...).
- **For equal types — by date** (older on top).

The user sees daily tasks first — they are the most important.

### `createTask`

```dotty
private def createTask(
    tasks: Vector[PeriodicTask],
    settings: Map[PeriodicType, Vector[PeriodicStep]],
    periodicType: PeriodicType,
    date: LocalDate,
    userId: UserId
): F[Option[PeriodicTask]] =
  val steps: List[PlanStep] =
    settings
      .getOrElse(periodicType, Vector.empty[PeriodicStep])
      .map: periodicStep =>
        PlanStep(
          number = periodicStep.number,
          step = periodicStep.name,
          completed = false
        )
      .toList
      .sortBy(_.number)

  if steps.isEmpty ||
    tasks.exists(task =>
      task.periodicType == periodicType &&
        task.date == date
    )
  then
    none.pure[F]
  else
    val createItem = CreatePeriodicTask(
      userId = userId,
      periodicType = periodicType,
      date = date,
      plan = Plan(steps),
      completed = false
    )
    periodicTaskService.create(createItem).map: id =>
      PeriodicTask(
        id = id,
        userId = createItem.userId,
        periodicType = createItem.periodicType,
        date = createItem.date,
        plan = createItem.plan,
        completed = createItem.completed
      ).some
  end if
end createTask
```

**Step-by-step breakdown:**

**1. Building a plan from templates:**

```dotty
val steps: List[PlanStep] =
  settings
    .getOrElse(periodicType, Vector.empty[PeriodicStep])
    .map: periodicStep =>
      PlanStep(
        number = periodicStep.number,
        step = periodicStep.name,
        completed = false
      )
    .toList
    .sortBy(_.number)
```

- **`settings.getOrElse(periodicType, Vector.empty)`** — templates for this type. If none — an empty vector.
- **`.map`** — each `PeriodicStep` is transformed into `PlanStep`:
    - `number = periodicStep.number` — step number.
    - `step = periodicStep.name` — name.
    - `completed = false` — a new step is always incomplete.
- **`.sortBy(_.number)`** — sorting by number. This is **important**: steps in the plan must go in the correct order (1, 2, 3, ...) not in DB insertion order.

**2. Checking "nothing to create":**

```dotty
if steps.isEmpty ||
  tasks.exists(task =>
    task.periodicType == periodicType &&
      task.date == date
  )
then
  none.pure[F]
```

Two conditions for skipping creation:

- **`steps.isEmpty`** — no templates of this type. Nothing to create.
- **`tasks.exists(...)`** — a task for this date **already exists**. This protects against duplicates.

**3. Creating:**

```dotty
val createItem = CreatePeriodicTask(
  userId = userId,
  periodicType = periodicType,
  date = date,
  plan = Plan(steps),
  completed = false
)
periodicTaskService.create(createItem).map: id =>
  PeriodicTask(
    id = id,
    userId = createItem.userId,
    ...
  ).some
```

- **`createItem`** — DTO for creation.
- **`periodicTaskService.create(createItem)`** — creates in DB, returns ID.
- **`.map: id => PeriodicTask(...)`** — assembles the full model from DTO + ID.
- **`.some`** — wraps in `Option` so `getTasks` can combine with existing tasks.

### `get`

```dotty
def get(id: PeriodicTaskId, userId: UserId): F[Option[PeriodicTaskCard]] =
  periodicTaskService.get(id, userId).map(_.map(PeriodicTaskCard.apply))
```

**Breakdown:**

- **`periodicTaskService.get(id, userId)`** — loads the task with owner verification.
- **`.map(_.map(PeriodicTaskCard.apply))`** — if the task exists, converts to a card.

**Why directly `periodicTaskService.get(id, userId)`?** In `cb36973` owner verification moved to the low-level service: the method takes `userId` and filters by it. `LifecycleService` simply passes `userId`. The previous private helper `getByUser(id, userId)` was removed.

### `completeStep`

```dotty
def completeStep(
    id: PeriodicTaskId,
    userId: UserId,
    number: String
): F[Boolean] =
  periodicTaskService.get(id, userId).flatMap:
    case Some(task) =>
      val updatedSteps =
        task.plan.steps.map: step =>
          if step.number.value == number then step.copy(completed = true)
          else step

      periodicTaskService.update(task.copy(plan = Plan(updatedSteps)))
    case None => MonadThrow[F].raiseError(
        new IllegalArgumentException(s"Periodic task with id '$id' not found")
      )
```

**Breakdown:**

1. **`periodicTaskService.get(id, userId)`** — loads the task with owner verification.
2. **`case Some(task)`** — if the task is found:
    - **`.map`** over steps: if the number matches — mark as completed.
    - **`periodicTaskService.update`** — save the updated plan.
3. **`case None`** — if the task is not found or belongs to someone else — `IllegalArgumentException`.

**Why an error instead of `false`?** Because "task not found" is an **error**, not a "operation failed".
The user expects the task to exist (they clicked on it). If it doesn't — something went wrong. `false` would hide the problem.

**Why compare by `number.value` instead of `number`?** `StepNumber` is an opaque type.
Comparing via `.value` is simpler and does not require a `given` instance of `Eq[StepNumber]`.

### `complete`

```dotty
def complete(id: PeriodicTaskId, userId: UserId): F[Boolean] =
  periodicTaskService.get(id, userId).flatMap:
    case Some(task) => periodicTaskService.update(task.copy(completed = true))
    case None       => false.pure[F]
```

**Breakdown:**

- **`Some(task)`** — mark the task as completed.
- **`None`** — return `false` (task not found or does not belong to the user).

**Why `false` instead of an error?** Because completing a task is an **idempotent** operation.
If the task is already completed or deleted — nothing terrible, just `false`. This is not an error, but normal behavior.

### `updatePlan`

```dotty
def updatePlan(id: PeriodicTaskId, userId: UserId, plan: Plan): F[Boolean] =
  periodicTaskService.get(id, userId).flatMap:
    case Some(task) => periodicTaskService.update(task.copy(plan = plan))
    case None       => false.pure[F]
```

**Breakdown:** updates **only the plan**, leaving other fields untouched. Used when editing a periodic task.

**Why `updatePlan` instead of `update(task)`?**
Because the user can edit **only the plan** — type, date, owner do not change.
A separate method makes the intent **explicit** and prevents accidental changes to other fields.

### `delete`

```dotty
def delete(id: PeriodicTaskId, userId: UserId): F[Boolean] =
  periodicTaskService.get(id, userId).flatMap:
    case Some(_) => periodicTaskService.delete(id)
    case None    => false.pure[F]
```

**Breakdown:** deletes the task only if it belongs to the user.

**Why is owner verification not in `LifecycleService`?** In `cb36973` it moved to the low-level service — `periodicTaskService.get(id, userId)` already filters by `userId`. `LifecycleService` does not keep its own private helper and simply calls `periodicTaskService.get(id, userId)`.

## UI: "In Progress" Tab

The "In Progress" tab is rendered by the `Views.welcomeInProgress` method, and the periodic tasks block
is output via `periodicTasks.map(_.render)` — each `TablePeriodicTaskCard` card renders itself. The resulting HTML looks like this:

```dotty
def welcomeInProgress(
    tasks: Vector[TableInProgressTaskCard],
    periodicTasks: Vector[TablePeriodicTaskCard]
): Modifier =
  frag(
    div(cls := "tab-actions")(
      button(
        cls            := "add-btn",
        attr("hx-get") := "/task/create/in-progress",
        Htmx.modalTarget,
        Htmx.modalSwap,
        attr("onclick") := "openCreateTaskModal()"
      )("+ Create task")
    ),
    if periodicTasks.nonEmpty then
      div(cls := "periodic-tasks-section")(
        h3(cls := "periodic-tasks-title")("🔄 Periodic tasks"),
        div(cls := "tasks-grid")(
          periodicTasks.map(_.render)*
        )
      )
    else frag(),
    div(cls := "tasks-grid")(
      tasks.map(_.render)*
    )
  )
  
final case class TablePeriodicTaskCard(
    id: PeriodicTaskId,
    name: String,
    progress: Double
):
  def render: Tag =
    div(
      attr("id") := id.toString,
      cls        := "task-card periodic-task-card",

      div(cls := "task-title")(name),
```

The full block (with title and grid) is output only if `periodicTasks` is not empty —
`if periodicTasks.nonEmpty then ... else frag()` in scalatags.

**Breakdown:**

- **`🔄 Periodic tasks`** — title with a cycle icon.
- **`onclick="openPeriodicTask('{task.id}')"`** — click opens `/periodic_task/{id}`.
- **`task.name`** — the generated name (`15.03.2026 - Daily task`).
- **Progress bar** — plan completion percentage.

**Why only name and progress, no dates?** Because **the date is already in the name**. Repeating it in metadata is redundant.
Periodic tasks do not have start/end dates — there is only one date. `name` contains all the needed information.

## Routes

Periodic task paths are declared locally within `PeriodicTaskHandlers` (see below). This keeps
the entire "route + handler" bundle for periodic tasks in one class.

```dotty
private val path = Path.root / "periodic_task" / uuidParam

private val openPeriodicTask = Route(
  Request.get(path).extractHeader[`Cookie`],
  Response.ok(Entity.html)
)

private val completePlanStepPeriodicTask = Route(
  Request.put(path / "completeStep" / Param.string)
    .extractHeader[Authorization],
  Response.ok(Entity.html).orNotFound
)

private val completeFormPeriodicTask = Route(
  Request.put(path / "complete").extractHeader[Authorization],
  Response.ok(Entity.html).orNotFound
)

private val editFormPeriodicTask = Route(
  Request.get(path / "edit").extractHeader[Authorization],
  Response.ok(Entity.html).orNotFound
)

private val editPeriodicTask = Route(
  Request.put(path).withEntity(Entity.formOf[EditPeriodicTaskRequest]),
  Response.ok(Entity.html).orNotFound
)

private val deletePeriodicTask = Route(
  Request.delete(path).extractHeader[Authorization],
  Response.ok(Entity.html).orNotFound
)
```

Note the **`uuidParam`** instead of `Param.string`: this is a `Param[UUID]`,
which decodes the path directly to `UUID` (see `UrlFormParser.uuidParam`), not to a string.
This eliminates the need to parse UUIDs manually in each handler.

**Routes breakdown:**

| Route                                            | Method  | Purpose                |
| ------------------------------------------------ | ------- | ---------------------- |
| **`/periodic_task/{id}`**                        | GET     | Task page              |
| **`/periodic_task/{id}/completeStep/{number}`**  | PUT     | Complete a step        |
| **`/periodic_task/{id}/complete`**               | PUT     | Complete the task      |
| **`/periodic_task/{id}/edit`**                   | GET     | Edit form              |
| **`/periodic_task/{id}`**                        | PUT     | Save changes           |
| **`/periodic_task/{id}`**                        | DELETE  | Delete the task        |

## `EditPeriodicTaskRequest`

```dotty
final case class EditPeriodicTaskRequest(
    token: String,
    plan: List[PlanStepRequest]
)

object EditPeriodicTaskRequest:
  given FormCodec[EditPeriodicTaskRequest] =
    new FormCodec[EditPeriodicTaskRequest](
      decode = { (urlForm: UrlForm) =>
        urlForm.getValue("token")
          .map: token =>
            EditPeriodicTaskRequest(
              token = token,
              plan = EditTaskRequest.decodePlanSteps(urlForm)
            )
          .leftMap(e => Chain(e))
      },
      encode = { (request: EditPeriodicTaskRequest) =>
        val baseFields = Map(
          "token" -> Chain(request.token)
        )

        UrlForm(baseFields ++ EditTaskRequest.encodePlanSteps(request.plan))
      }
    )
end EditPeriodicTaskRequest
```

**Breakdown:**

- **`token: String`** — JWT token.
- **`plan: List[PlanStepRequest]`** — plan as a list of steps.

**Why only `token` and `plan`?** Because **only the plan can be edited**.
Type, date, owner — do not change. This corresponds to the requirement: "Only plan steps can be edited".

**Reusing `EditTaskRequest.decodePlanSteps`:**
the plan decoding logic from the form (`plan[0].number`, `plan[0].step`, `plan[0].completed`) is already implemented in `EditTaskRequest`.
`EditPeriodicTaskRequest` **reuses** it — eliminating duplication.

## Handlers

For periodic tasks, **all handlers are gathered in one class** — `PeriodicTaskHandlers`, which:

- declares all periodic task routes (`private val openPeriodicTask`, `completeFormPeriodicTask`, etc.);
- contains one `val` public handler per route (`openHandler`, `editFormHandler`, ...);
- is registered in `Main` as a single dependency.

```dotty
final case class PeriodicTaskHandlers(
    middleware: JwtAuthMiddleware[IO, UserInfo],
    service: PeriodicTaskLifecycleService[IO]
)(using Logger[IO]) extends AuthorizationHandler(middleware):
  private val path = Path.root / "periodic_task" / uuidParam

  private val openPeriodicTask = Route(
    Request.get(path).extractHeader[`Cookie`],
    Response.ok(Entity.html)
  )
  private val completePlanStepPeriodicTask = Route(
    Request.put(path / "completeStep" / Param.string)
      .extractHeader[Authorization],
    Response.ok(Entity.html).orNotFound
  )
  private val completeFormPeriodicTask = Route(
    Request.put(path / "complete").extractHeader[Authorization],
    Response.ok(Entity.html).orNotFound
  )
  private val editFormPeriodicTask = Route(
    Request.get(path / "edit").extractHeader[Authorization],
    Response.ok(Entity.html).orNotFound
  )
  private val editPeriodicTask = Route(
    Request.put(path).withEntity(Entity.formOf[EditPeriodicTaskRequest]),
    Response.ok(Entity.html).orNotFound
  )
  private val deletePeriodicTask = Route(
    Request.delete(path).extractHeader[Authorization],
    Response.ok(Entity.html).orNotFound
  )

  val openHandler: Handler =
    openPeriodicTask.handleIO: (uuid: UUID, cookie: Cookie) =>
      withUserFromCookieOpt(cookie)(
        f = (user, jwtToken) =>
          service.get(PeriodicTaskId(uuid), user.id).map {
            _.map { periodicTask =>
              val html = Views.periodicTask(task = periodicTask, errorMessage = none)
              Views.base(Title, html)
            }
          },
        fallbackPage = NotFoundView
      )

  val compileStepHandler: Handler =
    completePlanStepPeriodicTask.handleIO:
      (uuid: UUID, number: String, authorization: Authorization) =>
        withUserFromHeaderOpt(authorization) { (user, jwtToken) =>
          val periodicTaskId = PeriodicTaskId(uuid)
          for
            _         <- service.completeStep(periodicTaskId, user.id, number)
            maybeTask <- service.get(periodicTaskId, user.id)
          yield maybeTask.map(task => Views.periodicTask(task, none).render)
        }

  val completeHandler: Handler =
    completeFormPeriodicTask.handleIO:
      (uuid: UUID, authorization: Authorization) =>
        withUserFromHeader(authorization): (user, token) =>
          service.complete(PeriodicTaskId(uuid), user.id).as(HomeView)

  val editFormHandler: Handler =
    editFormPeriodicTask.handleIO: (uuid: UUID, authorization: Authorization) =>
      withUserFromHeaderOpt(authorization): (user, jwtToken) =>
        val periodicTaskId = PeriodicTaskId(uuid)
        service.get(periodicTaskId, user.id).map {
          _.map { task =>
            Views.editPeriodicTask(
              periodicTaskId = task.id,
              name = task.name,
              request = EditPeriodicTaskRequest(
                token = jwtToken.show,
                plan = task.plan.map(PlanStepRequest.apply)
              ),
              token = jwtToken,
              errorMessage = none
            ).render
          }
        }

  val editHandler: Handler =
    editPeriodicTask.handleIO: (uuid: UUID, request: EditPeriodicTaskRequest) =>
      val run: ((UserInfo, SignedJwt)) => IO[Option[String]] =
        (user, jwtToken) =>
          request.plan.traverse(PlanStep.parse)
            .map { steps =>
              val periodicTaskId = PeriodicTaskId(uuid)
              val run: IO[Option[String]] =
                for
                  _ <- service.updatePlan(periodicTaskId, user.id, Plan(steps.sortBy(_.number)))
                  maybeTask <- service.get(periodicTaskId, user.id)
                yield maybeTask.map(task => Views.periodicTask(task, none).render)
              run
                .recover:
                  case ex: IllegalArgumentException =>
                    Views.editPeriodicTask(
                      periodicTaskId = periodicTaskId,
                      name = "Error editing task",
                      request = request,
                      token = jwtToken,
                      errorMessage = ex.getMessage.some
                    ).render.some
            }.valueOr(errors =>
              Logger[IO].error(errors.toChain.toVector.mkString("; ")).as(none)
            )
      // ToDo: https://github.com/creativescala/krop/pull/57
      val authorization: Authorization =
        Authorization(Token(AuthScheme.Bearer, request.token))
      withUserFromHeaderOpt(authorization)(run)

  val deleteHandler: Handler =
    deletePeriodicTask.handleIO: (uuid: UUID, authorization: Authorization) =>
      withUserFromHeader(authorization): (user, token) =>
        service.delete(PeriodicTaskId(uuid), user.id).as(HomeView)
end PeriodicTaskHandlers
```

### Open handler `openHandler`

`withUserFromCookieOpt(cookie)(f, fallbackPage)` extracts the token from cookie `token`, validates it,
calls `f`, passing `(user, jwtToken)`. If the token is missing/invalid or the task is not found
(the lambda returned `None`) — `fallbackPage` (`NotFoundView`) is displayed.
Token extraction from the cookie is encapsulated in `AuthorizationHandler`.

### Step completion handler `compileStepHandler`

`withUserFromHeaderOpt(authorization)(...)` validates the token from the header, `service.completeStep` marks
the step as completed, then the updated page is returned.

### Task completion handler `completeHandler`

`service.complete(...)` marks the task as completed. Returns `HomeView` — the main page,
because a completed task leaves the "In Progress" list.

**Why `HomeView` instead of the task page?** Because after completion the task **leaves** the open list.
It is more logical to return the user to the list, rather than show a completed task.

### Edit form handler `editFormHandler`

Similar to `openHandler`, but renders the **edit form** (`Views.editPeriodicTask`)
instead of the view page.

### Save edits handler `editHandler`

`request.plan.traverse(PlanStep.parse)` validates each plan step. If all steps are valid —
`service.updatePlan` updates the plan and the task page is returned. On `IllegalArgumentException`
(e.g., task not found) — the edit form is returned with an error message.

**Why `Plan(steps.sortBy(_.number))`?** Because `traverse` returns steps in order from the form
(which may be arbitrary). `sortBy(_.number)` guarantees the plan will be in the correct order.

### Delete handler `deleteHandler`

`service.delete(...)` deletes the task only if it belongs to the user. Returns `HomeView`.

**Why `HomeView`?** Because a deleted task is gone — showing its page makes no sense.
Returning to the list is the logical behavior.

## Complete Workflow

### Opening the task list

1. **User opens the main page** → `getTasks` is called in the handler.
2. **`getTasks`:**
    - Loads existing tasks.
    - Loads templates.
    - Creates missing tasks for each type on the corresponding dates.
    - Returns cards of **open** tasks, sorted by `(periodicType, date)`.
3. **User sees the "🔄 Periodic tasks" block** with cards (name + progress only).

### Completing a step

1. **User opens a task** → `/periodic_task/{id}`.
2. **Sees the plan** with steps.
3. **Clicks "✅ Complete"** on a step → htmx sends a PUT to `/periodic_task/{id}/completeStep/{number}`.
4. **`compileStepHandler`:**
    - Finds the step by number.
    - Marks `completed = true`.
    - Saves.
    - Returns the updated page.
5. **htmx replaces `#app`** — the step is marked completed, the progress bar is updated.

### Completing the task

1. **User clicks "✅ Complete task"** → PUT to `/periodic_task/{id}/complete`.
2. **`completeHandler`:**
    - Marks `completed = true`.
    - Returns `HomeView`.
3. **htmx replaces `#app`** — the task disappears from "In Progress" (filter `completed == false`).

### Editing the plan

1. **User clicks "✏️ Edit"** → GET to `/periodic_task/{id}/edit`.
2. **`editFormHandler`** renders the edit form.
3. **User changes steps** → PUT to `/periodic_task/{id}` with body `token` and `plan[...]`.
4. **`editHandler`:**
    - Validates plan steps (uuid is already decoded to `UUID` at the route level).
    - Updates the plan.
    - Returns the task page.
5. **htmx replaces `#app`** — the user sees the updated plan.

### Deleting a task

1. **User clicks "🗑️ Delete"** → confirm → DELETE to `/periodic_task/{id}`.
2. **`deleteHandler`:**
    - Deletes the task.
    - Returns `HomeView`.
3. **htmx replaces `#app`** — the task disappears from the list.

## Summary

Periodic tasks turn routine into an **automatic process**: the user configures templates once,
and the system creates new instances every day.
This frees up mental space for creativity and helps not to miss important recurring actions.
