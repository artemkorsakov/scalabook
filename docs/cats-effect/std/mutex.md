# Mutex — Взаимное исключение для волокон

`Mutex` (Mutual Exclusion) — это примитив синхронизации, который гарантирует, 
что доступ к критическому участку кода одновременно может получить только **одно волокно**. 
Остальные волокна выстраиваются в очередь и ждут, пока текущий владелец не освободит блокировку.

По сути, `Mutex` — это `Semaphore` **с одним разрешением** (Semaphore(1)), но с более удобным и безопасным API.

### Базовый интерфейс

```dotty
trait Mutex[F[_]]:
  /** Захватывает блокировку и возвращает Resource, который автоматически
    * освободит её при завершении.
    */
  def lock: Resource[F, Unit]
```

**Ключевая особенность:** `lock` возвращает не просто `F[Unit]`, а `Resource[F, Unit]`. Это означает, что:

1. **Захват блокировки** происходит при создании ресурса (внутри `Resource.make`).
2. **Освобождение блокировки** происходит автоматически при завершении `use` блока — не нужно вызывать `unlock` вручную.
3. Даже если произойдёт ошибка или отмена, блокировка **гарантированно освободится**.

### Простейший пример

```dotty
import cats.effect.IO
import cats.effect.std.Mutex

val criticalSection: IO[Int] = IO.println("Работаю...") *> IO.pure(42)

val program: IO[Unit] =
  for
    mutex  <- Mutex[IO]
    // захват → работа → освобождение
    result <- mutex.lock.surround(criticalSection) 
    _      <- IO.println(s"Результат: $result")
  yield ()
```

## Mutex vs Semaphore(1)

| Характеристика                    | `Semaphore(1)`                            | `Mutex`                                         |
|:----------------------------------|:------------------------------------------|:------------------------------------------------|
| **Количество разрешений**         | 1 (но можно и больше)                     | 1                                               |
| **Возвращаемый тип для захвата**  | `F[Unit]` (через `acquire`)               | `Resource[F, Unit]`                             |
| **Освобождение**                  | Ручное (`release`)                        | Автоматическое через `Resource`                 |
| **Реентерабельность**             | Нет (блокировка мертва)                   | Нет (блокировка мертва)                         |
| **Когда использовать**            | Когда нужно несколько разрешений, счётчик | Когда нужен простой "одно волокно в одно время" |

**Вывод:** Для простого взаимного исключения `Mutex` предпочтительнее из-за встроенной безопасности через `Resource`.

## Подробный разбор: lock как Resource

Метод `lock` возвращает `Resource[F, Unit]`. Это позволяет использовать его двумя основными способами:

### 1. `lock.surround(fa)` — самый короткий способ

```dotty
mutex.lock.surround {
  // критическая секция
  IO.println("Только одно волокно здесь!")
}
```

`surround` — это синтаксический сахар для `lock.use(_ => fa)`. Он захватывает блокировку, выполняет `fa` и автоматически освобождает.

### 2. `lock.use(_ => fa)` — явный способ

```dotty
mutex.lock.use { _ =>
  // критическая секция
  doSensitiveWork()
}
```

### 3. `Resource` в for-comprehension — для композиции с другими ресурсами

```dotty
val guardedResource: Resource[IO, Connection] =
  for
    mutex <- Resource.eval(Mutex[IO])
    conn  <- Resource.make(createConnection())(_.close)
    _     <- mutex.lock // блокировка будет держаться всё время жизни ресурса
  yield (mutex, conn)
```

## Пример: Безопасное обновление состояния

В этом примере `Mutex` защищает `Ref` от состояния гонки при обновлении, которое требует нескольких шагов.

```dotty
import cats.effect.{IO, Ref}
import cats.effect.std.Mutex

trait State

class Service(mutex: Mutex[IO], state: Ref[IO, State]):
  def modify(f: State => IO[State]): IO[Unit] =
    mutex.lock.surround {
      for
        current <- state.get  // 1. Читаем текущее состояние
        next    <- f(current) // 2. Вычисляем новое (возможно, с IO-эффектом!)
        _ <- state.set(next)  // 3. Записываем новое
      yield ()
    }
```

**Почему здесь нужен `Mutex`, а не просто `Ref.update`?**

| Метод            | Что делает                                                 | Проблема                                                                                           |
|:-----------------|:-----------------------------------------------------------|:---------------------------------------------------------------------------------------------------|
| `Ref.update`     | Читает → применяет функцию → CAS-цикл                      | Функция должна быть **чистой** (без IO) и быстрой.                                                 |
| `Ref.modify`     | Тоже CAS-цикл                                              | Функция тоже должна быть чистой. CAS может повторяться, вызывая `f` многократно.                   |
| **Mutex + Ref**  | Блокировка → чтение → IO-функция → запись → разблокировка  | Функция `f` может содержать **IO-эффекты** (запрос к БД, вызов API) и выполнится только один раз.  |

**Ключевой вывод:** Если ваше обновление требует **эффектных** операций (IO), `Mutex` — единственный безопасный способ.

## Блокировка не поддерживает повторный вход

**С возможностью повторного входа** (reentrant) блокировка позволяет одному и тому же волокну захватывать 
блокировку несколько раз, не блокируясь. `Mutex` **не поддерживает возможность повторного входа**.

```dotty
// ❌ ЗАВИСАНИЕ (deadlock)
mutex.lock.surround {
  mutex.lock.surround {
    IO.println("Это никогда не выполнится")
  }
}
```

**Что происходит:**

1. Волокно захватывает блокировку (первый `lock`).
2. Внутри критической секции оно пытается захватить **ту же самую** блокировку снова.
3. Поскольку блокировка уже занята этим же волокном, а `Mutex` не поддерживает повторный вход, 
   волокно **блокируется навсегда**, ожидая себя же.
4. Программа зависает (deadlock).

**Как избежать:** Проектируйте код так, чтобы не было вложенных вызовов `lock` из одного волокна. 
Если такая ситуация возможна, рассмотрите использование `Ref` для флага "уже внутри блокировки" или пересмотрите архитектуру.

## Реальный пример 1: Атомарное обновление с внешним вызовом

Представьте себе банковский счёт: списание средств должно проверить баланс, 
возможно, сходить в антифрод-сервис, и только потом изменить состояние.

```dotty
import cats.effect.IO
import cats.effect.std.Mutex

class BankAccount(
    balanceRef: Ref[IO, Long],
    antifraud: AntifraudService,
    mutex: Mutex[IO]
):

  def withdraw(amount: Long): IO[Boolean] =
    mutex.lock.surround {
      for
        current <- balanceRef.get
        // Это может быть сложная логика с IO-вызовами
        isSafe <- antifraud.checkWithdrawal(current, amount)
        result <- if current >= amount && isSafe then
          balanceRef.update(_ - amount).as(true)
        else
          IO.pure(false)
      yield result
    }
```

**Без `Mutex`** два волокна могли бы одновременно прочитать одинаковый `current`, 
оба проверить `>= amount`, оба пройти проверку, и в результате баланс стал бы отрицательным. 
`Mutex` исключает такую гонку.

## Реальный пример 2: Кеш с однократной загрузкой

```dotty
import cats.effect.{IO, Ref}
import cats.effect.std.Mutex

class Cache[K, V](mutex: Mutex[IO], storage: Ref[IO, Map[K, V]]):
  def getOrLoad(key: K, load: K => IO[V]): IO[V] =
    mutex.lock.surround {
      storage.get.flatMap: map =>
        map.get(key) match
          case Some(value) => IO.pure(value)
          case None        =>
            load(key).flatMap: value =>
              storage.update(_ + (key -> value)).as(value)
    }
```

**Почему здесь нужен `Mutex`?** Без него два волокна могли бы одновременно обнаружить отсутствие значения 
и начать загружать его дважды, что дорого и неправильно. 
`Mutex` гарантирует, что загрузка произойдёт только один раз, пока остальные ждут.

## Mutex и отмена волокон

`Mutex` корректно работает с отменой:

- **Ожидающее волокно** (в очереди на `lock`) может быть отменено. 
  Оно будет удалено из очереди, и блокировка перейдёт к следующему.
- **Волокно, владеющее блокировкой**, при отмене освободит блокировку автоматически, 
  но только внутри `Resource` — то есть после выполнения финализаторов.

```dotty
mutex.lock.surround {
  IO.never // бесконечная операция
}.start.flatMap { fiber =>
  IO.sleep(1.second) >> fiber.cancel
} // блокировка гарантированно освободится после отмены
```

## Mutex в сравнении с альтернативами

| Сценарий                                                    | Лучший выбор                 | Почему                                            |
|:------------------------------------------------------------|:-----------------------------|:--------------------------------------------------|
| Нужно защитить критическую секцию **с эффектами** (IO)      | **`Mutex`**                  | `Ref.update` не подходит из-за CAS-циклов.        |
| Нужно защитить **чистую** функцию, быстрое обновление       | `Ref.update` / `Ref.modify`  | Без блокировок, максимальная производительность.  |
| Нужно несколько разрешений (пул соединений)                 | `Semaphore(n)`               | `Mutex` только на одно.                           |
| Нужно координировать несколько волокон с ожиданием условий  | `Deferred`, `Queue`          | `Mutex` только для взаимного исключения.          |
| Нужно атомарно прочитать и изменить несколько `Ref`         | `Mutex` + композиция         | Без блокировки не получится.                      |

## Ошибки и лучшие практики

### ❌ Забыть использовать `surround` или `use`

```dotty
val lockResource = mutex.lock
// Ничего не захвачено и не освобождено!
lockResource
```

**Правильно:** всегда используйте `lock.use` или `lock.surround`.

### ❌ Захватывать блокировку вне `Resource` (через `allocated`)

```dotty
val (_, release) = mutex.lock.allocated.unsafeRunSync()
// ... много кода, где можно забыть release ...
release.unsafeRunSync()
```

Это антипаттерн. Используйте `Resource` для автоматического управления.

## Итог: Когда использовать Mutex?

✅ **Используйте `Mutex`, если:**

- Вам нужна **простая блокировка** "одно волокно в одно время".
- Критическая секция включает **операции с эффектом** (`IO`, обращения к БД, внешним API).
- Вам нужна гарантия освобождения блокировки даже при ошибке или отмене (через `Resource`).
- Вы не можете использовать `Ref.update`/`modify`, потому что функция обновления в этих методах **чистая**.

❌ **Не используйте `Mutex`, если:**

- Вам нужно несколько разрешений — используйте `Semaphore(n)`.
- Функция обновления **чистая и быстрая** — `Ref.update` будет быстрее и без блокировок.
- Вам нужен повторный вход — `Mutex` не поддерживает.
- Вам нужна блокировка между волокнами и внешними потоками — `Mutex` работает только с волокнами Cats Effect.

`Mutex` — это **простой, безопасный и эффективный** инструмент для защиты критических секций в конкурентном функциональном коде. 
В паре с `Resource` он даёт идиоматичный способ управления блокировками, устойчивый к ошибкам и отмене.
