# MapRef — атомарный словарь для ключей

`MapRef[F[_], K, V]` — это **специализированная структура данных**, которую можно представить 
как карту (словарь) пар ключ-значение, где каждое значение (тип `V`) для каждого ключа (тип `K`) 
хранится в собственной, независимой атомарной ссылке — `Ref[F, V]`.

Доступ к каждому элементу осуществляется через его ключ, 
и операции над разными ключами **могут выполняться одновременно**, не мешая друг другу.

### Простейший интерфейс

```dotty
trait MapRef[F[_], K, V]:
  /** Возвращает Ref для конкретного ключа. */
  def apply(k: K): Ref[F, V]
```

Вы берёте `MapRef`, передаёте ей ключ `k`, и она возвращает вам обычный `Ref[F, V]`. 
Далее вы работаете с этим `Ref` как обычно: `get`, `set`, `update`, `modify`.

## `MapRef` vs `Ref[F, Map[K, V]]`

Главный вопрос: зачем нужен `MapRef`, если можно просто положить целый неизменяемый словарь в один `Ref`?

| Операция                                   | `Ref[F, Map[K, V]]`                                                                                                                                                                                      | `MapRef[F, K, V]`                                                                                                   |
|:-------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------|
| **Обновление одного ключа**                | 1. Прочитать весь словарь (`map.get`). 2. Изменить одну запись (`map.updated`). 3. Записать весь словарь обратно (`ref.set`). **Весь процесс атомарен и блокирует доступ к словарю для других волокон.** | Получить `Ref[F, V]` по ключу и обновить его независимо. **Не блокирует доступ к другим ключам.**                   |
| **Параллельные обновления разных ключей**  | ❌ Невозможны. Даже два изменения разных ключей будут сериализованы.                                                                                                                                      | ✅ Возможны. Обновления ключей `A` и `B` выполняются полностью одновременно.                                         |
| **Атомарность сложных операций**           | Атомарна для **всего словаря** целиком.                                                                                                                                                                  | Атомарна **только в пределах одного ключа**. Нельзя сделать атомарное перемещение значения из ключа `A` в ключ `B`. |

**Простая метафора:**

- `Ref[F, Map[K, V]]` — это **сейф с одной дверцей**, внутри которого лежит большая папка. 
  Чтобы изменить одну страницу, вы запираете весь сейф, достаёте папку, правите страницу, кладёте папку обратно и отпираете сейф.
- `MapRef[F, K, V]` — это **стена с множеством маленьких ячеек**. У каждой ячейки своя дверца и свой ключик. 
  Вы можете одновременно открыть несколько ячеек и менять их содержимое, не мешая друг другу.

## Ключевые преимущества `MapRef`

### 1. Уменьшение конкуренции (Contention)

Это самое важное преимущество. В традиционной модели `Ref[F, Map]`, при любом обновлении любого ключа, 
блокируется (или вступает в CAS-гонку) **весь словарь**. Это становится узким местом при высокой нагрузке.

`MapRef` решает эту проблему, разбивая данные на **независимые сегменты (shards)**. 
Обновления разных ключей, попавших в разные сегменты, могут выполняться **полностью параллельно**.

### 2. Лучшая эргономика

Работать с `MapRef` интуитивно понятнее и лаконичнее, чем каждый раз делать `ref.update(map => map.updated(key, value))`.

**Сравните:**

```dotty
// С Ref[F, Map[K, V]]
def updateWithRef[F[_], K, V](ref: Ref[F, Map[K, V]])(key: K, value: V): F[Unit] =
  ref.update(_.updated(key, value))

// С MapRef
def updateWithMapRef[F[_], K, V](mapRef: MapRef[F, K, V])(key: K, value: V): F[Unit] =
  mapRef(key).set(value)
```

Код с `MapRef` короче и читается как работа с обычной, но конкурентным словарем.

### 3. Гибкость: работа с `Option` и значениями по умолчанию

Поскольку `MapRef` — это **полный словарь** (total map), конструкторы обычно предоставляют два варианта:

- **`MapRef.ofImmutableMap[F, K, V]`**: Возвращает `MapRef[F, K, Option[V]]`. 
  Это значит, что при запросе к несуществующему ключу вы получите `Ref` с `None`. 
  Это удобно, когда ключи создаются динамически, и их существование не гарантировано. Это наиболее распространённый и гибкий вариант.
- **`MapRef.ofHashMapWithDefault[F, K, V]`**: Конструктор, который принимает значение по умолчанию (`default: V`). 
  Он вернёт `MapRef[F, K, V]`, где для любого ключа уже есть значение по умолчанию.

## Реальный пример: In-Memory база данных

Рассмотрим пример — создание простой базы данных "в памяти". Это классический вариант использования `MapRef`.

```dotty
import cats.effect.IO
import cats.effect.std.MapRef

// Представьте, что это наша "таблица" в БД.
trait DatabaseClient[F[_], Id, Data]:
  def getDataById(id: Id): F[Option[Data]]
  def upsertData(id: Id, data: Data): F[Unit]

object DatabaseClient:
  // Фабричный метод для создания in-memory реализации.
  def inMemory[Id, Data]: IO[DatabaseClient[IO, Id, Data]] =

    // 1. Создаём MapRef[IO, Id, Option[Data]].
    //    shardCount = 5: Данные будут разбиты на 5 независимых "карманов" для уменьшения конкуренции.
    //    Пустые значения None для новых ключей.
    MapRef.ofShardedImmutableMap[IO, Id, Data](shardCount = 5).map { mapRef =>
      // 2. Реализуем интерфейс базы данных, используя наш mapRef.
      new DatabaseClient[IO, Id, Data]:

        override def getDataById(id: Id): IO[Option[Data]] =
          // Получаем Ref для конкретного Id и читаем его значение.
          // Это мгновенная, неблокирующая операция.
          mapRef(id).get

        override def upsertData(id: Id, data: Data): IO[Unit] =
          // Для upsert: получаем Ref для Id и устанавливаем его в Some(data).
          // Это атомарная операция для данного Id.
          mapRef(id).update(_ => Some(data))
    }
end DatabaseClient
```

### Почему это хороший пример?

1. **Живой пример сегментирования:** `shardCount = 5` — это не магия. Это указание `MapRef` создать 5 "ячеек", 
   ключи будут распределены по ним и, следовательно, могут обновляться параллельно.
2. **Эффективность:** `get` и `upsert` для разных `Id` (например, `"user1"` и `"user2"`) 
   будут выполняться одновременно и не будут блокировать друг друга.
3. **Простота:** Вся сложность одновременной работы со словарем инкапсулирована внутри `MapRef`.

## Другие варианты использования

### 1. Кеш с отдельной блокировкой на ключ

Вам нужно кешировать результаты дорогих операций. Загрузка дорогая, и вы хотите, 
чтобы для одного ключа она выполнялась только один раз, даже при одновременном доступе. 
`MapRef` идеален для этой задачи.

```dotty
import cats.effect.{IO, Ref}
import cats.effect.std.MapRef

class ExpensiveCache[K, V](mapRef: MapRef[IO, K, Option[V]]):
  def getOrLoad(key: K, load: K => IO[V]): IO[V] =
    mapRef(key).modify {
      case Some(v) => (Some(v), v.pure[IO]) // Уже есть в кеше
      case None    => (None, load(key))     // Нет в кеше, нужно загрузить
    }.flatten // flatten, так как modify возвращает F[F[V]]
```

**Важно:** В этом примере операция `load(key)` **выполняется внутри** `modify`, то есть под блокировкой этого ключа. 
Это гарантирует, что для одного и того же `key` функция `load` выполнится **один раз**. Остальные волокна будут ждать.

### 2. Тонкая настройка счётчиков или состояний

У вас есть миллион пользователей, и для каждого нужно хранить независимый счётчик действий. 
С `Ref[Map]` обновление счётчика для одного пользователя блокировало бы весь словарь. С `MapRef` — это просто:

```dotty
def incrementUserActionCount(userId: String): IO[Unit] =
  mapRef(userId).update(_.orElse(Some(0)).map(_ + 1))
```

## Важные характеристики и ограничения

### ✅ Преимущества `MapRef`:

- **Уменьшение конкуренции:** Высокая производительность при работе с большим количеством уникальных ключей за счёт шардирования.
- **Лучшая эргономика:** Код становится чище и понятнее.
- **Гибкость:** Работа с существующими и несуществующими ключами через `Option`.

### ❌ Ограничения и когда `MapRef` не подходит:

- **Нет атомарных операций над несколькими ключами:** Вы **не можете** атомарно переместить значение 
  из ключа `A` в ключ `B` или атомарно прочитать значения двух ключей. Для этого по-прежнему нужен `Ref[F, Map[K, V]]`.
- **Отсутствие полной итерации или `keys`.** Вы не можете эффективно получить все ключи или все значения. `MapRef` не итерируем.
- **`shardCount` — это компромисс.** Слишком малое количество шардов не даст выигрыша в параллелизме. 
  Слишком большое — добавит накладные расходы на хеширование и управление. 
  Нужно подбирать под свою нагрузку (обычно от количества ядер CPU).

## `MapRef` в сравнении с альтернативами

| Сценарий                                                             | Лучший выбор                         | Почему                                                       |
|:---------------------------------------------------------------------|:-------------------------------------|:-------------------------------------------------------------|
| Вам нужна атомарность и консистентность для всех ключей сразу        | `Ref[F, Map[K, V]]`                  | Только так можно атомарно прочитать и изменить весь словарь. |
| Вам нужно обновлять разные ключи параллельно, под большой нагрузкой  | **`MapRef`**                         | Лучшая производительность и масштабируемость.                |
| Ключи и значения создаются и удаляются динамически                   | **`MapRef`**                         | Используйте вариант `MapRef[F, K, Option[V]]`.               |
| Вам нужно также эффективно итерироваться по ключам или значениям     | `Ref[F, Map]` или внешнее хранилище  | `MapRef` не предоставляет API для итерации.                  |

## Итог

`MapRef` — это специализированный, мощный примитив для высококонкурентных сценариев, 
где вам нужно работать с большим количеством ключей, разделяя состояние между ними, 
но без необходимости в атомарных операциях над несколькими ключами сразу.

Он реализует паттерн **шардирования** из коробки, предлагая простой и эргономичный API. 
Если вы видите в своем коде `Ref[F, Map[K, V]]`, который часто обновляется для разных ключей 
и становится узким местом — скорее всего, вам нужно заменить его на `MapRef`.
