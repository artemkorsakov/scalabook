# Тип ввода-вывода общего назначения: IO

## Введение

При работе с побочными эффектами (ввод-вывод, чтение из базы данных и т.д.) 
в функциональном программировании важно сохранять чистоту ядра программы. 
Для этого мы часто используем абстракции, такие как `Free` алгебры, чтобы отделить описание действий от их выполнения.

Однако использование `Free` требует сложных типов и дополнительной логики для интерпретации программ. 
Это может усложнить понимание кода, особенно для новичков.

В этой части мы рассмотрим альтернативный подход: **моделирование эффектов через трейты возможностей** (capabilities). 
Этот метод позволяет:

- Упростить композицию эффектов.
- Сделать код более понятным и поддерживаемым.
- Сохранить преимущества принципа наименьшей мощности (least power).

### Принцип наименьшей мощности

Принцип наименьшей мощности означает, 
что программа должна использовать минимально необходимый набор операций для выполнения своей задачи. 
Это помогает:

- Избежать ненужных побочных эффектов.
- Повысить предсказуемость программы.
- Упростить тестирование и повторное использование кода.

Например, если программа работает только с консолью, она не должна зависеть от операций с файловой системой или сетью.

## Моделирование эффектов через трейты возможностей

Вместо использования `Free` алгебр мы можем моделировать эффекты как **трейты**, параметризованные целевой монадой. 
Трейт определяет набор примитивных операций, которые могут быть выполнены в рамках этой монады.

### Пример: Трейт `Console`

```dotty
trait Console[F[_]]:
  def readLn: F[Option[String]]
  def printLn(line: String): F[Unit]
```

Здесь:

- `F[_]` — это тип монады, в которой выполняются операции.
- `readLn` — возвращает значение типа `F[Option[String]]`, которое представляет собой операцию чтения строки с консоли.
- `printLn` — возвращает значение типа `F[Unit]`, представляющее операцию вывода строки на консоль.

Такие трейты позволяют создавать программы, которые работают с эффектами, но при этом остаются чистыми и легко тестируемыми.

### Реализация трейтов для конкретных монад

Мы можем предоставить реализации этих трейтов для разных монад, например, 
`Par` (асинхронная параллельность) или `Function0` (ленивая вычисляемая функция без аргументов).

#### Пример: Консоль для `Par`

```dotty
given parConsole: Console[Par] with
  def readLn: Par[Option[String]] =
    Par.lazyUnit(Try(readLine()).toOption)

  def printLn(line: String): Par[Unit] =
    Par.lazyUnit(println(line))
```

#### Пример: Консоль для `Function0`

```dotty
given thunkConsole: Console[Function0] with
  def readLn: () => Option[String] =
    () => Try(readLine()).toOption

  def printLn(line: String): () => Unit =
    () => println(line)
```

Каждая реализация соответствует разному способу выполнения эффектов, но логика программы остается одинаковой.

### Композиция эффектов

С использованием трейтов возможностей композиция становится проще.
Мы можем объединять разные эффекты в одной программе, не беспокоясь о сложных типах или явной композиции алгебр.

#### Пример: Программа приветствия

```dotty
def greet[F[_]](using c: Console[F], m: Monad[F]): F[Unit] =
  for
    _ <- c.printLn("What's your name?")
    n <- c.readLn
    _ <- n match
      case Some(n) => c.printLn(s"Hello, $n!")
      case None    => c.printLn(s"Fine, be that way.")
  yield ()
```

Здесь:

- Мы используем for-comprehension для последовательного выполнения операций.
- `Monad[F]` позволяет упорядочивать действия с помощью `flatMap`.
- Все эффекты описываются через `Console[F]`.

### Композиция нескольких эффектов

Рассмотрим пример, где программа использует несколько трейтов: `Console` и `Files`.

#### Пример: Операция `cat` (вывод содержимого файла)

```dotty
trait Files[F[_]]:
  def readLines(file: String): F[List[String]]
  def writeLines(file: String, lines: List[String]): F[Unit]

def cat[F[_]](file: String)(
  using c: Console[F], f: Files[F], m: Monad[F]
): F[Unit] =
  f.readLines(file).flatMap: lines =>
    c.printLn(lines.mkString("\n"))
```

Здесь:

- `Files[F]` предоставляет операции чтения и записи файлов.
- `cat` объединяет чтение из файла и вывод на консоль.
- Все операции происходят в рамках одной и той же монады `F`.

### Преимущества подхода

1. **Упрощение композиции**
   - Нет необходимости в сложных типах, таких как объединения алгебр (`[x] =>> Files[x] | Console[x]`).
   - Простое объединение разных эффектов в одной программе.

2. **Легкость тестирования**
   - Можно заменить реальные эффекты на тестовые реализации трейтов.
   - Например, вместо настоящего чтения из консоли можно использовать фиктивную реализацию.

3. **Стековая безопасность**
   - Если целевая монада (`F`) обеспечивает стековую безопасность (например, `TailRec`), то вся программа будет стеково-безопасной.
   - Это особенно важно для рекурсивных программ.

4. **Гибкость**
   - Можно выбрать любую монаду в зависимости от нужд (синхронная, асинхронная, ленивая и т.д.).
   - Изменение монады влияет только на внешнюю часть программы.

### Итого

Подход с использованием трейтов возможностей позволяет создавать программы с эффектами, 
сохраняя при этом преимущества функционального программирования.
Он упрощает композицию, делает код более понятным и легче тестируемым, 
а также позволяет гибко выбирать стратегию выполнения.

Такой подход является хорошей альтернативой `Free` алгебрам, особенно когда важна простота и читаемость кода.

## Тип ввода-вывода общего назначения: IO

### Общая методология работы с вводом-выводом

При создании программ, взаимодействующих с внешним миром (например, чтение файлов, запись данных, вывод на консоль), 
мы стремимся сохранять чистоту и предсказуемость основного кода. 
Для этого мы используем абстракции, такие как `IO`, чтобы отделить описание действий от их выполнения.

Итого: что такое `IO`?

`IO` — это тип данных, который позволяет описывать вычисления, связанные с вводом-выводом, 
без прямого выполнения побочных эффектов. 
Он моделирует действия, которые могут быть выполнены позже, например:

- Вывод строки на консоль.
- Чтение файла.
- Сохранение данных в базу данных.

В отличие от императивного кода, где эффекты происходят немедленно, `IO` представляет эти действия как значения, 
которые можно хранить, передавать и комбинировать, не вызывая их сразу.

```dotty
opaque type IO[A] = Free[Par, A]
```

Здесь:

- `Free[Par, A]` — это [свободная монада](../../typeclass/monad/free-monads.md), которая позволяет строить последовательности действий.
- `Par` — это тип для асинхронных вычислений (например, параллельные или неблокирующие).
- `A` — это результат вычисления, который может быть любого типа.

Таким образом, `IO[A]` представляет собой программу, которая:

- Может выполнять операции ввода-вывода.
- Может работать асинхронно.
- Может быть интерпретирована позже, когда это потребуется.

### Основная программа в the-end-of-the-world

Когда мы пишем приложение, которое запускается на JVM, нам нужно реализовать метод `main`.
Обычно он имеет сигнатуру `def main(args: Array[String]): Unit`, и его выполнение начинает работу программы.

Однако в функциональном программировании мы хотим, чтобы наша программа была **чистой**, 
то есть не содержала побочных эффектов.
Для этого мы можем разделить программу на две части:

1. **Чистую часть** — `pureMain`, которая возвращает значение типа `IO[Unit]`.
2. **Интерпретатор** — `main`, который запускает программу `pureMain`.

#### Пример реализации `IOApp`

```dotty
trait IOApp:
  import java.util.concurrent.{Executors, ExecutorService}
 
  // Расширение, добавляющее метод `unsafeRunSync` к типу `IO`
  extension [A](ioa: IO[A])
    def unsafeRunSync(pool: ExecutorService): A =
      ioa.run.run(pool)
 
  // Метод `main`, который запускает программу
  def main(args: Array[String]): Unit =
    val pool = Executors.newFixedThreadPool(8) // Создаем пул потоков
    pureMain(args.toList).unsafeRunSync(pool)  // Запускаем чистую программу
 
  // Чистый метод, описывающий программу в виде `IO[Unit]`
  def pureMain(args: List[String]): IO[Unit]
```

#### Как это работает?

- `pureMain` — это чистая функция, которая возвращает `IO[Unit]`.
  Она не содержит побочных эффектов напрямую; она просто описывает, какие действия должны быть выполнены.

- `main` — это метод, который запускает программу, используя пул потоков (`ExecutorService`).
  Он интерпретирует `IO[Unit]` и выполняет все действия, описанные в `pureMain`.

- `unsafeRunSync` — это метод, который преобразует `IO[A]` в `A`, фактически выполняя все действия.
  Название _"unsafe"_ (_"небезопасно"_) указывает на то, что это точка входа для реальных побочных эффектов.

### Различие между эффектами и побочными эффектами

Важно понимать разницу между **эффектами** и **побочными эффектами**:

- **Эффекты** — это действия, которые изменяют состояние внешнего мира, но описываются внутри `IO`.
  Например, чтение файла или вывод сообщения на экран.

- **Побочные эффекты** — это изменения, которые происходят внезапно и непредсказуемо, 
  нарушая принципы функционального программирования.
  Например, изменение глобальной переменной или запись в файл без явного указания.

В нашем случае `pureMain` — это чистая функция, которая **не содержит побочных эффектов**,
но описывает программу, содержащую **эффекты**.
Выполнение этих эффектов происходит только в методе `main`, за пределами видимости `pureMain`.

Таким образом, мы говорим, что наша программа **имеет эффекты**, но **не имеет побочных эффектов**.

### Преимущества такого подхода

1. **Чистота ядра программы**
   - Основная логика программы находится в `pureMain`, которая не содержит побочных эффектов.
   - Это делает её легко тестируемой и предсказуемой.

2. **Гибкость выполнения**
   - Мы можем использовать разные реализации `IO`, например, для синхронного или асинхронного выполнения.
   - Изменение способа выполнения влияет только на `main`, а не на всю программу.

3. **Безопасность типов**
   - Все эффекты описываются через типы, что позволяет компилятору проверять корректность программы.

4. **Масштабируемость**
   - Мы можем легко добавлять новые эффекты, определяя новые трейты и реализации для `IO`.

### Итого

Тип `IO` предоставляет мощную абстракцию для работы с вводом-выводом в функциональном программировании.
Он позволяет описывать эффекты как чистые значения, избегая побочных эффектов в основном коде.
С помощью `IOApp` мы можем разделить программу на чистую часть и интерпретатор,
что делает её более безопасной, гибкой и легкой для тестирования.

Этот подход становится особенно полезным при работе с асинхронными, параллельными или ресурсоемкими операциями,
где контроль над выполнением и порядком действий критически важен.

## Почему тип ввода-вывода недостаточен для потокового ввода-вывода

Тип `IO` и монады в функциональном программировании предоставляют мощную абстракцию для работы с побочными эффектами. 
Они позволяют описывать вычисления, связанные с вводом-выводом, как чистые значения, 
что делает код более предсказуемым и тестируемым. 
Однако, несмотря на все преимущества `IO`, этот тип имеет свои ограничения, 
особенно при работе с **потоковым вводом-выводом** (streaming I/O).

Далее мы рассмотрим, почему `IO` может быть недостаточным для эффективной обработки потоковых данных, 
и как можно улучшить ситуацию с помощью более композируемой и гибкой архитектуры.

### Проблема: Обработка больших файлов

Предположим, у нас есть текстовый файл `fahrenheit.txt`, в котором хранится последовательность температур в градусах Фаренгейта. 
Мы хотим преобразовать каждую температуру в градусы Цельсия и сохранить результат в новый файл `celsius.txt`.

#### Использование `IO` с загрузкой всего файла

Сначала мы можем попробовать использовать тип `IO`, чтобы реализовать эту задачу:

```dotty
trait Files[F[_]]:
  def readLines(file: String): F[List[String]]
  def writeLines(file: String, lines: List[String]): F[Unit]

def convert[F[_]](using f: Files[F]): F[Unit] =
  for
    lines <- f.readLines("fahrenheit.txt")
    cs = lines.map(s => fahrenheitToCelsius(s.toDouble).toString)
    _ <- f.writeLines("celsius.txt", cs)
  yield ()
```

Этот код работает корректно, но имеет существенный недостаток: он загружает **весь файл в память**.
Если файл велик (например, содержит миллионы строк), это может привести к **высокому потреблению памяти** 
и даже к **переполнению стека или вылету программы**.

### Попытка оптимизации: потоковая обработка

Чтобы избежать полной загрузки файла в память, мы можем использовать низкоуровневый API, 
который позволяет работать с файлом построчно или по буферу:

```dotty
trait Files[F[_]]:
  def openRead(file: String): F[HandleR]
  def openWrite(file: String): F[HandleW]
  def readLine(h: HandleR): F[Option[String]]
  def writeLine(h: HandleW, line: String): F[Unit]

trait HandleR
trait HandleW
```

Теперь мы можем реализовать обработку файла построчно:

```dotty
def loop[F[_]](hr: HandleR, hw: HandleW)(using f: Files[F]): F[Unit] =
  f.readLine(hr).flatMap:
    case None => IO.unit(())
    case Some(s) =>
      f.writeLine(hw, fahrenheitToCelsius(s.toDouble))
        .flatMap(_ => loop(hr, hw))

def convertFiles[F[_]](using f: Files[F]): F[Unit] =
  for
    hr <- f.openRead("fahrenheit.txt")
    hw <- f.openWrite("celsius.txt")
    _  <- loop(hr, hw)
  yield ()
```

Этот подход позволяет обрабатывать файл **по одной строке за раз**, что экономит память.
Однако у него есть **серьезный недостаток**: код становится **монолитным** и **некомпозируемым**.

### Проблема монолитного цикла

В примере выше мы использовали рекурсивную функцию `loop`, которая обрабатывает каждую строку и вызывает саму себя.
Хотя это работает, такой подход **не поддается композиции** — если нам нужно добавить дополнительную логику, 
например, вычисление скользящего среднего, нам придется менять саму функцию `loop`.

Сравните это с обработкой списков, где мы можем легко комбинировать операции:

```dotty
def movingAvg(n: Int)(l: List[Double]): List[Double] = ???

val cs =
  movingAvg(5)(
    lines.map(s => fahrenheitToCelsius(s.toDouble))
  ).map(_.toString)
```

Здесь мы можем применять функции к списку, как конвейер, и добавлять новые шаги без изменения существующего кода.
Такая **композиционная гибкость** отсутствует в нашем потоковом коде с `IO`.

### Суть проблемы

Проблема не в том, что `IO` плох, а в том, что он **не предоставляет достаточно удобных примитивов для потоковой обработки**.
Мы вынуждены писать **манипуляторы состояния** и **циклы**, которые трудно читать, тестировать и модифицировать.

Кроме того, `IO` — это **низкоуровневая абстракция**, которая требует от нас реализации всех деталей обработки.
Нам хочется иметь возможность выражать потоковые вычисления так же просто, 
как мы это делаем со списками или другими композируемыми структурами.

### Как это можно исправить?

Функциональное программирование дает нам инструменты для создания **собственных абстракций**, 
которые могут заменить `IO` в [случае потоковой обработки](../stream-processing.md).
Например, мы можем создать абстракцию, похожую на список, но которая работает с потоками:

- Можно определить `Stream[A]` как бесконечный или конечный список элементов, который можно обрабатывать по частям.
- Мы можем создать операции над потоками, такие как `map`, `filter`, `fold`, `windowed` и т.д.
- Эти операции будут композируемыми, как и обычные функции над списками.

#### Пример: Вычисление скользящего среднего

Если бы у нас был поток `Stream[Double]`, мы могли бы легко вычислить скользящее среднее:

```dotty
def windowed[A](n: Int, s: Stream[A])(f: A => B)(using m: Monoid[B]): Stream[B] = ???

val stream = Stream.fromFile("fahrenheit.txt").map(fahrenheitToCelsius)

val avgStream = windowed(5, stream)(_ => ...)

avgStream.toFile("celsius.txt")
```

Этот код гораздо проще понимать и модифицировать.
Кроме того, он использует те же принципы композиции, что и работа со списками.

### Итого

Тип `IO` — это отличная абстракция для работы с эффектами, 
но он **не является идеальным решением для потоковой обработки данных**.
Он требует использования монолитных циклов и ручного управления состоянием, что делает код сложным и менее гибким.

Чтобы улучшить ситуацию, мы можем:

- Создавать [собственные композируемые абстракции для потоков](../stream-processing.md).
- Использовать аналогии со списками, чтобы сделать работу с потоками более интуитивной.
- Разрабатывать универсальные комбинаторы, такие как `windowed`, `map`, `filter`, и т.д.

Функциональное программирование дает нам свободу выбора: мы можем использовать `IO`, когда это необходимо, 
но также можем строить более высокие уровни абстракции, которые лучше соответствуют нашим задачам.
