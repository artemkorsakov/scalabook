# Расширяемые `Pull` и `Stream`

## Контекст и Мотивация

Предыдущие реализации `Pull` и `Stream` предоставляли альтернативный, 
но схожий по выразительности с `LazyList` способ описания ленивых вычислений. 
Ключевое ограничение заключалось в том, что для выполнения операций ввода-вывода (таких как чтение файла) 
вся программа оборачивалась в монолитную `IO`-структуру, которая скрывала источник данных внутри себя. 
Это не позволяло эффектам (например, открытию файла) быть частью самой структуры потока.

Новый дизайн решает эту проблему, делая сами типы `Pull` и `Stream` расширяемыми для поддержки произвольных эффектов. 
Это позволяет описывать источники данных (например, чтение из файла или сети) напрямую внутри стрима, а не прятать их снаружи.

## Новая Структура `Pull`

Тип `Pull` был параметризован тремя типами:

- `F[_]` — тип эффекта (например, `IO`).
- `O` — тип выходных элементов потока.
- `R` — тип конечного результата вычисления.

Был добавлен новый конструктор данных:

```dotty
enum Pull[+F[_], +O, +R]:
  // Существующие конструкторы:
  case Result[+R](result: R) extends Pull[Nothing, Nothing, R]
  case Output[+O](value: O)  extends Pull[Nothing, O, Unit]
  case FlatMap[+F[_], X, +O, +R](
      source: Pull[F, O, X],
      f: X => Pull[F, O, R]
  ) extends Pull[F, O, R]

  // Новый конструктор:
  case Eval[+F[_], R](action: F[R]) extends Pull[F, Nothing, R]
```

### Пояснение нового конструктора:

**`Eval[+F[_], R](action: F[R])`**

- **Назначение:** Это фундаментальное нововведение. Конструктор `Eval` позволяет встраивать в структуру потока 
  произвольное действие с эффектом типа `F[R]`.
- **Семантика:** При интерпретации (выполнении) стрима, когда управление доходит до `Eval`, будет выполнено действие `action`. 
  Результат этого действия (`R`) будет использован для продолжения потока.
- **Типы:** `Eval[F, R] extends Pull[F, Nothing, R]`. Это означает:
    - Он вносит эффект типа `F`.
    - Он не производит никаких _выходных элементов_ потока (`Nothing` на месте `O`).
    - Он вычисляет _результат_ типа `R`.

**Параметр типа `F[_]` и ковариантность**

- Параметр `F` стал ковариантным (`+F[_]`). Это важное свойство системы типов, которое позволяет:
    - **`Result` и `Output` фиксировать `F` на `Nothing`:** Поскольку эти конструкторы не выполняют никаких эффектов, 
      они совместимы с любым другим эффектом `F` в композиции. 
      `Nothing` является "нижним" типом в иерархии Scala, что делает эти конструкции максимально универсальными.
    - **Безопасно комбинировать стримы с разными эффектами** через подтипизацию.

### Как это меняет подход?

- **Старый подход (монолитный IO):**

  ```dotty
  // Эффект (чтение файла) скрыт внутри IO
  val program: IO[Unit] = IO {
      val source = scala.io.Source.fromFile("file.txt")
      // ... использовать source для создания Stream ...
  }
  ```

  Источник данных создавался _до_ построения стрима и был скрыт внутри `IO`.

- **Новый подход (эффекты внутри Stream):**
  ```dotty
  // Эффект становится частью стрима
  def fileLines(path: String): Stream[IO, String] =
      Stream.eval(IO(scala.io.Source.fromFile(path))) // Eval эффект для открытия файла
        .flatMap(source => ... // Построение потока строк из source
  ```
  Действие по открытию файла (`IO(...)`) теперь может быть встроено в стрим как элемент `Eval`. 
  Это делает источник данных явной и управляемой частью ленивого потока.

Это изменение фундаментально повышает выразительность системы `Pull/Stream`. 
Теперь она может не только преобразовывать чистые данные, 
но и сама описывать, _как эти данные получить_, включая побочные эффекты. 
Это открывает путь к созданию сложных, комбинируемых потоков данных с чистым управлением ресурсами 
и эффектами непосредственно на уровне абстракции стрима.

## Аннотации дисперсии (вариативности) в типе `Pull`

При проектировании параметризованных типов в Scala ключевым решением является выбор аннотации дисперсии для параметров типа: 
инвариантность (`Pull[F, O, R]`) или ковариантность (`Pull[+F[_], +O, +R]`).

```dotty
enum Pull[F[_], O, R]: // Все параметры инвариантны
  case Result(result: R)
  case Output(value: O)
  case Eval(action: F[R])
  case FlatMap[F[_], X, O, R](
      source: Pull[F, O, X],
      f: X => Pull[F, O, R]
  ) extends Pull[F, O, R]
```

**Преимущество:** Это определение выглядит проще и интуитивно понятнее.

**Недостаток:** Оно создаёт значительные неудобства при практическом использовании и композиции значений `Pull`.

### Проблема на примере: Композиция `Pull`-объектов

Рассмотрим два простых, независимых выражения:

```dotty
Pull.Output(1)
// val res0: Pull[Nothing, Int, Unit] = Output(1)

Pull.Result(true)
// val res1: Pull[Nothing, Nothing, Boolean] = Result(true)
```

Логично предположить, что мы можем скомбинировать их с помощью оператора `>>` 
(который последовательно выполняет два `Pull`, игнорируя результат первого и возвращая результат второго).

**Ожидание:** `res0 >> res1` должно иметь тип `Pull[Nothing, Int, Boolean]`. 
Сначала выводится элемент `1` (тип `O = Int`), затем вычисляется результат `true` (тип `R = Boolean`).

**Реальность с инвариантным типом:**

```dotty
res0 >> res1
-- [E007] Type Mismatch Error: -------------------------------------------------
1 |res0 >> res1
  |        ^^^^
  |        Found:    (res1 : Pull[Nothing, Nothing, Boolean])
  |        Required: Pull[Nothing, Int, Any]
```

**Объяснение ошибки:** Оператор `>>` определён примерно так:

```dotty
def >>[F2[_], O2 >: O, R2](that: Pull[F2, O2, R2]): Pull[F2, O2, R2] = ...
```

Для `res0 >> res1` компилятор пытается подставить типы:

1. `res0` имеет тип `Pull[Nothing, Int, Unit]`.
2. Метод `>>` для `res0` ожидает аргумент типа `Pull[F2, Int, R2]` (так как `O2 >: Int`, и самым конкретным типом будет `Int`).
3. `res1` имеет тип `Pull[Nothing, Nothing, Boolean]`.
4. Тип `Nothing` для `O` в `res1` _не является_ подтипом `Int`, требуемого для `that`. 
   `Nothing` — это подтип всего, но здесь компилятору нужен аргумент, 
   тип `O` которого _совпадает или является супертипом_ типа `O` из `res0`. 
   `Nothing` не является супертипом `Int`. Следовательно, типы несовместимы.

**Обходной путь:** Единственный способ скомбинировать их — создать оба выражения _в одном выражении_, 
чтобы компилятор мог вывести общий, единый тип для всех параметров _до их фиксации_:

```dotty
Pull.Output(1) >> Pull.Result(true)
// val res2: Pull[Nothing, Int, Boolean] = ...
```

Здесь компилятор с самого момента конструирования видит цель — комбинацию, — 
и может вывести для всей конструкции общие параметры `O = Int` и `R = Boolean`.

### Решение: Ковариантная версия (Сложнее определение, но удобнее API)

```dotty
enum Pull[+F[_], +O, +R]: // Все параметры ковариантны
  case Result[+R](result: R) extends Pull[Nothing, Nothing, R]
  case Output[+O](value: O) extends Pull[Nothing, O, Unit]
  case Eval[+F[_], R](action: F[R]) extends Pull[F, Nothing, R]
  case FlatMap[+F[_], X, +O, +R](
    source: Pull[F, O, X], f: X => Pull[F, O, R]) extends Pull[F, O, R]
```

**Почему это работает:** Ковариантность означает, что `Pull[F1, O1, R1]` является подтипом `Pull[F2, O2, R2]`, 
если `F1 <: F2`, `O1 <: O2` и `R1 <: R2`.

Теперь рассмотрим выражение `res0 >> res1` с ковариантными типами:

1. `res0`: `Pull[Nothing, Int, Unit]`
2. `res1`: `Pull[Nothing, Nothing, Boolean]`
3. **Важно:** Благодаря ковариантности, тип `res1` (`Pull[Nothing, Nothing, Boolean]`) 
   **автоматически является подтипом** типа `Pull[Nothing, Int, Boolean]`:
    - `Nothing <: Nothing` (`F`)
    - `Nothing <: Int` (`O`) — `Nothing` является подтипом любого типа.
    - `Boolean <: Boolean` (`R`)
4. Следовательно, компилятор может безопасно "поднять" тип `res1` до требуемого `Pull[Nothing, Int, Boolean]` 
   и успешно проверить типы.

Выбор в пользу ковариантности — это классический компромисс между сложностью реализации и удобством использования (API).

- **Инвариантность** приводит к более простому определению типа, но создаёт неудобства 
  и неинтуитивное поведение для пользователя, требуя ручных ухищрений для компиляции.
- **Ковариантность** усложняет внутреннее определение типа и его методы (из-за необходимости сохранять вариативность), 
  но результат — это гораздо более выразительный, предсказуемый и приятный API, 
  где значения `Pull` свободно комбинируются так, как и ожидает пользователь, следуя принципу наименьшего удивления.

## Анализ метода `step`

Добавление конструктора `Eval` для поддержки произвольных эффектов (`F[_]`) фундаментально меняет семантику типа `Pull`. 
Это изменение напрямую затрагивает метод `step`, который разбирает структуру `Pull` на шаги.

**Старая сигнатура (без эффектов):**

```dotty
def step: Either[R, (O, Pull[O, R])]
```

Возвращала чистое значение: либо конечный результат `R`, либо очередной элемент `O` и хвост потока.

**Новая реализация:**

```dotty
enum Pull[+F[_], +O, +R]:
  ...

  def flatMap[F2[x] >: F[x], O2 >: O, R2](f: R => Pull[F2, O2, R2])
      : Pull[F2, O2, R2] =
    Pull.FlatMap(this, f)

  def step[F2[x] >: F[x], O2 >: O, R2 >: R](using
      F: Monad[F2] // #1
  ): F2[Either[R2, (O2, Pull[F2, O2, R2])]] =
    this match
      case Result(r)    => F.unit(Left(r))              // #2
      case Output(o)    => F.unit(Right(o, Pull.done))  // #3
      case Eval(action) => action.map(Left(_))          // #4
      case FlatMap(source, f) =>                        
        source match
          case FlatMap(s2, g) =>                        // #5
            s2.flatMap(x => g(x).flatMap(y => f(y))).step
          case other => other.step.flatMap:             // #6        
              case Left(r)         => f(r).step
              case Right((hd, tl)) => F.unit(Right((hd, tl.flatMap(f))))
end Pull

object Pull:
  val done: Pull[Nothing, Nothing, Unit] = Pull.Result(())
```

### Разбор реализации для каждого конструктора

Рассмотрим, как обрабатывается каждый случай в сопоставлении с шаблоном, а также новую сигнатуру:

1. **Новая сигнатура (с эффектами):**

   ```dotty
   def step[F2[x] >: F[x], O2 >: O, R2 >: R](
     using F: Monad[F2] // #1
   ): F2[Either[R2, (O2, Pull[F2, O2, R2])]]
   ```
   
   - **Возвращаемый тип:** `F2[Either[...]]`. Теперь сам процесс выполнения шага (`step`) является действием с эффектом.
     Результат этого действия — `Either`, завернутый в контекст `F2`.
   - **Контекст выполнения:** Для работы с эффектом `F2` требуется реализация `Monad[F2]` ([что такое монада?][monad]).
     Это позволяет использовать операции `map` и `flatMap` внутри реализации `step`.
   - **Параметры типа с нижними границами (`>:`):** `F2[x] >: F[x]`, `O2 >: O`, `R2 >: R`.
     Эти границы необходимы для сохранения ковариантности параметров `F, O, R`
     и обеспечения возможности "расширения" типа при комбинации с другими `Pull`-объектами.

2. **`case Result(r)`** — Конечный результат.

   ```dotty
   case Result(r) => F.unit(Left(r)) // #2
   ```

   - **Действие:** Создаётся действие с эффектом (`F.unit`), которое немедленно возвращает чистый результат `r`, обёрнутый в `Left`.
   - **`F.unit`**: Операция [монады][monad], которая поднимает чистое значение в контекст эффекта (`A => F[A]`).

3. **`case Output(o)`** — Выходной элемент.

   ```dotty
   case Output(o)    => F.unit(Right(o, Pull.done))  // #3
   ```

   - **Действие:** Создаётся действие с эффектом, которое возвращает элемент `o` и пустой хвост (`Pull.done`), обёрнутые в `Right`.

4. **`case Eval(action)`** — Эффектное действие.

   ```dotty
   case Eval(action) => action.map(Left(_))          // #4
   ```

   - **Действие:** Это ключевое изменение. Выполняется само действие с эффектом `action: F[R]`.
   - **Результат:** Результат действия `action` (значение типа `R`) маппится в `Left(R)`, 
     сигнализируя о завершении потока с этим результатом. 
     _Важно:_ `Eval` не производит выходных элементов (`O`), только результат.

5. **`case FlatMap(source, f)`** — Последовательная композиция.
   Это самый сложный случай, обеспечивающий стекобезопасность.
   ```dotty
   case FlatMap(source, f) =>
     source match
       // Правило ассоциативности: перегруппировка вложенных FlatMap
       case FlatMap(s2, g) =>             // #5
         s2.flatMap(x => g(x).flatMap(y => f(y))).step // Рекурсивный вызов step
       // Базовый случай, когда source - это не FlatMap.
       // Начинается цепочка с эффектом!
       case other => other.step.flatMap:  // #6
         // Если source завершился результатом r, применить f к r и перейти к следующему шагу
         case Left(r) => f(r).step 
         // Если source выдал элемент, выдать его, применив f к хвосту
         case Right((hd, tl)) => F.unit(Right((hd, tl.flatMap(f)))) 
   ```

   - **Ассоциативность (#5):** Первый случай переписывает `source.flatMap(g).flatMap(f)` в `source.flatMap(x => g(x).flatMap(f))`, 
     что предотвращает рост стека из-за вложенности `FlatMap`.
   - **Эффектная рекурсия (#6):** Обратите внимание на вызов `other.step.flatMap`. 
     Рекурсия теперь происходит не в стеке вызовов, а _внутри_ цепочки `flatMap` монады `F`. 
     Это делает процесс стекобезопасным, но **только если сама монада `F` имеет стекобезопасную реализацию `flatMap`** 
     (например, `IO` или `cats.Eval`).

### Сложность и альтернатива: Методы расширения

Сигнатура метода `step` стала чрезвычайно сложной из-за необходимости:

- Сохранять ковариантность.
- Вводить параметры с нижними границами.
- Требовать неявный `Monad`.

**Альтернативное решение: метод расширения (extension method)**

```dotty
// Определение становится проще, так как не нужно вводить F2, O2, R2
def step(using F: Monad[F]): F[Either[R, (O, Pull[F, O, R])]] =
  self match
    ... // реализация такая же как выше
```

- **Преимущество:** Гораздо более простая и читаемая сигнатура типа. Нет необходимости в сложных параметрах с границами.
- **Недостаток:** Некоторое ухудшение вывода типов. 
  Компилятору может быть сложнее вывести конкретные типы в местах вызова, особенно при сложных цепочках преобразований.

### Итог

Добавление эффектов резко увеличило сложность реализации core-примитивов, таких как `step`. 
Код переместился из мира чистых рекурсивных функций в мир монадических вычислений. 
Это плата за выразительность и возможность описывать источники данных и эффекты напрямую внутри стрима. 
Критически важным для корректной работы становится требование к монаде `F` быть стекобезопасной.

## Адаптация операций `fold`, `toList` и `uncons`

Добавление эффектов превращает ранее простые хвостово-рекурсивные операции в монадически-рекурсивные.

### Метод `fold`

```dotty
// Возвращает действие с эффектом, результатом которого является кортеж (ФинальныйРезультат, Аккумулятор)
def fold[F2[x] >: F[x], R2 >: R, A](init: A)(f: (A, O) => A)(
  using F: Monad[F2]
): F2[(R2, A)] = 
  // Выполняем шаг. Результат (F[Either[...]]) оборачивается в flatMap
  step.flatMap: 
    // Если поток завершился, возвращаем текущий аккумулятор и результат
    case Left(r)         => F.unit((r, init)) 
    // Если есть элемент, обновляем аккумулятор и рекурсивно продолжаем свёртку хвоста
    case Right((hd, tl)) => tl.fold(f(init, hd))(f) 
```

- **Изменение:** Метод больше не может быть помечен как `@tailrec`. 
  Рекурсия теперь происходит _внутри_ цепочки `flatMap` монады `F2`.
- **Стекобезопасность:** Теперь полностью зависит от реализации `flatMap` в монаде `F2`. 
  Если `F2.flatMap` стекобезопасен (например, использует [trampolining][trampolining]), 
  то и `fold` будет стекобезопасным.

### Метод `toList`

```dotty
def toList[F2[x] >: F[x]: Monad, O2 >: O]: F2[List[O2]] =
  // Используем Builder для эффективного построения списка
  fold(List.newBuilder[O])((bldr, o) => bldr += o) 
    // После свёртки получаем F2[(R, Builder)]. 
    // Берем второй элемент кортежа и вызываем .result
    .map(_(1).result) 
```

`toList` строится на основе `fold`, используя `List.newBuilder` для эффективного накопления элементов.

### Проблема с операцией `uncons` и её решение

`uncons` — это фундаментальная операция, которая "разбирает" поток на голову и хвост или обнаруживает его завершение.

**Наивный подход (Проблемный)**

Первая попытка адаптации аналогична чистой версии:

```dotty
// НЕРАБОТАЮЩИЙ вариант
def uncons[F2[x] >: F[x], O2 >: O, R2 >: R](
  using Monad[F2]
): Pull[F2, Nothing, Either[R2, (O2, Pull[F2, O2, R2])]] =
  Eval(step) // Пытаемся обернуть вызов step в узел с эффектом Eval
```

**Проблема:** Накладывает ограничение `Monad[F2]` даже на _построение_ значения `Pull`. 
Что делает невозможным вызов `uncons` для пула без эффектов (где `F = Nothing`), 
так как не существует экземпляра `Monad[Nothing]`. Это ломает полиморфизм.

**Решение: Введение нового конструктора `Uncons`**

Чтобы отложить требование монады до момента _интерпретации_ (выполнения `step`), 
а не _конструирования_, мы вводим новый конструктор данных:

```dotty
// Новый case в enum Pull
case Uncons(source: Pull[F, O, R])
  extends Pull[F, Nothing, Either[R, (O, Pull[F, O, R])]]
```

- **Семантика:** `Uncons` — это обещание, что когда-нибудь позже (при вызове `step`) мы разберём `source` на части.
- **Типы:** Конструктор не производит выходных элементов (`Nothing`), 
  а его результат — это `Either[R, (O, Pull[F, O, R])]`, описывающий возможные результаты разбора.
- **Отложенное выполнение:** Требование `Monad[F]` появляется только в методе `step`, когда он встречает этот конструктор.

Теперь мы можем определить метод `uncons` без ограничений:

```dotty
def uncons: Pull[F, Nothing, Either[R, (O, Pull[F, O, R])]] =
  Uncons(this) // Просто оборачиваем текущий Pull в конструктор Uncons
```

### Обработка `Uncons` в методе `step`

Метод `step` необходимо расширить для обработки нового конструктора:

```dotty
def step[F2[x] >: F[x], O2 >: O, R2 >: R](
  using F: Monad[F2]
): F2[Either[R2, (O2, Pull[F2, O2, R2])]] =
  this match
    // ... другие case'ы (Result, Output, Eval, FlatMap) ...
    case Uncons(source) =>
      source.step.map(s => Left(s.asInstanceOf[R2]))
```

**Пояснение:** Когда `step` встречает `Uncons(source)`, он:

1. Рекурсивно вызывает `source.step`. Это то место, где требуется `Monad[F2]`.
2. Результат `source.step` имеет тип `F2[Either[R, (O, Pull[F, O, R])]]`.
3. С помощью `.map` мы "достаём" `Either` из контекста `F2` и заворачиваем его обратно в `Left`. 
   _Замечание по типу:_ Здесь требуется приведение `s.asInstanceOf[R2]`, 
   которое безопасно благодаря ковариантности и нижним границам типа `R2 >: R`. 
   Результат шага `source` (`R`) всегда является подтипом `R2`.

### Итог и последствия

1. **Отложенные ограничения:** Введение `Uncons` позволяет отделить _конструирование_ потоковых преобразований 
   (которое остается полиморфным и без ограничений) от их _интерпретации_ 
   (где и требуются экземпляры трейтов типа `Monad`).
2. **Расширяемость:** Большинство других операций над `Pull` и `Stream` (такие как `map`, `filter`, `flatMap`) 
   переносятся с минимальными изменениями, часто требующими лишь добавления параметра типа эффекта `F` в их сигнатуры.
3. **Мощность:** `Pipe[F, I, O]` теперь естественным образом определяется как `Stream[F, I] => Stream[F, O]`, 
   и эти каналы могут сами по себе содержать эффекты типа `F`, 
   что делает всю систему чрезвычайно выразительной для описания реальных конвейеров обработки данных с `IO`.

## Тип `Stream`

Тип `Stream` остаётся псевдонимом для `Pull`, но теперь наследует его расширенную параметризацию:

```dotty
opaque type Stream[+F[_], +O] = Pull[F, O, Unit]
```

Это определение означает:

- `Stream[F, O]` — это поток элементов типа `O`.
- Для своего выполнения поток может использовать произвольные эффекты, 
  описываемые конструктором типов `F[_]` (например, `IO`, `Option`, `TailRec`).
- Конечным результатом (`R`) выполнения потока всегда является `Unit`, 
  так как основная цель стрима — это производство элементов, а не вычисление финального значения.

Все конструкторы и методы `Stream` были механически адаптированы для учёта нового параметра типа `F`.

### Конструкторы

```dotty
type Nothing1[A] = Nothing

object Stream:
  // #1: Пустой поток без эффектов
  def empty: Stream[Nothing1, Nothing] = Pull.done

  // #2: Поток из переменного числа аргументов (без эффектов)
  def apply[O](os: O*): Stream[Nothing1, O] =
    fromList(os.toList)

  def fromList[O](os: List[O]): Stream[Nothing1, O] =
    os match
      case Nil => Pull.done
      case hd :: tl => Pull.Output(hd) >> fromList(tl) // Рекурсивное построение
```

Ключевой момент: конструкторы, создающие потоки из чистых данных, фиксируют тип эффекта как `Nothing1`, 
указывая на отсутствие необходимости в эффектах для их генерации.

### Методы расширения

Методы, которые "разбирают" или "интерпретируют" поток, теперь возвращают значение, завернутое в контекст эффекта `F`.

```dotty
extension [F[_], O](self: Stream[F, O])
  def toPull: Pull[F, O, Unit] = self // Простое приведение типа

  // #3: Свёртка элементов потока. Возвращает действие с эффектом F[A].
  def fold[A](init: A)(f: (A, O) => A)(using Monad[F]): F[A] =
    self.fold(init)(f).map(_(1)) // Вызывает fold у Pull и извлекает аккумулятор

  // #4: Преобразование потока в список. Возвращает действие с эффектом F[List[O]].
  def toList(using Monad[F]): F[List[O]] =
    self.toList // Делегирует методу toList для Pull   
```

**Важно:** Для работы этих методов требуется неявный экземпляр `Monad[F]`. 
Это необходимо для того, чтобы можно было последовательно выполнять шаги потока внутри контекста `F`.

### Работа с потоками без эффектов

Потоки с `F = Nothing` (чистые, потоки без эффектов) по-прежнему очень полезны. 
Однако для их интерпретации теперь требуется явно указать, _в какой монаде_ должна происходить стекобезопасная интерпретация.

```dotty
// Раньше: 
Stream(1, 2, 3).repeat.take(5).toList
// Сейчас:
val x: List[Int] =
  Stream(1, 2, 3)
    .repeat  // #1: Бесконечный повтор (лениво)
    .take(5)
    .toList(using tailrecMonad) // Явно указываем монаду Trampoline
    .result // Запускаем вычисление Trampoline, чтобы получить чистый результат
// val x: List[Int] = List(1, 2, 3, 1, 2)
```

Здесь `tailrecMonad` — это [монада `TailRec`][trampolining], 
которая обеспечивает стекобезопасную рекурсию через преобразование в цикл:

```dotty
given tailrecMonad: Monad[TailRec] with
  def unit[A](a: => A) = TailCalls.done(a)

  extension [A](fa: TailRec[A])
    def flatMap[B](f: A => TailRec[B]) =
      fa.flatMap(f)
```

### Удобные методы-расширения для `Stream[Nothing, O]`

Чтобы избежать необходимости явно указывать монаду для чистых потоков, можно создать специальные методы-расширения:

```dotty
extension [O](self: Stream[Nothing, O])
  // Свёртка без эффектов. 
  // Внутри использует TailRec монаду для безопасности и извлекает результат.
  def fold[A](init: A)(f: (A, O) => A): A =
    self.fold(init)(f)(using tailrecMonad).result(1) // .result "запускает" Trampoline

  // Преобразование без эффектов в список.
  def toList: List[O] =
    self.toList(using tailrecMonad).result // Аналогично

// Пример использования:
val s = Stream(1, 2, 3).repeat.take(5)
// Тип выведен как Nothing для эффекта
// val s: Stream[Nothing, Int] = ... 

// #1: Вызываем наш новый метод-расширение
val x = s.toList 
// Получаем чистый результат сразу
// val x: List[Int] = List(1, 2, 3, 1, 2) 

// Если же поток с эффектами, будет вызван стандартный метод
val y = (s: Stream[IO, Int]).toList // #2: Приводим тип к потоку с эффектами
val y: IO[List[Int]] = ... // Возвращается IO-действие, а не сам список
```

**Итог:** Разделение на чистые и потоки с эффектами становится более явным на уровне типов. 
Это обеспечивает типобезопасность: компилятор не даст случайно выполнить действие с эффектами 
без указания правильного контекста интерпретации. 
Для чистых потоков предоставляются удобные методы, скрывающие под капотом механизм стекобезопасного выполнения.

### Упражнение 11.4.1: Реализация конструктора `eval` для `Stream`

> [Репозиторий с упражнениями и инструкцией по выполнению][sample]

**Задача:**

Реализуйте метод `eval` в сопутствующем объекте `Stream`, который создает поток из одного элемента, 
полученного путем выполнения эффекта `F[O]`. 
Метод должен иметь следующую сигнатуру:

```dotty
object Stream:
  def eval[F[_], O](fo: F[O]): Stream[F, O]
```

**Требования:**

- Метод должен возвращать `Stream[F, O]`, содержащий ровно один элемент
- Элемент должен быть получен путем выполнения переданного эффекта `fo`
- Реализация должна использовать существующие примитивы `Pull.Eval` и `Pull.Output`

**Пример использования:**

```dotty
// Создание эффекта, который возвращает случайное число
val randomNumber: IO[Int] = IO(scala.util.Random.nextInt(100))

// Создание потока из эффекта
val stream: Stream[IO, Int] = Stream.eval(randomNumber)
      
// Запуск потока и получение результата
val result = stream.toList.unsafeRunSync()

// Результат будет содержать List(randomNumber). Например:
// val result: List[Int] = List(91)
```

@:note(🔍 Показать решение)

Метод `eval` создает поток из одного элемента путем:

1. Сначала выполняется эффект `Pull.Eval(fo)` - это создает `Pull`, который выполняет эффект `fo`
2. Затем результат эффекта передается в `Pull.Output(_)` с помощью `flatMap`
3. `Pull.Output` оборачивает результат в выходной элемент потока
4. Комбинация этих операций создает `Stream`, который при выполнении:
    - Выполнит эффект `fo`
    - Выведет полученное значение `O`
    - Завершит поток

```dotty
def eval[F[_], O](fo: F[O]): Stream[F, O] =
  Pull.Eval(fo).flatMap(Pull.Output(_))    
```

### Упражнение 11.4.2: Реализация метода `mapEval` для `Stream`

**Задача:**

Реализовать метод `mapEval` как метод расширения (extension method) для типа `Stream[F, O]`. 
Метод должен применять функцию с эффектом к каждому элементу потока и объединять результаты в новый поток.

```dotty
extension [F[_], O](self: Stream[F, O])
  def mapEval[O2](f: O => F[O2]): Stream[F, O2]
```

**Требования:**

- Метод должен принимать функцию `f: O => F[O2]`, которая преобразует элемент в эффект
- Для каждого элемента входного потока должен быть выполнен эффект `f(o)`
- Результаты выполнения эффектов должны быть собраны в выходной поток в том же порядке
- Реализация должна быть ленивой - эффекты выполняются только при запуске потока
- Должна поддерживаться обработка ошибок и ресурсов в рамках эффекта `F`

**Пример использования:**

```dotty
// Асинхронное преобразование элементов
case class User(id: Int, name: String)

// Функция для загрузки дополнительных данных пользователя
def loadUserDetails(user: User): IO[String] = IO {
  // Имитация асинхронного запроса к API
  s"Details for ${user.name} (ID: ${user.id})"
}

val users = Stream(
  User(1, "Alice"),
  User(2, "Bob"),
  User(3, "Charlie")
)

val userDetailsStream: Stream[IO, String] =
  users.mapEval(loadUserDetails)

// Результат: Stream с деталями каждого пользователя
```

@:note(🔍 Показать решение)

Метод `mapEval` реализуется через комбинацию существующих примитивов:

1. `Stream.flatMap` используется для обработки каждого элемента входного потока
2. Для каждого элемента `o` применяется функция `f(o)`, которая возвращает эффект `F[O2]`
3. `Stream.eval` преобразует эффект `F[O2]` в поток с одним элементом
4. `flatMap` объединяет все эти потоки в один результирующий поток

```dotty
extension [F[_], O](self: Stream[F, O])
  def mapEval[O2](f: O => F[O2]): Stream[F, O2] =
    Stream.flatMap(self)(o => Stream.eval(f(o)))    
```

### Упражнение 11.4.3: Реализация генераторов `unfoldEval` для `Stream` и `Pull`

**Задача:**

Реализовать генеративные методы `unfoldEval` в сопутствующих объектах `Stream` и `Pull`. 
Эти методы создают потоки и пулы путем последовательного применения функции с эффектом к начальному состоянию.

```dotty
// Для Stream - генерирует поток элементов до тех пор, пока функция возвращает Some
object Stream:
  def unfoldEval[F[_], O, R](init: R)(f: R => F[Option[(O, R)]]): Stream[F, O]

// Для Pull - генерирует элементы до тех пор, пока функция возвращает Right, 
// либо завершается с результатом, когда функция возвращает Left
object Pull:
  def unfoldEval[F[_], O, R](init: R)(f: R => F[Either[R, (O, R)]]): Pull[F, O, R]
```

**Различия между версиями:**

- `Stream.unfoldEval`: использует `Option` для управления завершением (`None` = конец потока)
- `Pull.unfoldEval`: использует `Either` для управления завершением (`Left` = завершение с результатом)

**Требования:**

1. **Ленивое выполнение**: Эффекты должны выполняться только при запуске потока/пула
2. **Последовательная обработка**: Состояние должно передаваться последовательно между итерациями
3. **Корректное завершение**: Должна быть обеспечена правильная обработка условий завершения
4. **Эффектность**: Поддержка эффектов типа `F[_]` на каждом шаге генерации

**Пример использования `Pull.unfoldEval`:**

```dotty
// Генерация с явным результатом завершения
def nextWithResult(state: Int): IO[Either[Int, (String, Int)]] =
  IO {
    if state < 3 then Right((s"Current state: $state", state + 1))
    else Left(state)
  }

val pullWithResult: Pull[IO, String, Int] =
  Pull.unfoldEval[IO, String, Int](0)(nextWithResult)
pullWithResult.toList.unsafeRunSync()
// val res0: List[String] = List(Current state: 0, Current state: 1, Current state: 2)
```

**Пример использования `Stream.unfoldEval`:**

```dotty
// Генерация последовательности чисел с логикой с эффектами
def nextNumber(state: Int): IO[Option[(Int, Int)]] = IO {
  if state < 5 then Some((state * 2, state + 1))
  else None
}

val numberStream: Stream[IO, Int] =
  Stream.unfoldEval(0)(nextNumber)
// Результат: Stream(0, 2, 4, 6, 8)
```

@:note(🔍 Показать решение)

**Pull.unfoldEval:**

```dotty
object Pull:
  def unfoldEval[F[_], O, R](init: R)(f: R => F[Either[R, (O, R)]]): Pull[F, O, R] =
    Pull.Eval(f(init)).flatMap:
      case Left(result) => 
        // Завершаем с результатом
        Pull.Result(result)
      case Right((output, nextState)) => 
        // Выводим элемент и продолжаем рекурсивно
        Pull.Output(output) >> unfoldEval(nextState)(f)
```

**Пошаговое выполнение `Pull.unfoldEval`:**

1. Выполняем эффект `f(init)` → получаем `F[Either[R, (O, R)]]`
2. Если `Left(result)` → завершаем с результатом `result`
3. Если `Right((o, r))` → выводим `o` и рекурсивно продолжаем с состоянием `r`

**Stream.unfoldEval:**

```dotty
object Stream:
  def unfoldEval[F[_], O, R](init: R)(f: R => F[Option[(O, R)]]): Stream[F, O] =
    Pull.Eval(f(init)).flatMap:
      case None => 
        // Завершаем поток
        Stream.empty
      case Some((output, nextState)) => 
        // Выводим элемент и продолжаем рекурсивно
        Pull.Output(output) ++ unfoldEval(nextState)(f)
```

**Пошаговое выполнение `Stream.unfoldEval`:**

1. Выполняем эффект `f(init)` → получаем `F[Option[(O, R)]]`
2. Если `None` → возвращаем пустой поток
3. Если `Some((o, r))` → выводим `o` и рекурсивно продолжаем с состоянием `r`

**Ключевые особенности:**

- Рекурсия осуществляется через `flatMap`, что обеспечивает ленивое выполнение
- Состояние передается итеративно между вызовами
- Эффекты выполняются последовательно в порядке генерации
- Поддерживается корректная обработка ресурсов и ошибок

## Обновление определения `Pipe`

С добавлением поддержки эффектов в `Stream` необходимо обновить и определение типа `Pipe` (канала преобразования):

```dotty
type Pipe[F[_], -I, +O] = Stream[F, I] => Stream[F, O]
```

**Ключевые особенности нового определения:**

- **Параметр эффекта `F[_]`:** Канал теперь требует, чтобы и входной, 
  и выходной поток работали в одном и том же контексте эффектов `F`.
- **Инвариантность `F`:** Параметр `F` объявлен инвариантным. 
  Попытка сделать его ковариантным (`+F[_]`) или контравариантным (`-F[_]`) приведёт к ошибкам компилятора, 
  так как `F` используется и в контрвариантной позиции (`Stream[F, I]` как аргумент функции), 
  и в ковариантной позиции (`Stream[F, O]` как возвращаемый тип).
- **Альтернативное (более выразительное) определение:** 
  Теоретически, можно было бы определить `Pipe` с двумя параметрами эффектов для большей гибкости:
  ```dotty
  type Pipe[-F[_], -I, +G[_], +O] = Stream[F, I] => Stream[G, O]
  ```
  Это позволило бы каналу не только преобразовывать элементы, но и менять сам тип эффекта 
  (например, преобразовывать `Stream[IO, I]` в `Stream[Option, O]`). 
  Однако это значительно усложнило бы тип и его использование. 
  Поскольку `Pipe` — это всего лишь псевдоним типа, для сложных случаев всегда можно использовать явную функцию, 
  а для большинства стандартных сценариев достаточно более простого варианта с одним `F`.

### Приёмники (Sinks) в потоках с эффектами

Если источник данных представлен как `Stream[F, I]`, а преобразование — как `Pipe[F, I, O]`, 
то как представить приёмник (_sink_), то есть конечную точку, которая потребляет элементы?

Оказывается, специального типа для приёмника не требуется! 
Приёмник — это просто особый вид `Pipe`, преобразующий входной поток в поток, который:

1.  Производит побочные эффекты для каждого элемента (например, запись в файл, отправка в сеть).
2.  Не производит значимых выходных элементов (его выходной тип — `Unit` или `Nothing`).

Такую логику легко реализовать с помощью метода `mapEval` (который применяет функцию с эффектами к каждому элементу).

```dotty
def mapEval[O2](f: O => F[O2]): Stream[F, O2] =
  Stream.flatMap(self)(o => Stream.eval(f(o)))
```

#### Примеры приёмников

```dotty
// Приёмник, который логирует каждый элемент в консоль
def log[O]: Pipe[IO, O, Unit] =
  // Для каждого элемента `o` создаётся IO-действие печати
  _.mapEval(o => IO(println(o))) 

// Приёмник, который просто поглощает (игнорирует) все элементы потока
def drain[F[_], O]: Pipe[F, O, Nothing] =
  // Каждый элемент заменяется на пустой поток
  _.flatMap(_ => Stream.empty) 
```

- **`log`:** Тип `Pipe[IO, O, Unit]` говорит: "Возьми поток элементов `O` с эффектами `IO` и верни поток `Unit` с теми же эффектами". 
  Побочный эффект (печать) происходит внутри `IO`.
- **`drain`:** Тип `Pipe[F, O, Nothing]` говорит: "Возьми поток с любыми эффектами `F` 
  и верни поток, который не производит элементов (`Nothing`)". Это чистое поглощение.

#### Сборка полного конвейера

Теперь можно собрать весь пайплайн: источник -> преобразователь -> приёмник.

```dotty
// Допустим, у нас есть модель данных и источник сообщений из очереди (действие с эффектами)
case class Message(id: UUID, timestamp: Instant, ...)
def format(m: Message): String = s"id: $id, timestamp: $timestamp, ..."
// Действие с эффектом: получить следующее сообщение из очереди
val dequeue: IO[Message] = ... 

// Собираем поток: повторяем действие dequeue, 
// форматируем каждое сообщение, отправляем в log
val logAll: Stream[IO, Unit] =
  Stream.eval(dequeue) // Создаём поток из одного элемента, выполняя dequeue
    .repeat // Бесконечно повторяем предыдущий поток (получаем бесконечный поток сообщений)
    .map(format) // Чистое преобразование: Message -> String
    .pipe(log)   // Применяем приёмник-логгер (преобразование с эффектом: String -> Unit)

// Тип результата: Stream[IO, Unit]
```

### Запуск потока с эффектами: метод `run`

У нас есть поток `Stream[IO, Unit]`. Мы не хотим аккумулировать его результаты в список (`.toList`), 
так как нас интересуют именно побочные эффекты (логирование), а не сами значения `Unit`.

Нам нужен новый метод, который просто "прогонит" поток, выполнив все эффекты и проигнорировав выходные элементы.

```dotty
extension [F[_], O](self: Stream[F, O])
  // Запускает поток, выполняя все эффекты и игнорируя выходные элементы.
  def run(using Monad[F]): F[Unit] =
    // Свёртываем поток, игнорируя элементы и аккумулятор
    self.fold(())((_, _) => ()).map(_(1)) 

// Теперь можно "запустить" наш пайплайн
val program: IO[Unit] = logAll.run
```

**Как работает `run`:**

1. `self.fold(())((_, _) => ())` запускает свёртку потока. Начальное значение аккумулятора — `()`. 
   Функция `f` просто игнорирует и аккумулятор, и очередной элемент, возвращая `()`. 
   Этот вызов возвращает `F[(Unit, Unit)]` — действие с эффектом, результатом которого является кортеж `(final_result, accumulator)`. 
   Для `Stream` `final_result` всегда `Unit`.
2. `.map(_(1))` берёт результат этого действия (кортеж) и с помощью `map` извлекает из него второй элемент — 
   аккумулятор, который тоже `Unit`. В итоге получается `F[Unit]`.

Теперь `program` представляет собой значение типа `IO[Unit]` — описание всей программы логирования, 
которое можно выполнить в "точке запуска" (методом `unsafeRunSync` или аналогичным).
